## 1. 规范来源与适用边界

1. Java 开发以 Alibaba《Java 开发手册》黄山版（2022-02-03）为基线，保留原文的强制、推荐、参考等级。[官方来源](https://github.com/alibaba/p3c)。
2. HTTP 契约以 [OpenAPI Specification 3.1.0](https://spec.openapis.org/oas/v3.1.0.html) 为项目基线。选定 3.1 系列是为了与现有 Spring Boot 3 的生成、校验工具配套；升级规范必须同步验证整套工具并更新本文件，不能使用浮动的 `latest` 作为工程版本。
3. 下文 `ALI-*` 是项目检查分类编号，`OAS-*` 是标准符合性检查编号，`API-*`、`ENG-*` 是项目补充要求。项目要求不得冒充 OpenAPI 标准或 Alibaba 原文。
4. Java 规范覆盖 `media-service`、`control-service`、`bigscreen-bff`、`media-common` 的生产代码和测试代码。Go、Vue、Python 沿用各自语言规范，共同遵循接口契约和项目架构要求。
5. HTTP 接口包括浏览器入口、服务间接口和 HTTP 回调。WebSocket/MQTT 的消息、主题、ACK、重连和顺序语义继续由专项协议定义；仅生成 OpenAPI 不代表消息协议符合性已经验证。
6. 本轮限定为现有 Java 代码和 HTTP 接口的盘点、分批整改、测试验收，以及后续开发的本地检查和审查约束。CI 平台接入、远端合并限制和部署不纳入本轮；CI 仅保留为后续可选自动化。Demo 不纳入正式生产接口整改。

本文件是执行入口和检查索引，不替代完整手册。没有被静态工具覆盖的强制要求仍需人工审查；不能将“扫描通过”写成“完全符合两套规范”。

## 2. Alibaba 规则检查映射

以下为检查分类；具体强制程度以固定版本手册为准。已启用的 10 项规则、固定版本及覆盖限制见[自动检查说明](../../../quality/README.md)。后续规则启用前同样必须验证正反例。

| 编号 | 对应手册主题 | 本项目审查对象 | 检查方式 |
| --- | --- | --- | --- |
| ALI-NAMING | 命名风格、常量定义 | 包、类、字段、枚举、常量及业务含义 | 静态检查与审查 |
| ALI-STYLE | 代码格式、控制语句 | 缩进、括号、条件复杂度、方法可读性 | 静态检查与审查 |
| ALI-OOP | OOP 规约 | 空值、包装类型、相等性、对象职责 | 静态检查、单元测试与审查 |
| ALI-COLLECTION | 集合处理 | 初始化、遍历修改、泛型、集合使用方式 | 静态检查与单元测试 |
| ALI-CONCURRENT | 并发处理 | 线程池、任务队列、ThreadLocal、共享状态 | 静态检查、并发测试与审查 |
| ALI-COMMENT | 注释规约 | 类、接口、枚举、参数、返回值和异常说明 | 静态检查与审查 |
| ALI-EXCEPTION | 异常处理 | 异常边界、异常保留、资源关闭 | 静态检查、失败路径测试与审查 |
| ALI-LOG | 日志规约 | 日志框架、上下文、级别和异常栈 | 静态检查与审查 |
| ALI-TEST | 单元测试 | 正常、边界、失败场景及测试独立性 | 相关模块测试与审查 |
| ALI-SECURITY | 安全规约 | 输入、权限、数据访问和敏感信息处理 | 测试与审查 |
| ALI-DATABASE | MySQL 数据库 | 表、索引、SQL、ORM 和事务边界 | 静态检查、数据库测试与审查 |
| ALI-ENGINEERING | 工程结构、设计规约 | 分层、依赖、配置与职责 | 构建检查与审查 |

执行注意事项：

- 注释解释业务含义和限制；作者、日期必须真实，不为消除告警编造历史信息。
- 修改 Java 名称时检查 JSON 字段、枚举序列化值和外部协议，不能把内部命名整改自动扩展成协议重命名。
- 对 `record`、模式匹配、文本块、switch 表达式必须单独验证规则覆盖。解析成功不等于旧规则已经支持新语法。
- 事务相关提示必须结合实际事务管理方式检查，不能对所有方法机械添加 `@Transactional` 或回滚参数。
- 资源生命周期审查应包含本项目的推流进程、LiveKit 会话、后台任务及文件句柄。

### 2.1 统一注释标准

| 对象 | 必须说明的内容 |
| --- | --- |
| 类、接口、枚举、record | 使用简体中文说明职责和适用边界；不编造作者或历史日期 |
| 枚举值 | 每个值分别说明业务含义；涉及状态的说明进入、终止或后续处理语义，保留协议枚举拼写 |
| record 组成字段 | 在类型 Javadoc 中逐一写 `@param`，说明标识、单位、可空性及特殊约束；接口 `@Schema` 与 Java 说明保持一致 |
| 业务字段、配置项、实体/接口模型属性、公开/受保护字段 | Javadoc 说明业务意义；涉及单位、空值、默认值、状态或敏感信息时明确约束。字段保存的原值与访问器计算的回退值须区分 |
| 缓存、锁、线程池、共享状态和重要常量 | 说明键与隔离范围、容量/时间单位、并发保护、失效或释放条件；不根据名称推断不存在的跨实例保证 |
| 公开/受保护方法、接口方法、显式公开构造器 | Javadoc 说明用途；逐一解释参数；非 void 方法说明返回值；声明的异常说明触发条件。幂等、权限、默认值、异步完成和资源归属按实际行为补充 |
| 覆盖方法 | 行为完全沿用父类型契约时可以复用原文档；额外状态、副作用和失败边界仍需说明，不能因为有 `@Override` 就省略关键逻辑解释 |
| 重要或复杂逻辑 | 在决策附近说明为什么如此处理，重点包括锁/事务顺序、版本防护、重复和乱序、失败补偿、超时重试、资源关闭及未知值语义 |
| 简单私有辅助方法 | 名称与实现已足够清楚时不强制重复注释；有非显然约束仍须解释 |

普通类型和成员声明使用 Javadoc；局部原因说明使用 `//`。简单访问器通过 `{@link #字段名}` 引用已完整说明的属性，避免字段、getter、setter 三处复制；访问器包含回退、校验或其他行为时单独解释。删除或重命名参数时同步更新标签，不能保留过期说明。关键分支需人工复核，不能通过堆砌注释或只提高覆盖率替代阅读代码。

逐成员审查不等于逐成员重复中文名称。职责已由类型和名称清楚表达的普通依赖注入、日志器、序列化标识以及简单私有实现细节，不强制添加无信息量的说明；涉及特殊使用约束则仍须写明。测试类说明验证范围，测试方法可通过场景名称和断言表达目的，复杂准备过程或时序控制应解释原因。公开契约、业务状态和重要逻辑不得以“命名清楚”为由省略必要说明。

同为 record，应统一类型说明和逐字段 `@param` 的完整程度；注解按用途选择。HTTP 契约模型用 `@Schema` 描述实际字段约束；当前仅由 MQTT/WebSocket 消费的消息模型使用 Javadoc 和专项协议说明，不为外观一致批量添加未被生成或验证流程使用的 Swagger 注解。`@JsonInclude` 会影响序列化行为，必须按真实空值契约设置，不能作为统一格式复制。作者和日期按真实来源保留，不把某个文件的署名套到其他类型。

字段说明必须核对所在业务的生产者、消费者和默认值；不得仅凭同名字段全局套用说明，尤其是 `reason`、`status`、`type` 等跨业务重名字段。源码与说明不符属于整改缺陷，即使注释存在性和中文检查通过也不能视为关闭。

自动检查覆盖可客观识别的缺项、空说明、过期参数和至少 40 行方法的职责说明；字段自动覆盖公开/受保护字段、实体与配置类实例字段，以及带 `@Schema`、`@Column`、`@Value` 的实例字段。其他业务字段和重要状态仍逐项人工审查。行数阈值只是兜底，不豁免更短但重要的逻辑。Javadoc 语法及引用另外使用 JDK doclint 复核，规则和实际验证统一记录在现有检查说明与执行记录，不新增重复台账。

### 2.2 日志与注释语言

项目自有日志的说明文字及展示标签、类型/成员/局部注释、配置说明和接口注解的自然语言统一使用简体中文。MQTT 等载荷的日志摘要只转换展示标签，读取载荷的原字段及敏感字段白名单保持不变。新增开发和修改时一并遵循。

协议名称、代码标识符、JSON 字段与枚举值、事件/错误编码、配置键、路径、真实作者以及外部 API 名称保留原有拼写，不把翻译扩展成协议重命名。原始异常类型、堆栈和外部系统返回的诊断保持原样；框架和依赖自身的日志不通过修改依赖或隐藏异常来翻译。

调整日志文案必须保留日志级别、触发条件、占位符数量、参数顺序和异常对象，继续遵循现有脱敏边界。日志展示标签变化须在执行记录说明；接口注解仅修改说明时，也须重新生成契约并确认字段、类型和约束不变。语言和语义由源码扫描与人工复核确认，不把现有 10 项结构规则冒称为完整中文语义检查。

## 3. OpenAPI 标准和项目接口规则

| 编号 | 级别与来源 | 要求 | 验证方式 |
| --- | --- | --- | --- |
| OAS-VALID | 强制，OAS | 文档、路径参数、引用、Schema、安全方案等符合选定版本规范 | 规范校验器；包含 Schema 方言与引用检查 |
| API-IDENTITY | 强制，项目 | 每个操作提供稳定且在所属文档内唯一的 `operationId`、中文用途说明和分组 | 契约 lint |
| API-SCHEMA | 强制，项目 | 明确字段类型、必填性、可空性、枚举、单位、约束、默认行为及有效示例 | 契约 lint、示例校验、接口测试 |
| API-RESPONSE | 强制，项目 | 描述成功响应、实际错误响应、HTTP 状态、媒体类型和有业务意义的响应头 | 契约检查与失败路径测试 |
| API-AUTH | 强制，项目 | 描述当前入口的鉴权方式、权限要求和内部信任边界 | 契约检查与权限测试 |
| API-LIFECYCLE | 强制，项目 | 涉及状态变更时写明前置状态、幂等范围、异步完成条件和重试方式 | 审查与业务测试 |
| API-COMPAT | 强制，项目 | 删除、改名、类型、必填性、枚举、时间、分页等变化必须评估消费者兼容性 | 契约 diff、审查与调用方回归 |
| API-SYNC | 强制，项目 | 代码、生成契约、专项文档及实际响应保持一致 | 重新生成检查与契约测试 |

`@Schema`、`@Operation` 和 OpenAPI 中的约束负责描述行为；实际参数校验、权限判断、幂等和异常处理必须由代码实现并测试。不能仅补注解就认定业务要求已完成。

### 3.1 当前协议的兼容性边界

现有接口先准确描述当前行为，再单独安排行为整改；具体事实以[Java 服务接口通用约定](../../03-接口与协议/公共约定/Java服务接口通用约定.md)及专项协议为准。

- 现有上海时区 `yyyy-MM-dd HH:mm:ss` 字符串用字符串、格式说明和匹配约束表达，不能错误标成要求 RFC 3339 的 `format: date-time`。
- `required` 表示属性必须出现，可空性表示值能否为 `null`；二者分别定义。无数据和数值为零的业务含义不能混为一谈。
- 如实记录每个接口的分页起点、参数名称、默认值和范围。
- 保留当前 JSON、文件、PDF、HLS 和透传错误响应的真实结构；是否调整响应封装由接口迁移方案决定。
- BFF 使用 JWT 鉴权；下游受控 Header 的信任边界另行说明。不能在契约中虚构下游独立验签行为，也不能将浏览器伪造身份 Header 描述成有效认证方式。
- 对存量接口补充运行时必填校验或收紧范围同样属于行为变更，必须检查消费者。

### 3.2 服务契约的权威位置

普通 Spring MVC 接口以实现、DTO、实际校验和接口注解为生成来源，导出可版本管理的 OpenAPI 契约。新接口在实现前审查契约设计，合并时校验最终生成结果。

三个服务分别维护契约，对外和内部接口分别分组；`media-common` 只提供共享模型，不生成独立服务契约。生成产物应稳定排序，并去除仅由环境产生的地址变化。

BFF 通配代理不能由 `ResponseEntity<byte[]>` 自动推导出全部接口。契约应逐项引用或组合实际使用的下游接口，并验证路径及鉴权映射；这不表示当前所有代理已经实现白名单，也不授权本轮收紧路由。BFF 自有聚合接口由自身生成。Management 契约需取自对应仓库或经验证的导出物，缺失部分必须列为未覆盖，不能用空对象冒充完整模型。

Markdown 文档继续维护流程、状态机和跨协议含义，并链接契约；不要再手工复制一套完整字段表。尚未迁移到 OpenAPI 的接口继续使用现有专项文档。

## 4. 新增开发、存量整改和例外

新增代码立即按本规范开发；修改已有代码时处理本次涉及的违规及行为影响，避免附带格式化无关文件。本轮由本地检查、提交自查、代码审查和对应测试执行这些要求，交付时明确实际检查范围。

存量处理流程：

1. 工具试验与接口盘点，验证报告可信度。
2. 人工确认问题，建立可追踪的存量问题基线。
3. 按业务域安排批次，优先处理正确性、资源、并发和契约不一致问题。
4. 每批完成修复、调用方检查、相关测试和文档同步后关闭问题。

正式基线或例外每项至少记录：规则编号、文件/接口、问题证据、风险、原因、负责模块、整改批次或期限、复核结果。涉及规则豁免的内容必须经过评审；批量忽略目录、任意刷新基线、删除报告不能充当整改。

不能只用告警总数判定新增违规：删除旧问题和新增另一问题可能抵消数量。增量检查应使用可追踪的问题标识；工具、规则或识别算法升级必须重新核对基线变化。

## 5. 自动检查实施顺序

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：规则与现状 | 本文、开发入口、现状记录、工具试验 | 明确适用版本、执行范围、事实及未完成项 |
| B：检查基础 | 锁定的工具依赖、Java 规则映射、OpenAPI 校验配置、统一检查入口 | 正反例检测有效；Java 17 语法、规则异常、退出码和离线缓存行为验证完成 |
| C：接口试点 | Control 里程统计查询契约及 BFF 消费验证 | 契约可重复生成；真实请求/响应与契约一致；正常及关键失败路径测试通过 |
| D：全量盘点 | 全量接口清单、正式违规基线、整改批次 | 三个服务的代理、自有、内部接口覆盖清楚；生产和测试代码均纳入规则盘点 |
| E：分批整改与持续检查 | 每批代码、契约、调用方验证和关闭记录；后续开发执行本地增量检查与审查 | 本批问题有证据关闭，新增代码按规范验收；历史问题按清单推进 |

CI 自动执行和远端必过检查是阶段外的后续选项，不作为本轮验收条件。

阶段 B 的工具选择约束：

- Alibaba 手册和 P3C 扫描规则不是同一个覆盖集合。优先验证支持 Java 17 的检查引擎及其规则映射；P3C 旧规则只在相应兼容性和正确性得到验证后使用。
- springdoc 已采用与 Spring Boot 3.5.x 配套的 `2.8.17`，具体运行验证见执行记录。[官方兼容矩阵](https://springdoc.org/v2/#what-is-the-compatibility-matrix-of-springdoc-openapi-with-spring-boot)。
- OpenAPI 项目 lint 已采用 [Spectral](https://github.com/stoplightio/spectral) `6.15.0`；兼容性分类检查仍以 [oasdiff](https://github.com/oasdiff/oasdiff) 为候选，尚未启用。后续工具同样必须经过正反例验证并锁定版本。
- 工具解析失败、规则执行失败或缺少契约文件时检查失败；不能只检查 XML/JSON 中的违规数量而忽略运行错误。
- 不把完整服务启动、连接生产数据库或真实设备作为静态规则检查的前提。契约测试隔离非必要外部依赖，并明确未覆盖的线上场景。
- 修正并复用仓库检查入口时覆盖所有受影响模块；`dev-check.sh` 的构建成功不能替代规则、契约和业务测试。
