# 通用文件上传、存储与播放设计说明书

## 1. 范围

平台需要统一承载机器人端、前端和后端模块产生的文件，包括：

1. 手动录像、任务录像、LiveKit Egress 录制文件。
2. 前端抓拍图片、机器人本地抓拍图片。
3. 巡逻任务执行后产生的日志、配置、地图、图片、压缩包等产物。
4. 后端其他模块生成的诊断包、日志包或业务附件。

本方案提供统一 `file` 模型，支持上传、断点续传、下载、查询和视频 HLS 播放。通用扩展 ID 只按一对多文件关系处理，不设计多对多关系表。

## 2. 方案结论

上传入口分两类：

| 类型 | 接口 | 适用场景 | 特点 |
|---|---|---|---|
| 小文件单接口上传 | `POST /api/media/files` | 抓拍、小配置、小日志、小 JSON、小图片、小附件 | 调用端一次请求完成上传；服务端限制大小并直接写 MinIO |
| 大文件分片上传 | `POST /api/media/files/multipart-uploads` | 视频、大日志包、地图包、压缩包、其他大文件 | MinIO multipart，支持断点续传、并发分片和失败恢复 |

当前没有普通文件的“先申请单个上传 URL、再直传”接口；小文件使用简单上传，大文件使用 multipart。

视频处理规则：

```text
只要 file_type = VIDEO，上传完成后都进入 HLS 处理。
视频大小只决定上传方式，不决定播放方式。
```

任务关联规则：

```text
media_file.extension_id 可为空。
业务流程产生的文件可先上传，后续由对应业务模块更新 extension_id。
手动录像、独立抓拍、普通附件无需关联通用扩展 ID。
```

## 3. 核心流程

### 3.1 小文件单接口上传

```text
调用端
  -> POST /api/media/files multipart/form-data
  -> Media Service 校验大小、类型、权限
  -> Media Service 创建 media_file
  -> Media Service 写入 MinIO
  -> 非视频置 READY
  -> 视频置 PROCESSING，并异步生成 HLS
```

适用文件：

```text
IMAGE / AUDIO / LOG / CONFIG / MAP / DOCUMENT / OTHER
```

小视频也可以走单接口上传，但上传成功后仍进入 HLS 处理：

```text
VIDEO: UPLOADING -> PROCESSING -> READY
```

### 3.2 大文件分片上传

```text
调用端
  -> POST /api/media/files/multipart-uploads
  <- uploadId、partSize、partCount、首批 partUrls
  -> PUT parts 到 MinIO
  -> 必要时 POST /part-urls 获取后续或重签 URL
  -> POST /complete
  -> Media Service 校验 parts、complete multipart、stat object
  -> 非视频置 READY
  -> 视频置 PROCESSING，并异步生成 HLS
```

创建 multipart 上传时返回首批 `partUrls`，减少一次必然发生的接口调用；但仍保留 `part-urls` 接口，用于后续批次、断点续传、URL 过期重签和失败重试。

### 3.3 视频播放

```text
原始视频上传完成
  -> ffprobe 解析编码、时长、分辨率
  -> 必要时转码为浏览器兼容 H.264/AAC
  -> 生成 fMP4 HLS：index.m3u8 + init.mp4 + segment_xxx.m4s
  -> 上传 HLS 资产到 MinIO
  -> media_file.status = READY
  -> media_video_file.status = READY
```

浏览器和移动端统一播放 HLS，不再按视频大小区分 MP4 直播或 HLS。

ffprobe 输出与进程等待并行，输出只保留前 64 KiB，探测总时限为 60 秒。ffmpeg 总时限取
`max(MEDIA_FILE_HLS_PROCESSING_LEASE_SECONDS, 视频时长 × 2)`；超时或线程中断时终止整个
子进程树，短暂等待后强制回收，临时目录仍由任务 `finally` 统一删除。该收口不改变 HLS 编码、
分片格式或播放地址。

## 4. 数据模型

### 4.1 `media_file`

一行代表一个业务可见文件。

| 字段 | 说明 |
|---|---|
| `file_id` | 文件统一 ID，建议 `file_<uuid>` |
| `org_id` | 组织隔离 |
| `created_by` | 用户私有文件的创建人 Keycloak `sub`；为空表示组织共享 |
| `robot_id` | 机器人 ID，可为空 |
| `device_id` | 设备/摄像头 ID，可为空 |
| `extension_id` | 通用扩展 ID，可为空，可后补 |
| `source_file_id` | 调用端本地文件幂等键，可为空 |
| `file_type` | `VIDEO` / `AUDIO` / `IMAGE` / `LOG` / `CONFIG` / `MAP` / `DOCUMENT` / `OTHER` |
| `file_name` | 原始文件名 |
| `content_type` | MIME 类型 |
| `file_size` | 文件字节数 |
| `object_key` | MinIO 原始文件对象 key |
| `upload_mode` | `SIMPLE` / `MULTIPART` |
| `status` | `UPLOADING` / `PROCESSING` / `READY` / `FAILED` / `DELETED` |
| `metadata_json` | 少量类型扩展信息，可为空 |
| `error_code` / `error_message` | 失败信息 |
| `uploaded_at` | 原始文件上传确认时间 |
| `created_at` / `updated_at` | 创建与更新时间 |

索引建议：

```text
index(org_id, robot_id, created_at)
index(org_id, created_by, created_at)
index(org_id, extension_id)
index(file_type, status)
unique(robot_id, source_file_id) where source_file_id is not null
```

`source_file_id` 用于客户端重复扫描、断点续传和幂等恢复。通用扩展 ID 不参与 MinIO 路径，因为它可能后补。

### 4.2 `media_file_upload`

只记录 multipart 上传会话。小文件单接口上传不写该表，避免无意义会话记录。

| 字段 | 说明 |
|---|---|
| `upload_id` | 上传会话 ID，建议 `upl_<uuid>` |
| `file_id` | 对应 `media_file.file_id` |
| `upload_mode` | 固定 `MULTIPART` |
| `storage_upload_id` | MinIO multipart upload ID |
| `part_size` | 分片大小 |
| `part_count` | 分片总数 |
| `status` | `ACTIVE` / `COMPLETED` / `EXPIRED` / `ABORTED` / `FAILED` |
| `expires_at` | 上传会话过期时间 |
| `last_active_at` | 最近获取 URL、续传或 complete 时间 |
| `created_at` / `completed_at` | 创建与完成时间 |

不保存 part 明细表。恢复上传时以 MinIO `ListParts` 为已上传分片事实来源。

### 4.3 `media_video_file`

只在 `file_type = VIDEO` 时创建。

| 字段 | 说明 |
|---|---|
| `file_id` | 主键，同时引用 `media_file.file_id` |
| `video_codec` / `audio_codec` | 源视频编码信息 |
| `duration_seconds` | 服务端确认的时长 |
| `started_at` / `ended_at` | 视频开始与结束时间，接口字段与表字段一致 |
| `width` / `height` | 源视频分辨率 |
| `hls_playlist_object_key` | HLS 播放入口对象 key |
| `hls_segment_count` | HLS 分片数量 |
| `hls_total_size` | HLS 资产总大小 |
| `status` | `PROCESSING` / `READY` / `FAILED` |
| `error_code` / `error_message` | 视频处理失败信息 |
| `processing_started_at` / `processing_completed_at` | 处理时间 |

## 5. 对象存储

继续使用 MinIO 存储文件内容，MySQL 存储元数据。

有机器人来源的原始文件：

```text
files/{orgId}/{robotId}/{yyyy}/{MM}/{dd}/{fileId}/original/{fileName}
```

无机器人来源的原始文件：

```text
files/{orgId}/system/{yyyy}/{MM}/{dd}/{fileId}/original/{fileName}
```

视频 HLS：

```text
files/{orgId}/{robotId}/{yyyy}/{MM}/{dd}/{fileId}/hls/index.m3u8
files/{orgId}/{robotId}/{yyyy}/{MM}/{dd}/{fileId}/hls/init.mp4
files/{orgId}/{robotId}/{yyyy}/{MM}/{dd}/{fileId}/hls/segment_000001.m4s
```

存储规则：

1. `object_key` 由 Media Service 生成。
2. `extension_id` 不进入对象路径。
3. 原始文件始终保留，用于归档、重新处理和排障。
4. 视频正式播放只使用 HLS 资产。





## 8. 典型场景

### 8.1 前端抓拍

前端抓拍并入单接口上传：

```text
POST /api/media/files
fileType=IMAGE
metadata.source=WEB_SNAPSHOT
metadata.sessionId=vs_xxx
metadata.channel=visible
```

前端抓拍文件直接上传为 `media_file`。列表通过统一文件接口读取，预览通过已有下载接口获取
`inline=true` 的 MinIO 预签名地址，避免图片正文经过 Media、Control、BFF 多层缓冲：

```text
GET /api/control/files?fileType=IMAGE&status=READY&source=WEB_SNAPSHOT
POST /api/control/files/{fileId}/download-url?inline=true
```

浏览器按 `fileId` 合并重复签发请求并限制签发并发；签名地址距离响应中的 `expiresAt` 不足 60 秒时
重新申请。注销、切换用户或删除文件必须清除对应缓存，禁止跨用户复用预签名地址。

实时监控只展示手动抓拍。`source` 必须由 Media Service 在数据库分页前按
`metadata.source` 精确筛选，不能把告警图片等其他来源取回后再由前端过滤。
抓拍上传要求 `MEDIA_OPERATOR`，文件的 `created_by` 固定写入当前可信身份的
`userId`，调用方不能通过表单指定或覆盖。

### 8.2 手动录像

手动录像由浏览器发起、LiveKit Egress 在服务端执行，使用统一文件模型：

```text
file_type = VIDEO
extension_id = null
upload_mode = MULTIPART
source_file_id = livekit-egress:{sessionId}:{timestamp}
status = UPLOADING
metadata.source = LIVEKIT_EGRESS
metadata.startedClientId = 发起端 X-Client-Id
```

实时监控手动录像列表使用：

```http
GET /api/control/files?fileType=VIDEO&status=READY&source=LIVEKIT_EGRESS
```

手动录像要求 `MEDIA_OPERATOR`，创建记录时写入当前用户 `created_by`。录像停止除
`sessionId + startedClientId` 外还必须匹配 `created_by`，避免同一浏览器标签页切换账号后
复用 `clientId` 而停止前一个账号的录像。

任务录像是否绑定 `extension_id` 不再作为手动录像判断条件；文件来源以
`metadata.source` 为准，避免未绑定任务录像混入手动录像列表。

实时监控多媒体详情首次查询 20 条，列表滚动接近底部时继续请求下一页。图片文件正文和视频
缩略 HLS 只在列表项进入可视区域后加载；视频列表项离开可视区域后立即释放 HLS 实例。选中的
详情媒体独立加载，关闭弹窗、删除后刷新或重新打开列表时必须释放旧观察器和播放器。弹窗布局
沿用当前桌面版尺寸，本规则不包含半屏响应式改造。

### 8.3 手动媒体访问边界

- `created_by` 为空的任务、告警、机器人上传等业务文件继续按 `org_id` 共享。
- `created_by` 非空的用户私有文件只对同组织且 `userId = created_by` 的用户可见。
- 私有文件列表、详情、正文、下载和播放要求 `MEDIA_VIEWER`；`MEDIA_OPERATOR` 同时具备查看能力。
- 私有文件抓拍、录像启停、扩展绑定和删除要求 `MEDIA_OPERATOR`。
- 访问其他用户私有文件统一返回 `404`，不暴露文件是否存在；缺少功能角色返回 `403`。
- HLS 仍使用播放接口签发的短期文件令牌；只有通过所有权校验的用户才能取得令牌。
- 历史手动媒体无法从旧记录可靠恢复创建人，部署迁移时统一把 `WEB_SNAPSHOT` 和
  `LIVEKIT_EGRESS` 的空 `created_by` 回填给指定历史归属账号；其他来源不得回填。

流程：

```text
解析 LiveKit 房间真实视频 Track SID
启动 Track Egress 并直接写入 MinIO 源 MP4
停止 Egress 后进入 PROCESSING
生成 HLS
READY 后播放
```

同一视频会话同时只允许一条活动录像。刷新页面后前端通过活动录像接口恢复状态；主动停止观看、页面跳转和退出登录会停止当前 `clientId` 发起的录像；浏览器异常关闭或断网由 viewer 心跳超时兜底。重复停止按幂等方式返回文件当前状态。单次录像默认最长 14400 秒，后台清理任务到期后自动停止。

手动录像和任务录像的区别：

```text
任务录像：后续补充 extension_id
手动录像：extension_id 为空
```

### 8.3 任务产物文件

一次任务执行可能产生：

```text
多个视频
多个日志
多个配置文件
多个图片
多个地图或压缩包
```

上传时允许：

```text
extension_id = null
```

任务模块后续更新：

```text
media_file.extension_id
```

按通用扩展 ID 查询：

```http
GET /api/media/files?extensionId=ext_001
```

### 8.4 非视频大文件

非视频大文件使用 multipart，不需要独立接口：

```text
file_type = LOG / CONFIG / MAP / DOCUMENT / OTHER
upload_mode = MULTIPART
complete 后 status = READY
不创建 media_video_file
不生成 HLS
```

## 9. 客户端与后端接入

### 9.1 机器人客户端

当前 Python 机器人客户端已接入通用文件上传协议。模块名称仍保留 `recordingupload`，但职责已从“仅录像上传”扩展为“扫描目录内通用文件并上传”。

Python 客户端：

```text
python-client/robot_media_client/recordingupload
```

职责：

```text
扫描本地文件
按后缀识别 VIDEO / AUDIO / IMAGE / LOG / CONFIG / MAP / DOCUMENT / OTHER
维护本地 manifest
执行 multipart 断点续传
自动 complete
上传完成后记录 fileId
```

机器人客户端大文件统一调用：

```text
POST /api/media/files/multipart-uploads
POST /api/media/files/multipart-uploads/{uploadId}/part-urls
PUT uploadUrl
POST /api/media/files/multipart-uploads/{uploadId}/complete
GET  /api/media/files/{fileId}/status
DELETE /api/media/files/{fileId}
```

Manifest 写入 `fileId`。Python 客户端兼容读取旧 manifest 中的 `recordingId`，但后续写回统一使用 `fileId`。

业务模块不直接处理：

```text
partNumbers
partUrls
uploadedParts
completeMultipart
```

### 9.2 前端

前端提供统一工具方法：

```text
uploadFile(formData)
getFiles(params)
getFile(fileId)
getDownloadUrl(fileId)
getPlayUrl(fileId)
```

抓拍、附件、小配置上传均使用 Control 转发接口：

```text
POST /api/control/files
GET  /api/control/files
POST /api/control/files/{fileId}/play-url
POST /api/control/files/{fileId}/download-url
GET  /api/control/files/{fileId}/content
GET  /api/control/files/{fileId}/hls/{objectName}
```

`content` 和 HLS 对象代理仅作为兼容读取路径，单对象最大 32 MiB；超过上限返回 413。页面图片
展示和普通下载必须使用 `download-url`，视频播放使用 `play-url`。简单上传仍保持 20 MiB 业务
上限，但 BFF -> Control -> Media 的文件 Part 均以输入流转发，不在每层构造完整 `byte[]`。

### 9.3 后端模块

后端模块不建议 HTTP 调自己。提供内部服务：

```text
FileService.uploadSimple(...)
FileService.createMultipart(...)
FileService.completeMultipart(...)
FileService.registerExistingObject(...)
```

后端模块使用同一套表、对象路径和状态机。

## 10. 配置建议

```text
MEDIA_FILE_SIMPLE_UPLOAD_MAX_BYTES=20971520
MEDIA_FILE_PART_SIZE_BYTES=16777216
MEDIA_FILE_MAX_PART_URLS_PER_REQUEST=16
MEDIA_FILE_INITIAL_PART_URL_COUNT=16
MEDIA_FILE_UPLOAD_URL_TTL_SECONDS=900
MEDIA_FILE_MULTIPART_EXPIRE_HOURS=72
MEDIA_FILE_MAX_ACTIVE_UPLOADS_PER_ROBOT=20
MEDIA_FILE_MAX_ACTIVE_UPLOADS_GLOBAL=500
MEDIA_FILE_CLEANUP_DELAY_MS=60000
MEDIA_FILE_PLAY_URL_TTL_SECONDS=3600
MEDIA_FILE_PLAY_TOKEN_SECRET=file-playback-development-secret-change-me
MEDIA_FILE_HLS_FFMPEG_PATH=ffmpeg
MEDIA_FILE_FFPROBE_PATH=ffprobe
MEDIA_FILE_HLS_SEGMENT_DURATION_SECONDS=6
MEDIA_FILE_HLS_WORKER_CONCURRENCY=2
MEDIA_FILE_HLS_PROCESSING_LEASE_SECONDS=300
MEDIA_FILE_RETENTION_DAYS=30
MEDIA_FILE_LIVE_RECORDING_MAX_DURATION_SECONDS=14400
MEDIA_FILE_TRUSTED_ROBOT_NETWORK_ENABLED=false
MEDIA_FILE_TRUSTED_ROBOT_CIDRS=127.0.0.1/32,::1/128
MEDIA_FILE_DEFAULT_ORG_ID=org001
```

说明：

1. `MEDIA_FILE_SIMPLE_UPLOAD_MAX_BYTES` 控制单接口上传最大文件大小。
2. `MEDIA_FILE_MAX_PART_URLS_PER_REQUEST` 控制每批最多签发多少分片 URL。
3. `MEDIA_FILE_INITIAL_PART_URL_COUNT` 控制创建 multipart 时返回的首批 URL 数量。
4. `MEDIA_FILE_UPLOAD_URL_TTL_SECONDS` 控制预签名 URL 有效期。
5. `MEDIA_FILE_MAX_ACTIVE_UPLOADS_*` 控制未过期 `ACTIVE` 上传会话容量，不限制客户端实际 PUT 并发数；过期会话不再占用容量。
6. `MEDIA_FILE_CLEANUP_DELAY_MS` 控制过期会话清理周期，每轮最多处理 100 条，单条失败不阻塞其他清理任务。
7. `MEDIA_FILE_PLAY_*` 控制下载/播放签名有效期和 HLS token 签名密钥。
8. `MEDIA_FILE_HLS_*` 控制 ffmpeg/ffprobe 路径、HLS 分片时长和后台处理并发。
9. `MEDIA_FILE_TRUSTED_ROBOT_*` 控制机器人侧 multipart 上传与状态查询接口的内网可信访问。
10. `MEDIA_FILE_LIVE_RECORDING_MAX_DURATION_SECONDS` 控制单次手动录像最长持续时间；小于等于 0 时不限制。

`media.recording.*` 已移除。录像、上传、播放、HLS、清理和可信网段配置统一归入 `media.file.*`。

## 11. 取舍

保留：

```text
小文件单接口上传
大文件 multipart 断点续传
创建 multipart 时返回首批 partUrls
part-urls 接口用于续签和恢复
视频统一 HLS
手动录像
前端抓拍
通用扩展 ID 后补
metadata_json 轻量扩展
```

不做：

```text
普通文件 upload-url + PUT MinIO 两步上传
多对多文件关系表
biz_domain / biz_id / biz_role
extension_id 进入对象路径
所有文件都强制 multipart
所有文件都强制 complete
```

最终边界：

```text
小文件：调用简单，由 Media Service 承载上传正文。
大文件：走 MinIO multipart，保证可靠性和可恢复。
视频：不论大小，上传完成后统一生成 HLS 再播放。
```
