## 1. 调用链路基线

```text
浏览器 --JWT--> BFF :8090
  -> Control :8082 --MQTT/TLS--> EMQX --> 生产机器人客户端或 Camera Gateway
  -> Media :8088 --> LiveKit / MinIO / MySQL
浏览器 --短期 viewer Token--> LiveKit
```

BFF 是浏览器唯一业务入口；Control 到 Media 的 `/internal/media/**` 是服务间入口；RTSP URL、publisher Token、Management Token 和 MQTT 凭据均属于敏感数据。

### PROD-005：WebSocket 权限撤销窗口

**整改后实现（2026-08-23）**：

1. BFF 在 WebSocket 建连时使用当前 Token 分页查询 Management 的设备和固定摄像头；Management 明确返回 `401` 时以 `4001` 关闭，其他初始查询失败以 `4003` 关闭。前端会自动重连，但 `4003` 使用带随机抖动的指数退避，间隔从约 2 秒逐步增加到 30 秒并封顶，持续失败时显示“权限服务暂不可用”，不再固定每 2 秒无限请求。

- 不要求把现有双向 WebSocket 改造成纯事件通道，也不新增第二套控制协议。
- 不要求每个连续控制帧都同步调用 Management；允许按身份和资源使用不超过 30 秒的授权缓存。
- 不因单个资源失权关闭仍拥有其他资源的用户连接；只要快照有效，按新集合过滤即可。
- 不通过延长刷新周期、缓存 TTL、控制租约或 Token 有效期规避 Management 压力。
- 本项不负责处理已经进入 LiveKit 房间的 Viewer 强制踢出、Management 权限事务传播时延或 MQTT 设备身份，这些分别属于媒体会话撤权设计、Management 一致性和 PROD-004 边界。

**完成条件**：

1. Management 权威查询显示撤权后 30 秒内，目标资源事件停止下发，REST 和 WebSocket 控制均被拒绝，且没有对应 MQTT 命令发布。
2. 在多用户、多 WebSocket 会话以及 Management 慢响应/超时压测下，不存在年龄超过 30 秒仍可收发业务消息的授权快照；查询失败的会话以 `4003` 关闭。
3. Token 到期或 Management 明确返回 `401` 后连接以 `4001` 关闭，旧连接不能继续接收事件或发送控制帧；该分类不得依赖 BFF 与认证服务时钟完全一致。
4. 资源权限减少不影响同一用户仍有权资源的事件和操作；权限增加在下一份有效快照加载并由前端重拉 Overview 后生效，页面不得保留已撤权设备。
5. 自动化测试至少覆盖初始授权失败、快照过期、刷新失败、撤销单个资源、撤销全部资源、Control 缓存过期、MQTT 零下发和 Token 到期；生产联调记录 Management 生效时刻、BFF 拒收时刻、Control 拒绝时刻及最终延迟。
6. 连续观看超过两个 JWT 生命周期时，`4001` 换证重连不得断开 LiveKit Room、停止视频会话、
   清空视频墙或显示“权限服务暂不可用”；确认撤权后对应视频仍必须在授权窗口内停止。

### PROD-006：固定摄像头配置状态与健康状态分离

**整改前事实与问题定位（2026-08-23）**：

1. `PanoramaService.fixedCameraDevice` 当前直接执行 `enabled=true -> status=online`、
   `enabled=false -> status=offline`；`deviceStats` 和 `deviceTypeStats` 又按该 `status` 统计，
   因而现状不只是字段文案不清，而是在线数量已经混入配置启停口径。
2. Gateway 当前只向 `gateway/fixed-camera/{gatewayId}/video/status` 上报
   `publishing/streaming/failed/stopped`。该消息以 `sessionId` 为主键，只说明某次视频会话，
   不能证明 Gateway 整体存活，也不能证明未被观看摄像头的 RTSP 可用。
3. Gateway 入口没有机器人心跳；Control 只把上述会话状态转交 Media 更新 `VideoSession`，
   没有固定摄像头健康状态仓库，BFF 也没有可合并的健康来源。
4. 前端地图弹窗已隐藏固定摄像头的部分在线标签，但 Overview 总数、在线/离线统计和部分
   “在线装备”筛选仍消费通用 `status`，仅隐藏文案不能消除错误口径。

**确认后的四类状态必须独立**：

| 状态维度 | 权威来源 | 建议状态 | 用途 |
| --- | --- | --- | --- |
| 配置启停 | Management `enabled` | `ENABLED/DISABLED` | 是否允许平台发起播放，不代表设备在线 |
| 配置完整性 | Management 协议和主/子码流 | `READY/INVALID` | 是否具备发起 RTSP 探测的必要配置，不代表 RTSP 可达 |
| Gateway 存活 | Gateway 独立 MQTT 心跳 | `ONLINE/OFFLINE/UNKNOWN` | 判断负责该摄像头的 Gateway 是否可接收命令 |
| 摄像头流健康 | Gateway 对目标 RTSP 的最近探测 | `AVAILABLE/UNAVAILABLE/UNKNOWN` | 判断最近一次 RTSP 探测结果；必须带检查时间和过期边界 |

`VideoSession.status` 的 `publishing/streaming/failed/stopped` 继续只描述一次播放会话，不能写回
上述四类设备状态，也不能作为未播放摄像头的健康依据。

**本项代码整改边界**：

1. Gateway 新增独立心跳 Topic `gateway/fixed-camera/{gatewayId}/status`，QoS 1，至少包含
   `gatewayId`、`status`、`reportedAt`、`reasonCode`、`version`；默认每 10 秒上报，Control
   连续 30 秒未收到新心跳即判为 `OFFLINE`。进程刚启动、Control 刚重启或数据过期时为
   `UNKNOWN`，不得乐观恢复成在线。心跳不得携带 Token、RTSP URL 或摄像头凭据。
2. Gateway 新增摄像头健康 Topic
   `gateway/fixed-camera/{gatewayId}/camera/{cameraId}/status`，至少包含 `gatewayId`、
   `cameraId`、`health`、`checkedAt`、`reasonCode`。Gateway 通过有并发上限的周期探测和
   start 前探测更新状态；建议探测周期 60 秒、状态最长有效 120 秒。超过有效期统一为
   `UNKNOWN`，不能永久沿用最后一次成功。错误原因必须使用枚举码，说明文本需限长且不得
   包含 RTSP URL。
3. Control 校验 Topic 中的 `gatewayId/cameraId` 与 payload 一致，只保存最新且序号/时间
   更新的状态，并对外提供按当前用户摄像头权限过滤的查询接口和 WebSocket 变化事件。
   本轮只要求最新短期状态，不建设健康历史报表。单实例可使用内存仓库；多实例部署前必须
   使用共享短期存储，或证明每个实例都能独立收到完整心跳和摄像头状态，禁止跨实例返回
   不一致的在线结果。
4. BFF 固定摄像头模型明确输出 `enabled`、`configStatus`、`gatewayHealth`、
   `streamHealth` 和各自时间。现有 `playable` 只能表示“配置允许发起播放”，应改名为
   `configReady`；完成调用方迁移后删除旧字段。通用 `status` 不再由 `enabled` 推导：
   仅当配置启用且完整、Gateway 心跳有效且最近 RTSP 探测成功时为 `online`；Gateway
   离线或有效期内的 RTSP 探测失败、任一健康数据缺失/过期、配置停用时均为 `offline`。
5. `deviceStats` 与 `deviceTypeStats` 仅输出 `online/fault/offline`，且三类数量与总数可核对。
   前端固定摄像头展示“已启用/已停用”“Gateway 在线/离线/未知”“视频流
   可用/不可用/未知”，不得只显示一个“在线”。播放入口以 `enabled + configReady` 为配置
   门槛；Gateway 明确离线时可快速提示不可用，健康为 `UNKNOWN` 时允许发起一次真实探测，
   最终结果仍以该次 `VideoSession` 状态为准。
6. Gateway/摄像头健康变化通过现有 BFF WebSocket 连接按 `cameraId` 做用户资源过滤；事件
   只触发对应设备状态和统计刷新，不广播 RTSP 地址，也不要求前端轮询全量 Overview。

**已完成的代码整改**：

1. **Gateway 已完成**：增加 10 秒心跳、MQTT 遗嘱离线消息、60 秒摄像头周期探测、120 秒
   健康有效期所需载荷，以及 start 前即时探测；默认订阅 Control 的短租约目录快照，只探测
   未过期摄像头。原 Management 分页读取保留为显式 `management` 兼容模式；探测并发默认
   限制为 4，并用 single-flight 跳过尚未结束的重复扫描，避免慢 RTSP 导致任务堆积。
2. **Control 已完成**：订阅并校验 Gateway/摄像头健康 Topic 与载荷身份，拒绝乱序旧消息；
   心跳超过 30 秒转为 `OFFLINE`，流健康超过 120 秒转为 `UNKNOWN`；新增当前用户授权范围内的

   合并未过期租约并通过 MQTT 发布全量目录，最后租约过期时发布空目录。
3. **BFF 已完成**：Overview 合并 Control 健康快照，输出 `enabled/configStatus/configReady`、
   `gatewayHealth/streamHealth`；通用 `status` 仅在配置可用、Gateway 在线且 RTSP 可用时为
   `online`，并为总量和类型统计按 `online/fault/offline` 收敛。Control 健康接口失败时设备状态为离线，

4. **前端已完成**：固定摄像头分别展示配置、Gateway 和视频流状态；明确停用、配置无效或

   使用当前登录用户重新拉取 Overview，不携带或信任事件中的跨用户摄像头明细。
5. **兼容边界**：保留旧 `playable` 字段且其语义严格收缩为 `enabled && configReady`，新代码

**整改中新增发现及处理**：

- 原 Gateway、Control 授权健康接口和 BFF 若固定只读第一页，超页摄像头会长期未知或缺失；
  现均已改为分页读取并设置最多 1000 页的安全上限，超限不得返回伪在线。
- 周期到达时前一轮 RTSP 探测可能尚未结束，直接重入会形成并发风暴；现已增加 single-flight
  和可配置并发上限，重叠轮次只记录中文跳过日志。
- Gateway 遗嘱与健康消息不使用 retained。Control 重启后状态短暂为 `UNKNOWN` 是失败安全设计，
  最迟由下一次心跳/探测恢复；不得为消除该窗口而恢复旧在线值。
- 新默认方案不向 Gateway 配置 Management Token。BFF 只在当前用户授权列表完整分页成功后续租；
  Management 故障、用户退出或租约同步失败会使目录在最长 300 秒内收口为空，摄像头保持
  `UNKNOWN`，不允许用本地旧清单补在线。
- Control 原始健康变化事件包含 `gatewayId/cameraId`，若沿用通用事件透传会向其他用户泄露
  资源标识；BFF 现已抑制原始事件，只发送不含资源明细的用户范围失效通知，并按当前身份
  重拉 Overview 和统计。
- Control 健康仓库当前为进程内存。单实例部署可用；多实例部署仍属于未关闭的生产边界，
  上线前必须使用共享短期存储，或提供每个实例订阅同一 QoS 1 Topic 且接口不跨实例漂移的证明。

#### PROD-044：固定摄像头多路启动慢且轨道成功状态失真

**当前断点**：本地同时打开 9 路固定摄像头时，Gateway 会在 Publisher 读取 RTSP 前再启动一次
`ffprobe`，后台健康检查又按逻辑摄像头重复探测相同 RTSP；Publisher 的全局互斥锁覆盖进程创建和
启动等待，不同视频源也被串行化。进程存活短时间后 Gateway 即上报 `streaming`，Media 随即保存
占位 Track 状态，但 LiveKit 可能尚未出现真实视频 Track；浏览器 Room 连接成功后也没有首轨超时，
因此宫格可以长期停留“正在连接”。

**整改边界**：保持现有 MQTT Topic、状态字段、Room 命名、VideoSession 和前端宫格协议。会话启动
不再做重复 RTSP 预探测；后台健康检查对相同 RTSP 每轮只探测一次并回写各逻辑摄像头。Publisher
只按同一视频流串行，不同流并行；子进程只做 500 ms 快速失败保护，GStreamer/FFmpeg 回退窗口
保持原值。固定摄像头上报 `streaming` 只表示推流进程已启动，Media 保持 `ROOM_READY`，由现有
LiveKit Room API 查询到真实视频 Track 后才进入 `STREAMING`。前端等待固定摄像头首个视频 Track
最多 15 秒，超时断开临时 Room、停止本次新会话并清理宫格；机器人视频状态映射不变。

**验收要求**：相同和不同 RTSP 的 1 路、9 路并发启动；健康探测不产生同 URL 重复连接；每路
`STREAMING` 均可在 LiveKit 房间找到真实视频 Track；不可达、无 Track、进程立即退出和运行中退出
均有限失败且无自动重启风暴、宫格残留、Publisher/ffprobe 孤儿进程或失效会话复用。

**本地验证与部署（2026-08-30）**：Gateway `go test -race ./...`、`go vet ./...` 和生产二进制构建通过，
并发测试确认不同流不再被全局锁串行，新增原子运行标志消除了 `exec.Cmd.Wait` 竞态。Backend 全量
测试通过，覆盖固定摄像头占位状态、真实 Track 确认和初始进程退出收口；前端 42 项测试与生产构建
通过。Media 已备份并更新至 `192.168.124.23`，21:09:39 启动成功；robot-ui 已更新至 Nginx
`dist` 并通过 HTTPS 实际资源指纹和新逻辑内容核验。目标机不存在 fixed-camera-gateway 容器或
进程，未新增部署；实际 1/9 路画面、真实 Track 和失败收口仍待 Gateway 实际节点验证。部署后观察到
已有多路视频心跳并发时 Media 短时出现 Hikari 连接池耗尽和锁等待，队列排空后 `/api/media/files`
