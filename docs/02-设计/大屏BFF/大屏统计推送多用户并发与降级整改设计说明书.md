# 大屏统计推送多用户并发与降级整改设计说明书

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 评审中 |
| 编制日期 | 2026-09-05 |
| 适用模块 | `bigscreen-bff`、`robot-ui`，以及 Management 统计供数接口 |
| 事故范围 | 大屏首页左侧告警概览、右侧任务概览及其 WebSocket 统计刷新链路 |
| 核心目标 | 在多用户、24 小时长连接和高频事件场景下，保证统计刷新可扩展、可降级且绝不以伪 0 覆盖有效数据 |

## 1. 背景与结论

大屏首页首次通过 REST Overview 加载后，告警概览和任务概览能够展示正常数据；随后收到
`panorama.stats.changed` 推送后，今日告警和今日任务被 0 覆盖。现场保留了 4 轮统计推送，
但服务器已经关机，无法继续提取运行日志、线程池指标和 Management 请求耗时。

结合推送报文与当前代码，可以确认本次问题不是单一的“Management 响应慢”，而是以下问题叠加：

1. BFF 将任务或告警查询失败转换成空集合及数值 0，破坏了“查询失败”和“业务真实为 0”的语义边界。
2. `robot-ui` 的 WebSocket 消费路径没有像首次 Overview 一样校验数据质量，直接用降级结果覆盖正常值。
3. 当前 WebSocket 桥接、刷新调度和缓存以浏览器会话或用户主体为粒度，同一业务变化会按在线用户数放大。
4. 首页统计错误地复用了完整任务详情聚合 `taskPayload()`，单个用户的一次刷新也会按任务数量继续扇出大量异步任务。
5. 统计执行器容量较小并使用无等待队列；它可以在 Management 单次请求并不慢时，由 BFF 自身的瞬时并发直接触发拒绝。
6. 任务和告警还有独立的事件快照刷新及多轮收敛重试，同一源事件会触发多条并行查询链路。

因此，本次整改不能只扩大线程池或延长超时。正式方案必须同时解决：

- 数据正确性：失败不能伪装成 0；
- 查询收缩：首页统计只读取统计所需字段；
- 并发治理：按授权身份或权限范围合并刷新，不按浏览器会话重复计算；
- 事件架构：降低一浏览器一上游连接造成的事件复制；
- 权限边界：任何缓存和共享优化不得跨越用户实际可见范围；
- 可观测性：能够量化在线会话、查询放大、缓存命中、拒绝和降级。

## 2. 证据范围与结论等级

### 2.1 已掌握证据

- 用户提供的 4 轮 `panorama.stats.changed` 原始报文；
- 当前仓库中的 BFF、前端、接口协议和权限缓存设计；
- 报文中的 `TASK_EXECUTOR_SATURATED`、`TASK_QUERY_TIMEOUT` 和 `dataQuality.tasks`；
- 首次刷新正常、后续推送覆盖为 0 的页面现象。

### 2.2 结论等级

| 等级 | 含义 |
| --- | --- |
| 已确认 | 可由报文与当前代码直接闭环证明 |
| 高可信推断 | 缺少现场日志，但代码存在完整触发路径且与现象吻合 |
| 待压测确认 | 需要恢复环境后通过指标、故障注入或并发测试量化 |

本文不将下列内容描述为已确认事实：

- 当时具体哪个 Management 接口最先变慢；
- 当时 Management 单次请求的真实耗时；
- 当时的在线用户数、浏览器连接数和 BFF 实例数；
- 第 3 轮告警 0 对应的具体异常类型；
- 是否存在网络、数据库或连接池层面的附加故障。

这些未知项不影响对伪 0 覆盖、查询放大和执行器饱和机制的整改。

## 4. 当前调用链路

### 4.1 首次加载链路

```text
浏览器打开大屏
  -> GET /api/bigscreen/panorama/overview
  -> BFF 按当前用户查询 Management
  -> robot-ui setAll()
  -> 校验 dataQuality.tasks
  -> 写入 alarmSummary、taskOverview
  -> 首页首次展示正常
```

首次 Overview 的前端路径会读取 `dataQuality.tasks`。当任务降级时，前端使用未知占位，
不会把空任务集合直接当成真实统计。

### 4.2 后续 WebSocket 刷新链路

```text
中心端任务/告警变化
  -> 每条中心端 WebSocket 各收到一次事件
  -> 每个浏览器 session 各自 requestRefresh()
  -> BFF 按该用户重新查询 Management
  -> 计算 panorama.stats.changed
  -> robot-ui 无条件 SET_ALARM_SUMMARY / SET_TASK_OVERVIEW
  -> 正常首次快照被降级 0 覆盖
```

### 4.3 当前连接模型

`BigscreenWebSocketBridgeHandler` 在每个浏览器连接成功后调用 `connectCenter(browserSession)`，
并以浏览器 `sessionId` 保存对应的中心端连接。因此当前模型是：

```text
1 个浏览器会话 = 1 条浏览器到 BFF 连接 + 1 条 BFF 到 Center 连接
```

若有 `U` 个不同用户各打开一个大屏，则约有 `U` 条上游中心端连接。同一全局变化可能通过这些连接
重复进入 BFF，随后再按用户触发统计查询。

## 5. 问题清单

### 5.1 数据正确性 Bug

#### BUG-DATA-01：任务降级结果被计算为有效 0

确认等级：已确认；优先级：P0。

`PanoramaService.taskOverview()` 根据任务列表长度计算 `totalToday`。当任务查询失败时，任务聚合使用
空列表兜底，随后自然得到：

```json
{
  "totalToday": 0,
  "completedRate": null,
  "completedRateText": null,
  "running": 0,
  "pending": 0
}
```

虽然同一载荷已经携带 `dataQuality.tasks.degraded=true`，但数值结构本身仍像一份合法业务结果。
这使任何忽略质量字段的消费者都可能误用。

#### BUG-DATA-02：WebSocket 路径忽略任务数据质量

确认等级：已确认；优先级：P0。

`robot-ui/src/store/modules/websocket-extra-data.js` 的首次 `setAll()` 会判断任务是否完整；
`panorama.stats.changed` 分支却直接提交 `event.data.taskOverview`，没有读取
`event.data.dataQuality.tasks`。同一份数据在 REST 和 WebSocket 两条路径上具有不同的降级行为。

#### BUG-DATA-03：告警失败被静默转换为空页和 0

确认等级：已确认；优先级：P0。

`PanoramaService.alarmsPayload()` 并发查询高、中、低风险、今日总数、已处理和误报。
这些查询通过通用 `join(future, emptyAlarmPage)` 收口。超时和异常被捕获后直接返回空页，
且没有生成 `dataQuality.alarms`。

因此当前协议无法区分：

```text
查询成功且今日确实为 0
查询失败并由 emptyAlarmPage 兜底为 0
```

#### BUG-DATA-04：告警部分失败可生成内部矛盾数据

确认等级：已确认代码路径；优先级：P0。

六个告警查询分别兜底，可能组合出以下错误结果：

- 今日总数成功、已处理查询失败：处置率被低估；
- 今日总数失败、已处理成功：`handled > totalToday`；
- 今日总数失败、已处理成功：`unhandled = totalToday - handled` 可能为负数；
- 某个风险等级失败：告警分布和最新列表被静默少算；
- 多个风险等级失败：部分告警仍存在，但统计可能显示为 0。

这不是单纯的展示问题，而是聚合事务边界不完整。

#### BUG-DATA-05：页面将未知值再次格式化为 0

确认等级：已确认；优先级：P1。

`Left.vue` 和 `Right.vue` 使用 `value || 0` 或 `value || '0'`。当值为 `null`、`undefined`
或空字符串时，页面统一显示为 0，掩盖了“尚未加载”“查询失败”和“真实为 0”的区别。

#### BUG-DATA-06：统计推送不一定是协议声明的完整快照

确认等级：已确认；优先级：P1。

`PanoramaStatsEventRefresher` 只计算本次事件涉及的 `StatsPart`，再与当前 WebSocket 会话内的
`previousSnapshot` 合并。新会话如果先收到任务事件而没有收到告警统计，首条推送就不会包含
`alarmStats` 和 `alarmSummary`。第 1、2 轮报文已经体现该情况。

当前协议却将 `panorama.stats.changed` 描述为完整快照，并将多个统计块标记为必填，
实现与协议语义不一致。

#### BUG-DATA-07：统计缓存可能吞掉真实变化事件

确认等级：已确认代码路径；优先级：P1。

任务、告警统计使用 3 秒 TTL 缓存。设备事件会显式清除设备统计缓存，但任务刷新目前主要清除
Overview 缓存，没有同步清除 `statsCache` 中的 `tasks:<user>`；告警变化也没有显式清除
`alarms:<user>`。

如果变化事件在缓存有效期内到达：

1. 统计刷新读取旧缓存；
2. 新旧快照相同，不推送；
3. TTL 到期后如果没有新的事件，不会自动补算；
4. 页面可能持续停留在旧值，而不是最多只延迟 3 秒。

### 5.2 并发与容量 Bug

#### BUG-CONC-01：首页统计调用完整任务详情聚合

确认等级：已确认；优先级：P0。

`calculateStatsSnapshot(TASKS)` 调用 `taskPayload()`。该方法除任务计划和实例列表外，还按任务预取：

- 单个工作流实例；
- 任务回放；
- 设备任务实例；
- 工作流定义；
- 地图点和路径点；
- 每个任务的异步组装任务。

这些数据都不是首页任务数量和完成率所必需。代码中已经存在只读取计划和实例列表的
`taskSummaries()`，但统计刷新没有复用。

若任务数为 `T`，一次统计刷新可能产生约 `2 + 3T` 到 `2 + 5T` 个异步提交，
部分异步任务内部还会继续串行访问 Management。报文中 `T=12` 时，单用户一次刷新就可能产生数十个任务。

#### BUG-CONC-02：统计 I/O 执行器会主动拒绝瞬时突发

确认等级：已确认；优先级：P0。

当前统计 I/O 执行器为：

```text
corePoolSize = 4
maximumPoolSize = 8
queue = SynchronousQueue
rejection = AbortPolicy
```

`SynchronousQueue` 不保存等待任务。8 个线程都忙时，新任务立即抛出
`RejectedExecutionException`，再转换为 `TASK_EXECUTOR_SATURATED`。

因此，`TASK_EXECUTOR_SATURATED` 首先表示 BFF 本地执行器没有接纳任务，并不能直接证明
Management 单请求响应慢。Management 变慢会延长线程占用并加重问题，但不是触发拒绝的必要条件。

#### BUG-CONC-03：统计编排最多只容纳 20 个同时计算身份

确认等级：已确认；优先级：P0。

`STATS_EXECUTOR` 固定 4 个线程和 16 个排队位置。缓存未命中且 key 不同的刷新超过约 20 个时，
后续刷新会在编排层被拒绝。不同用户的 key 包含 JWT `subject`，因此大量不同用户会直接消耗独立位置。

此外，`statsSnapshotInFlight` 和 `statsPartInFlight` 的并发 key 上限为 128。超过上限时会抛出
“统计并发身份已达上限”，但当前 WebSocket 刷新只记录日志，不向浏览器发送明确的降级状态。

#### BUG-CONC-04：缓存容量与用户规模不匹配

确认等级：已确认；优先级：P1。

统计缓存总容量为 256，并由设备、任务、里程、告警等分块共享。一个完整活跃用户通常至少占用：

```text
devices:<user>
tasks:<user>
mileage:<user>
alarms:<user>
```

按四类计算，约 64 个不同身份即可占满缓存。超过后会持续淘汰最近较少使用的用户条目，
大量在线用户会形成缓存抖动，使 3 秒缓存难以发挥作用。

#### BUG-CONC-05：防抖和刷新状态按浏览器会话维护

确认等级：已确认；优先级：P0。

统计、任务和告警 Refresher 均以 `sessionId` 建立状态。相同用户打开多个浏览器或标签页时，
每个会话都拥有独立的定时、dirty、previousSnapshot 和重试状态。

底层统计缓存可能让同一用户短时间共享部分查询，但无法消除：

- 每会话的调度任务；
- 每会话的上游事件处理；
- 每会话的序列化和发送；
- 每会话的独立重试；
- 缓存过期或 key 不一致后的重复计算。

#### BUG-CONC-06：一个任务事件同时触发两条查询链路

确认等级：已确认；优先级：P0。

中心端任务事件到达后，同时触发：

1. `PanoramaStatsEventRefresher`，用于重新计算任务统计；
2. `PanoramaTaskEventRefresher`，用于重新查询任务事件快照和差异。

任务事件快照本身还会查询计划列表和活动实例。也就是说，同一个事件既执行完整统计任务聚合，
又执行任务事件摘要查询，存在重复读。

#### BUG-CONC-07：任务事件成功后仍可能固定进行多轮复查

确认等级：已确认；优先级：P1。

任务事件刷新收到 `followChanges=true` 后，即使当前查询完整成功，也会按 1、2、4、8 秒退避进行
最多四轮复查。该机制用于等待异步状态收敛，但目前仍按浏览器会话执行。

一次全局任务变化在 `U` 个会话中可能产生约 `4U` 轮额外任务摘要查询，不包含首次查询和统计刷新。

#### BUG-CONC-08：告警事件同时触发统计、列表和工作流收敛查询

确认等级：已确认；优先级：P0。

告警事件到达后会同时触发：

- 告警统计刷新：至少六个查询；
- 普通告警列表快照：三个风险等级查询；
- 可处置工作流告警刷新；
- 工作流告警在最长 5 秒内每 300ms 复查。

缓存失效时，单次告警变化至少可能产生约 9 个普通告警查询/用户，工作流告警查询另计。
若有 100 个不同用户在线，最坏情况下可形成约 900 个近同时普通告警查询。

#### BUG-CONC-09：一浏览器一中心端连接放大事件和资源占用

确认等级：已确认；优先级：P1。

该模型同时放大：

- 上游 WebSocket 连接数；
- TCP 文件描述符和内存占用；
- 心跳、断线检测和重连开销；
- 同一业务事件进入 BFF 的消息次数；
- 中心端 WebSocket 会话维护压力。

24 小时运行时还必须考虑网络闪断、服务发布和中心端重启造成的大规模同步重连。

#### BUG-CONC-10：连接初始化会形成启动风暴

确认等级：已确认；优先级：P1。

每个浏览器连接建立后都会立即进行权限快照加载、告警快照、中心端 WebSocket 连接和任务快照刷新。
服务重启、网络恢复或大量值班终端同时打开页面时，这些初始化操作会集中发生。

### 5.3 可用性风险

#### RISK-AVL-01：降级发生后页面静默显示错误数据

当前页面没有明显的数据延迟或降级标识。用户看到 0 会理解为“今日没有任务/告警”，
而不是“统计暂时不可用”。在指挥中心场景中，这属于错误决策风险。

#### RISK-AVL-02：统计刷新整体异常时只写日志、不通知前端

`PanoramaStatsEventRefresher` 捕获运行异常后记录日志并结束本轮刷新，没有向浏览器发送质量状态，
也没有有界补偿刷新。服务器日志不可用时，前端和运维都无法识别该轮刷新已经失败。

#### RISK-AVL-03：本地缓存和线程池使多实例重复放大

当前缓存、在途请求合并和 Refresher 状态均为 BFF 进程内数据。如果部署 `K` 个 BFF 实例，
相同授权范围和业务事件可能在每个实例各计算一次，理论下游压力还会再乘以 `K`。

#### RISK-AVL-04：缺少明确的容量基线和保护目标

当前线程池和缓存容量是代码常量，未体现计划支持的在线用户数、每秒事件数、任务数和告警数。
没有容量模型就无法判断 4/8 个线程、16 个排队位置和 256 个缓存项是否满足生产目标。

### 5.4 安全与权限风险

#### RISK-SEC-01：合法用户可通过大量连接放大后端负载

当前代码没有体现按用户、组织或来源限制 WebSocket 会话数的应用级配额。拥有合法 Token 的用户
如果打开大量标签页或自动建立大量连接，会同时放大中心端连接、刷新状态和查询任务。
这属于认证后可用性攻击面。是否已有 Nginx、网关或 WAF 限制需要部署侧另行确认。

#### RISK-SEC-02：不能用全局统计缓存直接解决并发问题

任务、告警和设备统计必须服从当前用户在 Management 中的真实可见范围。直接以全局或组织级结果
替换当前按用户查询，会造成越权统计、告警数量泄露或任务信息泄露。

#### RISK-SEC-03：保留最近成功值必须处理权限变化

为了避免降级 0 覆盖，可以在同一授权上下文中保留最近成功值，但必须在以下场景立即清除：

- 用户退出或切换账号；
- 授权资源集合变化；
- `authorization_version` 或等价权限版本变化；
- Token 主体、组织发生变化；
- 跨自然日且统计口径按“今日”重置。

否则，旧值虽然解决了可用性问题，却可能向已失权用户继续暴露历史统计。

#### RISK-SEC-04：权限范围复用不能只按角色名判断

两个用户具有相同角色，并不代表其设备、任务、告警可见集合相同。后续若实现权限分组缓存，
必须使用 Management 提供或 BFF 严格计算的授权范围指纹，不能只使用 `authorities`。

### 5.5 协议与维护风险

#### RISK-CONTRACT-01：`dataQuality` 只覆盖任务，不覆盖告警

消费者无法用统一规则处理不同统计块。后续应为设备、任务、告警、里程建立一致但可分块的质量模型。

#### RISK-CONTRACT-02：顶层 `dataQuality` 使用浅合并

当前 Refresher 对顶层 Map 使用 `putAll`。若未来任务和告警分别返回：

```json
{"dataQuality":{"tasks":{...}}}
```

和：

```json
{"dataQuality":{"alarms":{...}}}
```

后一次浅合并会覆盖整个 `dataQuality`，丢失另一分块质量。整改时必须使用分块深合并或独立质量字段。

#### RISK-CONTRACT-03：完整快照与增量快照语义混用

文档声明 `panorama.stats.changed` 是完整快照，实现却允许逐块积累。必须正式选择一种协议：

- 完整快照：每次必须包含全部成功或明确降级的统计块；
- 分块增量：事件显式携带 `changedParts`，客户端只更新这些块。

不应继续依赖“字段有时出现、有时缺失”的隐含语义。

## 6. 查询放大模型

定义：

| 符号 | 含义 |
| --- | --- |
| `U` | 同时在线的不同授权身份数 |
| `S` | 浏览器 WebSocket 会话数，通常 `S >= U` |
| `T` | 当前可见任务数 |
| `K` | BFF 实例数 |
| `E` | 单位时间内触发统计刷新的业务变化数 |

当前任务统计的瞬时工作量近似为：

```text
K × U × E × [任务计划/实例基础查询 + O(T) 的任务详情及组装]
```

当前告警变化的普通告警查询量近似为：

```text
K × U × E × [6 次统计查询 + 3 次列表查询]
```

任务、告警收敛重试和同一用户多会话还会继续增加调度与查询次数。3 秒用户级缓存只能削减同一身份
短窗口内的重复访问，无法消除不同用户和不同 BFF 实例之间的乘数。

## 7. 正式整改方案

### 7.1 总体原则

1. 真实 0、未知、降级、过期必须是四种可区分状态。
2. 首页统计只获取计算统计所需的最小数据，不复用任务详情聚合。
3. 同一授权身份或等价授权范围的相同刷新只能有一个在途计算。
4. 事件刷新采用 latest-only：中间事件可合并，最终状态不能丢失。
5. 下游失败时保留同一有效授权上下文中的最近成功展示，但必须明确标记陈旧。
6. 权限变化优先于可用性；无法证明仍有权限时必须清除旧数据。
7. 扩容线程池只能建立在查询收缩、背压和容量评估完成之后。

### 7.2 P0：任务统计改用轻量摘要

将 `calculateStatsSnapshot(TASKS)` 中的 `taskPayload()` 替换为专用统计方法，复用
`taskSummaries()` 的计划列表和实例列表，不加载：

- 回放；
- 设备任务明细；
- 工作流定义；
- 地图点；
- 路径点；
- 每任务异步组装任务。

目标查询复杂度从 `O(T)` 次远程访问收缩为固定次数的列表查询。若 Management 能提供按当前用户鉴权的
任务聚合接口，应进一步收缩为一次聚合查询，但不把该接口作为本轮正确性修复的前置条件。

### 7.3 P0：建立分块数据质量协议

建议统一结构：

```json
{
  "dataQuality": {
    "tasks": {
      "complete": false,
      "degraded": true,
      "stale": true,
      "reasonCodes": ["TASK_EXECUTOR_SATURATED"],
      "lastSuccessAt": "2026-09-04 14:29:16"
    },
    "alarms": {
      "complete": false,
      "degraded": true,
      "stale": true,
      "reasonCodes": ["ALARM_QUERY_REJECTED"],
      "lastSuccessAt": "2026-09-04 14:29:16"
    }
  }
}
```

要求：

- 查询成功并真实返回空集合：`complete=true`、`degraded=false`，允许统计为 0；
- 查询失败：不得生成新的有效 0；
- 部分失败：对应统计块整体不可提交，或进一步拆成具备明确原子性的子块；
- 401/403：不得用旧数据兜底，按登录或权限变化流程处理；
- `dataQuality` 必须按分块深合并，不能顶层浅覆盖。

### 7.4 P0：修正告警聚合原子性

`alarmSummary` 至少依赖今日总数、已处理和误报三个查询。只有三者全部成功，才提交新的 summary。
高、中、低风险分布也应作为一个原子统计块全部成功后提交。

正式实现不得继续使用 `join(future, emptyAlarmPage)` 作为统计成功结果。应返回显式结果对象：

```text
Success(value)
Unavailable(reasonCode)
Forbidden
```

失败时保留上一成功块并标记 stale，或者在增量协议中不携带该块；不能把空页混入成功计算。

### 7.5 P0：前端拒绝降级覆盖

`robot-ui` 的 Overview 和 WebSocket 必须复用同一个统计应用函数：

```text
质量完整 + 明确携带字段 -> 更新
质量降级 + 当前授权未变化 -> 保留最近成功值并标记延迟
质量降级 + 没有历史成功值 -> 展示 --
登录/权限变化 -> 清除旧值并重新加载
```

模板层不得使用 `value || 0` 表示未知，应使用显式状态或空值判断。真实数值 0 仍正常展示为 0。

### 7.6 P0：刷新调度从 session 提升到授权身份

建立身份级 Refresh Coordinator：

```text
identityKey
  -> 当前授权快照/版本
  -> dirtyParts
  -> scheduled/running
  -> lastSuccessfulParts
  -> sessions[]
```

同一身份的多个浏览器会话：

- 只安排一次任务/告警/设备统计刷新；
- 只执行一次 Management 查询；
- 结果按该身份的所有活动会话分别发送；
- 所有会话关闭后释放身份级状态。

### 7.7 P0：统一同源事件的刷新计划

任务事件不应分别触发完整统计聚合和另一套任务列表查询。建议一次获取轻量任务摘要后，同时产出：

- 任务集合差异事件；
- `taskOverview`；
- 巡检时长；
- 任务数据质量。

告警事件同理，应尽量由一次一致快照同时产出：

- 普通告警第一页；
- 风险分布；
- 今日告警汇总；
- 告警数据质量。

若 Management 当前接口无法一次返回，BFF 仍应在同一个身份级刷新上下文中共享查询结果，
不能由多个 Refresher 重复调用。

### 7.8 P1：按授权范围安全复用

不同用户之间的复用必须满足：

1. Management 明确保证两个身份的数据可见范围相同；或
2. Management 提供稳定的权限范围版本/指纹；或
3. BFF 能基于完整授权设备、任务和告警范围生成不可碰撞的范围摘要。

建议 key 至少包含：

```text
issuer + org + permissionScopeFingerprint + authorizationVersion + statisticalDate
```

在无法证明权限等价前，只做到同一身份多会话复用，不跨用户共享。

### 7.9 P1：收缩上游 WebSocket 连接

优先与中心端确认是否支持服务级或租户级“失效通知”订阅。目标模型：

```text
BFF 每实例/租户少量上游订阅
  -> 接收不含越权业务明细的变化通知
  -> 标记受影响统计块 dirty
  -> 按在线授权身份或等价范围合并刷新
  -> 向浏览器会话扇出
```

如果中心端只能按用户 Token 建立连接，至少实现：

- 同一授权身份只维护一条中心端连接；
- 多个浏览器会话复用该连接；
- 最后一个会话离开后延迟释放，避免短时刷新反复建连；
- 建连和重连增加抖动、速率限制和最大并发。

### 7.10 P1：背压与重试治理

统计卡片只关心最新状态，采用以下规则：

```text
空闲 + 事件到达 -> 延迟合并后刷新
正在刷新 + 事件到达 -> 只标记 dirty，不新增任务
刷新结束 + dirty -> 再执行一次
连续失败 -> 有界指数退避
新事件到达 -> 可提前退避，但仍只保留一个待执行任务
```

任务和工作流告警的收敛复查必须从“每会话重试”改为“每身份/范围重试”。同时为重试设置：

- 最大次数；
- 最大持续时间；
- 随机抖动；
- 全局并发上限；
- 新旧事件版本比较；
- 成功后仅在确实存在收敛条件时继续复查。

### 7.11 P1：缓存与失效修正

- 任务事件必须清除或版本化当前身份的任务统计缓存；
- 告警事件必须清除或版本化当前身份的告警统计缓存；
- 失效事件在 TTL 内到达时，不能读取旧值后永久丢失变化；
- 缓存 key 包含统计日期，跨日自动隔离；
- 缓存容量按峰值授权身份/范围数设计，不再固定为无依据的 256；
- 多实例部署需评估共享缓存或事件版本，不要求所有业务值进入分布式缓存；
- 降级结果不得写入成功缓存。

### 7.12 P1：连接与初始化治理

- 配置每用户、每组织和每实例 WebSocket 会话上限；
- 同一身份的权限加载、Overview 和初始化快照使用 single-flight；
- REST Overview 刚成功后，WebSocket 初始化复用其有效统计，不立即重复查询；
- 批量重连加入随机抖动；
- 慢消费者采用有界发送队列或断开策略，不能拖住其他会话；
- 会话关闭必须释放浏览器状态、身份引用和上游连接。

### 7.13 P2：Management 聚合接口优化

若压力测试表明轻量列表查询仍无法满足峰值，可由 Management 提供按用户鉴权的聚合接口：

```text
GET /tasks/statistics/today
GET /alarms/statistics/today
```

接口直接返回首页所需计数和数据版本，避免 BFF 拉取明细后计算。该优化属于跨服务协议扩展，
必须同步定义权限、统计口径、日期时区、版本和降级错误码；不是本轮伪 0 修复的前置条件。

## 8. 执行器整改边界

线程池调整必须在查询收缩和调度合并之后进行。建议顺序：

1. 去除 `taskPayload()` 的任务级扇出；
2. 合并同身份会话和同源查询；
3. 建立压测容量模型；
4. 再确定线程数、队列长度和拒绝策略；
5. 将参数外部化并设置安全上下限。

不应使用无限队列。推荐有界队列配合 latest-only 合并；队列满时保留 dirty 状态并退避，
不能继续生成空列表或 0。不同用途的执行器继续隔离：

- 首屏 Overview；
- WebSocket 统计刷新；
- 任务收敛；
- 告警收敛；
- 权限刷新。

隔离的目标是故障域分离，不是允许各链路重复查询相同数据。

## 9. 可观测性要求

以下指标作为已有运维体系可承接时的增强项，不作为本轮整改上线前置条件。本轮不新增
Prometheus、Grafana、Actuator、Micrometer、监控端口或对外调试接口；当前验收只复用
应用日志、容器资源采样和压测端观测。

### 9.1 连接指标

- 当前浏览器 WebSocket 会话数；
- 当前不同授权身份数；
- 当前中心端 WebSocket 连接数；
- 每用户会话数分布；
- 建连、断连、重连次数及原因；
- 连接建立耗时和失败率。

### 9.2 刷新指标

- 各类源事件接收数；
- 去抖合并数；
- 身份级实际刷新数；
- 同源重复事件数；
- dirty 二次刷新数；
- 重试次数和停止原因；
- 每个统计块最近成功时间。

### 9.3 执行器与缓存指标

- active、pool、queue、completed、rejected；
- `statsSnapshotInFlight`、`statsPartInFlight` 数量；
- 缓存 size、命中、未命中、过期和淘汰；
- 按身份与按权限范围的 single-flight 合并次数。

### 9.4 下游调用指标

- 按接口统计 QPS、并发数、P50/P95/P99、超时和错误码；
- 每次源事件实际触发的 Management 请求数；
- 每次统计刷新实际触发的任务级明细请求数；
- 401/403 与普通可用性错误分开统计。

### 9.5 数据质量指标

- `tasks/alarms/devices/mileage` 各分块降级次数；
- 伪 0 防护触发次数；
- stale 持续时间；
- `handled > total`、`unhandled < 0` 等不变量违例；
- 页面收到的完整、增量和降级快照数量。

## 10. 测试与验收方案

### 10.1 功能回归

1. 首次 Overview 任务 12、告警 5，页面展示正确。
2. 后续任务查询拒绝，页面保留 12 并标记数据延迟。
3. 后续告警任一查询超时，页面保留 5，不显示 0。
4. 查询成功且业务真实为 0，页面从非零正确更新为 0。
5. 降级恢复后，新成功值能够覆盖旧值并清除 stale。
6. 首条 WebSocket 统计事件具有明确的完整或分块语义。
7. 缓存有效期内发生变化，TTL 到期前后均不会永久漏掉更新。

### 10.2 权限回归

1. 两个不同权限用户看到不同统计。
2. 同一用户多个窗口共享计算但分别收到结果。
3. 权限版本变化后旧值立即清理。
4. 用户退出、切换账号后不保留旧统计。
5. 跨自然日不继续展示前一天最近成功值。
6. 401/403 不走可用性兜底。

### 10.3 容量与稳定性

以正式规划的峰值在线用户数为基线，至少覆盖：

- 不同身份同时在线；
- 同一身份多标签页；
- 任务数 12、100、500；
- 高频任务变化；
- 高频告警变化；
- 任务和告警同时变化；
- BFF 单实例及生产实例数；
- 服务重启后全部客户端重连；
- 中心端短暂断连后批量重连；
- Management 正常、延迟、超时和拒绝故障注入；
- 慢浏览器消费者。

验收必须证明：

- 统计远程查询次数不再随任务数线性增长；
- 同身份查询次数不再随浏览器会话数增长；
- 同一源事件不会产生无上限重试；
- 执行器无拒绝，或拒绝时页面不出现伪 0；
- 在约定压测档位内，下游超时、错误和熔断不持续增长；
- 24 小时稳定运行无连接、状态或缓存持续增长。

## 11. 整改跟踪台账

### 11.1 状态标记规则

每个整改项分别维护研发、验证和上线三个状态，不能用一个“已完成”混合表达：

| 维度 | 可用状态 | 判定标准 |
| --- | --- | --- |
| 研发状态 | 待实施、实施中、已完成、阻塞、不实施（范围收缩） | 代码和文档修改是否已经形成完整闭环；明确退出本轮范围的事项单独标记，不伪装成已完成 |
| 验证状态 | 未验证、单元测试通过、模块验证通过、并发压测通过、并发压测未通过、不适用 | 必须填写实际执行命令、日期和结果；未执行或验收失败不能写通过 |
| 上线状态 | 未部署、已部署待验证、已部署待整改、线上已验证、已回退、不适用 | 本地构建或测试通过不等于生产环境已经生效；没有部署对象的文档或测试项标记不适用 |

维护要求：

1. 开始修改某项时，将研发状态改为“实施中”。
2. 代码、协议和相关测试全部完成后，才能将研发状态改为“已完成”。
3. 每完成一级验证，更新验证状态，并在“证据”中记录测试命令、报告或提交号。
4. 生产发布后单独更新上线状态；没有部署证据时必须保持“未部署”。
5. 一个提交尽量只关闭一个可验证的整改项；确需合并时，在提交说明中列出全部整改 ID。
6. 发现新问题时新增独立 ID，不覆盖原问题描述或删除历史状态。
7. 状态变化必须同时更新“最后更新”和“证据”，不能只修改状态文字。

### 11.17 `STAT-P0-09` 根因、优化方案与整改边界（2026-09-06）

#### 11.17.1 根因结论

本次故障是“授权刷新超过硬期限 → 4003 断链 → 客户端重连并重复初始化 → 连接与对象分配放大 → 512 MiB 堆耗尽 → 共享 HTTP Client 和 WebSocket 线程失效”的正反馈，不是单个 Management 请求数据量过大，也不能仅归因于 Management 响应慢。

1. **直接触发条件已确认。** BFF 授权快照硬有效期被代码限制为最多 30 秒，15 秒后开始刷新；30 个不同身份同时登录时会在相近时间进入刷新。正式轮次首批“拒绝使用过期快照”发生在快照年龄约 30.4 秒，整个正式窗口记录 187 次过期快照拒绝、5 次调度检查发现快照过期和 177 次固定摄像头租约主动释放。
2. **失败反馈环已确认。** 快照过期后 `validSnapshot` 和定时检查立即以 4003 关闭浏览器会话。前端虽采用 2 至 30 秒指数退避，但每次重连仍重新执行完整授权资源加载、中心端 WebSocket 建连、任务初始化和告警初始化。预备轮次 4 分 25 秒内建立 204 次连接并发生 174 次 4003；正式轮次 6 分 32 秒内又建立 201 次连接并发生 171 次重连，稳定的 30 条业务连接被放大为数百次生命周期创建与销毁。
3. **授权时间预算缺陷已确认。** `loadAuthorizationSnapshot` 在远程设备和固定摄像头查询开始前记录 `loadedAt`，查询和线程池排队时间会直接消耗 30 秒硬有效期。刷新线程池固定 8 线程并使用无界队列；30 个同时到期身份只有 15 秒刷新窗口，任何短暂排队或单轮查询抖动都可能让后续批次在成功替换快照前先被判过期。线上没有覆盖 `BIGSCREEN_WS_*`，实际就是该默认组合。
4. **中心端建连资源无界已确认。** `StandardWebSocketClient` 默认使用 `SimpleAsyncTaskExecutor`，每次建连创建新的异步任务线程；线上 OOM 日志出现 `SimpleAsyncTaskExecutor-448`、多个 `WebSocketClient-AsyncIO-*`、`panorama-task-event-io` 和权限刷新线程同时堆溢出，说明内存枯竭已经扩散到多个执行面。该事实证明连接尝试缺少并发和队列上限，但不能仅凭线程序号推断 448 个线程同时存活。
5. **关闭与建连竞态已确认存在于代码。** `connectCenter` 阻塞等待异步建连完成后直接写入 `centerSessions`，没有再次确认浏览器会话仍打开、会话预留仍属于当前身份。如果浏览器在等待期间因 4003、Token 到期或网络错误关闭，迟到的中心端连接可能在清理完成后才写回 Map，成为仍接收上游事件但已没有有效浏览器消费者的孤儿连接。当前无故障时序下可正常释放，但异常时序没有闭环。
6. **OOM 后无法自愈已确认。** JVM 只有 `-Xms512m -Xmx512m`，Docker 没有内存限制；堆溢出后 JVM 没有退出，因此 `restart: unless-stopped` 不会触发。共享 JDK HTTP Client selector 已关闭，权限刷新和固定摄像头租约同步/释放持续失败，容器仍显示 running，但服务实际不可恢复，只能人工重启。
7. **堆内对象占比尚未确认。** 线上运行镜像没有 `jcmd/jmap`，故障前也未启用受控 heap dump。本轮可以确认分配风暴和若干生命周期缺口，但不能把某一个 Map、某一种消息或某个第三方类断言为唯一内存泄漏点；是否存在长期不可达对象未回收，需要整改后的受控短压和类直方图/heap dump 才能最终排除。

#### 11.17.2 最小整改方案

整改按先切断反馈环、再补齐资源边界、最后调整部署自愈的顺序执行；不得以单独扩大堆内存替代代码整改。

1. **P0-A：授权过期改为连接内 fail-closed。** 授权快照超过硬期限时，当前连接进入“授权暂不可用”状态：停止向上游发送控制消息、停止向浏览器发送需资源授权的业务事件，保留最后成功页面数据但不把它当新数据，不立即以 4003 断开。后台继续按身份单飞、带退避刷新；刷新成功后恢复同一连接并触发一次权威任务/告警/统计校准。Management 明确 401 或 JWT 到期仍必须以 4001 关闭，不能降低鉴权强度。
2. **P0-B：修正授权时间语义和刷新容量。** `loadedAt/expiresAt` 只在全部授权查询成功后生成；软刷新时间和硬失效时间分离，加入按身份确定性的抖动，避免同时登录的身份同秒刷新。授权刷新执行器改为显式有界线程池和有界队列，拒绝时只保留一个 dirty 状态并退避，禁止无界积压。30 秒权限撤销边界若必须保持，应按“30 身份、单次加载最坏 8 秒”重新计算线程数与提前量；如业务允许把硬陈旧上限放宽到 60 或 120 秒，必须单独确认权限撤销 SLA，不能静默放宽。
3. **P0-C：中心端 WebSocket 生命周期闭环。** 建连使用有界执行器和明确超时；连接完成后再次核对浏览器会话、身份预留和连接代次，迟到或重复连接立即关闭，不写入 Map。浏览器关闭、中心端关闭、传输异常和调度发现死连接统一走一个幂等清理入口，先删除本地集合并关闭中心端连接，再执行固定摄像头租约释放；外部 DELETE 失败不得阻断本地清理。应用销毁时同时关闭授权执行器、建连执行器和自建 `WebSocketContainer`。
4. **P0-D：抑制重连初始化放大。** 任务、告警和统计刷新状态继续按授权身份 single-flight，但断线清理不能让尚在运行的旧任务与新连接任务并行发布。为状态增加代次或失效标记；新连接只接管最新 publisher，旧任务完成后必须丢弃结果且不得继续重试。固定摄像头租约在瞬时授权不可用时不反复 DELETE/PUT，只在身份真正离线或授权集合变化时同步。
5. **P0-E：OOM 明确失败并自动恢复。** JVM 增加 `-XX:+ExitOnOutOfMemoryError`，让现有 Docker `restart: unless-stopped` 真正接管恢复；保留 512 MiB 作为整改后的首轮基准，证明代码可在当前边界内稳定后，再根据稳定态占用决定是否调整 Xmx。heap dump 只在受控复测环境临时启用并限制目录和磁盘，不作为长期线上默认，因为转储可能包含 Token 和业务数据。
6. **可观测性只做模块内最小闭环。** 不建设新的监控平台、不新增对外调试 API。通过低频结构化日志或测试可见计数记录浏览器会话数、中心端会话数、在途建连数、身份快照数、授权刷新运行/排队数和 4001/4003/4008 次数；发现中心端会话数大于浏览器会话数时直接告警，压测结束后据此证明资源已回收。

- 根据生产用户规模完成容量压测；
- 评估多实例共享事件版本或分布式 single-flight 的必要性。

完成标准：在明确约定的用户数、实例数和事件档位下，连接成功率、刷新延迟、BFF/Management 资源采样及错误日志均在验收边界内。

## 13. 整改边界

### 13.1 本次范围内

- `bigscreen-bff` 首页统计聚合、缓存、执行器、刷新和 WebSocket 桥接；
- `robot-ui` 首页统计状态管理和展示；
- `panorama.stats.changed` 数据质量和快照语义；
- 必要的 Management 轻量聚合接口评估；
- 多用户、长连接、重连和多实例容量验证；
- 相关接口、设计、测试文档和指标。

### 13.2 本次范围外

- Control Service、Media Service、MQTT 和机器人客户端；
- 告警和任务本身的业务状态机；
- 视频会话、LiveKit 和媒体流；
- 通过修改业务数据制造“非零”假数据；
- 与首页统计无关的任务详情页面功能重构。

### 13.3 禁止采用的伪整改

- 仅扩大线程池；
- 仅增加超时时间；
- 查询失败时继续返回 0；
- 前端降级后立即无上限重试 Overview；
- 每个浏览器增加定时轮询；
- 使用无限线程池或无限队列；
- 跨用户复用未验证权限边界的统计；
- 权限变化后继续保留旧值；
- 把本次问题归因于 Management 慢而不处理 BFF 查询放大。

## 14. 待确认事项

实施前需要产品、架构、Management 和部署共同确认：

1. 生产峰值在线用户数、单用户最大标签页数和 BFF 实例数；
2. 中心端 WebSocket 是否支持服务级、租户级或同身份复用订阅；
3. Management 是否能提供稳定的权限范围版本或统计聚合接口；
4. 今日任务、今日告警的时区和跨日切换规则；
5. 页面在数据陈旧时采用图标、文案还是时间提示；
6. Nginx/网关是否已有 WebSocket 连接配额和重连保护；
7. 生产监控平台和指标采集方式。

上述事项影响容量目标和二、三阶段架构，不阻塞第一阶段正确性止血。
