# 大屏任务实时轨迹设计说明书

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 已批准 |
| 编制日期 | 2026-09-02 |
| 适用范围 | 指挥中心首页、全景地图中的主 SLAM 地图 |
| 改造模块 | control-service、robot-ui；bigscreen-bff 仅调整普通定位 mapId |
| 设备侧依据 | 《轨迹查询 MQTT 接口设计》 |

## 1. 最终方案

本期按最小闭环实现：

- 不修改 EIOP Management、任务模型、任务事件和设备轨迹协议。
- 页面根据现有任务状态决定观看目标；没有观看者时不查询设备。
- Control 从设备状态取得 taskInstanceId，通过现有 MQTT 连接查询轨迹。
- 首次观看、执行中刷新或 WebSocket 重连时，使用 full 分页恢复已执行轨迹。
- 正常执行时每秒查询 summary；点数跳增时使用增量 full 补齐。
- Control 通过现有 WebSocket 直接发送 robot.trajectory.changed，BFF 使用现有桥接和 robotId 权限
  过滤透明转发，不增加轨迹专用业务。
- 任务结束后停止查询，轨迹只在当前浏览器页面保留 5 分钟。
- 同一机器人新任务开始时清除旧轨迹；同地图其他机器人的轨迹不受影响。
- 前端首版复用现有单折线，不提前实施 500 点 SVG 分段优化。

不引入历史轨迹库、Control 终态缓存、Redis、内部 REST 租约、轨迹心跳、generation、
sequence、snapshotId 或结束补齐流程。

## 2. 需求边界

### 2.1 本期实现

- 页面已经打开时，任务开始后自动出现已执行轨迹。
- 任务执行期间，轨迹和机器人图标约每秒更新。
- 执行中刷新页面或 WebSocket 重连后，从起点恢复到当前点。
- 任务完成或终止后，当前页面保留冻结轨迹 5 分钟。
- 单台设备按最长 4 小时、约 1 点/秒、约 14400 点设计。
- 保持现有约 10 秒普通定位，作为非任务状态和轨迹不可用时的位置来源。

### 2.2 本期不实现

- 不持久化轨迹，不改造任务历史回放。
- 不恢复已结束任务的轨迹；结束后刷新或重新进入页面不再显示。
- 不查询从未被大屏观看且已经结束的任务。
- 不使用 compressed 代替完整轨迹。
- 不在 GIS、3D 静态图和监控页小地图展示任务轨迹。
- 不增加轨迹异常弹窗、手动重试按钮和运行参数配置。
- 不预先实现前端折线分段；只有真实 4 小时数据验证出现性能问题时再优化。

## 3. 已核实的现有数据

### 3.1 workflowInstanceId

Management 启动任务时先保存 TaskWorkflowInstance，初始状态为 PREPARING，并取得
workflowInstanceId，之后才准备设备任务并启动工作流。

任务计划中的 executionStatus、activeWorkflowInstanceId 和
activeWorkflowInstanceStatus 来自同一个 activeInstance。BFF 把 PREPARING 和 RUNNING
统一映射为前端 running，因此收到 running 时正常情况下已经同时取得
workflowInstanceId，但设备轨迹可能尚未初始化。

运行中轨迹只使用 activeWorkflowInstanceId。lastWorkflowInstanceId 不能作为运行中轨迹
身份的兜底。running 缺少 workflowInstanceId 时忽略并记录
TASK_WORKFLOW_INSTANCE_MISSING，等待下一次任务状态刷新。

### 3.2 taskInstanceId

设备任务 ID 来自：

~~~text
Topic:   eiop/v1/edge/{serialNumber}/status
字段:    payload.status.task.taskInstanceId
robotId: Topic 中的 serialNumber
~~~

设备每次执行产生新的 taskInstanceId，但任务结束后仍可能继续上报上一轮 ID。
taskInstanceId 只在 Control 内部使用，不推给前端，也不假设它与 workflowInstanceId 相等。

### 3.3 mapId

panorama.device.location.changed.location.mapId 当前来自设备 SLAM 图 ID，不是数据库地图主键，
也没有可靠映射。本期 BFF 停止向前端输出该字段。前端按当前数据库地图的机器人集合确定坐标
归属；未来若需要 mapId，只能输出可靠映射后的数据库地图主键。

轨迹观看和事件均不携带 mapId。

## 4. 标识

| 标识 | 来源 | 用途 | 发给前端 |
| --- | --- | --- | --- |
| robotId | 设备 serialNumber | 机器人和 MQTT Topic | 是 |
| workflowInstanceId | Management activeWorkflowInstanceId | 隔离不同执行轮次 | 是 |
| taskInstanceId | 设备状态 | MQTT 查询参数 | 否 |
| commandId | Control 生成 | MQTT 请求响应关联 | 否 |
| taskId | Management 任务计划 ID | 现有任务展示 | 轨迹协议不需要 |
| mapId | 设备 SLAM 图 ID | 本期不使用 | 否 |

前端轨迹唯一键：

~~~text
robotId + workflowInstanceId
~~~

## 5. 总体链路

~~~text
Management 现有任务状态
  -> BFF 现有 panorama.task.changed
  -> robot-ui 计算当前地图观看集合
  -> trajectory.watch.sync
  -> BFF 现有 WebSocket 权限过滤和透明转发
  -> Control 绑定设备 taskInstanceId
  -> MQTT summary/full 查询
  -> Control 定向发送 robot.trajectory.changed
  -> BFF 透明转发
  -> robot-ui 更新轨迹和机器人图标
~~~

职责边界：

- robot-ui：决定观看目标、保存本页轨迹、渲染和 5 分钟保留。
- control-service：设备任务 ID 绑定、MQTT 查询、分页、补洞和定向推送。
- bigscreen-bff：复用现有 WebSocket 桥接和 robotId 权限过滤，不理解轨迹状态机。
- Management：继续提供现有任务状态、workflowInstanceId 和装备关联。
- 设备：保存真实轨迹并响应既有查询协议。

## 6. 前端观看生命周期

### 6.1 任务状态

以下状态继续观看：

~~~text
running
pausing
paused
resuming
terminating
failed
~~~

说明：

- PREPARING 已映射为 running；
- paused 期间继续每秒查询，不增加降频分支；
- failed 可能来自仍然活动的 CONTROL_FAILED，不能直接作为终态；
- terminating 继续查询，直到任务状态收口或设备轨迹 stopped。

以下条件停止查询并冻结当前页面轨迹：

~~~text
任务状态 waiting
任务状态 completed
任务状态 terminated
设备已绑定轨迹返回 stopped
~~~

机器人离线不等于任务结束。

### 6.2 生成观看目标

1. 从当前数据库地图的机器人集合取得 robotId。
2. 排除固定摄像头、模拟机器人和监控页小地图。
3. 从 taskData 找到包含该机器人且状态仍活动的任务。
4. 读取 workflowInstanceId，生成 robotId + workflowInstanceId。
5. 同一机器人发现多个活动任务时不猜测，记录 TRAJECTORY_TASK_CONFLICT 并跳过。

不使用 robotBaseInfo.runningTaskId 代替 workflowInstanceId。

以下时机重新发送完整集合：

- 首次进入有效主 SLAM 地图；
- 当前地图、地图机器人集合、任务状态或 workflowInstanceId 变化；
- WebSocket 重连成功；
- 离开页面、切换 GIS/3D 或地图预览不可用时发送空集合。

### 6.3 无人观看

- 每条 trajectory.watch.sync 表示本会话的完整期望集合。
- Control 原子替换会话旧集合；重复集合幂等。
- 同一目标被多个会话观看时共享一个轮询器。
- 任务启动时，当前所有观看会话都接收首次完整恢复，均由 RESET 建立本轮轨迹基线。
- 运行中新增或重连的会话触发一次共享完整恢复；只有缺少基线的会话接收 RESET。
- 已有基线的会话不重复接收历史点，只接收恢复开始后新增的点，避免清空重画和无效传输。
- 同一会话重复提交相同目标不触发完整恢复；恢复尚未发出第一页时加入的会话合并到本轮恢复。
- 最后一个会话移除目标时立即停止查询。
- WebSocket 关闭时在 afterConnectionClosed 中清理该会话目标。
- 不增加轨迹心跳、租约和过期扫描。
- 无人观看期间任务已经结束，之后进入页面不查询、不显示该轮轨迹。

## 7. WebSocket 协议

### 7.1 前端请求

~~~json
{
  "type": "trajectory.watch.sync",
  "payload": {
    "targets": [
      {
        "robotId": "robot-001",
        "workflowInstanceId": 9001
      }
    ]
  }
}
~~~

不传 taskId、taskInstanceId 或 mapId。targets 可以为空。

BFF 现有 canForwardClientMessage 已会递归提取 robotId 并校验权限，不增加轨迹专用任务查询、
地图补充或缓存。Control 只接受字段完整、同一集合内一台机器人对应一个
workflowInstanceId 的请求；整包非法时忽略并记录日志，不做部分替换。

不同会话临时提交同一机器人不同 workflowInstanceId 时，暂停该机器人查询并记录
TRAJECTORY_WATCH_CONFLICT，待观看集合重新一致后恢复。

### 7.2 Control 事件

Control 直接通过现有一对一 WebSocket 发送：

~~~text
event = robot.trajectory.changed
~~~

只有三种 action：

| action | 用途 |
| --- | --- |
| RESET | 完整恢复第一页，替换该执行轮次的旧轨迹 |
| APPEND | 完整恢复后续页、实时点、补洞点或单独 currentPose |
| STOPPED | 设备确认轨迹停止，前端冻结 |

RESET 示例：

~~~json
{
  "event": "robot.trajectory.changed",
  "data": {
    "robotId": "robot-001",
    "workflowInstanceId": 9001,
    "action": "RESET",
    "points": [
      {
        "timestamp": 1723356126.584,
        "x": 6.07,
        "y": 2.15,
        "yaw": 0.0
      }
    ]
  }
}
~~~

APPEND 示例：

~~~json
{
  "event": "robot.trajectory.changed",
  "data": {
    "robotId": "robot-001",
    "workflowInstanceId": 9001,
    "action": "APPEND",
    "points": [],
    "currentPose": {
      "timestamp": 1723356127.584,
      "x": 6.08,
      "y": 2.16,
      "yaw": 0.01
    }
  }
}
~~~

STOPPED 示例：

~~~json
{
  "event": "robot.trajectory.changed",
  "data": {
    "robotId": "robot-001",
    "workflowInstanceId": 9001,
    "action": "STOPPED"
  }
}
~~~

事件不包含 taskId、taskInstanceId、mapId、generation、sequence、snapshotId、pageIndex、
summary、finishedAt 或 retainUntil。BFF 使用现有出站 robotId 权限过滤，不做事件转换。

## 8. 设备任务 ID 绑定

EdgeDeviceStatusHandler 读取 payload.status.task.taskInstanceId 并通知轨迹协调器：

~~~text
observeTaskInstance(robotId, taskInstanceId)
~~~

status.task 在增量状态中缺失时保留上次 ID；收到合法新 ID 时按 MQTT 接收顺序更新，并立即
使旧候选和旧在途请求失效。

绑定规则：

1. 有观看目标后，使用当前 taskInstanceId 发送一次 summary。
2. 只有返回 recording 才绑定为本轮设备轨迹 ID 并开始 full 恢复。
3. 尚未绑定时返回 stopped，认为仍是上一轮 ID；拒绝该候选并等待 ID 变化，不重复查询。
4. 尚未绑定时返回 not_found，可能是新轨迹尚未初始化，对同一候选每 3 秒重试。
5. error、发布失败或超时同样每 3 秒重试。
6. 任务结束或无人观看时停止候选探测。

已知边界：新任务极短且首次查询已经直接返回 stopped 时，本期不展示该轮轨迹。覆盖该情况
需要可靠的 workflowInstanceId 到 taskInstanceId 映射，不属于最小实现。

## 9. Control 最小状态机

~~~text
IDLE
  -> WAITING_TASK_ID    有人观看，等待或探测设备任务 ID
  -> RESTORING          已绑定，full 分页恢复
  -> STREAMING          每秒 summary
  -> GAP_FILLING        点数跳增，增量 full 补洞
  -> STREAMING

任意活动状态
  -> IDLE               无人观看、任务收口或目标换轮

RESTORING / STREAMING / GAP_FILLING
  -> STOPPED            设备返回 stopped，发送事件且不再查询
  -> IDLE               观看目标移除或换轮
~~~

每个机器人只保存一个轻量运行态，不创建每机器人线程。共享调度器负责安排后续查询。

首版固定常量：

| 项目 | 数值 |
| --- | --- |
| summary 间隔 | 1 秒 |
| 失败重试 | 3 秒 |
| 单次请求超时 | 3 秒 |
| full 每页 maxPoints | 500 |
| 前端结束保留 | 5 分钟 |
| 前端轨迹点上限 | 15000 |

## 10. MQTT 查询

### 10.1 Topic 和请求关联

~~~text
查询: eiop/v1/platform/{serialNumber}/trajectory/query
响应: eiop/v1/edge/{serialNumber}/trajectory/snapshot
QoS: 1
~~~

复用 Control 现有 MQTT 发布客户端和状态订阅客户端，不新增 MQTT 连接。

每次查询生成唯一 commandId。同一机器人最多一个在途请求。响应必须同时满足：

- commandId 仍在等待；
- Topic serialNumber、taskInstanceId 和 format 与请求一致；
- 当前观看目标和候选/绑定 ID 仍然有效。

第一条有效响应消费 commandId。QoS 1 重复响应、3 秒超时后的迟到响应、设备 ID 或执行轮次
变化后的旧响应全部忽略。目标结束或最后观看者离开时立即使在途请求失效。

日志只记录 robotId、workflowInstanceId、taskInstanceId、format、点数、耗时和错误，不打印
完整 points。首版不增加专用日志限频器。

### 10.2 完整恢复

候选 summary 返回 recording 后：

1. 发送 format=full、maxPoints=500，第一页不传 sinceTimestamp。
2. 第一页向当前全部观看会话发送 RESET，收到后立即显示。
3. hasMore=true 时继续查询，后续页统一发送 APPEND。
4. 下一页 sinceTimestamp 使用当前页最后点的原始绝对时间：

~~~text
absoluteTimestamp = summary.startTime + point.t
~~~

sinceTimestamp 保留小数秒。若设备实现包含边界点，由前端毫秒去重消除重复。

hasMore=false 后立即查询一次 summary，补上恢复期间新增的点，再进入每秒查询。

任务运行中有新会话加入或重连时复用同一个轮询器，不新增按浏览器独立查询器：

1. 记录恢复前 lastTrajectoryTimestamp，从第一页重新执行一次 full 分页。
2. 缺少基线的会话接收第一页 RESET 和后续 APPEND，恢复从起点到当前点的轨迹。
3. 已有基线的会话只接收时间戳大于恢复前游标的点，不接收重复历史点，也不执行 RESET。
4. 多个会话在第一页返回前加入时合并到本轮恢复；分页已经开始后再加入则从第一页重新恢复，
   保证每个新会话都先收到 RESET。

新会话恢复只增加加入或重连时的一轮 full 查询；日常仍是同一目标一个 summary 轮询器，
浏览器数量不会放大每秒查询次数。首版不在 Control 缓存最长 4 小时的完整轨迹。

以下任一情况停止本轮分页，3 秒后从第一页重新恢复；新的 RESET 到达前保留前端已有轨迹：

- hasMore=true 但 points 为空；
- 最后绝对时间没有前进；
- 连续返回同一页；
- 请求超时、error 或数据结构无效。

### 10.3 summary 和补洞

Control 保存 startTime、lastTotalPoints、lastTrajectoryTimestamp 和 lastPublishedPose。

| summary 变化 | 动作 |
| --- | --- |
| 点数和 currentPose 都不变 | 不发送事件 |
| 点数不变，currentPose 变化 | APPEND points=[]，只更新图标 |
| totalPoints 增加 1 | 用 lastUpdateTime + currentPose 生成一个 APPEND 点 |
| totalPoints 增加超过 1 | 暂停 summary，用增量 full 补洞 |
| totalPoints 减少或 startTime 改变 | 从第一页 full 恢复并发送 RESET |
| 点数增加但 lastUpdateTime 未前进 | 从第一页 full 恢复 |
| currentPose 缺失或非法 | 不合成点，执行增量或完整恢复 |

补洞使用 lastTrajectoryTimestamp 作为 sinceTimestamp，分页结果发送 APPEND。补洞完成后立即
再查一次 summary；补洞期间不使用 currentPose 跨缺口画直线。

时间和去重：

- startPose 时间取 startTime；
- currentPose 时间取 lastUpdateTime；
- full 点时间取 startTime + t；
- 原始小数秒用于分页；
- 四舍五入后的 Unix 毫秒作为前端点唯一键；
- 同一毫秒重复点保留第一个。

### 10.4 结束

- 已绑定轨迹返回 stopped 时，先处理当前有效响应中的点，再发送 STOPPED，不再查询。
- 任务状态先恢复 waiting 或进入 completed/terminated 时，前端立即冻结并移除观看目标。
- Control 不执行结束补洞或最终 full。
- 目标移除前已经完成的响应正常处理；移除后到达的响应忽略。
- 接受最多约一个查询周期的末段缺失。

## 11. 前端处理

### 11.1 轨迹事件

- 按 robotId + workflowInstanceId 保存。
- RESET 替换当前轮次轨迹；后续 APPEND 追加。
- 新 workflowInstanceId 先删除同一机器人旧轨迹和计时器。
- APPEND、STOPPED 的 workflowInstanceId 不匹配时忽略。
- 所有点按绝对毫秒去重。

因为 Control 保证单在途查询、WebSocket 保证连接内有序、RESET 总是完整恢复第一页，所以
首版不再增加 snapshotId、pageIndex 和 sequence。

### 11.2 普通定位和轨迹位姿

- 已绑定活动轨迹时，机器人图标使用 currentPose。
- 约 10 秒普通定位继续更新其他设备状态和最后普通坐标。
- 普通定位不能覆盖活动轨迹位姿，也不能追加到任务轨迹。
- 轨迹结束时先保持最后轨迹位姿，下一条普通定位到达后自然接管图标。
- 5 分钟到期仍无新普通定位时，回退到最后普通坐标。

### 11.3 当前页面保留

任务状态 waiting/completed/terminated 或 STOPPED 谁先到达，谁冻结轨迹并启动一次 5 分钟
计时；重复通知不得延长计时。使用 setTimeout，并在状态变化时通过 Date.now 再次检查。

提前清理条件：

- 同一机器人出现新的 workflowInstanceId；
- 机器人不再属于当前数据库地图；
- 切换地图、GIS 或 3D；
- 离开或刷新页面。

同地图其他机器人开始任务不清理本机器人轨迹。WebSocket 临时重连不清除当前页轨迹，但已
结束任务不会由服务端恢复。

### 11.4 渲染

- 复用 session-traveled-path.js 的坐标转换、双层折线和方向箭头。
- 普通定位不再向已执行轨迹追加点。
- 现有 4000 点上限提高为 15000。
- 首版继续使用现有单 SVG 折线，不改为 500 点分段。
- 达到 15000 点后停止接受额外折线点并记录一次警告，不删除起点；currentPose 仍更新图标。
- 使用真实约 14400 点数据验证性能；只有确认卡顿后再单独实施分段优化。

## 12. 异常降级

| 场景 | 行为 |
| --- | --- |
| 初始 not_found/error/timeout | 使用普通定位、不显示轨迹、3 秒重试 |
| 已有轨迹后临时错误 | 保留折线和最后轨迹位姿，3 秒重试 |
| 完整恢复中断 | 保留已显示数据，重试后用 RESET 替换 |
| 增量补洞失败 | 保留已有轨迹，优先重试补洞 |
| 机器人离线 | 保留轨迹，查询失败按 3 秒重试 |
| 任务结束时仍有错误 | 停止重试，有多少轨迹保留多少 |
| 从未取得有效点 | 任务结束后不创建空轨迹 |
| QoS 1 重复或迟到响应 | 忽略 |
| 分页游标不前进 | 停止本轮，3 秒后重新恢复 |
| 同机器人多活动任务 | 跳过并记录 TRAJECTORY_TASK_CONFLICT |
| 多会话执行轮次冲突 | 暂停并记录 TRAJECTORY_WATCH_CONFLICT |

轨迹异常不阻断地图、任务状态、普通定位、视频和控制功能，不反复弹出用户提示。

## 13. 代码改造范围

### 13.1 control-service

- EdgeDeviceStatusHandler 提取 taskInstanceId 并通知轨迹协调器。
- 现有 MQTT 发布器增加 trajectory/query 方法。
- 现有 MQTT 订阅器增加 trajectory/snapshot Topic。
- 新增一个轨迹协调器，集中处理观看集合、设备 ID 绑定、调度、分页、补洞和请求关联。
- MediaWebSocketHandler 增加 trajectory.watch.sync 分支，并在连接关闭时释放目标。
- 使用 MediaWebSocketPublisher 现有定向 send 方法发送 robot.trajectory.changed，不使用全局广播。

### 13.2 bigscreen-bff

轨迹功能不增加专用代码，复用：

- 现有浏览器与 Control 一对一 WebSocket；
- canForwardClientMessage 的 robotId 上行权限检查；
- canReceive 的 robotId 出站权限过滤；
- 未识别事件透明转发。

仅修改普通定位事件转换：不再输出设备 SLAM mapId。

### 13.3 robot-ui

- WebSocket 模块保存最近观看集合，提供发送方法并在重连后重发。
- websocket-extra-data 处理 RESET、APPEND、STOPPED 并保存本页轨迹。
- session-traveled-path.js 改为消费真实轨迹，不再从普通定位累计。
- GlobalSlamMap 复用现有单折线，容量提高到 15000。
- 增加任务和地图变化时的观看同步、页面销毁清理及 5 分钟保留。

### 13.4 无需修改

- EIOP Management；
- EIOP 任务接口和 STOMP；
- Media Service；
- 设备轨迹协议；
- 数据库和 Redis。

## 14. 最小测试清单

### 14.1 Control

1. 正确观察 taskInstanceId，增量状态缺少 task 时不清空。
2. 第一个观看者启动、重复同步幂等、最后观看者或断连停止。
3. 旧 taskInstanceId 返回 stopped 不绑定，新 ID 返回 recording 后绑定。
4. not_found、error、发布失败和超时按 3 秒重试。
5. full 首页面 RESET，后续页 APPEND，游标不前进时停止重试。
6. summary 点 0、1、多点变化分别不发、追加或补洞。
7. QoS 1 重复、超时迟到和换轮响应不污染当前轨迹。
8. stopped 处理当前响应后发送 STOPPED，不执行结束补齐。
9. 多会话相同目标只产生一个设备轮询器，事件只发送给观看会话。
10. 多会话先进入再启动任务时均收到首次 RESET；运行中新增会话只有新增会话收到 RESET，
    已有会话只补恢复期间新增点。
11. 同一会话重复同步相同目标不触发额外 full；多个新会话在恢复第一页前加入时合并恢复。

### 14.2 前端和 BFF

1. 任务开始、切图、重连和离开时发送正确完整集合。
2. RESET、APPEND、STOPPED 和毫秒去重正确。
3. 普通定位不覆盖活动轨迹；结束后下一条普通定位接管。
4. 当前页保留 5 分钟，同机器人新任务和页面销毁立即清理。
5. 执行中刷新恢复，任务结束后刷新不恢复。
6. 约 14400 点在现有单折线上可接受；若不满足再立项分段优化。
7. BFF 继续阻止无权限 robotId 上下行，普通定位不再输出设备 SLAM mapId。

### 14.3 联调验收

1. 页面已打开时，任务从 waiting 变为 running 后无需刷新即出现轨迹。
2. 管理端先 running、设备仍上报上一轮 ID 时不显示旧轨迹。
3. 新 taskInstanceId recording 后从起点恢复并约每秒更新。
4. 执行中刷新或 WebSocket 重连后完整恢复且不重复。
5. summary 跳增时增量 full 补齐中间线路。
6. paused、resuming、terminating 和 CONTROL_FAILED 期间不错误结束轨迹。
7. waiting 或 stopped 后停止 MQTT 查询，当前页保留 5 分钟。
8. 结束后刷新不显示旧轨迹；同机器人新任务清旧轨迹。
9. 无观看者时不查询，多观看者共享轮询；运行中新增观看者可完整恢复且不清空已有观看者轨迹。
10. 多个浏览器已在地图页时启动任务，各浏览器都能从首次 RESET 开始持续渲染。
11. 4 小时约 14400 点数据可以恢复和持续渲染。

## 15. 开发结论

当前方案可以直接开发，不依赖 EIOP 改造。生产代码集中为：

~~~text
一个 Control 轨迹协调器
现有 MQTT 发布/订阅各增加一个入口
现有 WebSocket 增加一个观看命令和一个轨迹事件
前端复用现有轨迹图层
~~~

联调环境只需确认 MQTT 账号具备轨迹查询 Topic 的发布、订阅权限，并用真实长轨迹验证
sinceTimestamp 分页和单折线性能。
