# 具身智能装备统一控制一期设计说明书

## 1. 一期目标

一期目标是完成远程控制最小闭环，支撑以下设备组合：

- R1轮式机器人：本体、双光云台、捕网器、警示灯、车灯光、语音对讲。
- G1四足机器狗：本体、双光云台、捕网器、语音对讲。
- G2四足机器狗：本体、双光云台、探照灯。

一期只做平台统一控制骨架、控制权仲裁和手动/导航模式切换，不做复杂机械臂轨迹规划、激光雷达点云流、完整任务调度系统和多厂商插件市场。

## 2. 一期范围

### 2.1 必须实现

| 能力 | 一期要求 |
|---|---|
| 设备注册绑定 | 机器人和上装设备提前注册，前端按绑定设备展示 |
| Effective Profile | 后端返回机器人当前有效控制能力 |
| 控制权 | 支持整机控制权和设备控制权 |
| 控制模式 | 只保留 `MANUAL`、`NAVIGATION`；后端同时返回中文名称供前端渲染 |
| 导航人工接管 | `NAVIGATION` 下通过 takeover 原子申请本体控制权并下发 `MANUAL`，机器人确认后才允许发送移动指令 |
| 本体遥控 | 前端按 10Hz 发送运动控制帧；点触发少量帧，长按持续发帧 |
| 双光云台 | 前端按 10Hz 发送云台控制帧；点触发少量帧，长按持续发帧 |
| 发射器 | 支持真实安全开关、二次确认、6 发通道发射、审计 |
| 捕网枪 | 前端本地安全开关解锁、二次确认、1 发发射、审计 |
| 多合一喊话设备 | 支持实时喊话、实时收音、警报、文字转语音、音频文件播放、音量、喊话器俯仰、照明灯和照明灯俯仰控制；媒体流和文件传输不进入普通控制 MQTT payload |
| 急停 | 独立 topic，最高优先级 |
| WebSocket 高频控制 | 本体和云台连续控制走 WebSocket |
| MQTT 控制链路 | 后端按设备类型组装参数并通过 MQTT 下发给 Go 客户端 |
| 客户端状态上报 | Go 客户端通过 `robot/{robotId}/media/client/status` 统一上报在线状态、控制模式、任务状态、摄像头清单和设备状态 |

### 2.2 暂不实现

| 能力 | 放到二期原因 |
|---|---|
| 机械臂复杂控制 | 需要软限位、碰撞、轨迹和姿态策略 |
| 激光雷达点云流和模式控制 | 一期暂不接入雷达控制代码，后续如需接入放到二期 |
| 完整任务调度系统 | 一期只做控制权仲裁，不实现任务编排、路线规划和恢复策略 |
| 多厂商 driver 插件化 | 一期可先内置 driver |
| 协议灰度和版本协商 | 一期固定 `embodied-control 1.0` |

## 3. 一期抽象模型

### 3.1 Robot 与 Device 不合并

一期前端展示可以把设备嵌套在机器人下面，但后端领域模型和控制协议不合并。

```text
Robot = 主装备、载体、调度对象、MQTT 路由根节点
Device = Robot 上的可控/可感知能力单元、动作执行目标
```

控制寻址固定为：

```text
robotId + target.deviceId + action
```

示例：

```json
{
  "robotId": "robot-songling-001",
  "target": {
    "scope": "PAYLOAD",
    "deviceId": "ptz-dual-001",
    "deviceType": "DUAL_LIGHT_PTZ"
  },
  "action": "left"
}
```

### 3.2 一期数据来源

一期不在控制服务中新增机器人、设备或能力数据库表，也不返回固定测试设备。控制服务组合管理端登记信息与机器人客户端实时状态：

| 数据 | 一期实现 |
|---|---|
| 机器人及绑定设备 | 从管理端设备接口查询 |
| 平台设备 ID、类型、名称 | 以管理端组件登记信息为准 |
| 动作能力 | 优先使用管理端登记动作；未登记时，仅对已经完成端到端联调的设备类型使用生产兼容动作 |
| 控制 profile | 管理端登记值覆盖生产兼容参数范围 |
| 设备运行状态 | 从 `robot/{robotId}/media/client/status` 的 `devices[].status` 获取，不生成在线、灯光、音量或弹筒等模拟状态 |
| 控制权 session | 控制服务进程内管理 |
| 命令状态 | 控制服务进程内记录并通过 WebSocket 返回发布结果 |

管理端设备查询使用短时缓存，接口暂时不可用时可继续使用最近一次成功结果。客户端状态仍持续上报；每条状态消息经管理端数据合并后只广播一次 `robot.state`。

### 4.5 导航模式人工接管

```text
POST /api/control/robots/{robotId}/control-sessions/takeover
```

该接口表示“中断导航并转入人工本体控制”，不表示强制抢夺其他终端的控制权。若其他终端已持有 `base` 控制会话，返回 `CONTROL_LOCKED`。

请求：

```json
{
  "observedStateSeq": 1288
}
```

处理流程：

1. 校验机器人在线、当前真实模式和 `observedStateSeq`。
2. 为当前终端申请包含 `base` 的整机控制会话；存在其他终端锁时拒绝。
3. 当前为 `NAVIGATION` 时发布 `control.mode.set=MANUAL`。
4. 不提前修改后端状态，不广播模拟的 `robot.state`。
5. 返回控制会话和 `modeChangeStatus=PUBLISHED`，前端继续等待机器人确认。

响应示例：

```json
{
  "controlSessionId": "tc_20260603_0001",
  "robotId": "robot-songling-001",
  "scope": "ROBOT",
  "deviceIds": ["base"],
  "actions": ["control.mode.set", "drive.velocity"],
  "status": "ACTIVE",
  "modeChangeStatus": "PUBLISHED",
  "controlMode": "NAVIGATION",
  "controlModeName": "导航模式",
  "requestedControlMode": "MANUAL",
  "requestedControlModeName": "手动模式",
  "stateSeq": 1288,
  "issuedAt": "2026-06-03T10:30:30+08:00"
}
```

### 4.6 控制模式切换

```text
POST /api/control/robots/{robotId}/control-mode
```

使用场景：

- 前端在“装备控制”标题右侧展示控制模式下拉框。
- 下拉框当前值来自机器人端通过 `robot/{robotId}/media/client/status` 实时上报的 `controlMode`。
- 用户只可选择 `MANUAL` 或 `NAVIGATION`。
- 前端调用接口前必须先通过 acquire 获得包含 `base` 的控制会话。
- 接口返回 `PUBLISHED` 只表示 MQTT 已发布，不表示机器人已完成切换。
- 机器人端再次上报 `controlMode` 后，前端按 `controlModeName` 渲染中文模式名称。

前端请求：

```json
{
  "controlMode": "NAVIGATION",
  "controlSessionId": "tc_20260603_0001",
  "observedStateSeq": 1288
}
```

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `controlMode` | string | 是 | 目标模式：`MANUAL` / `NAVIGATION` |
| `controlSessionId` | string | 是 | 当前终端持有且包含 `base` 的有效控制会话 |
| `observedStateSeq` | number | 是 | 前端最近一次收到的机器人状态序号，必须等于后端最新值 |

后端 MQTT 下发：

```json
{
  "robotId": "robot-songling-001",
  "seq": 1289,
  "target": {
    "deviceId": "base",
    "deviceType": "WHEELED_BASE"
  },
  "action": "control.mode.set",
  "params": {
    "controlMode": "NAVIGATION"
  },
  "issuedAt": "2026-06-03T10:30:30+08:00"
}
```

成功响应：

```json
{
  "status": "PUBLISHED",
  "robotId": "robot-songling-001",
  "requestedControlMode": "NAVIGATION",
  "requestedControlModeName": "导航模式",
  "controlMode": "MANUAL",
  "controlModeName": "手动模式",
  "stateSeq": 1288,
  "issuedAt": "2026-06-03T10:30:30+08:00"
}
```

后端不会在发布 MQTT 后提前修改本地 `controlMode` 或广播模拟的 `robot.state`。前端保持当前模式，直到机器人客户端真实上报新状态。若前端状态序号已过期，返回 `ROBOT_STATE_CHANGED`；若会话不属于当前终端、已失效或不包含 `base`，请求失败。

## 5. 一期 WebSocket 协议

连接地址：

```text
/ws/control
```

用途：

- 本体摇杆。
- 本体方向键长按。
- 双光云台方向键长按。
- 变焦长按。
- 客户端状态变化推送。

前端发送：

```json
{
  "type": "control.command",
  "requestId": "req_20260603_0001",
  "payload": {
    "robotId": "robot-songling-001",
    "controlSessionId": "tc_20260603_0001",
    "target": {
      "scope": "BODY",
      "deviceId": "base",
      "deviceType": "WHEELED_BASE"
    },
    "action": "drive.velocity",
    "params": {
      "linearX": 0.3,
      "linearY": 0,
      "angularZ": -0.2
    },
    "client": {
      "terminalId": "web-client-001",
      "source": "body_joystick",
      "seq": 1024,
      "timestamp": "2026-06-03T10:30:00+08:00"
    }
  }
}
```

```json
{
  "type": "control.command.accepted",
```

说明：以上 ID 和状态值仅为结构示例，不是控制服务内置数据。前端通过 `/ws/control` 发送控制命令时，后端即时响应仍使用 `{type, requestId, payload}`；后端面向所有连接广播的业务事件使用统一 `{event, timestamp, data}`。`control.command.published` 广播的 `data` 包含 `commandId`、`status`、`robotId`、`target`、`action`、`issuedAt`。

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `robotId` | string | 是 | 机器人 ID |
| `clientId` | string | 否 | 机器人侧客户端 ID |
| `name` | string | 否 | 机器人展示名称 |
| `type` | string | 否 | 机器人类型 |
| `battery` | number | 否 | 电量百分比 |
| `status` | string | 否 | 客户端原始在线状态 |
| `controlMode` | string | 是 | `MANUAL` / `NAVIGATION` |
| `controlModeName` | string | 是 | 中文名称：`手动模式` / `导航模式` |
| `stateSeq` | number | 是 | 客户端状态递增序号，用于模式切换防止使用旧状态 |
| `currentTaskId` | string | 否 | 当前任务 ID |
| `missionStatus` | string | 否 | `RUNNING` / `PAUSED` / `IDLE` |
| `navigationStatus` | string | 否 | 导航状态 |
| `controlOwner` | object | 否 | 当前控制者；为空表示无人持有 |
| `estopActive` | boolean | 是 | 急停是否生效 |
| `cameras` | array | 否 | 摄像头列表，包含 `cameraId`、`deviceId`、`groupType`、`name`、`quality` |
| `devices` | array | 否 | 本体和上装设备能力列表，结构同控制能力 `devices`；`devices[].status` 用于刷新音量、静音和开关类按钮 |
| `timestamp` | datetime | 是 | 机器人端状态产生时间；缺省时后端补当前时间 |

前端使用规则：

- `controlMode=NAVIGATION` 且要控制本体时，调用 `4.5 导航模式人工接管`。
- `controlMode=MANUAL` 且无人持有控制权时，可直接申请普通控制权。
- `controlMode=NAVIGATION` 时，云台控制默认可申请设备级控制权，不打断导航。
- 本体移动只有在机器人真实上报 `controlMode=MANUAL` 后才允许发送。

## 6. 一期 MQTT Topic

| Topic | 方向 | 一期用途 |
|---|---|---|
| `robot/{robotId}/control/body/command` | 后端 -> Go | 机器人本体控制，前后、转向、左移右移 |
| `robot/{robotId}/control/ptz/command` | 后端 -> Go | 双光云台控制，8 方向、自动旋转、变焦等 |
| `robot/{robotId}/control/audio/command` | 后端 -> Go | 扬声器音量控制，滑块调节、音量加减、静音 |
| `robot/{robotId}/control/multi-function/command` | 后端 -> Go | 多合一喊话设备的音量、TTS、文件播放、警报、照明和喊话会话控制 |
| `robot/{robotId}/control/launcher/command` | 后端 -> Go | 发射器控制，6 发类设备 |
| `robot/{robotId}/control/net-gun/command` | 后端 -> Go | 捕网枪控制，1 发类设备 |
| `robot/{robotId}/control/warning-light/command` | 后端 -> Go | 红蓝警示灯整体开关和模式控制 |
| `robot/{robotId}/control/vehicle-light/command` | 后端 -> Go | 前后车灯整体开关控制 |
| `robot/{robotId}/control/safety/estop` | 后端 -> Go | 急停 |
| `robot/{robotId}/media/client/status` | Go -> 后端 | 统一客户端状态上报，包含在线状态、控制模式、任务状态、摄像头清单和设备状态 |

说明：

- 机器人客户端订阅 `robot/{robotId}/control/#`，按 topic 和 payload 中的 `target.deviceId/action` 解析和分发。
- 控制 topic 只保留设备大类，不再携带 `{deviceId}`；具体设备由 payload 中的 `target.deviceId` 标识。
- 前端实时状态由后端消费 `media/client/status` 后通过 WebSocket 推送 `robot.state`。
- 每收到一条 `media/client/status`，控制服务先合并管理端设备标识和能力，再更新机器人注册状态并广播一次 `robot.state`；“一次”指每条上报只产生一条合并事件，不是机器人生命周期只发布一次。
- `controlMode`、`stateSeq`、`cameras` 随 `media/client/status` 上报。
- 后端发布控制命令成功后即可向前端返回 `PUBLISHED`；一期不等待客户端接收确认。

后端 topic 构造规则：

| `deviceType` / action | 下发 topic |
|---|---|
| `WHEELED_BASE`、`QUADRUPED_BASE`、`BIPED_BASE` | `robot/{robotId}/control/body/command` |
| `DUAL_LIGHT_PTZ` | `robot/{robotId}/control/ptz/command` |
| `SPEAKER`、`CLIENT_AUDIO`、`INTERCOM`、`VOLUME_CONTROL` | `robot/{robotId}/control/audio/command` |
| `MULTI_FUNCTION_BROADCASTER` | `robot/{robotId}/control/multi-function/command` |
| `LAUNCHER` | `robot/{robotId}/control/launcher/command` |
| `NET_GUN`、`NET_LAUNCHER` | `robot/{robotId}/control/net-gun/command` |
| `WARNING_LIGHT` | `robot/{robotId}/control/warning-light/command` |
| `VEHICLE_LIGHT`、`SEARCHLIGHT` 或 `light.vehicle.*` | `robot/{robotId}/control/vehicle-light/command` |

`devices[].status` 用于刷新前端有状态控件。一期统一规则：机器人端若提供某个设备的真实状态接口或状态上报，客户端应把结果写入 `devices[].status`，前端必须优先按 `status` 渲染；没有真实状态时只能使用本地临时态或展示“同步中”。控制服务不会生成扬声器音量、发射器连接与弹筒、云台旋转、警示灯或车灯状态。多合一喊话设备的真实定时上报字段为 `volumePercent`、`volumeLimitPercent`、`temperatureC`；`audioPlayback` 仅表示客户端成功写入的最近播放命令，并在停止或完成事件后清空，不视为设备查询状态；TTS、警报和照明状态只有在机器人端提供查询/上报接口后才标记为设备真实状态。

设备合并规则：

1. 对外 `devices[].deviceId` 以管理端组件 `code/deviceId/id` 为准。
2. 客户端驱动侧 ID 不一致时，可放在 `devices[].status.driverDeviceId`，用于后端关联运行状态。
3. 后端依次按平台 `deviceId`、`status.driverDeviceId`、唯一 `deviceType` 匹配运行状态。
4. 合并时保留客户端 `status`，以管理端的设备 ID、类型、名称、动作和控制 profile 覆盖平台能力字段。
5. 管理端暂时不可用时使用最近一次成功缓存；没有管理端数据时不伪造设备运行状态。

各设备状态渲染原则：

| 设备 | 状态字段 | 前端渲染规则 |
|---|---|---|
| 双光云台 | `autoRotateEnabled`、`panSpeed`、可扩展 `zoomLevel` | 方向点触/长按不依赖状态；自动旋转按钮必须按 `autoRotateEnabled` 显示开启/停止 |
| 车灯 | 无状态查询能力 | 页面使用一个总开关控制前后灯，并保存最近一次成功操作的本地状态 |
| 警示灯 | `powerOn` / `enabled`、`mode`、`online` | 如果上报则 switch 按真实开关状态渲染；未上报时不显示同步提示，使用本地最近一次操作状态 |
| 扬声器 | `volumePercent` / `volume`、`muted` | 滑块、静音按钮按状态渲染；按钮加减只计算新的绝对音量 |
| 多合一喊话设备 | `connected`、`volumePercent`、`volumeLimitPercent`、`temperatureC`、`audioFiles` | 音量和温度按设备上报渲染；文件列表按最近一次查询结果渲染；播放、TTS、警报和照明没有真实状态时显示“状态未同步”，不得把前端按钮值伪装成设备真实状态 |
| 捕网枪 | `connected`、可扩展 `ready` / `cooldownRemainingMs` | 若有状态则显示连接/可用状态；若无状态，一期仍使用前端本地安全开关和二次确认 |
| 发射器 | `connected`、`safetySwitchEnabled`、`tubeCount`、`tubes[]` | 必须按真实安全开关和弹筒状态渲染，只有 `LOADED` 且安全开关打开才可发射 |

## 7. 一期 MQTT 命令格式

一期 MQTT 下发给 Go 客户端的是“执行指令”，不是完整业务上下文。控制权、操作者、确认令牌、控制模式、风险策略等字段由后端在下发前完成校验，并记录在后端日志或审计数据中，不作为客户端执行的必需字段。

一期建议使用精简执行 payload。MQTT topic 已经表达了机器人和设备域，payload 中只保留客户端执行需要的字段。

```json
{
  "robotId": "robot-songling-001",
  "seq": 1024,
  "target": {
    "deviceId": "base",
    "deviceType": "WHEELED_BASE"
  },
  "action": "drive.velocity",
  "params": {
    "linearX": 0.3,
    "linearY": 0,
    "angularZ": -0.2
  },
  "issuedAt": "2026-06-03T10:30:00+08:00"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `robotId` | string | 是 | 控制哪台机器人，也与 MQTT topic 中的 `{robotId}` 一致 |
| `seq` | number | 建议 | 前端递增序号，客户端可用于日志和观察丢帧/乱序 |
| `target.deviceId` | string | 是 | 控制哪个设备，例如 `base`、`ptz-dual-001`、`net-gun-001` |
| `target.deviceType` | string | 是 | 设备类型，客户端按类型分发处理 |
| `action` | string | 是 | 平台动作名，例如 `drive.velocity`、`left`、`fire` |
| `params` | object | 是 | 后端校验、限幅后的动作参数 |
| `issuedAt` | datetime | 是 | 后端下发时间 |

以下字段不进入一期 MQTT 执行指令：

| 字段 | 不下发原因 |
|---|---|
| `protocol` | topic 已按控制域隔离，一期客户端只消费控制 topic，可不再用 payload 字段识别协议 |
| `version` | 一期协议固定，暂不做版本协商；后续多版本兼容时再恢复或放到 topic/header |
| `messageType` | 当前 topic 只承载命令，不混传事件或 ack |
| `commandId` | 无客户端 ack 和去重要求时可不下发；后端可在日志、接口响应中内部保留 |
| `operator` | 操作者信息用于后端鉴权、审计，不参与客户端执行 |
| `controlSessionId` | 控制权由后端校验，客户端不再二次判断 |
| `controlMode` | 控制模式由后端结合客户端状态判断，客户端只执行已放行的指令 |
| `traceId` | 链路追踪保留在后端日志即可，一期客户端不依赖 |
| `target.vendor` / `target.model` | 设备归属由客户端配置或后端 profile 管理，执行指令只要求设备 ID 和类型 |
| `policy` | 风险等级、二次确认、独占控制、过期策略由后端处理 |
| `params.frameRateHz` | 10Hz 是前端发送频率，不是动作参数；速度由 `params` 中的速度值决定 |

## 8. 一期 Action 参数

### 8.1 连续控制类

连续控制类不区分点触、长按或结束状态。前端统一按 10Hz 发送控制帧；点触就是发送少量帧，长按就是持续发送帧。后端不解释点触或长按语义，只校验、限幅并按设备类型组装 MQTT 参数。

#### `drive.velocity`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `linearX` | number | 是 | 前后速度，正数向前 |
| `linearY` | number | 否 | 横移速度；不支持横移的设备由后端裁剪为 0 |
| `angularZ` | number | 是 | 转向角速度 |

#### 双光云台方向动作：`up`、`down`、`left`、`right`、`left_up`、`right_up`、`left_down`、`right_down`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `speed` | number | 是 | 方向移动速度，后端按云台能力限幅；建议 `10~40` |
| `duration` | number | 是 | 单帧移动持续时间，单位秒；建议 `0.2~0.8` |

#### `camera.zoom`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `zoomSpeed` | number | 是 | 变焦速度，正数放大，负数缩小 |

#### `ptz.auto_rotate`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `enabled` | boolean | 是 | true 开启云台自动旋转，false 停止自动旋转 |
| `panSpeed` | number | 否 | 自动旋转水平速度，默认 0.3，由后端按云台能力限幅 |

### 8.2 离散动作类

#### 发射器 `fire`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `tube` | number | 是 | 发射器弹筒编号，范围 `1~6` |
| `waitStatusAfterFire` | boolean | 否 | 发射后是否等待/查询最新状态，默认 `true` |
| `keepSafetyOn` | boolean | 否 | 发射后是否保持 safety 状态，默认 `false` |
| `confirmToken` | string | 是 | 二次确认 token |

#### 发射器 `set_safety`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `safety_on` | boolean | 是 | true 打开安全开关，false 关闭 |
| `wait_status` | boolean | 否 | 设置后是否等待/查询最新状态，默认 `true` |

#### 发射器 `get_status`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `temporarilyEnableSafety` | boolean | 否 | 查询前是否临时打开安全开关，默认 `true` |
| `restoreSafetyAfterQuery` | boolean | 否 | 查询后是否恢复原安全开关状态，默认 `true` |

#### 捕网器 `fire`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `confirmToken` | string | 是 | 二次确认 token |

一期约束：发射器 `LAUNCHER` 的真实安全开关通过 `set_safety` 下发；捕网枪 `NET_GUN` 页面上的安全开关只作为前端本地解锁按钮，不调用后端接口，不下发 MQTT。捕网器可能没有状态查询接口，一期不要求捕网器状态查询。

#### 扬声器 `set_volume`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `volumePercent` | number | 是 | 绝对音量百分比，范围 0-100；前端滑块、加号、减号都换算成该绝对值下发 |

#### 扬声器 `set_mute`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `mute` | boolean | 是 | true 静音，false 取消静音 |

设备类型固定为 `MULTI_FUNCTION_BROADCASTER`。它是一个物理 `Device`，通过 `actions` 暴露多种能力，不拆成喊话器、TTS、播放器和照明灯四个虚拟设备。

| action | params | 必填 | 说明 |
|---|---|---:|---|
| `set_volume` | `volumePercent: number` | 是 | 设置绝对音量，范围 `0~100`；后端还应按 `controlProfile.maxVolumePercent` 限幅 |

## 9. 前端到 MQTT 参数构造

本章说明前端如何构造请求参数，后端如何根据设备类型解析并组装 MQTT 下发参数。客户端收到后如何抽象 ROS2 调用不在本文档范围内，由客户端同事负责。

示例使用 JSONC 写注释，实际 HTTP、WebSocket、MQTT 传输时必须去掉注释，使用标准 JSON。

### 9.1 通用构造规则

前端只传“当前控制帧”或“一次性动作意图”，不传厂商底层协议字段。

连续控制类：

```text
前端点触：按 10Hz 发送少量控制帧。
前端长按：按 10Hz 持续发送控制帧。
前端结束操作：不再发送控制帧。
后端：每收到一帧就校验、限幅、组装 MQTT 并下发。
客户端：消费后端参数并调用 ROS2 或设备 driver。
```

后端负责补齐：

| 后端补齐字段 | 来源 | 说明 |
|---|---|---|
| `seq` | 前端 `client.seq` | 终端递增序号 |
| `issuedAt` | 后端时间 | 后端下发时间 |

说明：`protocol`、`version`、`messageType`、`commandId` 不进入一期 MQTT 执行 payload；其中 `commandId` 如需排查问题，可由后端保留在接口响应和日志中。

后端内部处理但不下发 MQTT：

| 内部字段 | 用途 |
|---|---|
| `controlSessionId` | 校验控制权和当前终端 |
| `controlMode` | 校验当前模式下是否允许该动作 |
| `operator` | 鉴权、审计、日志 |
| `confirmToken` | 捕网器等高风险动作的二次确认校验 |
| `policy` | 后端内部风险策略、确认策略、冷却策略 |
| `traceId` | 后端链路日志追踪 |

前端必须传：

| 前端字段 | 说明 |
|---|---|
| `robotId` | 控制哪台机器人 |
| `controlSessionId` | 已申请到的控制权 ID；不需要控制权的动作可为空 |
| `target.scope` | 控制目标范围，如 `BODY`、`PAYLOAD`、`SENSOR` |
| `target.deviceId` | 控制哪一个设备 |
| `target.deviceType` | 设备类型，用于后端选择参数构造策略 |
| `controlMode` | 控制模式：`MANUAL` / `NAVIGATION`；本体手动控制固定为 `MANUAL` |
| `action` | 平台动作名 |
| `params` | 动作参数 |
| `client.terminalId` | 当前终端 ID |
| `client.source` | 控件来源 |
| `client.seq` | 当前终端递增序号 |
| `client.timestamp` | 前端发送时间 |

后端处理流程：

```text
1. 解析 HTTP/WebSocket 请求体
2. 解析 CurrentUser：userId、orgId、roles、clientId
3. 从管理端登记信息或其最近一次成功缓存中校验 robotId
4. 校验 target.deviceId 是否属于该机器人已登记组件
5. 根据 target.deviceType 选择参数构造策略
6. 校验 action 是否在 devices[].actions 中
7. 校验 controlMode 与后端缓存的最新客户端状态是否允许执行
8. 校验 controlSessionId 是否有效，或判断该 action 是否无需控制权
9. 按 action 校验 params
10. 按 controlProfile 裁剪速度、角速度、亮度等参数
11. 对高风险 action 校验 confirmToken、安全开关、冷却时间等后端策略
12. 生成 commandId、issuedAt
13. 组装简化 MQTT 执行 payload
14. 按设备类型发布到对应设备域 topic，急停发布到 safety/estop topic
15. 通过 WebSocket 给前端回 accepted/rejected
```

后端设备类型构造策略：

| `deviceType` | 典型 action | 后端构造重点 |
|---|---|---|
| `WHEELED_BASE` | `drive.velocity` | 不支持横移时 `linearY=0`，按轮式底盘限速 |
| `QUADRUPED_BASE` | `drive.velocity` | 允许横移时保留 `linearY`，按四足限速 |
| `DUAL_LIGHT_PTZ` | `up`、`down`、`left`、`right`、`left_up`、`right_up`、`left_down`、`right_down`、`ptz.auto_rotate`、`camera.zoom` | 裁剪方向移动速度和持续时间、自动旋转速度、变焦速度 |
| `LAUNCHER` | `get_status`、`set_safety`、`fire` | 安全开关真实下发，发射按 1 到 6 弹筒构造 |
| `NET_GUN` | `fire` | 前端本地安全开关解锁后才能点击；后端校验 confirmToken |
| `SEARCHLIGHT` | `light.set` | 裁剪亮度，校验模式 |
| `WARNING_LIGHT` | `get_state`、`set_state`、`set_mode` | 按 `lightId` 构造单灯或全部灯查询、开关和模式参数 |
| `VEHICLE_LIGHT` | `light.vehicle.set` | 前后灯作为一个整体设备，后端只下发平台通用 `mode/brightness` 语义 |
| `MULTI_FUNCTION_BROADCASTER` | `set_volume`、`start_broadcast`、`stop_broadcast`、`start_monitor`、`stop_monitor`、`set_monitor_suppressed`、`play_tts`、`stop_tts`、`list_audio_files`、`play_audio_file`、`stop_audio_file`、`delete_audio_file`、`play_alarm`、`stop_alarm`、`light.set`、`set_speaker_tilt`、`set_light_tilt` | 只保留平台语义参数；TCP/HTTP 前缀、十六进制音量、Opus 分帧和设备地址由机器人客户端适配 |

管理端不需要为车灯重复登记独立组件。当 `BODY` 组件的 `DEVICE_CONTROL`
能力包含 `SET_LIGHTS` 动作时，控制服务从该能力派生一个控制目标：
`deviceId=vehicle-light`、`deviceType=VEHICLE_LIGHT`、
`actions=[light.vehicle.set]`。机器人本体设备仍按原能力生成，二者共享同一份
管理端能力来源，但控制目标和 MQTT 设备域彼此独立。

后端组装伪代码：

```text
intent = parse(frontendPayload)
profile = managementProfile.find(robotId, intent.target.deviceId)
builder = commandBuilderFactory.get(intent.target.deviceType)
params = builder.validateAndBuildParams(intent.action, intent.params, profile.controlProfile)
checkControlSession(intent.controlSessionId, intent.target, intent.action)
checkControlMode(intent.controlMode, latestRobotState, intent.action)
checkInternalPolicy(intent.action, intent.params, currentUser)

mqttPayload = {
  robotId: intent.robotId,
  seq: intent.client.seq,
  target: {
    deviceId: intent.target.deviceId,
    deviceType: intent.target.deviceType
  },
  action: intent.action,
  params: params,
  issuedAt: now()
}
```

### 9.4 发射器与捕网枪：`get_status`、`set_safety`、`fire`

使用场景：

- 发射器打开/关闭真实安全开关，并通过接口下发给客户端。
- 发射器二次确认后按 1 到 6 弹筒发射。
- 捕网枪页面保留本地安全开关按钮，只用于解锁前端发射按钮，不调用后端接口。
- 捕网枪二次确认后触发发射；捕网器可能没有状态接口，一期不强制查询状态。

发射器和捕网枪动作建议走 REST `/commands`，不走高频 WebSocket。

发射器渲染规则：

- `controlProfile.tubes` 表示平台登记的弹筒能力范围，例如 `[1,2,3,4,5,6]`，只用于兜底生成按钮。
- `status.connected`、`status.safetySwitchEnabled`、`status.tubeCount`、`status.tubes[]` 表示客户端上报的真实运行态，前端渲染与禁用逻辑必须优先使用 `status`。
- 当前没有 `status.tubes[]` 时，前端可以按 `controlProfile.tubes` 展示按钮，但状态应显示“未知”，且不能判定为可发。
- 只有 `safetySwitchEnabled=true` 且目标弹筒 `state=1 / LOADED` 时，发射按钮才可点击。

客户端通过统一状态 topic `robot/{robotId}/media/client/status` 回写发射器状态，示例：

```jsonc
{
  "deviceId": "launcher_38mm",
  "deviceType": "LAUNCHER",
  "status": {
    "connected": true,                           // 发射器是否连接
    "safetySwitchEnabled": false,                // 真实安全开关状态
    "tubeCount": 6,                              // 弹筒数量
    "tubes": [
      {
        "tube": 1,                               // 弹筒编号
        "state": 1,                              // 0 空，1 已装填，2 发射中，3 堵塞，255 未知
        "stateName": "LOADED"                    // EMPTY / LOADED / FIRING / BLOCKED / UNKNOWN
      }
    ]
  },
  "controlProfile": {
    "tubes": [1, 2, 3, 4, 5, 6],                 // 能力配置，不等于实时弹筒状态
    "requiresConfirm": true,                     // 发射前需要二次确认
    "requiresSafetySwitch": true                 // 发射前需要打开真实安全开关
  }
}
```

```jsonc
  "issuedAt": "2026-06-03T10:30:30+08:00"        // 后端时间
}
```

### 9.5 红蓝警示灯：`get_state`、`set_state`、`set_mode`

管理端能力来源：

- 组件：`component.code=warning_light`。
- 能力：`capability.code=DEVICE_CONTROL`。
- 动作：`GET_LIGHT_STATE`、`SET_LIGHT_MODE`、`SET_LIGHT_STATE`。
- Control Service 不再把该组件拆成左、右两个虚拟设备，而是生成一个
  `deviceId=warning_light`、`deviceType=WARNING_LIGHT` 的控制设备。
- 大屏使用一个总开关控制全部红蓝警示灯，并提供一个“切换模式”按钮。
- 大屏加载该设备能力或切换机器人后，自动下发一次 `get_state`，查询动作不申请设备控制权。
- 大屏下发时固定使用 `lightId=all`；客户端负责映射机器人端 ROS2 Service。

设备能力示例：

```jsonc
{
  "deviceId": "warning_light",                   // 与管理端 component.code 一致
  "deviceType": "WARNING_LIGHT",                 // 红蓝警示灯
  "displayName": "警示灯",
  "actions": ["get_state", "set_state", "set_mode"],
  "status": {
    "powerOn": false,                            // 全部灯是否开启
    "mode": 0,                                   // 全部灯模式一致时返回
    "online": true
  },
  "controlProfile": {
    "lightId": "all",                            // 大屏整体控制固定值
    "lightIds": ["light-001", "light-002", "all"],
    "modes": [0, 1, 2],
    "supportsAll": true
  }
}
```

整体开关前端 REST 请求：

```jsonc
{
  "controlSessionId": "tc_20260603_0004",        // 警示灯设备控制权
  "target": {
    "scope": "PAYLOAD",                          // 上装
    "deviceId": "warning_light",                 // 管理端警示灯组件 ID
    "deviceType": "WARNING_LIGHT"                // 警示灯类型
  },
  "action": "set_state",                         // 设置开关状态
  "params": {
    "lightId": "all",                            // 固定控制全部灯
    "powerOn": true                              // true 全开，false 全关
  },
  "client": {
    "terminalId": "web-client-001",
    "source": "warning_light_on",
    "seq": 4001,
    "timestamp": "2026-06-03T10:30:40+08:00"
  }
}
```

后端 MQTT：

```jsonc
{
  "robotId": "robot-songling-001",
  "seq": 4001,
  "target": {
    "deviceId": "warning_light",
    "deviceType": "WARNING_LIGHT"
  },
  "action": "set_state",                         // 客户端映射 /payload/light/set_state
  "params": {
    "lightId": "all",                            // 映射 light_id
    "powerOn": true                              // 映射 power_on
  },
  "issuedAt": "2026-06-03T10:30:40+08:00"
}
```

设置模式：

```jsonc
{
  "target": {
    "deviceId": "warning_light",
    "deviceType": "WARNING_LIGHT"
  },
  "action": "set_mode",
  "params": {
    "lightId": "all",
    "mode": 2                                    // 脉冲一次，由设备切换当前灯光模式
  }
}
```

一期大屏不提供 `mode=0`、`mode=1` 的模式单选控件。点击“切换模式”固定下发
`mode=2`，该动作是一次性命令，不维护持续选中状态。

查询状态：

```jsonc
{
  "target": {
    "deviceId": "warning_light",
    "deviceType": "WARNING_LIGHT"
  },
  "action": "get_state",
  "params": {
    "lightId": "all"                             // 查询全部警示灯
  }
}
```

客户端适配：

| 平台 action | ROS2 Service | Request 映射 |
|---|---|---|
| `get_state` | `/payload/light/get_state` | `light_id=params.lightId` |
| `set_state` | `/payload/light/set_state` | `light_id=params.lightId`，`power_on=params.powerOn` |
| `set_mode` | `/payload/light/set_mode` | `light_id=params.lightId`，`mode=params.mode` |

客户端状态上报应将全部灯聚合到 `devices[deviceId=warning_light].status`。若
底层返回数组，可上报 `powerOn[]`、`modes[]`；若全部灯状态一致，也可归一化为
标量 `powerOn`、`mode`。大屏在数组场景下仅当全部 `powerOn=true` 时显示总开关开启。

### 9.7 车灯光：`light.vehicle.set`

使用场景：

- R1轮式机器人本体登记 `DEVICE_CONTROL/SET_LIGHTS` 能力时，控制服务派生车灯控制目标，用于控制前灯和后灯。
- 管理端无需额外登记 `vehicle-light` 组件；`vehicle-light` 是控制服务面向前端和 MQTT 使用的稳定设备 ID。
- 页面只显示一个车灯总开关，不展示前灯、后灯独立控件。
- 开启时前灯和后灯都提交 `ON`；关闭时都提交 `OFF`，亮度固定为 `0`。

### 9.8 扬声器：`set_volume`、`set_mute`

### 9.9 语音对讲：沿用媒体对讲链路

一期语音对讲建议沿用当前实时视频模块的对讲设计，不纳入 `embodied-control` 普通设备控制 MQTT。

原因：

- 对讲使用 LiveKit 音频链路，不是普通设备动作。
- 当前项目已有视频会话绑定对讲的接口和 MQTT topic。
- 前端点击对讲按钮时，应走媒体模块的 intercom start/stop，而不是 `/commands`。

一期调用方式：

```text
POST /api/control/robots/{robotId}/cameras/{deviceId}/video/intercom/start
POST /api/control/video-sessions/{sessionId}/intercom/stop
```

如果二期需要把语音对讲也纳入统一设备目录，可增加：

```text
target.scope = AUDIO
target.deviceId = intercom-001
action = audio.intercom.start / audio.intercom.stop
```

但一期不建议迁移，避免和现有 LiveKit 对讲链路重复。

### 9.10 多合一喊话设备

#### 9.10.1 建模和能力注册

多合一设备虽然包含喊话、文字转语音、音频播放和照明灯等能力，但在平台注册时仍是一个物理设备：

```text
deviceType = MULTI_FUNCTION_BROADCASTER
```

前端不得按设备名称硬编码面板。前端查询 `control-profile` 后，根据该设备的 `actions` 和 `controlProfile` 动态显示控件。能力示例：

```jsonc
{
  "deviceId": "broadcaster-001",                 // 平台内该物理上装的唯一 ID
  "bindingId": "bind-r1-broadcaster-001",        // 与当前机器人的绑定关系
  "scope": "PAYLOAD",                            // 机器人上装
  "deviceType": "MULTI_FUNCTION_BROADCASTER",    // 多合一喊话设备
  "displayName": "多合一喊话照明设备",             // 前端显示名称
  "onlineStatus": "online",                      // 客户端上报的设备在线状态
  "enabled": true,                               // 平台是否允许使用
  "actions": [
    "set_volume",                                // 设置音量
    "start_broadcast",                           // 开始实时喊话
    "stop_broadcast",                            // 停止实时喊话
    "start_monitor",                             // 开始收音
    "stop_monitor",                              // 停止收音
    "set_monitor_suppressed",                    // 设置喊话时是否暂停设备收音数据
    "play_tts",                                  // 播放文字转语音
    "stop_tts",                                  // 仅停止循环 TTS，单次 TTS 不支持中途停止
    "list_audio_files",                          // 查询设备音频文件
    "play_audio_file",                           // 播放设备音频文件
    "stop_audio_file",                           // 停止文件播放
    "delete_audio_file",                         // 删除设备音频文件
    "play_alarm",                                // 播放警报
    "stop_alarm",                                // 停止警报
    "light.set",                                 // 控制照明灯开关、亮度、爆闪和红蓝模式
    "set_speaker_tilt",                          // 控制喊话器俯仰
    "set_light_tilt"                             // 控制照明灯俯仰
  ],
  "controlProfile": {
    "minVolumePercent": 0,                       // 平台允许的最小音量
    "maxVolumePercent": 100,                     // 平台允许的最大音量，实际还受设备 volumeLimitPercent 限制
    "voices": ["MALE", "FEMALE"],               // TTS 可选音色
    "audioFileFormats": ["wav", "mp3", "aac", "m4a", "flac"],
    "liveBroadcast": {
      "codec": "OPUS",                          // 机器人客户端输出给设备的编码
      "sampleRateHz": 8000,                      // 设备协议要求 8kHz
      "channels": 1,                             // 单声道
      "frameDurationMs": 60                      // 每帧 60ms，480 个样本
    },
    "monitor": {
      "codec": "OPUS",                          // 设备返回给机器人客户端的编码
      "sampleRateHz": 16000,                     // 设备收音协议要求 16kHz
      "channels": 1,                             // 单声道
      "frameDurationMs": 20,                     // 每帧 20ms，320 个样本
      "supportsSuppression": true                // 支持在不结束收音会话时暂停设备数据
    },
    "light": {
      "minBrightnessPercent": 0,                 // 前端统一亮度范围
      "maxBrightnessPercent": 100,
      "supportsStrobe": true,                    // 是否支持爆闪开关
      "redBlueModeMin": 0,                       // 红蓝模式编码下限
      "redBlueModeMax": 16,                      // 红蓝模式编码上限
      "stateReadable": false                     // 设备协议无回复和查询接口
    },
    "speakerTilt": {
      "minPositionPercent": 0,                   // 前端喊话器俯仰滑块范围
      "maxPositionPercent": 100
    },
    "lightTilt": {
      "minPositionPercent": 0,                   // 前端照明灯俯仰滑块范围
      "maxPositionPercent": 100
    }
  }
}
```

管理端登记的 action 优先决定前端展示与后端校验。为保证已与机器人端完成联调的 MQTT 数据结构不发生变化，本体、云台、扬声器、发射器、捕网器、警示灯和多合一设备在管理端尚未登记 action 时可使用生产兼容动作；该兼容表只补动作和参数范围，不补设备运行状态。管理端应尽快登记多合一设备的真实 actions 和 controlProfile，以管理端数据覆盖兼容值。

#### 9.10.2 通用控制结构

多合一设备的低频动作统一调用：

```text
POST /api/control/robots/{robotId}/commands
```

以 TTS 播放为例，前端请求：

```jsonc
{
  "controlSessionId": "tc_20260721_0010",        // 当前设备级控制权
  "target": {
    "scope": "PAYLOAD",                          // 上装设备
    "deviceId": "broadcaster-001",               // 平台设备 ID，不是底层 IP
    "deviceType": "MULTI_FUNCTION_BROADCASTER"   // 后端据此选择构造器和 MQTT topic
  },
  "action": "play_tts",                          // 具体动作：播放 TTS
  "params": {
    "text": "请立即离开危险区域",                  // 待播放文本，UTF-8，不能为空
    "voice": "FEMALE",                           // MALE 男声，FEMALE 女声
    "loop": true                                 // true 循环播放，false 单次播放
  },
  "client": {
    "terminalId": "web-client-001",              // 当前终端 ID
    "source": "broadcaster_tts_button",          // 前端控件来源
    "seq": 10001,                                // 当前终端递增序号
    "timestamp": "2026-07-21T14:30:00+08:00"     // 前端产生动作的时间
  }
}
```

后端完成设备归属、action、控制权、参数和长度校验后，下发：

```jsonc
{
  "robotId": "robot-songling-001",               // 目标机器人
  "seq": 10001,                                  // 沿用前端序号，便于日志定位
  "target": {
    "deviceId": "broadcaster-001",               // 目标物理设备
    "deviceType": "MULTI_FUNCTION_BROADCASTER"   // 客户端选择设备适配器
  },
  "action": "play_tts",                          // 客户端按 action 分发
  "params": {
    "text": "请立即离开危险区域",                  // 已校验文本
    "voice": "FEMALE",                           // 平台音色枚举
    "loop": true                                 // 是否循环
  },
  "issuedAt": "2026-07-21T14:30:00+08:00"        // 后端发布时间
}
```

MQTT topic：

```text
robot/robot-songling-001/control/multi-function/command
```

设备 IP、TCP/HTTP 端口、协议前缀和厂商编码均不得由前端传入，也不进入 MQTT payload。它们属于机器人客户端的设备适配配置，客户端通过 `target.deviceId` 找到对应配置。

#### 9.10.3 各动作 params

| action | 前端和 MQTT 的 `params` | 校验和处理 |
|---|---|---|
| `set_volume` | `{"volumePercent": 60}` | 必须为整数 `0~100`；后端按 profile 和最新 `volumeLimitPercent` 限幅 |
| `start_broadcast` | `{"mediaSessionId": "ms_001"}` | 媒体会话必须属于当前 robot/device/terminal；普通 MQTT 不携带音频帧 |
| `stop_broadcast` | `{"mediaSessionId": "ms_001"}` | 停止指定媒体会话的实时喊话转发 |
| `start_monitor` | `{"mediaSessionId": "ms_001"}` | 开始设备收音，并把机器人客户端发布的收音 Track 返回当前媒体会话 |
| `stop_monitor` | `{"mediaSessionId": "ms_001"}` | 停止指定媒体会话的设备收音；机器人客户端停止发布收音 Track |
| `set_monitor_suppressed` | `{"suppressed": true}` | `true` 暂停设备收音数据，`false` 恢复；收音会话和 `monitorActive` 保持不变 |
| `play_tts` | `{"text": "你好", "voice": "MALE", "loop": false}` | 文本非空；音色必须在 profile 中；`loop=false` 为单次播放且不支持中途停止，`loop=true` 为循环播放 |
| `stop_tts` | `{}` | 仅停止 `loop=true` 的循环 TTS；单次 TTS 播放期间前端不得展示可用的停止按钮 |
| `list_audio_files` | `{}` | 客户端查询后通过统一状态上报刷新 `status.audioFiles` |
| `play_audio_file` | `{"fileName": "notice.mp3", "loop": true}` | 文件名必须来自最近查询结果；禁止目录路径和路径穿越字符 |
| `stop_audio_file` | `{}` | 停止当前文件播放 |
| `delete_audio_file` | `{"fileName": "notice.mp3"}` | 文件名必须来自最近查询结果；删除前端应二次确认 |
| `play_alarm` | `{}` | 播放设备内置警报 |
| `stop_alarm` | `{}` | 停止设备内置警报 |
| `light.set` | `{"enabled": true, "brightness": 80, "strobeEnabled": false, "redBlueMode": 2}` | 采用局部更新语义，只传本次需要改变的字段；亮度为整数 `0~100`，客户端映射为设备值 `0~30`；`redBlueMode=0` 表示关闭，`1~16` 表示闪烁模式 |
| `set_speaker_tilt` | `{"positionPercent": 50}` | 喊话页面俯仰滑块，整数范围 `0~100`；客户端线性映射为喊话器原始值 `80~220` |
| `set_light_tilt` | `{"positionPercent": 50}` | 照明页面俯仰滑块，整数范围 `0~100`；客户端线性映射为照明灯原始值 `100~200` |

音量、TTS 和照明等按钮均属于离散低频动作，不按 10Hz 重复发送。只有实时喊话的音频媒体帧按媒体编码节奏持续传输。

文件播放、TTS、警报、实时喊话、实时收音和照明由设备自身独立处理，一期不在平台侧建立互斥关系或抢占优先级，允许统一并发下发。并发只表示业务动作不互斥；机器人客户端仍必须串行写入同一 TCP 连接，保证一条设备报文或一帧音频数据不会与其他报文字节交叉。

#### 9.10.4 实时喊话与收音的数据面

实时喊话和实时收音共用一个多合一设备音频会话，但两个方向独立启停。前端连接的是平台 LiveKit 会话，不直接连接机器人局域网内的多合一设备；机器人客户端是平台与多合一设备之间的全双工音频网关。

```text
大屏喊话方向：
浏览器麦克风
  -> LiveKit Track：audio.operator.mic
  -> 机器人客户端订阅并转为 8000Hz、16bit、单声道 PCM
  -> 按 480 样本/60ms 编码为 Opus
  -> 设备局域网 TCP 8519：[10] + 单帧 Opus
  -> 多合一设备扬声器输出

大屏收音方向：
多合一设备麦克风输入
  -> 设备局域网 TCP 8519：[40] + 单帧 Opus
  -> 机器人客户端按 16000Hz、单声道、320 样本/20ms 解码
  -> LiveKit Track：audio.robot.mic
  -> 浏览器扬声器输出
```

大屏首次点击“开始喊话”或“开始收音”时，先创建或复用该设备的全双工音频会话：

```text
POST /api/control/robots/{robotId}/cameras/{deviceId}/video/intercom/start
```

当前复用平台已实现的对讲媒体接口，路径中的 `cameras` 是历史命名；
`deviceId=broadcaster-001` 时创建的是纯音频会话，不要求该组件是摄像头。
前端请求：

```jsonc
{
  "quality": "sub",
  "reuse": true
}
```

返回给前端：

```jsonc
{
  "sessionId": "vs_20260721_0001",               // 同时作为控制命令的 mediaSessionId
  "robotId": "robot-dog-001",                    // 机器人 ID
  "deviceId": "broadcaster-001",                 // 多合一设备 ID
  "roomName": "media.robot-dog-001.broadcaster-001.vs_20260721_0001",
  "livekitUrl": "wss://platform.example/livekit",
  "operatorToken": "eyJ...",                     // 只返回给当前大屏，允许发布和订阅音频
  "expiresAt": "2026-07-21T15:00:00+08:00"
}
```

Control Service 同时向机器人客户端下发媒体会话启动消息：

```text
robot/{robotId}/media/video/intercom/start
```

```jsonc
{
  "sessionId": "vs_20260721_0001",
  "robotId": "robot-dog-001",
  "deviceId": "broadcaster-001",
  "roomName": "media.robot-dog-001.broadcaster-001.vs_20260721_0001",
  "livekitUrl": "wss://livekit.internal:7880",
  "robotToken": "eyJ...",                        // 只下发机器人客户端，不返回前端
  "publishAudio": true,                          // 允许发布设备收音 Track
  "subscribeOperatorAudio": true,                // 允许订阅大屏麦克风 Track
  "publishVideo": false,
  "expiresAt": "2026-07-21T15:00:00+08:00"
}
```

机器人客户端加入 LiveKit 后，大屏再通过统一 `/commands` 分别下发 `start_broadcast`、`stop_broadcast`、`start_monitor`、`stop_monitor`、`set_monitor_suppressed`。会话结束时调用：

```text
POST /api/control/video-sessions/{sessionId}/intercom/stop
```

Control Service 随后发布：

```text
robot/{robotId}/media/video/intercom/stop
```

音频会话存续期间，大屏每 5 秒调用
`POST /api/control/video-sessions/{sessionId}/intercom/heartbeat`。喊话和收音共用
`sessionId`；只有两个方向均停止后才停止该 LiveKit 会话。

各段连接和异常处理约定：

1. 浏览器与机器人客户端通过 LiveKit 传输双向实时音频，MQTT 仅传媒体会话启动、停止和设备控制动作，不承载音频二进制。
2. 机器人客户端负责维护多合一设备 TCP `8519` 连接，可在同一物理设备的多次控制动作间复用长连接。
3. 同一 TCP 连接必须由单一发送队列串行写入，避免控制字符串和 `[10]+Opus` 音频帧在应用层发生字节交叉；TCP 仍可能把多个完整写入合并到同一接收片段，客户端读取时必须按字节流解析，不能把一次 `read/recv` 当成一条完整消息。
4. TCP 断开后由机器人客户端按有界退避重连。断线期间的喊话和收音实时帧直接丢弃，不缓存、不补播。
5. LiveKit 音频中断或前端停止发送时，机器人客户端立即停止向设备发送喊话音频；恢复后只发送最新实时帧。
6. “喊话时禁用收音”通过 `set_monitor_suppressed` 下发。`suppressed=true` 时客户端发送 `[45]`，设备暂停 `[40]+Opus` 数据但不结束收音会话；`suppressed=false` 时发送 `[46]`，设备恢复发送。该动作不得改写 `monitorActive`。开始喊话时若收音已开启，前端默认先启用该抑制，停止喊话后恢复，减少全双工声学回路导致的啸叫。
7. 文件查询和删除由机器人客户端访问设备 HTTP `8222`；文件上传先通过通用文件服务保存到 MinIO，再由机器人客户端从 Media Service 下载并调用厂商 `/upload-file`。三者均与 TCP 实时喊话和收音链路相互独立。
8. 连接状态、媒体会话状态和中断原因通过统一客户端状态上报；前端显示“连接中断”或“指令下发失败”，不自行重放历史音频。

禁止把以下内容放入普通 MQTT JSON：

- PCM 或 Opus 的 Base64 数据。
- `[10]`、`[40]` 等设备协议前缀。
- 采集缓冲区、帧序号等媒体内部字段。
- 设备 IP 和端口。

这样可以避免 JSON/Base64 膨胀、MQTT 控制消息阻塞，也能让未来其他厂商设备复用相同的双向音频会话语义。

#### 9.10.5 音频文件上传

设备文档中的 `/upload-file` 只能在机器人局域网内访问。大屏先复用通用文件上传接口：

```text
POST /api/control/files
Content-Type: multipart/form-data
```

上传成功取得 `fileId` 后，再调用：

```text
POST /api/control/robots/{robotId}/devices/{deviceId}/audio-file-transfers
Content-Type: application/json
{"fileId":"file_xxx"}
```

完整流程为：

```text
前端选择文件
  -> 调用通用文件接口保存到 Media Service / MinIO
  -> 前端携带 fileId 请求 Control Service 发起设备传输
  -> MQTT 下发 fileId、文件名、大小和组织 ID
  -> Go/Python 客户端通过 MEDIA_SERVICE_URL 从 8088 下载并校验大小
  -> 客户端调用机器人局域网内厂商 HTTP POST /upload-file
  -> 客户端查询文件列表并通过统一状态上报
```

该链路不在 Control Service 保存文件，也不使用 MQTT 分片传输文件。平台限制单文件
不超过 `20MB`，同名覆盖行为由厂商接口决定。MinIO 中的文件由通用文件服务统一管理。

#### 9.10.6 客户端设备协议映射

本节映射依据《横版多合一用户手册-20260512》《_23_喊话协议》《_27_四合一灯光控制》以及 2026-07-28 遥控手柄实机抓包整理。客户端适配层按以下规则解析平台命令。表中的底层数据只用于客户端实现，不进入前端或平台 MQTT：

| 平台 action / 状态 | 设备侧协议映射 |
|---|---|
| `set_volume` | TCP 发送 `[14]${volHex}`；`volumePercent` 转为两位小写十六进制，例如 `9 -> 09`、`47 -> 2f`、`100 -> 64` |
| 音量状态 | 每 2 秒解析 `[99]` 后的 JSON；`volume_real -> volumePercent`、`volume_limit -> volumeLimitPercent`、`temperature -> temperatureC` |
| `list_audio_files` | HTTP `GET /fetch-files`；成功后把文件名数组写入 `devices[].status.audioFiles` |
| `play_audio_file` | TCP 发送 `[12]${loopFlag}${fileNameUtf8}`；`loop=true -> 1`，否则 `0` |
| `stop_audio_file` | TCP 发送 `[13]` |
| `delete_audio_file` | HTTP `POST /del-file`，表单字段 `filename=params.fileName`；本次未抓包验证 |
| `play_tts` | 非循环使用 `[31]${voiceCode}${text}`，循环使用 `[32]${voiceCode}${text}`；`MALE -> 0`，`FEMALE -> 1` |
| `stop_tts` | TCP 发送 `[17]`；仅停止循环 TTS，单次 TTS 不支持中途停止 |
| TTS 完成事件 | 单次 TTS 播放结束后设备发送 `[30]`；该事件没有 commandId，只能更新当前设备最近一次 TTS 完成时间 |
| `play_alarm` | TCP 发送 `[18]` |
| `stop_alarm` | TCP 发送 `[19]` |
| `start_broadcast` | 建立媒体转发；每 60ms 向设备发送 `[10]` 加一帧 Opus 二进制数据；设备资料声明 `[42]` 兼容，但实机 APP 使用 `[10]` |
| `stop_broadcast` | 停止发送实时喊话音频帧并发送 `[11]`；`[11]` 为实机 APP 行为，原设备资料仅要求停止发送音频数据 |
| `start_monitor` | TCP 发送 `[40]`；持续接收 `[40] + Opus`，按 16000Hz、单声道、320 样本/20ms 解码后发布 `audio.robot.monitor` |
| `stop_monitor` | TCP 发送 `[41]`，停止设备收音和收音 Track 发布 |
| `set_monitor_suppressed` | `suppressed=true` 发送 `[45]`，设备停止输出 `[40]+Opus`；`suppressed=false` 发送 `[46]`，设备恢复输出；期间收音会话保持活动 |
| `set_speaker_tilt` | `speakerRaw = round(80 + clamp(positionPercent, 0, 100) * 140 / 100)`，映射结果为 `80~220`；TCP `12345` 发送二进制 `[0x8D][speakerRaw]` |
| `set_light_tilt` | `lightRaw = round(100 + clamp(positionPercent, 0, 100))`，映射结果为 `100~200`；TCP `8519` 发送 MSG_ID `0x09`，Payload 为 `[0xFF][lightRaw]` |
| `light.set/enabled` | TCP `8519` 发送设备报文：包头 `0x8D`、长度 `0x01`、MSG_ID `0x01`、Payload 为 `1/0`；设备不回复 |
| `light.set/brightness` | `brightnessRaw = round(clamp(brightness, 0, 100) * 30 / 100)`，映射结果为 `0~30`；TCP `8519` 发送 MSG_ID `0x02`；设备不回复 |
| `light.set/strobeEnabled` | `true` 发送 MSG_ID `0x03`、Payload `1`；`false` 按实机 APP 行为依次发送 MSG_ID `0x03` 的 `0` 和 MSG_ID `0x01` 的 `0`，关闭爆闪和照明；设备不回复 |
| `light.set/redBlueMode` | TCP `8519` 发送 MSG_ID `0x07`、Payload 为 `0x00~0x10`；设备不回复 |

照明控制设备报文统一格式为：

```text
[包头 0x8D][长度][MSG_ID][Payload...][CRC-8/MAXIM]
```

校验采用 `CRC-8/MAXIM`，计算范围从 `长度` 开始，到最后一个 `Payload` 字节结束，不包含包头 `0x8D`。参数为：

```text
poly    = 0x31（反射实现使用 0x8C）
init    = 0x00
refin   = true
refout  = true
xorout  = 0x00
```

设备资料示例和实机抓包中的照明报文均符合该算法：

```text
8D 01 01 01 31       // 开灯，CRC(01 01 01) = 31
8D 01 01 00 6F       // 关灯，CRC(01 01 00) = 6F
8D 01 02 07 B9       // 亮度 7，CRC(01 02 07) = B9
8D 01 03 01 A0       // 打开爆闪，CRC(01 03 01) = A0
8D 01 07 02 79       // 红蓝模式 2，CRC(01 07 02) = 79
8D 02 09 FF A2 1B    // 两路俯仰，CRC(02 09 FF A2) = 1B
```

前端和 Control Service 只传平台语义字段，不传 `0x8D`、MSG_ID、设备亮度值或 CRC 字节。机器人客户端负责按设备协议完成字段映射、报文组装和 CRC 计算。

滑块映射示例：

| 前端滑块值 | 亮度设备值 | 喊话器俯仰设备值 | 照明灯俯仰设备值 |
|---:|---:|---:|---:|
| `0` | `0`（`0x00`） | `80`（`0x50`） | `100`（`0x64`） |
| `50` | `15`（`0x0F`） | `150`（`0x96`） | `150`（`0x96`） |
| `100` | `30`（`0x1E`） | `220`（`0xDC`） | `200`（`0xC8`） |

同一个 `light.set` 同时包含多个字段时，机器人客户端按 `enabled -> brightness -> strobeEnabled -> redBlueMode` 的固定顺序逐条发送设备报文；未出现的字段不发送。`enabled=false` 按实机 APP 行为先发送 MSG_ID `0x03` 的 `0`，再发送 MSG_ID `0x01` 的 `0`，确保爆闪和照明同时关闭。实机抓包确认普通 ASCII 控制命令、状态报文、实时音频帧和灯光二进制报文可复用设备 TCP `8519` 连接。喊话器俯仰独立使用 TCP `12345`。设备地址和端口属于客户端适配配置，不进入前端请求、MQTT payload 或平台能力参数。

实机抓包观察到照明灯俯仰报文 `8D 02 09 FF 70 F0`，其中 `0x70` 是照明灯角度，`0xFF` 表示喊话器通道不参与本次调整。喊话器俯仰则由 APP 通过 TCP `12345` 发送两字节报文，例如 `8D 5D`。因此一期客户端按以下规则实现：

- `set_speaker_tilt`：TCP `12345` 发送 `[0x8D][speakerRaw]`，原始值范围 `80~220`。
- `set_light_tilt`：TCP `8519` 发送 `[0x8D][0x02][0x09][0xFF][lightRaw][CRC]`，原始值范围 `100~200`。
- 抓包未观察到通过 MSG_ID `0x09` 第一个 Payload 字段设置喊话器角度，一期不使用该方式。

四组实机抓包还形成以下结论：

- 设备约每 2 秒发送一次 `[99]` JSON 状态；设置音量后还会立即返回 `[14]"${volHex}"`。返回值不保证补足两位，例如 `10 -> [14]"a"`、`20 -> [14]"14"`，客户端必须兼容 1~2 位十六进制字符。
- APP 约每 2 秒发送一次 `8D 00 04 61`。该报文在所有操作场景中持续出现，行为符合适配层保活，但 MSG_ID `0x04` 未在资料中定义；不抽象为平台 action，客户端先作为可配置保活实现。
- 实时喊话实测约 `16.7` 帧/秒，对应每帧 `60ms`；收音实测约 `50` 帧/秒，对应每帧 `20ms`。
- 并发抓包中，灯光、TTS、文件播放和收音控制可插入持续实时喊话流，同一 TCP 连接没有断开或明显阻塞。
- 设备会把 `[99]`、多个 `[40]+Opus` 或控制消息合并在同一 TCP 接收片段中；客户端必须实现流式拆包和残包缓存。Opus 是二进制数据，可能自然包含 `0x8D`，只有完整且 CRC 校验正确的灯光帧才能作为收音帧边界。
- 文件播放停止后观察到一次 `[39]`，与“播放停止或结束通知”高度相关，但尚未验证文件自然播放结束时是否同样上报，一期只记录日志，不据此建立可靠播放状态。
- 本次没有执行文件上传和删除，`POST /upload-file`、`POST /del-file` 仍按设备接口资料开发，并列入真实设备联调验收项。

#### 9.10.7 状态上报和前端渲染

机器人客户端通过现有统一 topic 上报状态：

```text
robot/{robotId}/media/client/status
```

多合一设备状态示例：

```jsonc
{
  "deviceId": "broadcaster-001",                 // 平台设备 ID
  "deviceType": "MULTI_FUNCTION_BROADCASTER",    // 设备类型
  "onlineStatus": "online",                      // 设备连接状态
  "status": {
    "connected": true,                           // TCP 8519 长连接是否可用

      "state": "ACTIVE",                         // CONNECTING/ACTIVE/INTERRUPTED/FAILED/IDLE
      "broadcastActive": true,                   // 客户端正在转发大屏喊话音频
      "monitorActive": true,                     // 客户端正在接收并发布设备收音音频
      "monitorSuppressed": false,                // 客户端最近生效的喊话时禁用收音设置
      "monitorTrackSid": "TR_audio_monitor_001", // LiveKit 收音 Track
      "lastError": null                          // 最近媒体链路错误
    },
    "observedAt": "2026-07-21T14:30:02+08:00"    // 状态采集时间
  }
}
```

前端渲染规则：

- 音量滑块最大值取 `min(controlProfile.maxVolumePercent, status.volumeLimitPercent)`，当前值取 `status.volumePercent`。命令等待设备 `[14]` 或 `[99]` 确认期间保留用户刚设置的值，避免旧状态把滑块瞬时覆盖。
- 温度和在线状态直接按设备上报显示。
- 音频文件下拉列表取 `status.audioFiles`；列表未查询成功时显示“文件列表未同步”。
- “开始喊话/停止喊话”和“开始收音/停止收音”按 `status.audioSession` 渲染。这里表示机器人客户端媒体转发状态，不表示多合一设备提供了播放查询接口。
- “喊话时禁用收音”按 `status.audioSession.monitorSuppressed` 渲染。切换时调用 `set_monitor_suppressed`；打开后 `monitorActive` 仍为 `true`，但设备暂停收音帧。喊话和收音同时开启时默认自动打开，停止喊话后仅恢复由本次喊话自动打开的抑制状态。
- 单次 TTS 收到 `[30]` 后更新 `lastTtsCompletedAt`；该事件没有 commandId，不能关联多条并发 TTS 命令。
- 设备协议没有文件播放、警报和照明查询接口，`[39]` 的完整语义也未确认。客户端可上报 `audioPlayback` 表示最近一次已成功写入的文件播放命令，前端据此显示文件名和播放模式，但不得标记为设备查询状态；警报和照明仍由前端维护本页面最近下发值。
- 页面刷新、终端切换或机器人重连后，本地展示态无法恢复时，相关控件显示默认值或“状态未同步”，不能推断设备当前状态。
- 后续机器人端增加真实状态接口后，再扩展可区分真实设备状态的字段，不修改现有命令 envelope。

#### 9.10.8 确认结论

本节原待确认项已形成以下一期结论：

1. 照明灯接口通过设备 TCP `8519` 按二进制报文 `0x8D + len + MSG_ID + Payload + CRC-8/MAXIM` 对接，支持灯光开关、`0~100` 统一亮度、爆闪开关和 `0~16` 红蓝模式；设备不回复，也未提供状态查询接口。
2. TTS 单次播放不支持中途停止；`stop_tts` 只用于停止循环 TTS。
3. 文件上传由大屏调用通用文件接口保存到 Media Service / MinIO，再携带 `fileId` 请求 Control Service 下发；客户端通过 `MEDIA_SERVICE_URL` 下载后调用设备 `/upload-file`，平台限制单文件不超过 `20MB`。
4. 实时喊话和收音采用“MQTT 控制面 + LiveKit 全双工媒体数据面 + 机器人客户端设备适配”链路，连接复用、串行写入、断线重连和实时帧丢弃规则见 9.10.4。
5. 文件播放、TTS、警报、实时喊话、实时收音和照明不设置业务互斥关系或抢占优先级，均允许并发操作。
6. 协议已提供的查询或主动上报结果进入 `devices[].status` 并驱动前端；协议未提供状态接口的能力由前端维护本地最近下发值，不视为设备真实状态。
7. 喊话器俯仰通过 TCP `12345` 的 `[0x8D][speakerRaw]` 控制，平台 `0~100` 映射为设备 `80~220`；照明灯俯仰通过 TCP `8519` 的 MSG_ID `0x09` 控制，平台 `0~100` 映射为设备 `100~200`，另一通道固定填 `0xFF`。
8. 实时喊话采用 `[10]+Opus`，停止时发送 `[11]`；收音采用 `[40]+Opus`，`[41]` 停止；“喊话时禁用收音”采用 `[45]/[46]`，不会结束收音会话。
9. 文件上传和删除未完成实机抓包验证，真实设备验收时必须补测，不阻塞按既有 HTTP 接口资料开发。

尚待确认的底层事项仅包括 MSG_ID `0x04` 的业务含义，以及设备是否支持通过 MSG_ID `0x09` 的第一个 Payload 字段设置喊话器角度；二者均不阻塞一期已确认动作开发。

#### 9.10.9 大屏按钮与客户端动作映射

大屏打开多合一设备面板时，先为 `broadcaster-001` 申请一次设备级控制权。后续所有离散动作复用该 `controlSessionId`；实时喊话和收音额外创建或复用 9.10.4 定义的 `mediaSessionId`。

| 大屏操作 | 平台请求或本地动作 | 机器人客户端处理 | 大屏状态来源 |
|---|---|---|---|
| 开始喊话 | 确保音频会话 `ACTIVE`，发布浏览器麦克风 Track，再下发 `start_broadcast(mediaSessionId)` | 订阅 `audio.operator.broadcast`，按 `[10]+Opus` 持续发送设备 | `status.audioSession.broadcastActive` |
| 停止喊话 | 停止发布浏览器麦克风 Track并下发 `stop_broadcast(mediaSessionId)` | 停止发送喊话帧并发送 `[11]` | `status.audioSession.broadcastActive` |
| 开始收音 | 确保音频会话 `ACTIVE`，下发 `start_monitor(mediaSessionId)`并订阅收音 Track | 发送 `[40]`，接收设备 Opus 并发布 `audio.robot.monitor` | `status.audioSession.monitorActive` |
| 停止收音 | 下发 `stop_monitor(mediaSessionId)` | 发送 `[41]`并停止发布收音 Track | `status.audioSession.monitorActive` |
| 喊话时禁用收音 | `set_monitor_suppressed({"suppressed":true/false})` | `[45]` 暂停设备收音帧，`[46]` 恢复；不结束收音会话 | `status.audioSession.monitorSuppressed` |
| 播放/停止警报 | `play_alarm` / `stop_alarm` | `[18]` / `[19]` | 前端最近下发值 |
| 调整音量 | `set_volume({"volumePercent": 60})` | `[14]${volHex}` | 设备 `[99]` 定时上报 |
| 调整喊话器俯仰 | `set_speaker_tilt({"positionPercent": 50})` | 映射为 `80~220`，TCP `12345` 发送 `[0x8D][speakerRaw]` | 前端最近下发值 |
| 单次 TTS | `play_tts({"text":"...","voice":"MALE","loop":false})` | `[31]${voiceCode}${text}`；结束时接收 `[30]` | 播放按钮不切换为停止；客户端可记录最近完成时间 |
| 循环 TTS | `play_tts(...,"loop":true)`；停止时 `stop_tts` | `[32]...`；停止时 `[17]` | 前端在发布成功后切换播放/停止按钮 |
| 查询音频文件 | `list_audio_files` | HTTP `GET /fetch-files` | `status.audioFiles` |
| 单次/循环播放文件 | `play_audio_file({"fileName":"notice.mp3","loop":false/true})` | `[12]${loopFlag}${fileName}` | 前端最近下发值 |
| 停止文件播放 | `stop_audio_file` | `[13]` | 前端最近下发值 |
| 上传/删除文件 | 独立上传接口 / `delete_audio_file` | HTTP `/upload-file` / `/del-file` | 接口结果；成功后重新查询列表 |
| 开灯/关灯 | `light.set({"enabled":true/false})` | MSG_ID `0x01` | 前端最近下发值 |
| 开爆闪/关爆闪 | `light.set({"strobeEnabled":true/false})` | 开启发送 MSG_ID `0x03=1`；关闭依次发送 `0x03=0`、`0x01=0` | 前端最近下发值；关爆闪同时关闭照明，亮度滑块始终可操作 |
| 调整亮度 | `light.set({"brightness":0~100})` | 映射为 `0~30`，MSG_ID `0x02` | 前端最近下发值；与开关灯互不依赖 |
| 切换红蓝模式 | 前端把本地模式按 `1~16` 循环递增，调用 `light.set({"redBlueMode":n})` | MSG_ID `0x07`，Payload 为 `n` | 前端显示“模式 n（本地）” |
| 关闭红蓝灯 | `light.set({"redBlueMode":0})` | MSG_ID `0x07`，Payload 为 `0` | 前端最近下发值 |
| 调整照明灯俯仰 | `set_light_tilt({"positionPercent":50})` | 映射为 `100~200`，TCP `8519` 发送 MSG_ID `0x09`，Payload 为 `[0xFF][lightRaw]` | 前端最近下发值 |

前端切换标签页不得停止其他标签页已经启动的功能。只有用户点击对应停止按钮、关闭整个多合一设备音频会话或设备离线时，才停止相应动作。设备允许业务动作并发，不代表多个大屏终端可同时控制；一期仍由设备级 `controlSessionId` 保证同一时间只有一个终端持有该多合一设备控制权。

#### 9.10.10 当前实现状态与后续边界

当前已实现：

1. Control Service 识别 `MULTI_FUNCTION_BROADCASTER`，提供完整兼容 actions/controlProfile、逐动作参数校验、局部 `light.set` 组装和独立 `control/multi-function/command` 路由。
2. 大屏按管理端设备能力动态展示多合一面板，已接通音量、喊话/收音控制、收音抑制、TTS、文件查询/播放/停止/删除、警报、照明、红蓝模式和两个独立俯仰控件；开始喊话时申请浏览器麦克风，开始收音时订阅并播放机器人音频 Track。
3. 大屏按统一状态渲染连接、温度、音量、文件列表和媒体会话；设备没有查询接口的照明、警报和文件播放只保留当前页面最近下发值。
4. Go/Python 客户端已实现真实设备适配器：复用 TCP `8519` 长连接、串行写控制报文、按有界退避重连、发送灯光保活、解析 `[99]`/`[14]`/`[30]`/`[39]`/`[40]`，并调用 TCP `12345` 和 HTTP `8222`。
5. 客户端已将 MQTT 的多合一 action 路由到真实适配器，设备 TCP 连接、音量、温度、文件列表和音频会话状态通过统一 `media/client/status` 上报；不再使用固定音量、温度和示例文件模拟状态。
6. Go/Python 已用抓包样例完成 CRC、数值映射、分片/粘包解析和 TCP/HTTP 伪设备回归测试；Go 提供 `cmd/multi-function-test` 供机器人局域网现场测试。
7. Python 客户端已复用现有 Media Service 对讲房间，将浏览器麦克风转换为设备 `8kHz/60ms Opus`，并将设备 `16kHz/20ms Opus` 收音转换为 LiveKit `audio.robot.mic`；大屏负责音频会话创建、5 秒心跳和 Track 回收。

尚未闭环：

1. Python 多合一 LiveKit 全双工音频桥已完成代码与编解码测试，仍需在真实浏览器、LiveKit 和多合一设备链路上完成音质、时延、长时间稳定性与回声验收。
2. Go 客户端仍只提供 `[10]+Opus` 写入和 `[40]+Opus` 回调，尚未接通 LiveKit PCM 重采样、Opus 编解码与 Track 桥接。
3. 大屏已复用通用文件服务将音频保存到 MinIO；Go/Python 客户端消费 `upload_audio_file`，根据 `fileId` 从 Media Service 下载后调用厂商 `/upload-file`，并通过统一状态同步文件列表和传输结果。
4. 管理端生产环境需注册真实 `deviceId`、actions，并与客户端 `MULTI_FUNCTION_DEVICE_ID` 保持一致；当前 manifest 接口尚不支持登记 `controlProfile`。

## 10. 控制模式与控制权策略

### 10.1 控制模式

| 模式 | 说明 | 一期处理 |
|---|---|---|
| `MANUAL` | 手动模式，用户直接控制本体或设备 | 本体控制帧必须处于该模式 |
| `NAVIGATION` | 导航模式，机器人执行导航或任务 | 本体手动控制前需要切换到 `MANUAL`；云台可默认不打断导航 |

### 10.2 控制策略

| 最新客户端状态 | 前端动作 | 后端策略 |
|---|---|---|
| `MANUAL` 且无人控制 | 申请本体控制 | 允许创建控制权 |
| `MANUAL` 且他人控制本体 | 申请本体控制 | 拒绝，返回 `CONTROL_LOCKED` |
| `NAVIGATION` | 手动控制本体 | 调用 takeover；后端申请本体锁并发布切手动指令，等待机器人上报 `MANUAL` |
| `NAVIGATION` | 控制云台 | 默认允许申请设备级控制权，不打断导航 |
| `NAVIGATION` | 捕网器发射 | 默认禁止，除非任务策略明确允许 |
| 任意模式 | 急停 | 允许，最高优先级 |
| 急停生效中 | 普通控制 | 禁止 |

### 10.3 模式切换时序

```text
机器人客户端上报 media/client/status
  -> 控制服务合并管理端设备 ID、动作与控制 profile
  -> 后端缓存最新 stateSeq/controlMode
  -> WebSocket 广播一次 robot.state
  -> 用户点击本体控制或选择手动模式
  -> 前端调用 /control-sessions/takeover，携带 observedStateSeq
  -> 后端校验在线状态和状态序号
  -> 后端申请 base 控制权；不抢占其他终端
  -> 后端发布 control.mode.set=MANUAL
  -> 机器人客户端完成切换并上报 controlMode=MANUAL
  -> 后端广播真实 robot.state
  -> 前端开始按 10Hz 发送 drive.velocity 控制帧
```

注意：`PUBLISHED` 不是模式切换成功。前端必须等待机器人真实状态，后端也会在每一帧本体移动指令下发前校验控制会话和 `MANUAL` 模式。

## 11. 一期频率和安全

| 控制对象 | 前端发送频率 | 后端处理 |
|---|---:|---|
| 本体点触 | 10Hz，发送少量帧 | 每帧校验、限幅、按本体设备类型组装 MQTT |
| 本体长按/摇杆 | 10Hz，按住期间持续发送 | 每帧校验、限幅、按本体设备类型组装 MQTT |
| 云台点触 | 10Hz，发送少量帧 | 每帧校验、限幅、按云台设备类型组装 MQTT |
| 云台长按 | 10Hz，按住期间持续发送 | 每帧校验、限幅、按云台设备类型组装 MQTT |
| 变焦长按 | 10Hz，按住期间持续发送 | 每帧校验、限幅、按云台/相机设备类型组装 MQTT |

安全规则：

- 连续控制类不要求前端发送结束帧。
- 后端不区分点触、长按、松手，只处理收到的每一帧控制数据。
- 本体手动控制必须处于 `MANUAL`；`NAVIGATION` 下先完成人工接管。
- 发射器 `fire` 必须有控制权、confirmToken、真实安全开关和冷却校验。
- 捕网枪 `fire` 必须有控制权和 confirmToken；安全开关只在前端本地解锁按钮，不作为后端校验项。
- 急停使用 `robot/{robotId}/control/safety/estop`，不进入普通命令队列。
- 客户端如何消费控制帧并调用 ROS2，由客户端同事单独抽象实现。
