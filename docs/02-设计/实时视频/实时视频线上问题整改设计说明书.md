## 1. 背景与结论

实时视频程序已经上线，但用户长时间观看、多画面观看和断线恢复体验较差。典型表现如下：

- 视频正常播放一段时间后偶发黑屏，页面显示“未连接”。
- 点击 `restart` 后短暂恢复，随后再次无画面。
- 刷新整个页面后通常可以恢复。
- 同一故障期间可能出现重复的视频启动命令、重复 LiveKit Participant 和旧连接回调覆盖新连接状态。
- 浏览器存在 UDP ICE 候选，但部分现场最终选择 LiveKit TCP `7881`，网络丢包或抖动时更容易出现长时间卡顿和 DTLS 超时。

综合线上日志与当前代码确认，本问题不是单一的“机器人推流不稳定”，而是以下问题叠加：

1. 浏览器观看连接与机器人共享 Publisher 的故障域没有隔离。
2. 前端 Room、Track 和 Vuex 状态存在异步竞态，重连成功后仍可能显示未连接。
3. 前端、Media 和 Control 均缺少统一的启动/重启幂等保护。
4. 同源会话创建、Room 生命周期和 Publisher 生命周期没有统一的源粒度所有权。
5. 发布超时、viewer 计数与定时恢复存在数据竞态，在多实例下会被进一步放大。
6. 播放端部分网络未选中 UDP，TCP 链路丢包时恢复能力不足。
7. 线上缺少足以关联浏览器、会话、命令、Room、Participant 和 Track 的观测数据及长稳回归。

整改必须按生产正式方案处理，不能继续依赖用户刷新页面、反复点击重启或服务端盲目重发 start 命令。

## 2. 当前链路与故障边界

```text
robot-ui
  -> Bigscreen BFF
  -> Control Service
  -> Media Service
  -> EMQX
  -> 生产设备端媒体客户端（仓库外）
  -> RTSP
  -> Publisher
  -> LiveKit
  -> 浏览器 WebRTC 播放
```

正常职责边界应为：

- 浏览器只负责加入 Room、订阅 Track、绑定视频元素和恢复自身连接。
- Media 负责 `VideoSession`、viewer、Room、Token、Track 事实和资源引用关系。
- Control 只在确认设备侧 Publisher 需要启动、切换或恢复时下发 MQTT 命令。
- 生产设备端媒体客户端属于外部依赖；本项目只定义并验证 MQTT 命令/状态契约，不修改仓库内 `python-client` Demo。
- LiveKit Participant/Track 是媒体是否真实存在的事实来源，业务状态不能长期与其脱节。

当前实现把上述边界混在一起：浏览器连接失败可以触发机器人 Publisher 重启；单个 session 的释放可以删除共享 Room；多个 session 又可能使用同一个 Room 和 Publisher Identity。

### RV-P0-001 浏览器异常直接触发共享 Publisher 重启

**当前实现**

`robot-ui` 在 LiveKit `TrackUnsubscribed` 和 `Disconnected` 事件中，只要摄像头仍处于 watching，就调用 `restartCamera`。`restartCamera` 调用 Control `/video-sessions/{sessionId}/restart`，Media 重新生成 Publisher Token 和 start command，Control 再通过 MQTT 请求机器人启动 Publisher。

**问题**

浏览器到 LiveKit 的播放连接和机器人到 LiveKit 的发布连接是两条独立 WebRTC 连接。单个浏览器断网、标签页切换、ICE 失败或 DOM 绑定异常，不能证明共享 Publisher 已失效。

**影响**

- 一个观看端的问题会影响同一 session 下的所有观看者。
- 正常发布中的 Track 被主动重建，扩大故障范围。
- 重启期间所有观看者短暂黑屏。
- 多个浏览器同时异常时可能形成重启风暴。
- 新旧 Participant/Track 事件交错，进一步触发重复恢复。

**整改要求**

1. 删除 `TrackUnsubscribed/Disconnected -> restartCamera` 的直接调用。
2. 浏览器断线首先只恢复 viewer Room，不得下发设备 start。
3. 只有 Media 根据 LiveKit Publisher/Track 事实或机器人状态确认发布端中断时，才允许触发 Publisher 恢复。
4. 人工 restart 保留为明确运维动作，并进行权限、幂等和操作审计。

**验收标准**

- 单个浏览器断网 30 秒后恢复，不产生 MQTT start/restart。
- 同 Room 的其他浏览器连续播放，无黑屏、无 Participant 替换。
- 浏览器恢复后 10 秒内重新出画；失败时展示明确错误，不自动重启共享 Publisher。

### RV-P0-002 前端 Room 重连成功但页面状态未恢复

**当前实现**

前端使用多个异步 Room 事件更新 `camera.room`、`hasVideo`、`remoteVideoTrack` 和 `status`。连接失败、主动断开旧 Room、LiveKit 自动重连、Track 重新订阅和 Vuex 回写可能并发发生。

**问题**

- 缺少明确的 Room generation/epoch，旧 Room 回调可能修改新 Room 状态。
- `Disconnected` 会立即清空 Track 状态，但新 Room 或 SDK 自动重连成功后不一定重新校准 UI。
- 没有以 `RoomEvent.Reconnected + TrackSubscribed/现有 publication` 完整恢复状态。
- Room 已 active 与视频元素已绑定是两个不同阶段，当前使用少量布尔值表达，容易误判。
- Track 已经存在但组件晚挂载时，可能没有重新 attach。

**影响**

- 服务端显示 Participant active，页面仍显示“未连接”。
- restart 后短暂出画，又被旧连接回调清空。
- 刷新页面可以恢复，导致问题难以复现和定位。

**整改要求**

1. 每次创建 Room 分配单调递增的 `roomGeneration`。
2. 所有 Room/Track 回调必须校验 `cameraKey + sessionId + roomGeneration`，过期回调直接忽略。
3. 将播放状态拆分为 `SIGNAL_CONNECTING/CONNECTED`、`TRACK_WAITING/SUBSCRIBED`、`RENDER_ATTACHED/PLAYING` 和 `FAILED`。
4. 监听 `Reconnecting/Reconnected/Disconnected/TrackSubscribed/TrackUnsubscribed`，但只由当前 Room 修改状态。
5. `Reconnected` 后枚举现有 RemoteTrackPublication；已订阅 Track 必须重新绑定当前视频元素。
6. 组件挂载、切换布局和弹窗重开时执行幂等 attach，不依赖 Track 事件再次到达。

**验收标准**

- LiveKit Participant 重新 active 后，UI 状态与 Track/DOM 实际状态一致。
- 旧 Room 延迟触发 `Disconnected` 时，不影响新 Room。
- 页面布局切换、弹窗关闭重开和视频墙重排后无需重新启动 Publisher。
- 不刷新页面连续完成至少 100 次断网/恢复注入。

### RV-P0-003 前端 restart/connect 缺少统一在途锁

**当前实现**

`restartCamera` 检查状态副本上的 `camera.restarting`，随后只修改该副本。`restarting=true` 没有在 HTTP 请求前立即提交为所有事件共享的状态，最终在 5 秒定时器中才回写 Vuex。`connecting` 同样可能因多个 camera 副本而失去互斥效果。

**影响**

- `TrackUnsubscribed` 与 `Disconnected` 连续到达时，两者都可能通过防重判断。
- 同一 session 在毫秒级发出两个 restart HTTP 请求。
- 两次请求生成不同 commandId，MQTT 客户端无法将其识别为 QoS 重投。

**整改要求**

- 使用模块级 `Map<sessionId, Promise>` 或 Vuex 中不可复制的 operation registry 管理 connect/restart/stop。
- 在发 HTTP 前原子登记 in-flight，完成或失败后按同一个 Promise 清理。
- 不使用固定 5 秒定时器作为并发锁。
- stop 的优先级高于 connect/restart；stop 开始后禁止新的恢复动作。
- 为同一 session 的恢复请求设置单调 generation，迟到响应不得覆盖较新状态。

**验收标准**

- 同时注入 `TrackUnsubscribed + Disconnected + session interrupted`，前端最多产生一个恢复操作。
- 20 个并发事件不得产生第二个 restart HTTP 请求。

### RV-P0-004 Media/Control 重启命令不幂等

**当前实现**

Media 每次执行 restart 都创建新的 `cmd_<uuid>`，写入 `REQUESTING_CLIENT` 并返回新的 `VideoStartCommand`。Control 收到命令后直接发布 MQTT，没有针对 session、源或启动阶段的合并保护。

**问题**

- `REQUESTING_CLIENT` 状态仍可再次 restart。
- 同一 session 的并发事务之间没有乐观锁、悲观锁或分布式锁。
- `clientRequestId` 未持久化，也未参与幂等。
- MQTT 设备侧只能过滤相同 commandId，不能过滤业务上相同但 commandId 不同的命令。

**影响**

- 同一 session 出现成对或连续 start。
- 机器人反复停止和启动 Publisher。
- session 当前 commandId 可能被后写事务覆盖，迟到状态无法准确归属。

**整改要求**

1. 定义 `startGeneration` 或 `publisherGeneration`，同一源只能递增发布。
2. `REQUESTING_CLIENT/ROOM_READY` 且命令未超时时，restart 返回当前 in-flight 结果，不创建新 commandId。
3. REST 支持并持久化 `clientRequestId/idempotencyKey`，相同 key 返回相同结果。
4. `VideoSession` 增加 `@Version`，并对源运行态记录使用数据库锁或唯一租约。
5. Control 发布 MQTT 前记录并检查 `sessionId + generation + commandId`，禁止重复发布。

**验收标准**

- 20 个并发 restart 只生成一个 commandId，只发布一条 MQTT start。
- 同一 idempotency key 重试得到完全相同的响应。
- 迟到的旧 generation 状态不能覆盖新 generation。

### RV-P0-005 同源启动期间可能创建多个 VideoSession

**当前实现**

会话复用只查询 `ROOM_READY/STREAMING/IDLE_WAIT`。`INIT/REQUESTING_CLIENT/INTERRUPTED` 不属于可复用状态；创建过程是普通“查询后插入”，没有源粒度并发保护。Room 名称又由源、设备、通道和清晰度确定，不包含 sessionId。

**触发方式**

1. 第一个请求创建 `INIT`。
2. Control 请求 start，状态进入 `REQUESTING_CLIENT`。
3. 第二个 `reuse=true` 请求到达。
4. 第二个请求查不到可复用会话，创建另一个 session。
5. 两个 session 指向同一个 Room。

即使将更多状态加入复用集合，两个请求同时执行“先查后插”仍可能创建重复记录，因此只改状态集合不能彻底解决。

**影响**

- viewer 被分散到不同 session，`viewerCount` 失去源级意义。
- 同 Room 存在多个生命周期控制者。
- 两个 session 可能各自下发 start、stop 和 restart。
- 同一个 Publisher Identity 可能被重复连接。

**整改要求**

- 建立独立的 `VideoSourceRuntime` 或等价源运行态记录，以以下字段构成唯一键：

```text
sourceType + sourceId + deviceId + channel + quality
```

- 所有 session/viewer 引用同一个 source runtime；Room、Publisher generation 和发布状态归 runtime 所有。
- 数据库唯一约束负责最终防重，应用层捕获唯一冲突后读取已有 runtime。
- `INIT/REQUESTING_CLIENT/ROOM_READY/STREAMING/INTERRUPTED/IDLE_WAIT` 均视为源已被占用，差异只体现在恢复动作，不得另建 Room 所有者。

**验收标准**

- 50 个并发 start 最终只有一个 source runtime、一个 Room、一个 Publisher 和一条有效 start。
- 所有调用方获得可绑定到同一 runtime 的 session/viewer 结果。

### RV-P0-006 本地播放失败/人工刷新被实现为 stop/start 共享会话

**当前实现**

- `LeftVideo.resumeVideo()` 在 `HTMLVideoElement.play()` 失败或元素不存在时调用 `startCamera()`。
- `LeftVideo.refreshVideo()` 对已有 session 先执行 `stopCamera()` 再 `startCamera()`；即使 stop 失败也继续 start。
- `play()` 失败可能只是浏览器自动播放策略、DOM 替换、页面不可见或 Track 未 attach，并不代表后端会话或 Publisher 失效。

**影响**

- 本地 UI 问题会进入 Control/Media/MQTT 链路，扩大为共享资源变更。
- stop 失败后继续 start，可造成旧 viewer 未释放、新 viewer/session 又创建。
- 用户连续点击刷新可触发重复启动、Room 误删除和 Participant 替换。

**整改要求**

1. 将“重新播放”定义为前端本地操作：重新枚举 Track、attach 新 DOM、调用 `play()`，必要时重建 viewer Room。
2. 普通刷新不得 stop session，不得调用 Publisher restart。
3. 人工“重启设备推流”作为单独的运维能力，需要二次确认、权限、操作原因和审计日志。
4. stop 失败后不允许无条件 start；必须根据返回的服务端事实决定重试。

**验收标准**

- 模拟 `video.play()` 拒绝、DOM 重建和用户点击刷新，均不产生 start/stop/restart HTTP 和 MQTT 命令。
- 仅重建 viewer Room 即可恢复画面，其他 viewer 无中断。

### RV-P0-007 `startCamera` 可将新 session 错绑到旧 Room

**当前实现**

`startCamera()` 在调用 create API 之前，先基于 store 中旧 `camera.room` 计算 `reuseRoom`。API 返回后会覆盖 `camera.session`；如果事先判定 `reuseRoom=true`，就直接 attach 旧 Room 的 Track，没有比较新旧 `sessionId/roomName`。该方法在有可用 Room 时仍每次调用 create API，并且会无条件清除 `restarting`。

**影响**

- Media 因竞态或状态不可复用而返回新 session 时，store 记录新 session，实际还连着旧 Room。
- 旧 Room 回调、新 session 事件和 heartbeat 同时更新一个 camera，最终表现为服务端 active 而页面“未连接”。
- 新的 start 调用可以提前解除正在执行的 restart 互斥状态。

**整改要求**

- 先按 `cameraKey` 进入统一 start in-flight registry，同一条件的调用复用 Promise。
- 已有当前 session 和可用 Room 时，新增 viewer/consumer 只做本地 attach 与服务端 viewer heartbeat/attach，不重新 create session。
- create 返回后必须核对 `sessionId + roomName`；不一致时将旧 Room 当作过期 generation 有序断开，再连接新 Room。
- 只能由对应 operation 的 `finally` 清理自己的 in-flight 状态，禁止 start 顺手清除 restart。

**验收标准**

- 服务端故意返回不同 session/Room 时，前端最终 session、Room、Token、Track 四者一致。
- 对已播放摄像头连续调用 20 次 start，只增加必要的 attach target，不新建 Room 连接和 session。

### RV-P1-001 Session 释放与 Room 释放混在一起

**当前实现**

`releaseIdleSession(sessionId)` 只检查当前 session：

- 状态是否为 `IDLE_WAIT`；
- 当前 session 的 `viewerCount` 是否为 0；
- 当前 session 自己是否有 `STARTING/ACTIVE` 对讲。

检查通过后直接 unpublish Track、删除 Room、关闭 session，并返回机器人 stop payload。它没有查询相同 roomName 的其他 session、viewer、对讲或录像占用。

**影响**

在重复 session 已经形成时，一个旧 session 的定时释放可以删除另一个活跃 session 正在使用的 Room，导致所有 Participant 和 Track 同时消失。

**整改要求**

- Room 和 Publisher 生命周期归 source runtime 所有，不能由单个 viewer session 直接删除。
- 释放前聚合检查 runtime 下全部 viewer、对讲、录像、启动操作和有效 Track。
- 引用数归零后先进入 `IDLE_WAIT`，到期再次带版本号检查；只有版本未变化才能关闭。
- 删除 Room 与发送 stop 使用同一 release generation，重复执行必须幂等。

**验收标准**

- 构造两个 session 指向同一 Room，释放其中一个不得删除仍有占用的 Room。
- viewer、对讲或录像任意一项存在时均不得停止 Publisher。

### RV-P1-002 机器人视频状态可能与 LiveKit Track 事实脱节

**当前实现**

生产设备端上报 `streaming/track_published` 后，Media 对 `ROBOT_CAMERA` 直接进入 `STREAMING`。后续复用会话时，`hasPublishedTrack()` 对机器人源只检查数据库中 `trackSid/trackName` 非空，不调用 LiveKit Room API。Media 当前也没有消费 LiveKit Webhook。

即使调用 Room API，`resolveVideoTrackSid()` 在 preferred SID 不存在时会返回房间内“第一条视频 Track”，没有校验预期 Publisher Identity、Participant SID 和 generation。`MediaTrackService` 保存的 participant identity 也是根据 session 字段合成，不是 LiveKit 事实。

**影响**

- 业务状态可能是 `STREAMING`，但 Room 中已经没有 Publisher 或视频 Track。
- 前端拿到可复用 session，却长期等不到 Track。
- 自动恢复依赖机器人 MQTT 状态，无法及时识别 LiveKit 单侧中断。

**整改要求**

- 引入 LiveKit Webhook，处理 participant joined/left、track published/unpublished 和 room finished。
- 对关键状态增加 Room API 对账；Webhook 断档时由周期 reconcile 补偿。
- 业务状态保存 LiveKit 返回的真实 Participant Identity/SID、Track SID、最后媒体事实时间和 generation，不再合成事实字段。
- Room API 对账必须按当前 runtime 的预期 publisher identity 精确查找，禁止使用房间中任意第一条视频 Track。
- `STREAMING` 必须同时满足当前 generation Publisher active 且视频 Track published。

**验收标准**

- 强制踢出机器人 Participant 后，Media 在 10 秒内进入 `INTERRUPTED` 并启动一次受控恢复。
- MQTT 报 streaming 但 LiveKit 无 Track 时不得向前端宣称可播放。

### RV-P1-003 UDP 候选存在但部分播放端长期选择 TCP

**线上现象**

LiveKit 对外产生 `211.137.109.150:50000-50100/UDP` 候选，但 Windows 现场样本最终选择 `TCP 7881`。同一现场也观察到其他客户端成功使用 UDP，因此不能简单判断为服务端 UDP 全局关闭。

**可能范围**

- 客户端出口网络或安全软件阻止 UDP。
- 公网 NAT/端口映射只完成入站配置，返回路径、会话保持或上游 ACL 不完整。
- LiveKit `external_ip`、Docker UDP 映射与公网地址不一致。
- 多层 NAT、运营商网络或企业代理导致 UDP ICE 检测失败。

**影响**

- WebRTC 媒体复用 TCP，丢包时触发队头阻塞。
- 三路视频同时播放时更容易出现带宽拥塞、卡顿和 DTLS 超时。
- TCP 自动降级本身可用，但不能作为长时间多路播放的首选路径。

**整改要求**

1. 从真实大屏网络对完整 UDP 端口段执行双向验证，不能用普通 `nc -z` 的成功作为 UDP 可用结论。
2. 在服务端同步抓包，确认客户端探测包到达且响应能够返回。
3. 使用 Chrome `chrome://webrtc-internals` 保存选中 candidate pair、RTT、丢包、NACK、PLI 和可用带宽。
4. 核对云防火墙、宿主机防火墙、NAT、Docker 映射和 LiveKit advertised IP。
5. 保留 TCP `7881` 作为降级通道，并对 TCP 播放单独执行弱网恢复测试。

**验收标准**

- 允许 UDP 的大屏网络中，三个 Room 均选中 `udp` candidate pair。
- UDP 被明确阻断时可降级 TCP，并在短时网络抖动后恢复，不出现永久“未连接”。
- 监控能够按 Room/Participant 展示最终协议为 UDP 或 TCP。

### RV-P1-004 弱网与多路播放缺少明确的降载策略

**线上现象**

`camera01` 曾因 LOSS 将可用带宽估算降至约 `170 kbps`，Stream Allocator 进入 `DEFICIENT`。当前页面同时订阅三路视频，视频源默认可能持续发布高于现场可用带宽的码率。

**整改要求**

- 视频墙默认使用 sub 码流，单路放大后再切 main。
- 明确机器人 RTSP 主/子码流分辨率、帧率和目标码率上限。
- 评估并启用适合当前 Publisher 的 Simulcast/SVC；不支持时按页面可见性暂停不需要的订阅。
- 收集 inbound-rtp 丢包、jitter、framesDecoded、freezeCount 和 keyframe 指标。
- 弱网进入阈值后先降清晰度或暂停非主画面，不自动重启 Publisher。

**验收标准**

- 三路 sub 码流总码率不超过现场网络容量预算的 70%。
- 注入 5% 丢包和 300 ms RTT 时，主画面可恢复且不触发共享 Publisher restart。

### RV-P1-005 状态事件缺少 generation，迟到消息可覆盖新状态

**问题**

启动、重启和切换都会产生新的发布尝试，但客户端状态主要按 sessionId 更新。旧 Publisher 或旧命令的迟到 `publishing/streaming/failed/stopped` 可能覆盖新发布尝试的状态。

**整改要求**

- start、stop、restart、switch 和 status 统一携带 `runtimeId + generation + commandId`。当前 `VideoStatusMessage` 连 `commandId` 都没有，该 DTO、MQTT 订阅转发和 Media 状态接口必须同步升级。
- Media 只接受当前 generation 的状态；旧 generation 仅记录审计日志。
- stop 必须指定要停止的 generation，不能让旧 stop 关闭新 Publisher。

**验收标准**

- 人工乱序投递旧 streaming/failed/stopped，不改变当前发布状态。

### RV-P1-006 viewer 心跳会掩盖 Publisher/Track 发布超时

**当前实现**

`VideoSessionTimeoutScheduler` 通过 `status + updatedAt < threshold` 查找 `REQUESTING_CLIENT/ROOM_READY` 超时会话；而前端每 5 秒发送 viewer heartbeat，`heartbeat()` 每次都更新同一个 session 的 `updatedAt`。

**影响**

- 只要页面仍在心跳，永远没有 Track 的启动就可能永远达不到超时阈值。
- 前端持续显示“未连接/正在连接”，Media 不进入 `TIMEOUT/FAILED`，也不会给出可恢复的明确错误。

**整改要求**

- 发布超时只使用 `commandRequestedAt` 或独立 `publishDeadlineAt`，不得使用通用 `updatedAt`。
- 心跳只更新 viewer 的 `lastHeartbeatAt`；如需保存 session 活跃时间，使用独立 `lastViewerActivityAt`。
- 超时更新必须带 `generation` 条件，避免旧扫描结果将已成功的新 generation 置为失败。

**验收标准**

- viewer 保持 5 秒心跳但 Publisher 不发布 Track，会话在配置超时时间加一个扫描周期内进入明确失败状态。
- Track 在超时边界成功发布时，只有一个带版本条件的终态生效。

### RV-P1-007 viewer 无唯一约束且过期释放状态不完整

**当前实现**

- `addViewer()` 采用“先查再插入”，但 `media_session_viewer` 没有 `sessionId + participantIdentity + active` 唯一约束。
- `removeViewer()` 只关闭查到的第一条活跃记录；竞态形成的重复 viewer 可继续计数。
- 心跳过期的 `closeViewer()` 只在 session 状态为 `STREAMING` 时转入 `IDLE_WAIT`。`REQUESTING_CLIENT/ROOM_READY/INTERRUPTED/FAILED/TIMEOUT` 在 viewer 归零后可能长期滞留，而 idle release 又只扫描 `IDLE_WAIT`。
- Media 服务每次启动都会关闭数据库中全部 active viewer，却没有与浏览器 Room 连接建立恢复代际。

**整改要求**

1. 引入稳定 `viewerLeaseId`，数据库对 `runtimeId + viewerLeaseId` 建唯一约束；heartbeat 使用 upsert/条件更新。
2. stop 和过期必须关闭该 lease 的全部异常重复记录，并从表内实时聚合引用数，不信任可漂移的 `viewerCount` 缓存值。
3. 任何非终态 session/runtime 在所有引用归零后都必须进入统一的 idle/release 状态机。
4. 服务重启不应立即将所有 viewer 判死；使用 lease TTL 自然收敛，或为重启建立短暂 grace period，允许活跃浏览器续租。

**验收标准**

- 50 个并发心跳只有一个 active viewer lease。
- 所有中间/失败状态在最后 viewer 过期后均能进入 idle 并安全释放。
- 重启 Media 后仍在心跳的页面不会导致 Publisher 停止或 Room 被删除。

### RV-P1-008 定时恢复/释放无多实例单执行者保护

**当前实现**

Control 每 5 秒查询 interrupted/idle 候选并直接执行 restart/release；Media 也每 5 秒执行超时和 viewer 清理。代码中没有 ShedLock、分布式租约、数据库 `SKIP LOCKED` 领取或 generation CAS。Java `synchronized` 仅限制单 JVM。

**影响**

- 生产一旦水平扩容，多个 Control 实例可对同一 session 同时下发 restart/stop。
- 多个 Media 实例可对同一 viewer/session 同时过期或标记超时。
- 即使当前 compose 只启动一个实例，代码也不具备无损扩容边界。

**整改要求**

- 对每个 runtime/generation 采用数据库原子 claim：只有从 `INTERRUPTED -> RECOVERING` 或 `IDLE_WAIT -> RELEASING` 成功的执行者才能产生外部副作用。
- 定时任务全局锁可作为短期止损，但最终仍要求单 runtime 的状态 CAS 和副作用幂等。
- 所有 claim 必须有超时和接管机制，避免执行者崩溃后永久卡在 `RECOVERING/RELEASING`。

**验收标准**

- 同时启动 2 个 Control 和 2 个 Media 实例，单次中断只产生一条有效 start，单次 idle 只产生一条 stop 和一次 Room delete。
- claim 执行者在副作用前崩溃，租约超时后可由其他实例幂等接管。

### RV-P1-009 BFF 与跨服务调用的重试边界需固化

**当前边界**

`bigscreen-bff` 当前主要是鉴权后的 REST/WebSocket 透传，不承载媒体流，也不应持有 VideoSession/Room/Publisher 状态。此边界是正确的，但 start/restart/stop 在端到端幂等落地前属于非幂等变更，任意一层的超时自动重试都可创建重复副作用。

**整改要求**

- BFF 只负责传递身份、`traceId/clientRequestId` 和原始返回状态，不实现视频恢复决策。
- 在服务端幂等之前，BFF、Nginx、HTTP 客户端不得对 start/restart/stop 自动重试；仅 GET/明确幂等查询可重试。
- 幂等完成后，重试必须复用同一 `clientRequestId`，不得每次生成新 key。

**验收标准**

- 模拟 Control 已执行但 BFF 读取超时，重试后仍只存在一个 session/runtime 和一条设备命令。
- BFF 不出现 Room 管理、Track 判定或 MQTT 补发逻辑。

### RV-P2-001 可观测性不足，线上只能跨容器人工拼日志

**当前缺口**

- 前端未统一记录 Room generation、连接状态变化、Track SID 和选中 ICE candidate pair。
- 服务端日志缺少贯穿全链路的统一关联字段。
- 页面只显示“未连接”，没有区分信令失败、ICE 失败、无 Publisher、无 Track、未绑定 DOM 或解码冻结。
- 缺少重复 start、Duplicate Identity、DTLS timeout、Room 误删除和重连耗时告警。

**整改要求**

统一以下关联字段：

```text
traceId, clientRequestId, userId, clientId,
sourceRuntimeKey, sessionId, roomName, roomGeneration,
publisherGeneration, commandId,
publisherParticipantSid, viewerParticipantSid, trackSid,
connectionType, selectedCandidatePair, disconnectReason
```

前端提供可下载的诊断快照，至少包含最近 200 条 Room/Track 状态事件和当前 WebRTC stats 摘要；不得包含 Token、RTSP 凭据或敏感 SDP。

**告警建议**

| 指标 | 告警条件 |
| --- | --- |
| 同 session start 次数 | 60 秒内大于 1 |
| 同 source active runtime | 大于 1 |
| `DUPLICATE_IDENTITY` | 任意生产发生即告警 |
| viewer reconnect latency | P95 大于 10 秒 |
| `PEER_CONNECTION_DISCONNECTED` | 5 分钟内同 client 大于 3 |
| TCP 播放占比 | 超过现场约定阈值 |
| Room 删除时活跃引用数 | 必须恒等于 0 |

### RV-P2-002 自动化测试与上线验收不足

**当前缺口**

现有测试没有覆盖本次核心竞态：

- 同源并发创建 session。
- `TrackUnsubscribed + Disconnected` 同时发生。
- 旧 Room 回调覆盖新 Room。
- restart HTTP 并发幂等。
- 两个 session 共享 Room 时的释放保护。
- 机器人收到不同 commandId 的重复 start。
- UDP/TCP 两种传输的长时间三路播放。

整改完成后必须补充第 8 节测试矩阵，未执行或失败不得以“刷新可恢复”作为上线接受条件。

### RV-P2-003 前端“未连接”状态过度简化

`VideoBox` 在没有 `hasVideo` 时主要显示“未连接”，又将 `STREAMING/IDLE_WAIT` 等多个业务状态归入“正在连接”。页面无法告诉用户究竟是信令连接、ICE、Publisher、Track、订阅、DOM attach、自动播放还是解码冻结失败。

**整改要求**

- 展示分层状态和可操作错误码，不向普通用户暴露 Token、SDP 和内部网络信息。
- “重试播放”只修复 viewer；只有运维诊断显示 Publisher/Track 真实缺失时，有权用户才能选择“重启推流”。
- 前端错误码、Media 状态和 LiveKit 断开原因建立映射，并纳入诊断快照。

**验收标准**

- 任意黑屏可在一次诊断快照中定位到上述七个阶段之一，不再只有“未连接”。

## 5. 目标状态与所有权模型

### 5.1 三类对象必须分离

| 对象 | 粒度 | 所有者 | 生命周期 |
| --- | --- | --- | --- |
| ViewerSession | `userId + clientId + sourceRuntime` | Media | 单浏览器观看和心跳 |
| SourceRuntime | `sourceType + sourceId + deviceId + channel + quality` | Media | Room 与 Publisher 的唯一运行态 |
| BrowserRoomConnection | `clientId + roomGeneration` | robot-ui | 单浏览器 LiveKit 连接与 Track 绑定 |

单个 ViewerSession 的离开只能减少引用；不能直接关闭 SourceRuntime。单个 BrowserRoomConnection 的失败只能恢复浏览器连接；不能直接重启 Publisher。

### 5.2 目标恢复决策

```text
浏览器 Disconnected
  -> 前端重连当前 Room
  -> 重签 viewer Token（仅 Token 失效时）
  -> 重新订阅并 attach Track
  -> 不发送 MQTT start

Media 确认 Publisher/Track 消失
  -> SourceRuntime 进入 INTERRUPTED
  -> 生成唯一的新 publisherGeneration
  -> Control 发送一条 MQTT start
  -> 机器人受控替换 Publisher
```

### 5.3 Room 释放决策

```text
viewerCount == 0
and intercomCount == 0
and recordingCount == 0
and startOperationCount == 0
and publisherGeneration 未变化
and idle deadline 已到
  -> stop 当前 Publisher generation
  -> 等待或确认 Participant/Track 离开
  -> delete Room
  -> close SourceRuntime
```

### 5.4 模块整改边界

| 模块/系统 | 必须负责 | 明确不负责 |
| --- | --- | --- |
| `robot-ui` | viewer Room 连接、Track 订阅/attach、播放状态、本地重连、WebRTC stats | 不以浏览器事件判定共享 Publisher 失效，不自动下发设备 restart |
| `bigscreen-bff` | 鉴权代理、身份/关联 ID 透传、WebSocket 事件转发 | 不承载媒体流，不复制会话状态机，不对非幂等变更盲目重试 |
| `control-service` | 权限、业务入口、幂等命令发布、设备状态转发 | 不创建第二份 Room/runtime 真相，不根据 viewer 断线自主恢复 Publisher |
| `backend` | SourceRuntime/ViewerLease 真相、Room/Track 对账、generation、引用计数、超时与释放 | 不依赖前端布尔状态或设备端单方上报作为 Track 最终事实 |
| `media-common` | 命令/状态 DTO 的 `runtimeId/generation/commandId` 契约 | 不容忍调用方各自定义同名字段的不同含义 |
| LiveKit/部署 | Room/Participant/Track 事实、Webhook、ICE 候选、UDP/TCP 通道与指标 | 不承载业务 viewer 计费/引用所有权 |
| 生产设备端（仓库外） | 按协议执行幂等 start/stop，上报当前 generation 和发布结果 | 其具体代码改造不在本仓库；`python-client` Demo 不作为代替实现 |

关键边界规则：只有 `backend` 基于 LiveKit 事实与 runtime 状态机才能决定是否恢复 Publisher；`control-service` 只执行已领取的命令；浏览器始终只恢复自身 viewer 连接。

## 6. 分阶段整改计划

### 第一阶段：立即止损，P0

1. 前端取消浏览器异常自动调用 Publisher restart。
2. 增加 Room generation 和 connect/restart/stop in-flight registry。
3. 补齐 Reconnected 后的 Track 枚举、重新订阅和 DOM attach。
4. Media 合并 `REQUESTING_CLIENT/ROOM_READY` 阶段的重复 restart。
5. Control 对同 session/generation 的 MQTT start 防重。
6. 修正发布超时时钟，不再被 viewer heartbeat 掩盖。
7. 增加 Duplicate Identity、重复 start 和 viewer reconnect 日志。

### 7.1 第一阶段实施记录（2026-09-11）

| 整改项 | 已落地行为 | 异常与边界 |
| --- | --- | --- |
| viewer 恢复 | `TrackUnsubscribed` 不再 restart Publisher；`Disconnected` 仅换取 viewer token 并重建当前 Room；`Reconnected` 重新绑定已有 Track；记录 session/Room/generation 及 `DUPLICATE_IDENTITY` 分类 | 连接期间同时收到 `Disconnected` 时，等当前 connect Promise 收口后再发起一次 viewer 重连；停止后不重连 |
| 前端并发 | 同摄像头 `start/connect/restart/stop` 分别共享在途 Promise，stop 优先 | 新 session/Room 不复用旧 Room；过期 Room 回调由 `roomGeneration` 隔离 |
| 本地播放 | 人工刷新和 `video.play()` 失败只做 Track attach/viewer 重连 | 不调用 session stop/start，不影响其他观看端 |
| Media 命令合并 | `INIT/REQUESTING_CLIENT/ROOM_READY/INTERRUPTED` 可进入同源复用查找；启动/重启先锁定 session 行，发布等待窗口内返回同一 `commandId` | 本阶段不新增表和源唯一索引；真正同时的跨 Media 实例“先查后插”新会话竞态由 MS-02 解决 |
| Control 命令防重 | 近期 2048 个 `commandId` 仅发布一次 MQTT start，发布异常时释放占位以便重试 | 当前为 JVM 内防重；多 Control 实例间的单执行者由 MS-07/CS-03 解决 |
| 发布超时 | 候选查询改用 `commandRequestedAt`，落状态前再校验当前 `commandId`、状态和时间 | viewer heartbeat 即使持续刷新 `updatedAt`，也不会掩盖发布超时；旧命令扫描不能将新命令标记失败 |
| 重启锁冲突 | 删除应用启动完成后强制关闭全部 viewer 的逻辑；历史 viewer 统一由 TTL 清理；restart 不再刷新 viewer 占用；TTL 清理改为带心跳阈值的单行条件更新且不再用一个事务覆盖全部 viewer | 服务重启期间，正在恢复的浏览器心跳不会与全量清理形成多行锁环；扫描后已经续租的 viewer 不会被过期快照误关；viewerCount 在 TTL 窗口内可能短暂包含尚未续租的历史 viewer，这是延迟释放而非资源误删 |

## 9. 上线门禁与验收指标

以下条件全部满足后，实时视频整改版本才能结束灰度：

1. P0 问题全部关闭，并有自动化或可重复的故障注入证据。
2. 单浏览器网络异常不会产生机器人 start/restart。
3. 同源并发启动只能得到一个有效 SourceRuntime 和 Publisher。
4. 生产日志中连续 24 小时无 `DUPLICATE_IDENTITY`、无 60 秒内重复 start。
5. 三路视频 8 小时长稳测试无永久黑屏；短暂中断后 10 秒内恢复。
6. 页面不刷新完成网络切换、LiveKit 重连和 Track 重新绑定。
7. Room 删除时 viewer、对讲、录像和启动操作引用数全部为 0。
8. UDP 可用网络优先选择 UDP；TCP 降级场景有独立通过记录。
9. 所有失败均能从诊断数据区分：信令、ICE、Publisher、Track、订阅、DOM 绑定或解码问题。
10. Token、RTSP 地址、密码和完整 SDP 不进入普通生产日志。

## 10. 灰度与回滚要求

- 第一阶段先灰度单个测试机器人和单个大屏；若涉及生产设备端协议升级，由对应外部团队独立灰度。
- 前端与后端协议变更必须向后兼容一个灰度周期；generation 字段未升级的客户端不得进入多 Publisher 争抢状态。
- SourceRuntime 数据模型迁移前备份相关表，并提供只回滚应用、不删除新表数据的回滚方案。
- 每次灰度记录版本、机器人 ID、浏览器版本、网络类型、最终 ICE 协议和测试 sessionId。
- 发现重复 start、Duplicate Identity 或 Room 误删除时立即停止扩大灰度。
