## 1. 测试目标

验证实时视频从前端创建会话、服务端创建 Room 和签发 Token、MQTT 下发、机器人 RTSP 探测与推流、LiveKit Track 订阅到停止释放的完整生命周期，并覆盖多人复用、异常断线、双光切换、抓拍、录像和对讲。

## 2. 测试范围

- 单路视频创建、播放、停止和空闲释放。
- 最多 16 路视频墙及同一路多人复用。
- `visible`、`thermal` 与 `main`、`sub` 切换。
- RTSP 探测失败、Track 发布超时、机器人离线和恢复。
- WebSocket 状态事件与断线恢复。
- 抓拍、录像和文件服务联动。
- HTTPS/WSS 局域网访问和 LiveKit 媒体连通性。
- 视频会话内双向语音对讲。
- 固定摄像头单路/批量启动、主子码流回退、重启和释放。
- 固定摄像头 9 路并发启动、相同 RTSP 健康探测合并、真实 LiveKit Track 确认和首轨超时清理。
- 验证 BFF `/ws/media` 与直连 Media `/ws/media` 的不同上游语义。

## 3. 测试环境

测试前确认以下组件可用：

```text
MySQL
Redis
EMQX
LiveKit Server
MinIO
FFmpeg/ffprobe
至少一台机器人客户端和一个可访问的 RTSP 视频源
如验收固定摄像头，还需 Management 摄像头档案、登录用户授权和 Fixed Camera Gateway
```

局域网测试还需要可信任的 HTTPS 证书、可访问的 LiveKit TCP/UDP 端口以及正确的 ICE candidate。

## 4. 准入条件

1. 需求、设计和接口文档已确定本次测试范围。
2. 所有受影响模块完成构建和单元测试。
3. 测试环境变量、机器人 ID、摄像头 ID 和 RTSP 地址已登记。
4. 不使用真实生产凭据或未授权设备。
5. 已准备正常、离线、RTSP 不可达和重复请求等测试数据。

## 5. 测试策略

### 5.1 构建与自动化测试

### 5.2 接口与协议测试

- 校验 HTTP 状态码、响应 DTO 和错误响应。
- 校验 MQTT Topic、Payload、status 和重复 `commandId`；当前视频协议没有独立 ACK Topic。
- 校验目录租约版本、最长 300 秒有效期、空目录收口、过期记录过滤和错误 Gateway ID 拒绝。
- 校验 WebSocket 事件名称、载荷结构、顺序和重复事件。
- 校验 Token 权限，publisher 只能发布，viewer 只能订阅。
- 校验固定摄像头已建立的推流超过 publisher Token 有效期后仍持续播放；真实推流进程退出时进入
  `INTERRUPTED` 并由现有恢复调度重新签发凭证，不得按 Token 到期时间主动断流。
- 校验 LiveKit Webhook 的 JWT issuer、签名和原始正文 SHA-256 摘要；篡改正文必须返回 401。
- MQTT 上报 `streaming` 但 Room 中无预期 Publisher Track 时不得进入 `STREAMING`；Webhook 漏投时周期对账应在配置窗口内收敛。
- 房间存在其他 Publisher 的视频 Track 时不得误认；稳定 Track 周期对账不得重复写库或广播 `streaming`。
- 已确认 `STREAMING` 后重复或迟到的设备 `room_ready/streaming/failed` 不得覆盖 LiveKit 媒体事实。
- `IDLE_WAIT` 仍需核对 Track；仅有对讲或录像占用时 Track 消失，也应进入恢复候选而非永久中断。

### 5.3 集成与端到端测试

```text
前端
  -> Control Service
  -> Media Service
  -> EMQX
  -> 机器人客户端
  -> RTSP
  -> LiveKit
  -> 前端订阅
```

测试时记录 `sessionId`、`commandId`、`roomName`、`trackSid`、机器人 ID 和摄像头 ID，便于跨服务核对日志。

### 5.4 异常与恢复测试

- RTSP 不可达或探测超时。
- publisher 启动失败或运行中退出。
- 丢弃 Webhook、重复投递 Webhook、踢出 Publisher、仅保留非预期 Publisher Track。
- MQTT 重复消息和连接中断。
- 浏览器异常关闭且未发送停止请求。
- 机器人离线后重新上线。
- WebSocket 和 LiveKit 信令短暂断开。
- Publisher 以相同 identity 重新接入导致 Track 替换时，旧 Track 迟到退出不得清空新 Track；
  观看端必须自动恢复，不刷新页面、不下发共享 Publisher restart。
- Viewer Room 彻底断开且首次换证或重连失败时，应按封顶退避持续恢复；停止观看或会话关闭后必须取消重连。
- 连续播放超过两个 JWT 生命周期，验证 WebSocket 静默换证重连不重建页面、不清空视频墙、
  不断开既有 LiveKit Room；确认撤权事件仍会停止对应失权视频。
- 人为制造 BFF 时钟落后或模拟 Management 返回 `401`，确认 BFF 使用 `4001` 而非 `4003`
  关闭，前端静默换证且不显示“权限服务暂不可用”。
- 最后一个 viewer 离开后的延迟释放。
- 同时启动两个 Media 实例时，发布超时、viewer TTL、无观看者收口和 Track 对账只有一个实例执行；停止当前执行者后，另一实例在租约到期后接管。
- 固定摄像头未启用、无码流、Gateway 不可达和 Management 不可达。
- 登录会话存在时确认 BFF 每 30 秒以内续租；关闭最后一个会话后，确认租约过期并发布空目录，
  Gateway 不再周期探测。该结果应显示 `UNKNOWN`，不按 7×24 小时监测缺陷处理。
- 确认 Gateway 只使用 MQTT 短租约目录，不配置 Management 长期凭据或直连查询路径。
- 检查 MQTT 日志不应泄露 publisher Token 或固定摄像头 RTSP URL；当前代码未满足时记为上线阻断风险。
- 固定摄像头人工关闭时，左侧选中态和宫格播放意图必须立即清除；同时注入装备状态刷新，摄像头不得被自动重新拉起。
- 固定摄像头尚在启动时立即关闭，迟到的启动响应不得恢复左侧选中态、宫格或活动会话；存在其他消费者时只释放当前消费者。
- 快速执行 A→B→C 槽位替换并延迟 A/B 的停止响应，最终只能播放 C；旧停止失败也不得阻断 C 启动。
- 固定摄像头多界面同时观看时，关闭一个宫格、缩小分屏或销毁页面不得停止其他界面的播放；最后一个消费者关闭后才释放共享会话。
- 任务结束、任务装备同步和分屏缩小时应一次性撤销目标槽位意图，再异步停流；保留槽位不停止、不重启，移除槽位不得被状态监听恢复。
- 对同一套关闭、替换、启动失败和页面销毁操作回归机器人视频，确认机器人仍使用原有默认消费者载荷，播放、恢复、对讲及录像行为不变。
- 对讲挂断后确认浏览器麦克风占用标识消失；仍在观看时视频不中断，纯通话时 Room 正常断开。
- 分别验证主动挂断、对端结束、地图控制弹窗关闭、页面退出、现场呼叫结束和用户注销，所有路径均不得残留本地麦克风 Track。
- 页面退出只清理当前页面的对讲和实际观看视频，不得停止仅后台执行的独立录像；用户注销或身份刷新应额外清理全部录像、音频 Room 和业务 WebSocket。
- 注入麦克风授权拒绝、LiveKit 连接失败、发布失败、远端 Track `detach` 异常和 Room `disconnect` 异常；已创建的服务端对讲必须回滚，本地麦克风停止与其余资源清理不得被单点异常阻断。
- 快速重复点击通话按钮时，同一摄像头只能存在一条开始或结束流程，不得因并发响应回滚另一条已成功通话。
- 在对讲启动请求延迟期间分别关闭地图弹窗、切换页面、注销和点击另一摄像头通话；原请求必须取消或回滚，迟到响应不得重新开启麦克风，跨摄像头不得形成两条并行通话。
- 在 LiveKit Room `connect` 未完成时挂断、切页或收到对端结束事件；清理不得等待 SDK 超时，连接迟到成功后必须再次断开且不得发布麦克风。
- 在现场呼叫点击接听后、服务端返回 accepted 前立即尝试普通机器人对讲，反向也执行一次；后发流程必须被拒绝，不得弹出第二次麦克风授权。多合一通话不参与此互斥回归。
- 注入 `intercom/stop` 超时和 5xx，验证界面立即回到未通话、浏览器麦克风标识消失、本地 Room/音频元素被释放，后续可再次发起通话；同时确认后端心跳超时最终释放残留占用。
- 被叫接听连接 LiveKit 或启用麦克风期间收到结束/失败事件，接听启动必须取消、服务端占用必须回滚，迟到创建的麦克风轨道必须停止。
- 分别注入 LiveKit 最终断线、机器人离线和授权资源移除，确认本地麦克风立即停止、远端音频元素清理、对讲状态回到空闲；普通视频 Room 的既有远端音频不得被启动失败回滚误清理。
- 通话中仅执行麦克风静音时，允许浏览器继续显示麦克风占用；取消静音后应复用原 Track，不重新创建通话会话。
- 分别注入固定摄像头停用、配置不完整、Gateway 离线、RTSP 不可达、Publisher 失败/退出和发布超时，确认实时监控宫格与 GIS 弹框显示一致的具体文案；机器人视频仍显示原有通用文案。
- 固定摄像头状态增量事件只携带当前用户有权资源的 `gatewayHealth/streamHealth` 状态与枚举原因码，不得包含 `gatewayId`、RTSP 地址、凭据或原始错误信息。
- 固定摄像头首次启动失败应保留宫格播放意图和会话，Gateway/RTSP 恢复后无需刷新页面即可恢复；机器人启动失败仍沿用原槽位清理逻辑。
- 分别验证固定摄像头 `start` 复用健康 Publisher、`restart` 强制替换旧 Publisher 且保留同源会话绑定；任何 Viewer 事件不得发布固定摄像头 restart。
- Gateway `OFFLINE -> ONLINE` 每次状态跃迁最多触发一轮固定源恢复，RTSP 恢复只触发对应 source；首次健康快照、重复 ONLINE/AVAILABLE 心跳、其他机器人遥测及无 viewer/录像占用时不得启动 Publisher。
- Gateway 心跳恢复但 LiveKit Track 仍健康时不得强制重启；Track 确实缺失时才生成新命令。
- 同 runtime 存在多个有观看者的 `FAILED/TIMEOUT` 会话时，只启动一个 Publisher，Track 恢复后所有占用会话均回到 `STREAMING`。
- 模拟 restart 已发送但 stop 先到 Gateway，后到的同 `sessionId` start/restart 必须被终止水位拒绝，不得复活 Publisher。
- 模拟 Gateway 断线期间恢复命令丢失，Control 应使用原 `commandId` 补发，Gateway 重新执行一次；并发恢复重复补发同一命令时只执行一次。

### 5.6 Management 暂不可升级时的 RTMP 联调

机器人和 RTSP 视频源均不可用、且 Management 暂时不能部署 RTMP 版本时，可使用
`scripts/rtmp_management_mock.py` 验证 RTMP 媒体主链路。该脚本是测试代理，不属于正式部署组件：

- 除固定摄像头测试资源外，所有请求均透传到当前旧 Management。
- 在固定摄像头列表第一页注入一台 `protocolType=RTMP`、`publisherRevision=0` 的测试摄像头。
- 将该摄像头的 publish-config GET/POST/PUT/DELETE 转发到新 Media Ingress 内部接口。
- 默认只监听 `127.0.0.1`，不会加入 Compose、离线包或生产容错链路。
- 不模拟 Management 协议切换、权限、持久化状态机和删除编排，因此不能替代最终 Management 验收。

启动前确保已部署匹配版本的 Media、Control、BFF、robot-ui、LiveKit Server 和 LiveKit Ingress，已执行
Media 数据库迁移，并设置 `LIVEKIT_INGRESS_ENABLED=true`。使用实际地图 ID 启动测试代理：

```bash
cd /path/to/robot-mediaserver

MANAGEMENT_MOCK_UPSTREAM_BASE_URL='https://<旧Management地址>/api-gw' \
MANAGEMENT_MOCK_MEDIA_BASE_URL='http://127.0.0.1:8088' \
MANAGEMENT_MOCK_INSECURE_TLS='true' \
MANAGEMENT_MOCK_LISTEN_HOST='0.0.0.0' \
MANAGEMENT_MOCK_CAMERA_ID='900000000000000001' \
MANAGEMENT_MOCK_CAMERA_MAP_ID='<实际地图ID>' \
MANAGEMENT_MOCK_CAMERA_X='0' \
MANAGEMENT_MOCK_CAMERA_Y='0' \
python3 scripts/rtmp_management_mock.py
```

仅在旧 Management 使用测试环境自签名证书时设置 `MANAGEMENT_MOCK_INSECURE_TLS=true`。若 Control/BFF
运行在 Docker 中，需要如上监听宿主机接口，且只允许测试网段访问 `18866`；二者统一设置：

```text
CENTER_MANAGE_BASE_URL=http://host.docker.internal:18866
```

重建 Control 和 BFF 后生成一次性推流地址：

```bash
curl -sS -X POST \
  http://127.0.0.1:18866/api/v1/management/fixed-cameras/900000000000000001/publish-config
```

将响应 `data.pushUrl` 完整填写到摄像头“服务器地址”，开启主码流、关闭音频和子码流。随后登录大屏，
确认装备列表出现“RTMP联调摄像头”，点击后验证：

1. Control 不发送 Gateway MQTT start/restart。
2. Media 会话的 `publisherMode` 为 `LIVEKIT_INGRESS`，状态进入 `STREAMING`。
3. LiveKit Room 中 Publisher identity 为 `fixed-camera:<cameraId>`。
4. 摄像头断网后状态进入 OFFLINE/UNKNOWN，恢复推流后页面无需 Gateway 即重新出画。
5. PUT publish-config 轮换后旧地址失效，新地址可以恢复推流；DELETE 后配置变为未配置。

2026-09-19 在公网联调环境执行了一次 RTMP 摄像头重启恢复验证：

- 大屏已在播放该摄像头时重启设备，页面和视频会话均不手工刷新。
- 设备恢复后的第一次 Ingress 尝试因发布 Track 超时结束；摄像头随后自动重连，
  `12:35:47` 开始稳定发布新 Track，大屏约在 `12:35:58` 自动恢复实时画面。
- 从源端中断到恢复出画的观测窗口内，BFF 的
  `/video-sessions/{sessionId}/token` 请求数为 `0`，浏览器没有重建 LiveKit Viewer WSS。
- 浏览器保留原 Viewer Room，新 Publisher Track 出现后自动订阅，未再出现连续换取
  约 10 次视频 Token 和重复 WSS 连接的连接风暴。
- Network 面板中出现的一次 `auth.js` Token 请求是大屏登录态刷新，不是媒体会话
  Token，验收统计时应按请求路径区分。
- 同日再次由用户手工重启摄像头，大屏在不刷新页面的情况下恢复出画；画面内时间推进到
  `12:47:24`，Ingress 输入与 LOW/MEDIUM/HIGH 三层输出均恢复有效码率。

本次验证同时说明：摄像头启动慢或首次 RTMP 恢复失败可导致暂时保留最后一帧，但不应触发
Viewer Room 反复重建。最终是否恢复应以画面时间持续推进、Ingress Track 有效码率且浏览器
无新增媒体 Token/WSS 风暴为准，不能仅以页面仍显示最后一帧判定恢复。

同日继续执行了运行组件逐项重启验证，摄像头持续推送且大屏保持在同一播放页面：

1. 重启 BFF：启动窗口内一次心跳请求短暂返回 `502`，业务 WebSocket 自动重连，视频未中断，
   未换取新媒体 Token，也未重建 LiveKit Viewer WSS。
2. 重启 Control：启动窗口内两次心跳请求短暂返回 `502`，业务 WebSocket 自动重连，视频未中断，
   未换取新媒体 Token，也未重建 LiveKit Viewer WSS。
3. 重启 Media：启动窗口内心跳和录像状态查询短暂返回 `500`，LiveKit 数据面和视频播放未中断，
   服务恢复后请求自动回到 `200`。
4. 重启 LiveKit Ingress：摄像头在 Ingress 恢复后自动重连并重新发布 Track，大屏自动恢复出画；
   浏览器未换取新媒体 Token，也未重建 Viewer WSS。
5. 重启 LiveKit Server：因 Viewer 所连接的媒体服务本身中断，浏览器发生有限次数的 WSS 重连属于
   必要恢复行为；浏览器复用原媒体 Token，最终仅保留一个有效 Viewer，约 `19` 秒恢复出画。

验收时必须区分两类恢复：仅摄像头、Ingress 或 Publisher Track 中断时，已有 Viewer Room 应保持，
不得触发 Token/WSS 重建风暴；LiveKit Server 本身中断时允许 Viewer WSS 有界重连，但不得连续换取
媒体 Token、残留重复 Viewer 或需要手工刷新页面。

该方式可以验证“摄像头 RTMP -> Ingress -> LiveKit -> Media VideoSession -> Control/BFF -> 大屏”，但以下项目
必须等新版 Management 部署后补测：新增保存自动生成地址、对象权限、双 revision、服务重启续跑、
RTSP/RTMP 双向切换、删除收口以及管理端页面交互。联调结束后恢复 Control/BFF 的正式
`CENTER_MANAGE_BASE_URL` 并停止 Mock，禁止保留测试摄像头入口。

新版 Management 部署后的正式补测已于 2026-09-22 完成。新增配置、一次性凭据、双 revision、
RTSP/RTMP 双向切换、轮换、撤销、删除收口和既有链路回归的实际结果见
[固定摄像头 RTMP 直推验收记录（2026-09-22）](../执行记录/固定摄像头RTMP直推验收记录-20260922.md)。

## 6. 退出条件

2. P0/P1 缺陷已关闭或有明确的风险接受结论。
3. 跨服务字段、状态和事件不存在未解释的不兼容。
4. 未执行项目已记录原因、影响和补测条件。
