# 机器人主动呼叫中心端对讲方案

## 1. 目标

在现有“中心端主动呼叫机器人端”的对讲能力基础上，增加“机器人端主动呼叫中心端”的能力。

目标效果：

```text
机器人发起呼叫
-> 中心端收到来电弹窗
-> 操作员手动接听
-> 系统建立现有 LiveKit 对讲
-> 机器人与中心端开始语音通话
```

如果中心端拒接、无人接听、已有通话占用或机器人取消呼叫，则不启动语音通话，只回传对应状态给机器人端。

## 2. 设计结论

机器人主动呼叫中心端时，只新增“呼叫邀请/振铃/接听/拒接”的业务信令层，不新增独立语音媒体链路。

媒体通话仍复用现有方案：

| 项目 | 方案 |
|---|---|
| 媒体会话 | 继续使用 `VideoSession` |
| LiveKit Room | 继续使用现有 `media.{robotId}.{deviceId}.{channel}.{quality}` |
| 机器人上行音频 | `audio.robot.mic` |
| 中心端上行音频 | `audio.operator.mic` |
| 对讲启动命令 | 继续使用 `robot/{robotId}/media/video/intercom/start` |
| 对讲停止命令 | 继续使用 `robot/{robotId}/media/video/intercom/stop` |

关键原则：

1. 机器人端发起的是“来电请求”，不是直接发起媒体通话。
2. 中心端接听前，不创建 LiveKit Room，不签发 Token，不打开机器人麦克风。
3. 中心端接听后，再进入现有 `VideoSession + LiveKit + intercom/start` 对讲链路。
4. Media Service 不负责管理来电邀请；来电邀请由 Control Service 管理。
5. 同一机器人、同一操作员、同一中心端 `clientId` 同一时间分别只允许一通对讲。
6. 多台机器人可以同时等待接听，当前通话不会被新来电打断。
7. 实时视频观看不占用对讲名额，机器人来电与中心端主动对讲共用对讲占用规则。

正式部署边界：

- Control Service 和 Media Service 均采用单实例部署。
- 来电状态保存在 Control Service 内存中，不新增 Redis 或 MySQL 呼叫表。
- 服务重启、升级或异常退出时，振铃和正在进行的通话均视为中断，不恢复原通话。
- 服务恢复后机器人需要重新呼叫，MQTT 来电消息禁止设置 retained。
- 不提供历史来电查询和通话统计，问题追踪使用业务日志。

## 3. 模块分工

### 3.1 机器人端

开发功能：

- 增加“呼叫中心端”入口。
- 通过 MQTT 上报来电请求。
- 接收中心端返回的呼叫状态。
- 中心端接听后，复用现有 `intercom/start` 处理逻辑启动对讲。
- 呼叫取消、拒接、超时、占线时，停止本次呼叫流程并提示本地状态。

达到效果：

- 机器人可以主动请求与中心端通话。
- 机器人不会绕过中心端手动接听直接进入通话。

### 3.2 Control Service

开发功能：

- 订阅机器人来电 MQTT 消息。
- 维护来电状态。
- 在单实例内原子处理接听、拒接、取消和超时状态竞争。
- 向前端推送“机器人来电”WebSocket 事件。
- 提供接听、拒接操作入口。
- 接听前校验机器人、操作员和中心端客户端的对讲占用。
- 机器人存在待接来电时，阻止从主动对讲入口绕过来电接听。
- 接听后调用现有对讲能力，创建或复用 `VideoSession`。
- 接听后向机器人下发现有 `intercom/start` 命令。
- 拒接、超时、占线、取消时，向机器人下发呼叫状态。

达到效果：

- Control Service 成为机器人来电的调度中心。
- 只有中心端操作员手动接听后，通话才真正建立。

### 3.3 Media Service

开发功能：

- 原则上不新增来电邀请逻辑。
- 继续复用现有 `VideoSession`、LiveKit Token、Room、对讲状态、心跳和释放逻辑。
- 统一校验机器人、操作员和中心端 `clientId` 的对讲占用，作为所有对讲入口的最终保护。
- 仅在 Control Service 接听呼叫后，参与创建或复用对讲会话。

达到效果：

- 媒体链路保持稳定，不引入第二套语音会话模型。
- 来电阶段不会占用媒体资源。

### 3.4 前端

开发功能：

- 接收 WebSocket 来电事件。
- 来电窗口默认展示在大屏右下角，并可在大屏范围内拖动。
- 展示机器人名称和呼叫原因，振铃超时以服务端 `expiresAt` 为准，不在窗口中显示倒计时。
- 提供“接听”和“拒接”按钮。
- 接听成功后默认进入语音通话窗口，提供挂断、本地麦克风静音、本地扬声器静音和开启视频功能。
- 开启视频后在当前通话窗口播放机器人主摄像头画面，不重新建立一通电话。
- 视频画面上提供“关闭视频”操作，关闭后保留语音并恢复语音通话窗口。
- 视频通话窗口提供“上装控制”入口，跳转到已有远程控制界面。
- 点击“上装控制”前先关闭通话弹窗中的视频并恢复语音窗口，再由远程控制页面打开实时视频。
- 多通来电时显示等待数量；通话期间新来电进入等待队列，不覆盖当前通话。
- 远程控制页面已经进行主动对讲时，来电可以等待和拒接，但当前客户端不能接听。
- 拒接、超时、被其他人接听、机器人取消时关闭弹窗并提示状态。

达到效果：

- 中心端像接电话一样处理机器人来电。
- 多个中心端在线时可以同时收到提醒，但只有一个人能接听成功。

## 4. 呼叫状态

新增呼叫邀请状态，与现有对讲状态分开管理。

| 状态 | 说明 |
|---|---|
| `RINGING` | 机器人已发起来电，等待中心端接听 |
| `ACCEPTED` | 中心端已接听，准备进入对讲链路 |
| `REJECTED` | 中心端主动拒接 |
| `TIMEOUT` | 超过等待时间，无人接听 |
| `CANCELED` | 机器人端取消呼叫 |
| `BUSY` | 当前机器人已有对讲或来电占用 |
| `ENDED` | 已接听后的通话结束 |
| `FAILED` | 呼叫或接听后的对讲启动失败 |

现有对讲状态继续表示媒体链路状态：

```text
IDLE -> STARTING -> ACTIVE -> STOPPING -> IDLE
                  -> INTERRUPTED / FAILED
```

注意：

- `RINGING` 不等于 `STARTING`。
- `RINGING` 阶段还没有启动 LiveKit 对讲。
- 中心端点击接听后，才进入 `STARTING`。

## 5. MQTT 协议

### 5.1 机器人发起来电

Topic：

```text
robot/{robotId}/media/video/intercom/call/invite
```

方向：

```text
Robot -> Control Service
```

Payload：

```json
{
  "callId": "call_20260714103000001",
  "robotId": "robot-001",
  "deviceId": "camera01",
  "channel": "visible",
  "quality": "sub",
  "reason": "机器人请求人工对讲",
  "timeoutSeconds": 30,
  "timestamp": "2026-07-14T10:30:00+08:00"
}
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `callId` | 是 | 机器人端生成的本次呼叫 ID，用于幂等和状态回传 |
| `robotId` | 是 | 机器人 ID |
| `deviceId` | 是 | 默认绑定摄像头或对讲设备对应的摄像头 ID |
| `channel` | 否 | 默认 `visible` |
| `quality` | 否 | 默认 `sub` |
| `reason` | 否 | 呼叫原因 |
| `timeoutSeconds` | 否 | 中心端等待接听时间，默认 30 秒 |
| `timestamp` | 是 | 发起时间 |

### 5.2 中心端回传呼叫状态

Topic：

```text
robot/{robotId}/media/video/intercom/call/state
```

方向：

```text
Control Service -> Robot
```

Payload：

```json
{
  "callId": "call_20260714103000001",
  "robotId": "robot-001",
  "status": "accepted",
  "sessionId": "vs_xxx",
  "message": "operator accepted",
  "timestamp": "2026-07-14T10:30:08+08:00"
}
```

`status` 可选值：

| 值 | 说明 |
|---|---|
| `ringing` | 中心端已收到来电并推送前端 |
| `accepted` | 操作员已接听 |
| `rejected` | 操作员已拒接 |
| `timeout` | 呼叫超时 |
| `busy` | 当前机器人通话占用 |
| `canceled` | 呼叫已取消 |
| `failed` | 呼叫处理失败 |
| `ended` | 通话结束 |

### 5.3 机器人取消呼叫

Topic：

```text
robot/{robotId}/media/video/intercom/call/cancel
```

方向：

```text
Robot -> Control Service
```

Payload：

```json
{
  "callId": "call_20260714103000001",
  "robotId": "robot-001",
  "reason": "用户取消呼叫",
  "timestamp": "2026-07-14T10:30:10+08:00"
}
```

## 6. WebSocket 事件

### 6.1 机器人来电

事件：

```text
video.intercom.call.incoming
```

Payload：

```json
{
  "event": "video.intercom.call.incoming",
  "timestamp": "2026-07-14T10:30:00+08:00",
  "data": {
    "callId": "call_20260714103000001",
    "robotId": "robot-001",
    "robotName": "R1轮式机器人",
    "deviceId": "camera01",
    "cameraName": "前视摄像头",
    "reason": "机器人请求人工对讲",
    "status": "RINGING",
    "expiresAt": "2026-07-14T10:30:30+08:00"
  }
}
```

### 6.2 来电状态变化

事件：

```text
video.intercom.call.status
```

Payload：

```json
{
  "event": "video.intercom.call.status",
  "timestamp": "2026-07-14T10:30:08+08:00",
  "data": {
    "callId": "call_20260714103000001",
    "robotId": "robot-001",
    "status": "ACCEPTED",
    "sessionId": "vs_xxx",
    "acceptedBy": "operator-001"
  }
}
```

前端处理：

| 状态 | 前端动作 |
|---|---|
| `RINGING` | 展示来电弹窗 |
| `ACCEPTED` | 当前用户接听成功则进入对讲；其他用户关闭弹窗 |
| `REJECTED` | 关闭弹窗 |
| `TIMEOUT` | 关闭弹窗并提示无人接听 |
| `CANCELED` | 关闭弹窗并提示机器人已取消 |
| `BUSY` | 关闭弹窗并提示占线 |
| `FAILED` | 关闭弹窗并提示失败 |
| `ENDED` | 更新通话结束状态 |

## 7. 主流程

### 7.1 正常接听

```mermaid
sequenceDiagram
    participant Robot as 机器人端
    participant MQTT as MQTT
    participant CS as Control Service
    participant FE as 中心端前端
    participant MS as Media Service
    participant LK as LiveKit

    Robot->>MQTT: call/invite(callId, robotId, deviceId)
    MQTT->>CS: 收到来电请求
    CS->>CS: 创建呼叫记录 RINGING
    CS->>MQTT: call/state(ringing)
    CS->>FE: WS video.intercom.call.incoming
    FE->>CS: 操作员点击接听
    CS->>CS: 校验 RINGING、机器人在线、未占用
    CS->>MS: 创建或复用 VideoSession 对讲
    MS-->>CS: IntercomResponse(operatorToken)
    CS->>MQTT: intercom/start(sessionId, robotToken)
    MQTT->>Robot: 启动对讲音频桥
    Robot->>LK: 发布 audio.robot.mic，订阅 audio.operator.mic
    FE->>LK: 发布 audio.operator.mic，订阅 audio.robot.mic
    Robot->>MQTT: intercom/status active
    MQTT->>CS: 对讲 active
    CS->>FE: WS video.intercom.active
```

### 7.2 拒接

```text
机器人 call/invite
-> Control Service 创建 RINGING
-> 前端展示弹窗
-> 操作员点击拒接
-> Control Service 更新 REJECTED
-> Control Service 通知机器人 rejected
-> 前端关闭弹窗
```

### 7.3 超时

```text
机器人 call/invite
-> Control Service 创建 RINGING
-> 超过 expiresAt 无人接听
-> 定时任务更新 TIMEOUT
-> Control Service 通知机器人 timeout
-> 前端关闭弹窗
```

### 7.4 占线

```text
机器人 call/invite
-> Control Service 检查该机器人已有 ACTIVE/STARTING 对讲或 RINGING 来电
-> 不创建新来电
-> Control Service 通知机器人 busy
```

### 7.5 机器人取消

```text
机器人 call/invite
-> Control Service 创建 RINGING
-> 机器人 call/cancel
-> Control Service 更新 CANCELED
-> 前端关闭弹窗
```

### 7.6 通话挂断

接听成功后，通话挂断复用现有对讲停止流程。

中心端挂断：

```text
操作员点击挂断
-> 前端停止本地麦克风发布
-> Control Service 停止当前对讲
-> Control Service 向机器人下发 intercom/stop
-> 机器人停止音频桥
-> Control Service 更新来电状态 ENDED
-> Control Service 向机器人回传 call/state ended
-> 前端退出对讲状态
```

机器人端挂断：

```text
机器人触发挂断
-> 机器人停止本地音频桥
-> 机器人上报对讲停止状态
-> Control Service 更新来电状态 ENDED
-> Control Service 向前端推送通话结束事件
-> 前端退出对讲状态
```

### 7.7 多来电与占用

```text
多个机器人同时来电
-> Control Service 分别创建 RINGING
-> 前端按到达时间展示第一通，并显示剩余来电数量
-> 接听一通后，其余来电继续等待
-> 当前客户端不能同时接听第二通
-> 其他空闲操作员可以接听等待来电
-> 当前通话结束后展示下一通未超时来电
```

机器人来电和中心端主动对讲统一遵循以下规则：

| 占用对象 | 规则 |
|---|---|
| 机器人 | 同一时间只能有一通来电或对讲 |
| 操作员 | 同一时间只能与一台机器人对讲 |
| 中心端 `clientId` | 同一时间只能发布一路对讲麦克风 |
| 实时视频 | 可以多路观看，不占用对讲名额 |

## 8. 异常处理

| 场景 | 处理 |
|---|---|
| 重复 `callId` | 幂等处理，返回当前呼叫状态 |
| 同一机器人重复来电 | 已有 `RINGING` 或对讲占用时返回 `busy` |
| 不同机器人同时来电 | 分别保持 `RINGING`，进入同一等待队列 |
| 当前客户端正在通话 | 新来电继续等待，当前客户端不能接听，其他空闲客户端仍可接听 |
| 远程控制页面正在主动对讲 | 按当前客户端正在通话处理，不允许再接听或开启第二通对讲 |
| 机器人有待接来电时主动开启对讲 | 阻止主动对讲，提示通过来电窗口接听 |
| 中心端多人同时接听 | 通过状态抢占保证只有一个成功，其余返回已被接听 |
| 接听者已有其他对讲 | 本次接听失败但来电保持 `RINGING`，不影响其他操作员接听 |
| 接听时机器人离线 | 呼叫更新为 `FAILED`，前端提示机器人离线 |
| 接听后 `intercom/start` 下发失败 | 呼叫更新为 `FAILED`，对讲状态走现有失败处理 |
| 机器人收到 `intercom/start` 后启动失败 | 机器人上报 `intercom/status failed`，Media Service 更新对讲失败 |
| 通话中中心端挂断 | 下发 `intercom/stop`，机器人停止音频桥，来电状态更新为 `ENDED` |
| 通话中机器人端挂断 | 机器人停止音频桥并上报状态，前端退出对讲状态 |
| 前端 WebSocket 断开 | 重连后通过当前状态同步机制恢复未超时来电 |
| 重复挂断或通话已释放 | 按幂等成功处理，不向用户显示 HTTP 409 |
| Control Service 或 Media Service 重启 | 当前来电和通话全部中断，服务恢复后不恢复旧通话 |

## 9. 权限与安全

1. 只有具备对讲权限的用户可以接听。
2. 接听操作需要校验用户所在组织是否有权限访问该机器人。
3. LiveKit Token 仍由 Media Service 签发，机器人端不能自行生成。
4. 接听成功后才允许前端发布 `audio.operator.mic`。
5. 同一机器人同一时间只允许一个对讲操作员。
6. 所有 MQTT 消息使用 QoS 1，并通过 `callId`、`commandId` 做幂等。
7. 同一操作员和同一中心端 `clientId` 同一时间只允许一通对讲。

## 10. 资源释放

振铃阶段：

- 不创建 `VideoSession`。
- 不创建 LiveKit Room。
- 不签发 Token。
- 不启动机器人麦克风。
- 不占用媒体资源。

接听后：

- 进入现有对讲资源治理。
- 对讲心跳超时按现有规则关闭。
- 对讲结束后，如果无人观看视频，会话按现有空闲释放策略释放。
- 关闭通话弹窗视频时只结束当前弹窗的视频观看，不停止语音对讲。
- 进入上装控制前关闭弹窗视频，远程控制页面按自身规则重新建立视频观看。

服务重启：

- 不恢复内存中的 `RINGING` 或 `ACCEPTED` 呼叫。
- 浏览器停止本地音视频，机器人端通过停止命令或心跳超时退出对讲。
- 服务恢复后双方回到空闲状态，需要通话时重新发起呼叫。

## 11. 开发清单

### 11.1 机器人端

- 新增呼叫入口。
- 新增 `call/invite` 上报。
- 新增 `call/cancel` 上报。
- 新增 `call/state` 订阅。
- 保持现有 `intercom/start|stop` 处理逻辑不变。

### 11.2 Control Service

- 订阅机器人来电、取消呼叫 MQTT 消息。
- 维护机器人来电状态，包括振铃、接听、拒接、超时、取消、占线。
- 使用单实例内存状态原子处理同一来电的并发操作。
- 接听前校验操作员和中心端客户端是否已有其他对讲。
- 机器人有待接来电时阻止主动对讲入口绕过接听。
- 向前端推送来电和来电状态变化事件。
- 接听成功后复用现有对讲能力，创建或复用 `VideoSession`。
- 接听成功后向机器人下发 `intercom/start`。
- 拒接、超时、占线、取消时向机器人回传 `call/state`。

### 11.3 Media Service

- 不管理机器人来电流程。
- 不新增独立音频 Room。
- 接听后复用现有 `VideoSession`、LiveKit Token、Room、对讲状态、心跳和释放逻辑。
- 所有对讲入口统一限制同一机器人、操作员和中心端客户端只能占用一通对讲。

### 11.4 前端

- 新增来电弹窗组件。
- WebSocket 增加 `video.intercom.call.incoming` 和 `video.intercom.call.status` 事件处理。
- 新增接听、拒接操作。
- 来电、语音通话、视频通话使用同一个可拖动窗口展示。
- 接听成功后复用现有对讲连接逻辑，默认只建立语音通话。
- 麦克风静音只控制中心端浏览器的本地麦克风发布；扬声器静音只控制中心端浏览器的远端音频播放。
- “开启视频”在当前会话中启动机器人主摄像头视频并挂载远端视频轨道。
- 视频画面提供关闭操作，关闭后保留语音并恢复语音通话窗口。
- “上装控制”跳转已有远程控制界面，并保留当前选中的机器人。
- 跳转上装控制前先关闭弹窗视频并恢复语音通话窗口。
- 多来电时显示等待数量，当前通话期间不覆盖通话窗口。
- 挂断、远端结束或异常断开时释放本地音视频轨道和媒体元素。
- WebSocket 重连后恢复未处理来电。

## 12. 验收场景

| 编号 | 场景 | 预期结果 |
|---:|---|---|
| 1 | 机器人主动呼叫，中心端接听 | 前端进入对讲，双方语音可通 |
| 2 | 机器人主动呼叫，中心端拒接 | 机器人收到 `rejected`，不启动对讲 |
| 3 | 机器人主动呼叫，中心端无人接听 | 超时后机器人收到 `timeout` |
| 4 | 已有对讲时机器人再次呼叫 | 机器人收到 `busy` |
| 5 | 多个前端同时收到来电，一个人接听 | 接听者进入对讲，其他前端关闭弹窗 |
| 6 | 接听时机器人离线 | 前端提示失败，机器人不启动对讲 |
| 7 | 接听后机器人音频桥启动失败 | 前端收到对讲失败事件 |
| 8 | 机器人取消来电 | 前端弹窗关闭 |
| 9 | 前端 WebSocket 断开后恢复 | 仍能恢复未超时来电 |
| 10 | 语音通话中切换麦克风或扬声器静音 | 只影响中心端本地采集或播放，不向机器人下发设备控制命令 |
| 11 | 语音通话中点击开启视频 | 当前通话升级为主摄像头视频通话，语音不中断 |
| 12 | 视频通话中点击上装控制 | 进入已有远程控制界面，目标机器人保持选中 |
| 13 | 展示或拖动任一状态的通话窗口 | 窗口默认位于大屏右下角，可在 1920×1080 范围内移动且不会拖出边界 |
| 14 | 语音或视频通话中任一端挂断 | 通话窗口关闭，本地音视频资源被释放 |
| 15 | 多个机器人同时呼叫 | 所有来电独立振铃，前端展示第一通并显示剩余来电数量 |
| 16 | 与机器人 A 通话时机器人 B 来电 | A 通话不中断，B 保持等待，当前客户端不能接听 B |
| 17 | 远程控制页面正在主动对讲时其他机器人来电 | 来电保持等待，接听按钮不可用，不建立第二通对讲 |
| 18 | 同一操作员或 `clientId` 尝试开启第二通对讲 | 服务端拒绝并提示先结束当前通话 |
| 19 | 机器人存在待接来电时从远程控制入口主动开启对讲 | 主动对讲被阻止，提示通过来电窗口接听 |
| 20 | 视频通话中点击画面上的关闭视频 | 视频停止展示，语音不中断，窗口恢复语音通话样式 |
| 21 | 视频通话中点击上装控制 | 先关闭弹窗视频并恢复语音样式，再跳转远程控制页面打开实时视频 |
| 22 | 重复挂断或服务端已释放对讲 | 前端按通话已结束处理，不显示 409 异常 |
| 23 | 中心端服务重启 | 当前来电和通话中断，不恢复旧通话，机器人可重新呼叫 |

### 12.1 自动化回归

在项目根目录执行：

```bash
node scripts/intercom-e2e.cjs
```

默认验证 `192.168.124.234:4443` 中心端与 `192.168.124.235:1884` MQTT 服务。可通过
`CENTER_HOST`、`CENTER_HTTPS_PORT`、`MQTT_URL` 环境变量切换测试环境。

脚本覆盖单机器人呼叫、接听、拒接、超时前状态查询、同一操作员并发限制、多机器人并发来电、
重复来电忙线、语音升级视频、关闭弹窗视频后保持语音、挂断清理，以及迟到推流状态不得恢复空闲会话等场景。
