# 通用文件服务接口文档

本文档定义通用文件服务的 HTTP 接口。数据模型、状态机、对象存储和处理流程见[通用文件上传、存储与播放设计说明书](../../02-设计/文件服务/通用文件上传存储与播放设计说明书.md)。面向调用方的完整示例见[任务视频上传接口对接指南](../对接指南/任务视频上传接口对接指南.md)。

## 1. API 定义

### 1.1 小文件单接口上传

```http
POST /api/media/files
Content-Type: multipart/form-data
```

表单字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `file` | 是 | 文件内容 |
| `fileType` | 是 | 文件类型 |
| `robotId` | 否 | 机器人 ID |
| `deviceId` | 否 | 设备 ID |
| `extensionId` | 否 | 通用扩展 ID，可为空 |
| `sourceFileId` | 否 | 本地文件幂等键 |
| `metadata` | 否 | JSON 字符串 |

响应示例：

```json
{
  "fileId": "file_xxx",
  "fileType": "IMAGE",
  "fileName": "snapshot.jpg",
  "contentType": "image/jpeg",
  "fileSize": 345678,
  "uploadMode": "SIMPLE",
  "status": "READY",
  "uploadedAt": "2026-06-30T10:00:00Z"
}
```

小视频响应示例：

```json
{
  "fileId": "file_xxx",
  "fileType": "VIDEO",
  "uploadMode": "SIMPLE",
  "status": "PROCESSING"
}
```

大小限制：

```text
MEDIA_FILE_SIMPLE_UPLOAD_MAX_BYTES=20971520
```

超过限制返回：

```json
{
  "code": "FILE_TOO_LARGE_USE_MULTIPART",
  "message": "File is too large for simple upload"
}
```

#### 1.1.1 各文件类型单接口上传示例

小文件优先使用单接口上传。`fileType` 表示业务分类，`contentType` 表示 MIME 类型，两者都要传对。

| 文件类型 | 典型后缀 | fileType | contentType 示例 | 上传后状态 | 说明 |
|---|---|---|---|---|---|
| 视频 | `.mp4` / `.mov` / `.m4v` | `VIDEO` | `video/mp4` | `PROCESSING -> READY` | 小视频也会进入 HLS 处理 |
| 音频 | `.wav` / `.mp3` / `.aac` / `.m4a` / `.ogg` / `.flac` | `AUDIO` | `audio/wav` / `audio/mpeg` | `READY` | 不生成 HLS |
| 图片 | `.jpg` / `.png` / `.webp` | `IMAGE` | `image/jpeg` / `image/png` | `READY` | 抓拍、截图 |
| 日志 | `.log` / `.txt` | `LOG` | `text/plain` | `READY` | 运行日志、诊断日志 |
| 配置 | `.json` / `.yaml` / `.ini` / `.conf` | `CONFIG` | `application/json` / `application/yaml` | `READY` | 配置快照、参数文件 |
| 地图 | `.map` / `.json` | `MAP` | `application/json` / `application/octet-stream` | `READY` | 地图、点位、路径文件 |
| 文档 | `.pdf` / `.docx` / `.xlsx` | `DOCUMENT` | `application/pdf` | `READY` | 报告、表格、说明文档 |
| 其他 | `.zip` / `.bin` | `OTHER` | `application/zip` / `application/octet-stream` | `READY` | 诊断包、压缩包、未知类型 |

音频上传：

```bash
curl -X POST "{MEDIA_SERVICE_URL}/api/media/files" \
  -F "file=@notice.wav;type=audio/wav" \
  -F "fileType=AUDIO" \
  -F "robotId=test001" \
  -F "deviceId=speaker01" \
  -F "sourceFileId=test001/audio/notice.wav/123456/1784705200" \
  -F 'metadata={"type":"audio_file","name":"提示音"}'
```

```bash
curl -X POST "{MEDIA_SERVICE_URL}/api/media/files" \
  -F "file=@snapshot.jpg;type=image/jpeg" \
  -F "fileType=IMAGE" \

  -F "deviceId=camera01" \
  -F "sourceFileId=test001/camera01/snapshot.jpg/345678/1784705200" \
  -F 'metadata={"type":"snapshot","channel":"visible"}'
```

日志上传：

```bash
curl -X POST "{MEDIA_SERVICE_URL}/api/media/files" \
  -F "file=@robot.log;type=text/plain" \

  -F "robotId=test001" \
  -F "sourceFileId=test001/logs/robot.log/20480/1784705200" \
```

### 1.2 创建或恢复 multipart 上传

```http
POST /api/media/files/multipart-uploads
```

请求：

```json
{
  "robotId": "test111",
  "deviceId": "camera01",
  "extensionId": null,
  "sourceFileId": "camera01/video.mp4/1073741824/1710000000",
  "fileType": "VIDEO",
  "fileName": "video.mp4",
  "contentType": "video/mp4",
  "fileSize": 1073741824,
  "metadata": {}
}
```

响应：

```json
{
  "fileId": "file_xxx",
  "uploadId": "upl_xxx",
  "uploadMode": "MULTIPART",
  "status": "UPLOADING",
  "partSize": 16777216,
  "partCount": 64,
  "uploadedParts": [
    { "partNumber": 1 }
  ],
  "partUrls": [
    {
      "partNumber": 2,
      "uploadUrl": "http://minio-presigned-part-url"
    }
  ],
  "expiresAt": "2026-06-30T10:00:00Z"
}
```

说明：

1. 创建接口直接返回首批 `partUrls`。
2. 首批数量由配置控制，建议默认 16。
3. 已上传分片通过 `uploadedParts` 返回，客户端跳过这些 part。

### 1.4 上传分片到 `uploadUrl`

`uploadUrl` 是对象存储的预签名 PUT 地址。调用端拿到后，不再请求 Media Service，而是直接把对应分片的二进制内容 PUT 到该地址。

单个分片上传规则：

```text
partNumber = 1 时，读取文件 [0, partSize)
partNumber = 2 时，读取文件 [partSize, partSize * 2)
最后一个 part 读取到文件末尾
PUT uploadUrl 的 body 只放该 part 的原始二进制
PUT 成功以 HTTP 2xx 为准
失败或 URL 过期时，重新调用 part-urls 获取新的 uploadUrl 后重试
```

curl 示例：

```bash
# 例：partSize = 16777216，上传第 1 个分片。
# bs/count/skip 只用于演示如何截取分片；实际代码应使用文件随机读取或流式读取。
dd if=video.mp4 bs=16777216 skip=0 count=1 2>/dev/null \
  | curl -X PUT \
      -H "Content-Type: application/octet-stream" \
      --data-binary @- \
      "http://minio-presigned-part-url"
```

JavaScript/TypeScript 浏览器或 Node 伪代码：

```js
async function uploadPart(file, part, partSize) {
  const start = (part.partNumber - 1) * partSize
  const end = Math.min(start + partSize, file.size)
  const blob = file.slice(start, end)
  const response = await fetch(part.uploadUrl, {
    method: 'PUT',
    body: blob
  })
  if (!response.ok) {
    throw new Error(`part ${part.partNumber} upload failed: ${response.status}`)
  }
}
```

Go 伪代码：

```go
func uploadPart(path string, partNumber int, partSize int64, uploadURL string) error {
    file, err := os.Open(path)
    if err != nil {
        return err
    }
    defer file.Close()

    start := int64(partNumber-1) * partSize
    stat, err := file.Stat()
    if err != nil {
        return err
    }
    size := min(partSize, stat.Size()-start)
    reader := io.NewSectionReader(file, start, size)

    req, err := http.NewRequest(http.MethodPut, uploadURL, reader)
    if err != nil {
        return err
    }
    req.ContentLength = size
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return err
    }
    defer resp.Body.Close()
    if resp.StatusCode < 200 || resp.StatusCode >= 300 {
        return fmt.Errorf("part %d upload failed: %s", partNumber, resp.Status)
    }
    return nil
}
```

完整视频上传调用顺序示例：

```text
1. POST /api/media/files/multipart-uploads
   -> 得到 fileId、uploadId、partSize、partCount、uploadedParts、首批 partUrls

2. 客户端计算待上传 partNumbers
   -> 跳过 uploadedParts 中已存在的 part

3. 对 partUrls 中每个 part 执行 PUT uploadUrl
   -> PUT 的 body 是该 part 的文件二进制
   -> 可并发 PUT，但并发数由客户端控制，例如 2 或 4

4. 首批 partUrls 用完但还有未上传 part
   -> POST /api/media/files/multipart-uploads/{uploadId}/part-urls
   -> 获取下一批或重新签发失败 part 的 uploadUrl

5. 所有 part PUT 成功
   -> POST /api/media/files/multipart-uploads/{uploadId}/complete

6. 若 fileType = VIDEO
   -> GET /api/media/files/{fileId}/status 轮询 PROCESSING / READY / FAILED
   -> READY 后调用 POST /api/media/files/{fileId}/play-url 获取 HLS 播放地址
```

注意事项：

```text
一次返回 16 个 partUrls 不代表必须 16 并发上传；partUrls 是可用地址池，并发数由客户端按网络和设备性能控制。
uploadUrl 有有效期，长时间未使用或 PUT 返回签名过期时，重新调用 part-urls 获取新的地址。
Media Service 不接收分片正文，只负责创建上传、签发 URL、校验完成和维护元数据。
MinIO 在 complete 前只记录已完整 PUT 成功的 part；未完成的 PUT 不应被客户端视为已上传。
MINIO_ENDPOINT 决定 uploadUrl 的协议、主机和端口；机器人直传时必须配置为机器人可访问的外部 IP 或域名。
```

### 1.5 完成 multipart 上传

```http
POST /api/media/files/multipart-uploads/{uploadId}/complete
```

服务端处理：

```text
ListParts
校验分片数量、序号、大小
CompleteMultipart
StatObject
更新 media_file_upload.status = COMPLETED
非视频：media_file.status = READY
视频：media_file.status = PROCESSING，并触发 HLS
```

非视频响应：

```json
{
  "fileId": "file_xxx",
  "status": "READY"
}
```

视频响应：

```json
{
  "fileId": "file_xxx",
  "status": "PROCESSING"
}
```

### 1.6 绑定通用扩展 ID

调用方在拿到一个或多个文件 `fileId` 后，调用该接口后补 `extension_id`。

```http
POST /api/media/files/extension-binding
```

请求：

```json
{
  "extensionId": "ext_001",
  "fileIds": ["file_video_001", "file_point_001"]
}
```

兼容字段：历史任务/巡逻链路仍可传 `videoFileIds` 和 `pointFileId`，服务端会合并到 `fileIds` 处理。

处理规则：

```text
只更新 media_file.extension_id
不移动对象存储文件
不重新上传
不重新生成 HLS
```

成功响应：

```http
204 No Content
```

### 1.7 查询文件

文件详情：

```http
GET /api/media/files/{fileId}
```

文件列表：

```http
GET /api/media/files?robotId=test111
GET /api/media/files?fileType=VIDEO
GET /api/media/files?extensionId=ext_001
GET /api/media/files?status=READY
GET /api/media/files?fileType=IMAGE&source=WEB_SNAPSHOT
```

可选参数 `source` 对 `metadata.source` 做精确匹配，并在数据库分页前参与筛选。它用于区分相同
`fileType` 下的业务来源，不能在前端取回一页数据后再过滤，否则总数和翻页结果会失真。

文件列表始终按当前可信身份过滤：`createdBy` 为空的组织共享文件按 `orgId` 返回；
`createdBy` 非空的用户私有文件只返回 `createdBy = 当前 userId` 的记录。手动媒体查看要求
`MEDIA_VIEWER` 或 `MEDIA_OPERATOR`。

实时监控底部“多媒体记录”只查询用户手动产生的文件：

| 页签 | 查询条件 | 排除内容 |
|---|---|---|
| 图片 | `fileType=IMAGE&status=READY&source=WEB_SNAPSHOT` | 告警图片、任务图片及来源不明图片 |
| 视频 | `fileType=VIDEO&status=READY&source=LIVEKIT_EGRESS` | 任务录像、机器人本地录像及来源不明视频 |

`robotId`、`deviceId`、`extensionId`、`fileType`、`status` 和 `source` 可以组合使用。
上述两个手动来源在创建时由 Media Service 写入 `createdBy`，客户端不能指定其他归属人。

视频列表项时间字段：

`startedAt` / `endedAt` 来源于 `media_video_file.started_at` / `media_video_file.ended_at`。视频处理完成拿到真实 `durationSeconds` 后会统一校正：

```text
1. 若已存在 started_at，则 ended_at = started_at + durationSeconds
2. 若不存在 started_at，但可从 sourceFileId 解析本地文件修改时间，则该时间作为 ended_at，started_at = ended_at - durationSeconds
3. 若 sourceFileId 无法解析，则用 uploaded_at / created_at 兜底，再反推 started_at
```

录像处于 `PROCESSING` 状态时，响应中的 `elapsedSeconds` 由媒体服务按服务器时间计算，表示当前录像已持续秒数。前端计时应使用该字段作为初始值，再使用浏览器单调时钟递增，不应直接用 `startedAt` 与用户系统时间相减。

```json
{
  "fileId": "file_xxx",
  "fileType": "VIDEO",
  "status": "READY",
  "durationSeconds": 120,
  "elapsedSeconds": null,
  "startedAt": "2026-06-30T09:58:00Z",
  "endedAt": "2026-06-30T10:00:00Z"
}
```

### 1.8 下载文件

```http
POST /api/media/files/{fileId}/download-url
```

可选查询参数：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `inline` | boolean | `false` | `true` 时预签名 URL 使用 `Content-Disposition: inline`，浏览器新标签页直接渲染（如图片查看）；默认 `attachment` 触发下载。 |

规则：

```text
media_file.status = READY 才允许下载。
返回 MinIO 预签名 GET URL 或后端代理下载 URL。
用户私有文件还必须满足 `orgId + createdBy`，否则返回 404。
```

响应：

```json
{
  "fileId": "file_xxx",
  "downloadUrl": "http://minio-presigned-get-url",
  "expiresAt": "2026-06-30T10:00:00Z"
}
```

### 1.9 视频播放

```http
POST /api/media/files/{fileId}/play-url
```

规则：

```text
file_type = VIDEO
media_file.status = READY
media_video_file.status = READY
用户私有文件必须属于当前用户。
```

响应：

```json
{
  "fileId": "file_xxx",
  "format": "hls",
  "contentType": "application/vnd.apple.mpegurl",
  "playUrl": "/api/media/files/file_xxx/hls/index.m3u8?token=xxx",
  "expiresAt": "2026-06-30T10:00:00Z"
}
```

HLS 资源：

```http
GET /api/media/files/{fileId}/hls/{objectName}?token=xxx
```

支持：

```text
index.m3u8
init.mp4
segment_xxx.m4s
```

### 1.10 删除文件

```http
DELETE /api/media/files/{fileId}
X-Org-Id: org001
```

删除规则：

```text
1. 组织共享文件只能由当前组织用户删除；用户私有文件还必须属于当前用户，否则返回 404。
2. 用户私有文件删除要求 `MEDIA_OPERATOR`。
3. 删除 MinIO 中该文件的原文件、暂存分片和 HLS 资源。
4. 若存在 ACTIVE 分片上传会话，先终止会话并将其标记为 ABORTED。
5. media_file 数据不物理删除，状态更新为 DELETED。
6. 接口支持幂等调用，重复删除仍返回 204。
```

成功响应：

```http
HTTP/1.1 204 No Content
```

### 1.11 批量删除文件

```http
DELETE /api/media/files/batch
Content-Type: application/json
X-Org-Id: org001

{
  "fileIds": ["file_image_001", "file_video_001"]
}
```

`fileIds` 必填，每次最多 100 个。批量删除沿用单条删除的组织隔离、资源清理和幂等规则；单个文件失败不会中断其他文件，接口返回逐条结果。

```json
{
  "total": 2,
  "succeeded": 1,
  "failed": 1,
  "results": [
    {
      "fileId": "file_image_001",
      "success": true,
      "code": "DELETED",
      "message": "删除成功"
    },
    {
      "fileId": "file_video_001",
      "success": false,
      "code": "FILE_NOT_FOUND",
      "message": "未找到文件"
    }
  ]
}
```

## 2. 错误响应

文件接口的业务错误统一返回以下结构：

```json
{
  "timestamp": "2026-08-07 17:00:00",
  "status": 429,
  "code": "UPLOAD_SESSION_LIMIT",
  "message": "机器人未完成上传会话数量达到上限，请稍后重试",
  "retryable": true,
  "requestId": "req_xxx",
  "path": "/api/media/files/multipart-uploads",
  "details": {
    "scope": "ROBOT",
    "robotId": "test115",
    "activeCount": 20,
    "limit": 20
  }
}
```

响应头同时返回 `X-Request-Id`，便于服务端按请求定位日志。可重试的限流响应返回 `Retry-After: 60`，对象存储故障返回 `Retry-After: 5`。

常见错误：

| HTTP | code | retryable | 说明 |
|---|---|---|---|
| `400` | `VALIDATION_ERROR` | `false` | 请求字段缺失或格式错误 |
| `409` | `SOURCE_FILE_CHANGED` | `false` | 相同 `sourceFileId` 对应的源文件属性发生变化 |
| `409` | `UPLOAD_INCOMPLETE` | `false` | 分片不连续或尚未全部上传 |
| `409` | `UPLOAD_SIZE_MISMATCH` | `false` | 分片总大小或合成对象大小不匹配 |
| `409` | `UPLOAD_NOT_ACTIVE` | `false` | 上传会话已完成、终止或过期 |
| `429` | `UPLOAD_SESSION_LIMIT` | `true` | 未过期上传会话达到机器人或全局容量上限 |
| `503` | `STORAGE_UNAVAILABLE` | `true` | MinIO/S3 未启用、不可达、凭据错误或存储操作失败 |

上传会话容量默认值：

```text
MEDIA_FILE_MAX_ACTIVE_UPLOADS_PER_ROBOT=20
MEDIA_FILE_MAX_ACTIVE_UPLOADS_GLOBAL=500
MEDIA_FILE_CLEANUP_DELAY_MS=60000
```

容量只统计 `status=ACTIVE` 且 `expires_at` 晚于当前时间的会话。它用于限制未完成会话堆积，不等于客户端同时 PUT 的文件数或分片数；客户端仍应根据网络与设备性能控制实际上传并发。
