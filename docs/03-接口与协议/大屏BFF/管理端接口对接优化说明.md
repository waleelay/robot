# 管理端接口对接优化说明

> 状态：待实施，文中新增接口、配置开关和迁移步骤均为目标方案，不代表当前已上线能力。
> 适用范围：bigscreen-bff、control-service 与 eiop 管理端（8866）/控制端（8867）的对接。
> 目标：解决大屏侧对管理端/控制端的过重查询，将聚合/统计/状态历史能力下沉管理端；**保证现有前端完全不受迁移影响**。
> 核心原则：**BFF 作为适配层——内部数据源从「拉全量本地聚合」换成「调管理端聚合」，对外 HTTP 契约（前端消费的响应结构）保持不变**。
> 文档版本：v1.1

## 1. 背景与目标

- 大屏（bigscreen-bff）与 control-service 对管理端（8866）存在**全量翻页、超长 queryParam、N+1、每连接全量拉取、无缓存全表扫描**等过重调用。
- **大屏访问用户数明显多于管理端**：重活（聚合/统计/状态历史）下沉管理端（管理端调用者少、可加服务端缓存、组织过滤由数据权限处理器自动生效），大屏 BFF 保持轻量。
- 迁移约束：**现有前端（robot-ui）不做改动即可继续工作**，通过 BFF 适配层保证对外契约不变。

> 下沉只改变 **BFF 内部数据获取**，上述对外结构由 BFF 适配层映射保证，**前端零改动**。

## 4. 架构调整总览（BFF 适配层）

```
robot-ui（不变）→ BFF 对外接口（契约不变）
                    │  BFF 适配层：内部数据源切换 + 字段映射
                    ▼
            管理端(8866) 新增聚合/批量接口 ←（组织过滤自动生效、服务端缓存）
                    ▲ 定时采样（长稳）
            控制端(8867) 实时状态
```

- 管理端接口按 eiop 风格（`ApiResponse`/`PageResult`/camelCase/ISO 时间/数据权限过滤）。
- **BFF 对外结构不变**：管理端返回的字段（原始 code/英文名）由 BFF 映射为现有前端结构（中文名、分组口径）。

## 5. 兼容性设计（下沉映射表 + 边界）

### 5.1 下沉映射表

| 前端块（BFF 对外） | 当前 BFF 数据来源 | 下沉后 BFF 数据来源（管理端接口） | 字段映射 |
|---|---|---|---|
| `kpis.taskTotal` | 周期任务全量 `size()` | `statistics/tasks.total` | 直接 |
| `kpis.aiAlarmTotal` | 周期告警全量 `size()` | `statistics/alarms.total` | 直接 |
| `kpis.patrolMileage(+compareRate)` | 本项目 Control 里程 | **保持**（非管理端数据） | — |
| `equipmentRuntime.onlineRate` | 当前 realtimeStatuses | `devices/with-status` 或 `devices/realtime-statuses` 在线占比 | 在线数/总数 |
| `equipmentRuntime.taskCompletionRate` | 周期任务本地算 | `statistics/tasks`（completed/total） | BFF 算比率 |
| `equipmentRuntime.items` | registry 采样 + 文件 | `statistics/equipment-runtime` | 秒→小时（BFF 换算） |
| `aiAlarmAnalysis.alarmTypeRanking` | 告警全量本地按 alarmType 分组 | `statistics/alarms.typeRanking` | alarmType code → 中文名（BFF `alarmTypeName`） |
| `aiAlarmAnalysis.handleMethodRanking` | 告警全量本地按 handleResult 分组 | `statistics/alarms.handleMethodRanking` | handleResult → 中文名（BFF `handleMethodName`） |
| `alarmTrend` | 告警全量本地按时/日/月分组 | `statistics/alarms.trend`（`granularity=hour\|day\|month`） | 直接映射 points |
| `taskCompletion` | 任务全量本地按状态分组 | `statistics/tasks.byStatus`（原始 status code） | status → 4 组（BFF `taskStatusGroup`）+ 中文名 |
| `alarmAreaRanking` | 告警全量本地按**自由文本 address** 分组 | **保持 BFF**（见 5.2） | — |
| 设备/地图/任务明细（全景） | 管理端分页接口 | **保持**（地图点位大数据量、任务明细需要详情，不聚合） | — |

### 5.2 不适下沉 / 保持的块

- **`alarmAreaRanking`**：BFF 从告警 `areaName/location/rawPayload.location.address` 的**自由文本**解析区域（`StatisticsService.alarmAreaName`），管理端 SQL 无法按此分组。若告警量大需下沉，前提是管理端告警落库带**区域维度**（regionId/areaCode），否则**保持 BFF**。
- **`patrolMileage`**：来自本项目 Control 里程接口，不涉及管理端，保持。
- **地图/点位/路径/固定摄像头流**：大数据量或媒体链路，保持直查 + per-request 去重。
- **透传路径**（`/api/bigscreen/business/**`、`/api/manage/**`）：前端既有直连功能保持；管理端新增聚合后前端逐步切换。
- **STOMP 事件桥接**：事件订阅，非查询，保持。

### 5.3 迁移安全（不破坏前端）

1. **分块灰度**：逐个块切换（先 `kpis`/`taskCompletion`，再 `aiAlarmAnalysis`/`alarmTrend`，后 `equipmentRuntime`），每块上线后验证前端统计页无回归。
2. **双跑对比**：切换期间 BFF 可保留原逻辑旁路，对比新旧结果一致后再移除旧逻辑。
3. **管理端接口先上线**（对 BFF 不可见），BFF 用配置开关灰度：`statistics.management.aggregation-enabled`（默认 `false`，开启后走管理端聚合；可再按块细分 `statistics.management.aggregation-tasks/alarms/equipment-runtime`），回滚只需关开关。
4. **对外结构锁定**：新增 BFF 单测断言对外契约字段结构，防止映射回归（覆盖 `kpis`/`equipmentRuntime`/`aiAlarmAnalysis`/`alarmTrend`/`taskCompletion` 的字段与类型）。

## 6. 管理端新增接口（按 eiop 风格）

**通用约定**：
- 统一封装 `ApiResponse{code,message,data,traceId}`；分页 `PageResult{records,total,pageNum,pageSize}`；字段 camelCase；时间 ISO-8601；枚举/字典值大写。
- 鉴权走 `Authorization: Bearer <JWT>` + `PermissionCatalog` 权限码；组织过滤由 MyBatis-Plus 数据权限处理器按 `owner_org_id` 自动注入（无需 BFF/control 传组织参数）。
- **新增权限码**：`statistics/view`（`statistics/tasks`、`statistics/alarms`、`statistics/equipment-runtime`），`resource/device-view-status`（`devices/with-status`、`devices/realtime-statuses`、`devices/batch-detail`），需在 `PermissionCatalog` 注册。
- **缓存**：`statistics/*` 接口内置 30~60s 服务端缓存（key = `occurredFrom|occurredTo|deviceType|granularity`），多用户共享；`devices/with-status`、`devices/realtime-statuses` 建议 10~30s 缓存（在线状态时效性要求低）。

### 6.1 `GET /api/v1/management/statistics/tasks`

入参：`occurredFrom, occurredTo, deviceType?, regionId?`
响应 `data`：

```json
{
  "total": 10, "completed": 6, "failed": 1, "terminated": 1,
  "successRate": 75.0, "avgDurationSeconds": 1800,
  "byStatus": [ { "status": "COMPLETED", "count": 6 }, { "status": "RUNNING", "count": 1 } ],
  "dailyTrend": [ { "date": "2026-08-18", "total": 4, "completed": 3, "failed": 0 } ]
}
```

> - `byStatus` 返回管理端**原始任务状态码**（`PREPARING|RUNNING|PAUSING|PAUSED|RESUMING|TERMINATING|CONTROL_FAILED|COMPLETED|FAILED|TERMINATED`），BFF 按 `taskStatusGroup` 归并到前端 4 组（COMPLETED/RUNNING/PENDING/INTERRUPTED）并映射中文名。
> - `successRate = completed / total × 100`；`avgDurationSeconds` 用任务实例 `durationSeconds` 平均值。
> - 实现：按 `occurredFrom/occurredTo` 过滤 `task_workflow_instance`（`startedAt/completedAt`），`GROUP BY status`、按天 `DATE_FORMAT(started_at,'%Y-%m-%d')`；组织过滤由数据权限处理器自动注入 `owner_org_id`。

### 6.2 `GET /api/v1/management/statistics/alarms`

入参：`occurredFrom, occurredTo, deviceType?, severity?, status?, granularity?=day|hour|month`
响应 `data`：

```json
{
  "total": 50, "totalToday": 12,
  "bySeverity": { "INFO": 10, "WARN": 25, "CRITICAL": 15 },
  "byStatus": { "NEW": 8, "ACKNOWLEDGED": 5, "HANDLED": 30, "FALSE_ALARM": 7 },
  "handleRate": 74.0,
  "typeRanking": [ { "alarmType": "FIRE", "count": 20 } ],
  "handleMethodRanking": [ { "handleResult": "IMMEDIATE_DISPOSAL", "count": 30 } ],
  "trend": { "granularity": "day", "points": [ { "label": "2026-08-18", "count": 4 } ] }
}
```

> - `bySeverity`/`byStatus` 用管理端**大写枚举**（`INFO|WARN|CRITICAL`；`NEW|ACKNOWLEDGED|HANDLED|FALSE_ALARM`），BFF 映射为前端显示。
> - `handleRate = (HANDLED + FALSE_ALARM) / total × 100`；`totalToday` = 当日 0 点起告警数。
> - BFF 把 `alarmType`/`handleResult` 映射为前端中文名；`trend` 直接映射 `alarmTrend.points`（`granularity=day|hour|month`，`label` 对应 `MM.dd`/`HH:00`/`yyyy-MM`，由 BFF 按范围选粒度或透传）。
> - 实现：按 `occurredAt` 过滤 `alarm_record`，`GROUP BY severity/status/alarm_type/handle_result`、按粒度 `DATE_FORMAT(occurred_at, ...)`；组织过滤自动注入 `owner_org_id`。

### 6.3 `GET /api/v1/management/devices/with-status`

入参：`pageNum, pageSize, deviceType?, keyword?, regionId?`
响应 `data` = `PageResult`，`records[]` 每项 = `DeviceResponse` + `onlineStatus, lastReportedAt`。

> 替代「设备全量 + 单独批量状态」两步；Management 内部调 Control 批量状态拼接。

### 6.4 `GET /api/v1/management/devices/realtime-statuses`

入参：`serialNumbers`（query 分片，每批 ≤500）
响应 `data`：`[ { "serialNumber": "x30_test_1", "onlineStatus": "online", "lastReportedAt": "2026-08-18T10:00:00" } ]`

### 6.5 `GET /api/v1/management/devices/batch-detail`

入参：body `{"ids": [...]}`（≤500）
响应 `data`：`[ { "device": {...}, "components": [...] } ]`（替代 control N+1）

### 6.6 增强 `GET /task-workflow-instances`

新增入参 `startedFrom, startedTo`（时间过滤，统计链路不再拉全量）。

### 6.7 `GET /api/v1/management/statistics/equipment-runtime`（依赖 6.8）

入参：`occurredFrom, occurredTo, deviceType?`
响应 `data`：

```json
[ { "deviceType": "ROBOT_DOG", "deviceTypeName": "机器狗",
    "runningSeconds": 7200, "offlineSeconds": 3600, "faultSeconds": 0 } ]
```

### 6.8 设备状态历史（长稳方案）

- 新表 `device_status_daily(serial_number, device_type, stat_date, online_count, offline_count, fault_count)`（**按天聚合**，空间可控）。
- 数据来源：Management 定时任务（每 1 分钟）调 Control 实时状态，归一化 `online/offline/fault`（online 且 healthStatus 异常 → fault），累加到当天计数。
- 长稳考量：不依赖事件链路；Control 状态权威；单次失败只缺一点，不影响历史。
- 聚合口径：状态时长 = 采样跨度（首末采样时间差）× 状态计数占比。

## 8. 性能与并发设计

### 8.1 改造前后请求数对比（单用户冷 Overview，未命中 BFF 秒级缓存）

| 数据获取 | 改造前（到 8866/8867） | 改造后 |
|---|---|---|
| 设备 + 状态 | `devices` 全量翻页(≥3) + `realtimeStatuses` 超长 URL | `devices/with-status` ×1 |
| 任务统计 | `task-workflow-instances(ALL)` 全量翻页 | `statistics/tasks` ×1 |
| 告警统计 | `alarms` 时间窗全量翻页 + `alarmsPayload` 6 请求 | `statistics/alarms` ×1 |
| 装备时长 | BFF registry 采样 + 文件 | `statistics/equipment-runtime` ×1 |
| 里程 | 本项目 Control ×1（含上期 ×2） | 保持 |
| **合计** | **≈ 15~20 次** | **≈ 4~5 次** |

> 多用户并发：改造后由管理端聚合接口 30~60s 服务端缓存吸收，BFF 不再按用户放大全量拉取。

### 8.2 设计要点

- **聚合统计全部下沉管理端**，管理端聚合接口内加 **30~60s 服务端缓存**（key = `occurredFrom/occurredTo/granularity`），大屏多用户并发由管理端缓存吸收。
- 大屏 BFF 只做秒级短缓存转发，不再承担全量聚合；BFF 适配层映射开销可忽略。
- 消除项：全量翻页（devices/fixedCameras/tasks/alarms）、超长 queryParam（realtimeStatuses/mileage）、N+1（taskDetail/control 预热）、每连接全量（WS 授权）。
- 统计类数据允许 30~60s 延迟（缓存命中），非实时性不影响大屏展示。
- 管理端聚合接口建议独立于业务写接口做缓存，避免热点表争用；`granularity` 参数避免 BFF 端二次聚合大表。

## 9. 实施优先级

- **P0**：6.1/6.2（任务/告警统计聚合）、6.3/6.4（设备+状态/批量状态）、`StatisticsService`/`PanoramaService`/WS 授权改造（含映射与单测）。
- **P1**：6.5（批量详情）、6.6（任务时间过滤）、`ControlManagementClient` 预热与固定摄像头缓存。
- **P2**：6.8+6.7（设备状态历史 + 采样 + equipment-runtime），大屏 BFF 移除本地采样。
- **可选/边界**：`alarmAreaRanking` 下沉（需管理端告警带区域维度，另行评估）。
