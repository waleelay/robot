## 1. 结论摘要

本次重构不应把 BFF 内所有查询合并成一个「超级接口」，而应按数据归属处理：

直接目标是解决指挥中心、巡逻巡查全景地图和数据统计页的查询成本、数据完整性与口径问题：
把 BFF 全量拉取后筛选/聚合改成数据所属服务的有界查询，减少 N+1、重复扇出、分页截断和超长 URL，
并让页面按已确认的筛选条件展示真实数据。接口数量减少只是手段，页面查询正确、完整、长期稳定才是验收结果。

1. **持久业务事实的统计下沉 Management**：任务、告警的时间窗口聚合在数据库完成，不再向 BFF 传输全量历史记录。
2. **设备状态归本项目 Control**：当前状态和永久状态区间同源；不在 Management 创建长期耦合的 `devices/with-status`，BFF 用 Management 当前授权资源筛出可查 `robotIds`。
3. **明细与大数据资源保留分页/按需查询**：设备、地图、点位、路线、任务详情和回放不能用统计结果替代。
4. **BFF 继续是前端反腐层**：Management/Control 返回原始枚举和领域读模型；BFF 继续维护中文标签、任务四组状态、比率、数据质量和前端 DTO。`robot-ui` 只完成筛选和日期边界、报告条件、零值/不可用判定、请求竞态与失效选项恢复等必要适配；名称、布局及展示项按第 4 节冻结，不新增解释文案或重做页面结构。

迁移顺序：

```text
消除无界全量/N+1/超长 URL
  -> 下沉任务和告警统计
  -> 下沉全景告警快照和任务卡片读模型
  -> 建立可审计的设备状态区间历史
  -> 删除 BFF 全量聚合和本地采样兼容路径
```

| EIOP Control | 保持现有功能，本方案不新增或修改其正式接口、MQTT、Redis 和 Admin UI 链路 | 仅在新增事实证明必须保留某个字段依赖时重新评估 |

执行规则：

1. **本仓库与 EIOP 分开交付**：不在同一提交、同一未完成闭环中夹带两个仓库的实现。
2. **先逐项确认，再分仓实现**：虽然本次由同一开发者完成 EIOP 与本项目的改造，仍必须先确认接口、权限、数据范围、错误、时间口径和发布顺序；先在 EIOP 完成独立可验证交付，再在本仓库接入。
3. **不改变现有 EIOP 语义**：查询迁移只增加读能力及精确的接入配置，不改原列表、详情、写操作和权限授予。报告档案是独立新增领域；派生汇总优先从持久事实异步读取。区域快照需要新增采集点，必须在其独立包列出准确修改范围和零业务行为变化的证据，不能夹带进查询迁移。
4. **不清晰项只阻塞对应闭环**：字段权威、业务口径、权限、历史回填或失败语义未明确时，不进入依赖它的编码或切换。当前按用户要求仅梳理文档；后续获准开发后，独立明确的分页、精确查询等整改可先交付。常规实现细节由代码和测试验证，不反复重新确认已定业务口径。
5. **每次只做一个可回滚闭环**：一个数据块的契约、适配、测试、灰度和回滚完成后，再进入下一个数据块。
6. **实现能力不随审核加码**：以 1.2 的页面问题和已确认需求为范围基线；正确性问题优先修正现有查询、判定或生命周期，
   不默认增加服务、端点、表、定时任务种类或通用平台。确需超出已列能力时只记录依据并单独确认，不能通过新增验收项变相扩大开发范围。

### 2.1 EIOP 已有能力

| 能力 | 当前契约 | 结论 |
| --- | --- | --- |
| 运营概览 | `GET /api/v1/management/overview` | 已聚合当日设备/任务/告警/资源和 7 日趋势；复用其读模型实现思路，但不直接替换大屏契约 |

| 计划摄像头 | `GET /api/v1/management/task-workflow-plans/{id}/fixed-cameras` | 已覆盖计划及依赖工作流，继续按需读取 |
| 任务列表 | `GET /api/v1/management/task-workflow-instances` | 支持 `scope/status/triggerType`，不支持时间窗口；统计不应复用列表全量翻页 |

### 2.2 对初稿的重要修正

- 不新建 `GET /devices/batch-detail` 并携带 request body；复合批查统一使用 `POST .../*-queries`。
- 不声称 Management 统计缓存可「多用户无条件共享」；数据范围不同时必须隔离。
- 不用 `online_count/offline_count/fault_count × 首末跨度` 估算运行时长；长期模型改为幂等状态区间。
- 不把 EIOP Management 概览直接当作大屏概览：两者的权限、时间窗口、告警列表、设备运行态和前端 DTO 都不同。
- WebSocket 授权已有按身份共享、最大陈旧 5 分钟、错峰刷新和 fail-closed；需优化的是每次刷新的全档案载荷，不是重做一套缓存。

### 2.3 必须保持的服务边界

- Management 持久化设备档案、地图、任务、告警和历史事实，不处理 MQTT，不成为 Redis 当前状态的第二权威。
- EIOP Control 保存 Redis/MQTT 实时状态；本项目 Control 保存大屏当前使用的机器人注册表与里程。两套状态在统一前不得混用。
- BFF 负责 JWT 传递、授权资源与全局运行态的安全关联、字段转换、前端契约和降级语义。
- `robot-ui` 只消费 BFF 契约，不直接组合 Management 与 Control 数据。

#### 3.2.1 A0 摘要与详情缓存的最小隔离

源码中 `ControlManagementClient.cachedDeviceBySerialNumber()` 在详情未命中时回退列表摘要；
`EquipmentControlService.handleClientState()/mergeEdgeStatus()` 又用该对象重建 `devices`，
而 `devices(robot, runtimeDevices)` 在缺少 `components` 时返回空列表。因此不能只删除预热调用，
否则冷缓存/详情过期后可能把「尚未加载组件」解释成「设备没有组件」。这是本项目缓存消费风险，不是 EIOP 业务缺陷。

1. 列表摘要和完整详情必须具有可判别的内部来源/完整性，采用分开的访问方法或缓存类型；
   不用「Optional 非空」「存在 id」或 `components` 缺失来证明详情完整。列表刷新不得覆盖仍有效的完整详情。
2. 状态合并只允许完整、有效且属于当前授权身份的档案驱动组件集合替换；摘要仅补充明确拥有的基础字段，
   不依据缺字段清空已有 `devices`、相机或运行态。客户端显式上报和已验证完整详情中的空组件集合仍按各自原契约处理。
3. 冷缓存不伪造空组件事实；保留已有有效运行态，没有数据时保持既有未知/未加载语义。
   实际进入设备详情或控制能力校验时按单设备精确加载完整档案；详情不可取得时该操作按原失败语义处理，不能借摘要授权控制。
4. 不在每条 MQTT/状态消息中补查详情，不将 N+1 从建连搬到事件处理；同身份同设备的必要详情请求合并。
   缓存沿用身份隔离、有效期及撤权清理，过期详情不能继续作为权限或能力凭据；保留运行态不等于允许越权展示。
5. A0 的文件边界增加本项目 `EquipmentControlService` 必要的合并保护和对应测试，
   不改 MQTT/WS 协议、设备控制规则、EIOP 档案接口或写入行为，不新增表。

### 3.4 数据统计页实际核验（2026-09-26）

对已登录的现行部署页面进行了只读核验，与 `robot-ui` 和 BFF 代码对照后确认：

- 页面顶部只有时间范围和设备类型筛选，没有区域筛选器。
- 页面标签为「全部/今日/本周/本月/自定义」，但当前 BFF 实现将「本周」解释为含今日的最近 7 个自然日，将「全部」固定为最近 6 个月，与字面含义不一致。
- 两组筛选是整页查询条件，不是只影响部分图表：KPI、在线率、运行/故障/离线时长、告警分析/趋势/排行、任务完成率和 PDF 都必须使用同一组条件。
- 第二组只展示「全部+当前授权且已启用设备中实际存在的机器人类型」；当前 BFF 强制追加的 `FIXED_CAMERA/固定摄像头` 选项需移除，「全部」也不包含停用机器人或固定摄像头事实。
- 当前 BFF `devices()` 未向 Management 传 `enabled`，而 EIOP 设备列表仅在该参数非空时过滤，因此现状会把停用设备带入统计候选集合；目标实现必须显式查询 `enabled=true`，不能依赖默认行为。
- 当前 `equipmentRuntime.onlineRate` 使用请求时刻的在线设备数，没有应用页面时间范围；目标口径必须改为筛选窗口内的在线时长比。
- AI 告警总数、页面当前标题为「告警类型分布排行」的饼图、处理方式分布和告警趋势均有数据，
  但「告警高发区域排行榜」单独显示「暂无数据」。
- 现行 BFF 将 `alarm_type` 按 `FIRE/SMOKE/INTRUSION/TEMPERATURE` 硬编码成该饼图，但 Management
  告警页对应的业务维度是 `source_type` 表达的「告警范围」，当前契约值只有
  `TASK/任务告警`、`DEVICE/设备告警`、`COMPONENT/组件告警`。`alarm_type` 是可扩展的技术告警码，
  不适合由 BFF 穷举名称，也不应继续被该图误称为 Management 告警类型。
- 前端只展示 BFF `alarmAreaRanking[].areaName/count/percent`；BFF 当前仅对能解析出
  `areaName/locationName/address` 的告警分组，并将 `areaId` 固定为 `null`。

因此「告警高发区域」是正式页面能力，不是可删除字段；但当前地址文本来源覆盖不足。
迁移不能将「当前为空」误判为「长期只需文本分组」。

## 4. 对外契约红线

- 保持 `/api/bigscreen/panorama/**`、`/api/bigscreen/statistics/**`、报告和 `/ws/bigscreen` 入口不变。
- 统计块 `kpis/equipmentRuntime/aiAlarmAnalysis/alarmAreaRanking/alarmTrend/taskCompletion` 字段、类型、空值不变。

- 下游失败不得映射为真实 0/空集合，继续用 `dataQuality.available/complete/degraded/reasonCodes` 表达；`401/403` 不降级。

- 质量字段必须保留，但不新增覆盖提示卡片、说明文案或第四类图例。必要数值事实缺失时使用现有 `--`/不可用占位，不展示部分结果冒充整窗；真实零值仍显示 0。里程统一按 8.3.1 判断已入账数值是否完整可核算，采集质量单独披露，不因任一历史质量码永久隐藏 ALL，也不把估算标为实测完整。PDF 在既有说明区域记录覆盖与原因，不扩展网页布局。

### 4.1 时间格式兼容与工程契约门禁

新增与整改遵循 [Alibaba 与 OpenAPI 开发规范](../../02-设计/工程规范/Alibaba与OpenAPI开发规范.md)，
自动检查范围以 [quality/README.md](../../../quality/README.md) 和
[规范整改执行记录](../../04-测试与验收/执行记录/规范整改执行记录-20260929.md) 为准。
当前里程旧 GET 的机器契约试点不等于本文新查询端点已实施或全接口已覆盖。

1. BFF 既有对外时间字段按实际现行契约保持格式。统计 Overview 的 `serverTime/range.startTime/range.endTime`
   保留上海时区 `yyyy-MM-dd HH:mm:ss`；ALL 的 startTime 仍为 null。归一化截止口径的修正不附带改变序列化格式。
   这些字符串不得标为 RFC 3339 的 `format: date-time`，应在 Schema 中描述格式/时区/匹配约束及可空性。
2. 本文新增内部查询的时间使用带偏移的 RFC 3339 字符串，并明确 `zoneId=Asia/Shanghai`；
   BFF 在边界转换同一时刻，不直接把下游字符串透传到旧字段。新增质量字段的时间可使用该明确格式，
   但不能带动旧 HTTP、WS 或报告元数据字段全局换格式；存量字段逐项以消费者测试核实。
3. 每包列出生产者、消费者及变更前后样例，明确 `operationId`、字段类型/单位、必填与可空、分页/批次上限、
   成功和真实错误响应、鉴权及内部信任边界。检查枚举扩展、时间精度、`Idempotency-Key` 必填等行为变化，
   不以「只增加字段/注解」替代兼容性评估。报告 D 包须列全调用方，按 8.5.1 同包切换；旧客户端缺键明确失败，不静默生成新键。
4. 新 HTTP 端点实现前审查契约设计，实现后核对生成契约、真实响应与消费者；
   Management 契约来自 EIOP 对应实现/经核验导出物，BFF 代理另核对路径和鉴权映射，缺失覆盖必须列出。
   本文保留业务流程和示例，不另建与生成物漂移的第二套完整 Schema。
5. 后续 Java 变更运行已启用的增量规则和相关测试，HTTP 变更执行其实际覆盖的契约检查；
   未覆盖规则人工审查，未覆盖端点不能用旧 GET 的检查通过代替。WS/MQTT 生命周期单独验证。
   本轮仅修改设计文档，不新增检查平台、不更新生成契约，也不将既往试点结果记为本方案验收。

## 5. 目标架构

```text
robot-ui
  -> Bigscreen BFF（前端 DTO、安全关联、秒级缓存、降级语义）
       -> EIOP Management（授权后的持久事实、SQL 聚合、历史读模型）
       -> EIOP Control（现有 HTTP/WebSocket、Redis TTL 和 MQTT 能力保持不变；BFF 最终不再依赖其状态明细）
       -> robot-mediaserver Control（大屏当前运行态、永久状态区间/日汇总、里程、固定摄像头健康）
```

禁止形态：

- Management 为每个设备串行调 Control，把 N+1 从 BFF 搬到 Management。
- 统计接口返回数千条「供 BFF 自行聚合」的半成品。
- BFF 或 Management 用全局缓存跨用户共享数据权限结果。
- 用设备当前类型/区域覆盖已有历史快照或改写已生成 PDF；本页按当前类型选择机器人，只改变查询集合，不修改原始历史事实。

## 7. 新接口设计

### 7.1 通用规则

- 批量或复合查询使用 `POST .../*-queries` + JSON body；它们是无副作用读操作。
- 时间窗口统一为 `[from,to)` 左闭右开，入参携带 ISO-8601 时区偏移。
- 列表批量上限 500；超限返回 HTTP 400 / `400001`，不静默截断。
- EIOP 新接口响应使用 `ApiResponse{code,message,data,traceId}`；本项目 Control 内部接口沿用本项目现有响应/异常约定，BFF 统一归一化下游错误。
- 计数使用 `long`，时长使用整数秒；比率由 BFF 使用计数计算，避免多端舍入差异。
- 统计返回原始代码，不返回 BFF 专用中文。

#### 7.1.1 通用性与扩展性约束

统计类接口采用「统一查询信封 + 领域化响应块」，不为每个大屏卡片新建一个接口，
也不建立跨任务、告警和设备的通用 SQL/DSL 查询器。

| 结构 | 作用 | 扩展规则 |
| --- | --- | --- |
| `timeRange` | 统一表达时间字段、左闭右开边界和分桶时区 | `basis` 使用受控枚举；P0 只实现有明确口径的值，不支持的值返回 400 |
| `filters` | 领域过滤条件 | 多值统一用数组；字段为加法式扩展，不把 `null/all/空字符串` 混作业务值 |
| `includes` | 调用方声明需要的聚合块 | 只允许各领域白名单值；未请求的高成本块不计算，未知值返回 400 |
| `options` | 分桶粒度、排行上限等有界参数 | 只对已请求的聚合块生效，必须有默认值和最大值 |
| `summary` | 领域稳定核心计数 | 返回可复算的原始计数，不固化 BFF 文案和百分比 |
| 可选响应块 | 状态分布、趋势、排行等 | 新增块不改旧块语义；破坏性变更必须新版本/新端点 |

其他约束：

- `snapshotAt` 必须返回，明确「历史范围 + 查询时当前状态」的快照时点。
- `filters` 字段缺省或数组为空表示不限制；`includes` 缺省时只返回 `summary`，调用方应显式请求其他聚合块。
- 服务端拒绝未知请求字段和枚举，防止拼写错误被静默忽略；消费者必须容忍响应中新增的可选字段和聚合块。
- 同一业务事实在 Management 内一次 SQL/有界查询完成；不在通用层跨服务 join。
- 空集返回零计数和空聚合块；下游失败不伪装成空集。
- 请求组合必须是服务端白名单，并限制时间窗口、分组数和排行数；通用性不等于开放任意字段、表达式或排序。
- 页面需要同期比时，BFF 在 `options.comparisonTimeRange` 显式传入由 8.4 规则推导出的上一窗口；Management 复用同一权限和 `filters`，只额外返回 `comparisonSummary`，不为上一窗口重复计算趋势、排行或状态分布。`ALL` 不传该选项。

#### 7.1.2 当前机器人集合与历史事实归属（2026-09-27 修订确认）

本页所有统计域统一按「当前授权、启用且当前类型匹配」选定机器人集合，再查询该集合关联的历史事实。
`filters.deviceTypeCodes` 表示设备当前档案类型；空数组表示全部当前启用授权机器人类型。
这项确认替代先前“任务/告警按历史类型、状态/里程按当前类型”的混合口径。

| 统计域 | 与选中机器人集合的关联 | 计数规则 |
| --- | --- | --- |
| 任务 | 通过设备子任务关联当前选中机器人，使用 `exists`/半连接匹配 | 对 `task_workflow_instance.id` 去重；同一实例匹配多台机器人仍只计一次 |
| 告警 | 告警关联设备属于当前选中机器人集合 | 每条持久告警只计一次；关联必须唯一且通过当前权限检查 |
| 里程、运行时长 | Control 接收 BFF 解析出的同一组 `robotIds` | 按设备汇总窗口内的里程、状态秒数 |

具体约束：

1. 机器人从 A 类型改为 B 类型后，其历史任务、告警、里程和时长统一参与 B 类型查询；
   A 类型查询不再包含该机器人，但共有任务仍可因另一台 A 类型机器人命中而计入。
   各类型任务数不能直接相加得到“全部”，后者必须重新按工作流实例去重。
2. 当前窗口、上一比较窗口、图表和新生成 PDF 使用同一机器人筛选条件。
   Management 必须复用当前设备权限、启用状态和类型条件，并验证与 BFF 资源版本一致；变化时重新取得集合，不能混用类型变更前后的结果。
3. 已有历史类型快照保留供审计，本页不按快照筛选、不覆盖其原值。
   本次查询迁移不再要求为类型筛选新增 `device_type_snapshot`、修改事实写入或回填存量；
   尚未存在的快照采集能力不作为本次前置，也不在本次额外开发。
4. 原方案 `dimensionQuality.deviceType` 的历史类型回填质量不再决定本页可用性；
   当前类型编码仍按 Management 字典严格校验，关联缺失或历史覆盖不足另行披露，不能伪装成完整历史。
5. 已生成 PDF 及生成时筛选元数据保持不可变。类型变更后重查历史窗口或生成新 PDF 可以得到不同分组结果，
   这是按当前设备集合查询的明确语义，不回写旧报告。

#### 7.1.3 设备集合与类型字典的只读投影（2026-09-28 技术细化）

为同时替代统计设备全字段翻页、消除类型字典 200 条截断和校验跨接口设备集合，新增一个设备领域读接口：

```http
POST /api/v1/management/devices/scope-queries
```

```json
{
  "filters": {"enabled": true},
  "includes": ["DEVICES", "TYPE_OPTIONS"],
  "cursor": null,
  "limit": 200,
  "expectedRevision": null
}
```

响应 `data` 包含 `deviceScopeRevision/snapshotAt/total/nextCursor`，按 includes 返回
`records[].id/serialNumber/deviceType/enabled` 和 `deviceTypeOptions[].value/label/sortOrder`。
`total` 是全部当前启用授权机器人数量；类型选项从这整个集合生成，不随 UI 当前选中类型缩小。
ID 按既有服务约定传输，BFF 必须区分 Management 主键与 Control 序列号。

边界和一致性机制：

1. 新接口只读现有设备、字典和权限事实，要求 `resource.device.view`；不授予字典管理权限，
   不返回未被当前可见设备引用的字典项，不返回组件明细或凭据。本次固定 `enabled=true`，其他组合不预建空实现。
2. 设备记录按稳定 ID 游标分页，`limit` 默认 200、最大 500，适用新 DTO，不修改旧 `PageQuery`。
   类型查询使用该集合中的实际编码在数据库关联字典，不调用固定单页选择器；按 sortOrder、稳定编码排序。
   类型数量随可见设备实际类型增长，不能静默取前 200。缺项、重复值、空名按现有根数据质量规则失败。
3. `deviceScopeRevision` 是服务端在同一只读数据库快照中计算的内容指纹：固定协议版本、
   当前身份、有效设备/任务/告警查看权限及各自数据范围、按 ID 排序的全部启用可见设备
   `id/serialNumber/deviceType`、被引用类型的代码/名称/排序。规范化序列化后计算 SHA-256；
   不包含当前时钟、在线状态或页码。权限字段仅参与指纹，不向调用者返回角色、组织或授权明细。
4. 它是内容一致性校验值，不是新的持久版本表或授权凭证；仍逐请求执行权限检查。
   不为生成指纹修改 EIOP 原设备/字典/角色写流程，不依赖可能漏送的 WebSocket 事件。
   对当前资源投影做一次有界内存或流式哈希，禁止据此重新拉取全量历史任务/告警。
5. 后续设备页携带 `expectedRevision` 和游标，服务端重算并校验；游标绑定该指纹和末项 ID。
   不一致返回 409 / `409000`，不返回部分页；BFF 丢弃整轮拼接。篡改/非法游标返回 400。
   `includes=[]` 只返回摘要与指纹，供最终复核；`TYPE_OPTIONS` 只需首轮请求。
6. 任务/告警统计在 `options.deviceScopeRevision` 接受该指纹，在其只读事务内重算同一资源上下文后
   校验，再关联同一可见设备集合及各自事实权限；响应回显实际 `deviceScopeRevision`。
   任意第三方调用不传指纹时仍自行执行全套权限与筛选，不能据缺省扩大数据范围。
   BFF 必须传指纹并校验回显，不将按设备分批的任务计数相加，以免同一任务重复计数。
7. BFF 固定本次时间边界，取得完整设备投影后并行查各域，再用 scope-queries 摘要复核一次。
   当前/上一窗口复用同一设备集合。分页、统计或最终复核发生 409 时最多整轮重试一次；
   持续变化返回 BFF 503 和 `RESOURCE_SCOPE_CHANGED`，401/403 则直接按鉴权失败处理。
   这三个 Management 只读端点中的 409 专指上下文失效，沿用通用错误封装，不新增业务码或依赖文案解析。
8. 一致性保证止于最终复核时点；后续变化由事件触发刷新。任务、告警事实仍是各域各自读取时的当前结果，
   不承诺跨服务事务快照，也不为此引入分布式锁或历史组织/类型投影。

字典和权限指纹计算复用现有领域查询与权限解析，设备/任务/告警权限范围必须分别求值。
若当前权限插件导致新 Mapper 被错误叠加另一领域的组织谓词，按 18.3 使用局部、精确可测试的查询适配；
不得修改全局角色授予、关闭全局数据权限或创建另一套权限算法。
此端点属于 A1 统计接入的必需基础，不能以“正式上线后再补”替代；M1 可先完成纯接口 fixture，
但正式消费者接入必须与该契约一起验证。资源规模下的指纹开销需纳入压测，不能承诺零成本。

### 7.2 任务统计

```http
POST /api/v1/management/task-workflow-instances/statistics-queries
```

```json
{
  "timeRange": {
    "basis": "STARTED_AT",
    "from": "2026-09-01T00:00:00+08:00",
    "to": "2026-09-26T10:30:00+08:00",
    "zoneId": "Asia/Shanghai"
  },
  "filters": {
    "executorResourceTypes": ["DEVICE"],
    "deviceEnabled": true,
    "deviceTypeCodes": [],
    "triggerTypes": [],
    "statuses": []
  },
  "includes": ["STATUS_DISTRIBUTION"],
  "options": {
    "deviceScopeRevision": "scope-revision-example",
    "comparisonTimeRange": {
      "from": "2026-08-01T00:00:00+08:00",
      "to": "2026-08-26T10:30:00+08:00"
    }
  }
}
```

```json
{
  "snapshotAt": "2026-09-26T10:30:00+08:00",
  "summary": {"instanceCount": 10},
  "deviceScopeRevision": "scope-revision-example",
  "comparisonSummary": {"instanceCount": 8},
  "statusDistribution": [
    {"status": "COMPLETED", "instanceCount": 6},
    {"status": "RUNNING", "instanceCount": 3},
    {"status": "FAILED", "instanceCount": 1}
  ]
}
```

口径：

- 任务数、完成率和状态分布统一使用 `started_at` 归入 `[timeRange.from,timeRange.to)`；
  EIOP `task_workflow_instance.started_at` 为非空的平台工作流实例创建/启动时间，不再回退到
  `completed_at` 或 `created_at`。它不等于边缘设备首次 ACK 或物理开始执行时间。
- P0 只接受 `timeRange.basis=STARTED_AT`。若未来需要「本期完成任务数」，可加法式增加
  `COMPLETED_AT`，但必须作为另一种查询口径，不得在同一结果中将启动分母与完成分子跨窗口混算。
- 一个实例只归入启动时间所在窗口，完成时不再计入另一窗口。`statusDistribution` 表示
  `snapshotAt` 时的当前状态，因此任务进入终态前，重查同一历史启动窗口的状态分布可变；
  报告是生成时快照，不冒充「窗口结束时状态」。
- P0 实现 `summary + STATUS_DISTRIBUTION`，供 KPI、完成率、四组状态和报告使用。
  P1 按 7.10 加法式实现已确认的 `LIFECYCLE_OVERLAP + DURATION_SUMMARY`，仅用于生命周期经过时长；
  它不能改变 STARTED_AT 的现有含义。`TRIGGER_TYPE_DISTRIBUTION/TIME_TREND` 仍为后续可选扩展，不预建空实现。
- 「今日巡逻时长」是任务区间在今日的累计经过时间，包含准备、暂停和等待，不代表设备实际运动或扣除暂停后的有效执行时长。
  后两种指标仍不在本次范围；不得为查询迁移新增任务状态采集或改动原任务状态机。
- `deviceTypeCodes` 按 7.1.2 匹配设备当前类型，并与当前授权、启用条件作用于同一设备关联；任务按匹配子任务所属工作流实例去重，不按历史类型快照过滤。
- BFF 固定传 `executorResourceTypes=[DEVICE],deviceEnabled=true`，表示当前页面只统计至少有一台「查询时当前启用且有权限」机器人执行者的任务；仅绑定停用机器人或固定摄像头的事实不纳入，启用机器人任务附带固定摄像头资源仍按机器人任务统计。
- BFF 将原状态归并为 `COMPLETED/RUNNING/PENDING/INTERRUPTED`。
- `comparisonSummary` 只供 `kpis.taskTotal.compareRate` 使用，按同一 `deviceTypeCodes` 和数据权限统计；不得复用当前窗口的状态分布，也不得因上一窗口为 0 而伪造无限增长率。

### 7.3 告警统计

```http
POST /api/v1/management/alarms/statistics-queries
```

```json
{
  "timeRange": {
    "basis": "OCCURRED_AT",
    "from": "2026-09-01T00:00:00+08:00",
    "to": "2026-09-26T10:30:00+08:00",
    "zoneId": "Asia/Shanghai"
  },
  "filters": {
    "deviceEnabled": true,
    "deviceTypeCodes": [],
    "severities": [],
    "statuses": []
  },
  "includes": [
    "SCOPE_DISTRIBUTION",
    "HANDLE_METHOD_RANKING",
    "LOCATION_RANKING",
    "TIME_TREND"
  ],
  "options": {
    "trendGranularity": "DAY",
    "rankingLimit": 10,
    "deviceScopeRevision": "scope-revision-example",
    "comparisonTimeRange": {
      "from": "2026-08-01T00:00:00+08:00",
      "to": "2026-08-26T10:30:00+08:00"
    }
  }
}
```

```json
{
  "snapshotAt": "2026-09-26T10:30:00+08:00",
  "summary": {
    "recordCount": 50,
    "handledCount": 30,
    "unhandledCount": 20
  },
  "comparisonSummary": {"recordCount": 40},
  "deviceScopeRevision": "scope-revision-example",
  "alarmScopeDistribution": [
    {"alarmScope": "TASK", "recordCount": 20},
    {"alarmScope": "DEVICE", "recordCount": 22},
    {"alarmScope": "COMPONENT", "recordCount": 8}
  ],
  "handleMethodRanking": [
    {"handleMethod": "HANDLE_NOW", "recordCount": 25},
    {"handleMethod": "FALSE_ALARM", "recordCount": 5}
  ],
  "locationRanking": {
    "dimension": "LOCATION_TEXT",
    "items": [{"locationKey": "address:一号车间", "locationName": "一号车间", "recordCount": 12}]
  },
  "timeTrend": [{"bucketStart": "2026-09-01T00:00:00+08:00", "recordCount": 4}],
  "dimensionQuality": {
    "alarmScope": {"validCount": 50, "invalidCount": 0, "complete": true}
  }
}
```

口径：

- `summary.recordCount` 是持久告警记录数，表示进入告警列表、通知和工作流处置的业务告警事件。
  大屏 `aiAlarmTotal`、告警范围/区域/处理方式分布和告警趋势统一使用该口径。
- **不得再传 `sourceResourceTypes=[DEVICE]` 或等价的 `sourceType=DEVICE` 过滤**。Management 的
  `source_type` 是告警范围，这种过滤会错误丢失同一机器人上的任务告警和组件告警。
  本页排除停用机器人和固定摄像头应通过「告警关联当前启用且授权的机器人」条件完成，
  不能把告警范围当成资源类型。无法通过 `alarm_record.device_id/serial_number` 关联到该机器人集合的告警不进入本页 KPI、分布或趋势。
- `SCOPE_DISTRIBUTION` 只使用 `alarm_record.source_type`，领域值为
  `TASK`、`DEVICE`、`COMPONENT`；Management 返回原始枚举和计数，不返回大屏专用中文名称。
  `alarm_type` 继续作为告警技术码用于列表、详情和后续专项分析，不参与本页这张分布图。
- BFF 将 `alarmScopeDistribution` 映射到现有对外字段
  `aiAlarmAnalysis.alarmTypeRanking[]`，以保持前端 DTO 兼容：`TASK -> 任务告警`、
  `DEVICE -> 设备告警`、`COMPONENT -> 组件告警`，再按计数倒序组装现有 `name/count/percent`。
  `robot-ui` 保留现有「告警类型分布排行」标题，按第 4 节只调整供数与绑定，不新增筛选、图例或交互。
- 正常数据下三个范围计数之和必须等于 `summary.recordCount`。鉴于现有同步 DTO 对
  `sourceType` 只做非空和长度校验，新统计读接口不应顺带改动原写入接口的拒绝行为。
  若存量出现三值以外的异常数据，不渲染「未知类型」或第四块图例；返回
  `dimensionQuality.alarmScope.complete=false/invalidCount`，接口中的已分类百分比以 `validCount` 为分母；页面该图使用现有不可用态，PDF 在原说明区记录不完整原因，
  其他告警 KPI 仍按全部持久告警记录计数。是否后续收紧写入校验单独评审，不与本次读迁移捆绑。
- 这与 EIOP 的风暴抑制只有一个迁移边界：例如同设备同告警码 10 秒内上报 100 次，
  EIOP 持久化 1 条告警并记录 `suppressed_count=99`；当前大屏看到和统计的是 1 条，
  新聚合接口也必须返回 `recordCount=1`，不得改成 100。
- P0 不查询、不返回、不展示 `suppressed_count`，不为大屏新增「告警风暴」功能。
  若未来有独立运维需求，再单独设计原始上报强度和时间桶，不与本次大屏查询迁移捆绑。
- `HANDLE_METHOD_RANKING` 不读取自由文本 `handle_result`，而是按当前持久终态稳定映射：
  `status=HANDLED -> HANDLE_NOW`，`status=FALSE_ALARM -> FALSE_ALARM`。
  `NEW/ACKNOWLEDGED` 以及执行 `DEFER` 后仍未终结的告警不进入排行，计入 `unhandledCount`。
- `summary.handledCount` 等于 `HANDLED + FALSE_ALARM`，`unhandledCount=recordCount-handledCount`；
  `handleMethodRanking[].recordCount` 之和必须等于 `handledCount`。BFF 以 `handledCount` 为分母计算现有
  `aiAlarmAnalysis.handleMethodRanking[].percent`，因此两类方法百分比合计为 100%，未处理告警不稀释该图。
- `handle_result` 是最长 1000 字符的用户处置结果/说明，`handled_by` 是处置人；两者都不是处理方式，
  不参与该排行，也不得将任意自由文本直接回显成图例。现有历史记录可直接按终态统计，不需要回填或修改处置写逻辑。
- 页面当前不展示单独处置率；如未来增加，复用 `handledCount/recordCount` 计算，Management 仍返回原始计数，不返回大屏专用百分比。
- `bucketStart` 是真实桶起点，BFF 再格式化为 `HH:00/MM.dd/yyyy-MM`。
- `comparisonSummary` 只供 `kpis.aiAlarmTotal.compareRate` 使用，复用同一告警口径、设备类型和数据范围；上一窗口不重复返回排行与趋势。
- 当前 `alarm_record` 只在 `raw_payload` 中有地址文本。P0 按与 BFF 相同的优先级聚合，
  并显式标记 `dimension=LOCATION_TEXT`；具体边界见 7.3.1。

#### 7.3.1 告警高发区域数据源（已确认）

结合 3.4 的页面实际核验，这一项需分成两个可独立回滚的阶段：

**P0：先完成查询迁移，不伪造区域数据**

1. `LOCATION_RANKING` 按现有 `areaName/locationName/address` 优先级和非空原文精确分组，
   不新增去空白、分词、模糊合并、地理编码或行政区推断。
2. 响应标记 `dimension=LOCATION_TEXT`，BFF 继续转为现有
   `alarmAreaRanking[].areaName/count/percent`，`areaId` 仍为 `null`，不改 `robot-ui` 契约。
3. 当 `recordCount > 0` 且无任何告警可解析位置文本时，Management 返回
   `dimensionQuality.locationText.complete=false/availableCount=0`，BFF 记录数据质量原因；
   对现有前端仍返回空榜，不用「其他」伪造区域。
4. 对外 `areaId` 参数暂保留但明确标记「未生效」，P0 不传给 Management，
   不在查询迁移中顺带改变页面功能。

**P1：使正式「告警高发区域」卡片具备稳定数据源**

2. 区域解析优先级为 `location.mapId -> Map.region` 优先，无可用地图区域时回退到

3. Management 新增 `REGION_RANKING`；BFF 优先将它适配为现有 `alarmAreaRanking`，

4. 存量告警先使用原有地址文本；如要使现有空榜尽快可用，可一次性按当前地图/设备区域回填，
   但必须分别标记 `BACKFILLED_CURRENT_MAP/BACKFILLED_CURRENT_DEVICE`，无法解析为 `UNKNOWN`，
   并通过 `dimensionQuality.region` 披露，不宣称为精确历史。

`filters.regionIds` 仅在 P1 区域快照、数据质量和页面交互都确认后再激活；

### 7.4 全景告警快照

```http
POST /api/v1/management/alarms/snapshot-queries
```

```json
{
  "periodTimeRange": {
    "basis": "OCCURRED_AT",
    "from": "2026-09-26T00:00:00+08:00",
    "to": "2026-09-26T10:30:00+08:00",
    "zoneId": "Asia/Shanghai"
  },
  "severities": ["CRITICAL", "WARN", "INFO"],
  "latestPerSeverity": 20,
  "includes": ["ACTIVE_MAX_SEVERITY_BY_DEVICE"]
}
```

响应一次返回 `activeTotal`、`activeBySeverity[]`、每等级有界 `latest[]`、`periodTotal`、`periodByStatus[]`和 `generatedAt`。
可选 `ACTIVE_MAX_SEVERITY_BY_DEVICE` 块按固定的当前有效状态返回
`deviceActiveSeverities[].deviceId/serialNumber/maxSeverity/activeCount`；它用于 BFF 保持现有
`devices[].alarmLevel` 字段兼容，不把 EIOP Control 运行态字符串继续当作正式告警等级。
它只替换全景首屏 6 路查询，不替代告警分页、详情、处置或 `actionable-workflow`。

`alarmLevel` 迁移口径已确认为：

1. 「当前有效告警」与 Management 现有概览和告警页一致，包含 `NEW`和
   `ACKNOWLEDGED`；后者只表示已确认、仍待处置，不得因确认动作从设备告警标记中消失。
   `HANDLED/FALSE_ALARM` 为终态，不参与当前最高等级。
2. 严重程度优先级固定为 `CRITICAL > WARN > INFO`，Management 返回原始枚举；BFF 仅在对外适配时映射为现有
   `HIGH/MEDIUM/LOW`，不从标题、内容、`alarm_type`或 `source_type` 推断等级。
3. 同一设备无当前有效告警时，`devices[].alarmLevel=null`，不返回 `NONE/NORMAL/UNKNOWN`伪枚举；
   有多条时返回最高等级及 `activeCount`。处置最高等级告警后必须立即降级到剩余有效告警的最高等级，全部终结后才置空。
4. 快照查询沿用 `monitor.alarm.view` 和 Management 告警列表同一数据范围；BFF 只向当前授权设备关联结果，不把无权设备的最高等级带入页面。
5. 告警快照失败时使用现有全景 `dataQuality.alarms.available=false`披露，不回退 EIOP `alarmStatus`，也不将 `alarmLevel=null` 表述为「已确认无告警」。

当前快照和当日汇总必须使用两组不同的时间语义：

| 响应块 | 事实集合 | 时间条件 | BFF 现有字段 |
| --- | --- | --- | --- |
| `activeTotal/activeBySeverity/latest/deviceActiveSeverities` | `status in (NEW, ACKNOWLEDGED)` | **不按发生时间截断**，直到告警进入终态 | `alarms.total/high/medium/low/latest`、`devices[].alarmLevel` |
| `periodTotal/periodByStatus` | `occurred_at` 落入时间窗的全部持久告警 | `periodTimeRange=[from,to)` | `alarms.summary.totalToday/handled/unhandled/handleRate` |

具体规则：

1. `activeStatuses` 不由 BFF 自由传入；「当前有效」是 Management 领域契约，固定为
   `NEW+ACKNOWLEDGED`。若其他页面需要任意状态分组，使用 7.3 统计查询，不改动快照语义。
2. 跨日未处置告警在零点后仍必须出现在活动总数、等级列表和设备 `alarmLevel`中；
   它不属于新一天的 `totalToday`，两个总数无需相等。
3. `periodTimeRange.basis` 本次只接受 `OCCURRED_AT`。`handled/unhandled/handleRate` 表示「该时间窗内发生的告警在 `generatedAt` 时的处置结果」，
   `handled=HANDLED+FALSE_ALARM`、`unhandled=NEW+ACKNOWLEDGED`；不改为按 `handled_at` 计算「今日处理了多少」。
4. 响应所有块共用一个 `generatedAt`；查询实现应在同一读一致性边界下聚合，避免处置动作恰好发生时各块互相对不上。

#### 7.4.1 设备告警等级的首屏与实时闭环

当前 `PanoramaWebSocketEventAdapter.statsRefreshParts()` 将告警事件归入 `ALARMS`，前端
`panorama.alarm(s).changed` 主要更新告警列表/摘要，不能认为已自动更新 `devices[].alarmLevel`。
迁移必须在现有刷新链路中同时补足以下生产者、缓存和消费者约束，不新增 EIOP 写入事件或第二条 WS 通道：

1. 首屏与重连快照均从 7.4 的有效告警聚合设置设备等级。完整、授权范围匹配的快照中没有有效告警的设备才可置 `null`；
   部分结果、权限失败或下游失败不能解释为「无告警」。查询所得等级只关联当前有权展示的设备。
2. 创建、确认、处置、误报及既有 Management 告警失效事件，同时使告警摘要和设备告警等级派生结果失效。
   事件带设备标识时记录受影响设备；不带标识时合并刷新当前授权范围的告警快照，不逐设备拉详情。
   不能仅删除告警列表项而保留设备旧等级，也不从单条告警推断该设备剩余告警的最高等级。
3. 复用 `panorama.stats.changed`，加法式携带 `deviceAlarmLevels[]`（Management `deviceId`、Control `robotId`/序列号、`alarmLevel`）及对应质量。
   更新项必须可表达 `alarmLevel=null`；字段未携带表示本次未刷新，不能解释为全部清空。
   BFF 在 ALARMS 刷新结果中生成该块；前端按设备标识 patch 共享设备对象，不覆盖电量、位置、在线状态等 Control 字段。
4. 新快照尚未成功时立即使相关等级质量失效，沿用现有不可用呈现，不把保留旧值当作有效新结果。
   成功时按同一刷新代次发布摘要、等级更新和 `dataQuality.alarms`；禁止先发成功质量再异步补发无版本的等级。
   一次刷新失败不应清空任务、里程或 Control 当前运行态。
5. HTTP 在途响应、合并刷新和 WS 增量必须校验资源/授权上下文及刷新代次，旧代结果不得覆盖新等级。
   沿用现有会话与请求竞态机制；如需附加告警刷新序号，只作用于该派生块，不能拿 Control `stateSeq` 充当告警业务版本。
   撤权先移除对应设备；重连重新取得授权快照，不能用旧会话等级恢复无权设备。

切换门是设备标记依次 `HIGH → MEDIUM → LOW → null` 无需刷新页面即可生效，且确认不清空、
快照失败不伪装无告警、旧响应/重连不恢复旧等级。完成后才允许删除 EIOP `alarmStatus` 的 BFF 依赖。

### 7.5 当前状态权威与批查放置

本节必须区分「地图当前状态」和「统计窗口在线率」，两者同源但不是同一个读模型：

1. `PanoramaService.statusBySerial()`：在指挥中心/全景地图共用 Overview 组装设备时，批量取 EIOP 实时状态。其中
   `status.basic` 目前只补充 `alarmLevel`，`status.task` 只补充设备任务列表，`lastSeenAt/receivedAt/reportedAt`
   补充 `lastHeartbeatAt`。设备 `status`、电量、定位、速度、充电和 `taskStatus` 已以本项目 Control
   `/api/control/robots/registry` 为准，并非由本节 EIOP 接口决定。
2. `StatisticsService.equipmentRuntime()`：当前批量取 EIOP `onlineStatus/status`，用请求时刻的设备快照计算
   `equipmentRuntime.onlineRate`。这不会随「全部/今日/本周/本月/自定义」变化，与页面组合筛选要求不符。

经评估并于 2026-09-26 确认，**本项目 Control 同时是当前状态和状态历史唯一权威**；
指挥中心/地图读当前快照，统计页读筛选窗口的状态秒数。具体责任如下：

| 责任 | 最合适位置 | 原因 |
| --- | --- | --- |
| 设备当前 `online/offline/fault` 事实及心跳超时 | `control-service` 的 `RobotRegistryService` | 它直接消费边缘 MQTT 状态，已为指挥中心、全景地图和 WebSocket 权威源 |
| 按设备 ID 返回精简状态快照 | `control-service` 的 `status-queries` | 仅供指挥中心/全景地图组装当前运行态，不再为统计页计算在线率 |
| 按设备 ID 和时间窗口返回各状态秒数 | `control-service` 的 `runtime-queries` | 为「全部/今日/本周/本月/自定义」返回 `running/offline/fault/unknownSeconds` |
| 当前用户启用可见机器人集合和类型筛选 | EIOP Management 查询 + BFF 关联 | Management 掌握数据范围、`enabled` 和档案；BFF 只向 Control 传递当前授权且 `enabled=true` 的机器人 ID，并排除停用设备和固定摄像头 |
| `equipmentRuntime.onlineRate` 计算 | `bigscreen-bff` 的统计领域 | 使用同一组筛选机器人的历史秒数计算 `(runningSeconds + faultSeconds) / (runningSeconds + faultSeconds + offlineSeconds)`；`unknownSeconds` 不充当离线，单独披露覆盖质量 |
| 对外契约 | `GET /api/bigscreen/statistics/overview` | 前端无需感知底层状态源迁移 |

不将历史在线率下沉到 EIOP Management：会迫使 Management 同步调用 Control，并引入第二套状态历史。
也不让 Control 直接返回百分比：Control 只返回指定 ID 的原始秒数，BFF 对 Management 当前启用授权机器人集合完成安全关联、汇总和舍入。

| 需求 | 现有/目标字段 | 时间语义 | P0 处理 |
| --- | --- | --- | --- |
| 机器人本体最后状态时间 | `devices[].runtimeUpdatedAt` | 本项目 Control 最后接受非 retained 边缘状态的服务端时间；媒体心跳、GIS 补全和离线扫描均不推进 | 保持 Overview 和 `panorama.device.status.changed` 原样输出，前端用于新鲜度和新旧版本判断 |
| 机器人最后有效定位 | `devices[].location` / `edgeLocation` | `location.updatedAt` 为边缘状态事件时间；Control 只接受不早于已有定位的新位置，GIS 换算只补充经纬度，不伪造新定位时间 | 保持 Overview 和 `panorama.device.location.changed` 原样输出；设备离线时保留快照中最后位置及其时间，不把离线时间写成定位时间 |

P0 只承诺「Control 当前内存注册表尚保留该设备」时的最后状态和最后定位。当前离线条目默认只保留 60 秒，
Control 重启后内存快照也会丢失，因此不能将它描述为「长期最后已知位置」。

已确认的长时间离线或 Control 重启后仍可查询能力，作为 P2 独立持久化读模型交付。
这项能力不改 EIOP，也不复用 Management 作为写入目标；本项目 Control 是边缘状态和定位的直接消费者，
因此应由 Control 保存「每台机器人一行」的最新已知快照：

| 建议字段 | 含义 |
| --- | --- |
| `robot_id` | 稳定机器人标识，主键 |
| `last_reported_status` | 最后一次非 retained 边缘状态中的原始运行态；不冒充当前在线态 |
| `runtime_updated_at` | Control 最后接受本体状态的服务端时间 |
| `location_json/location_schema_version` | 最后有效定位快照及其结构版本，兼容地图坐标和经纬度加法式扩展 |
| `location_updated_at` | 边缘位置事件时间，与 `runtime_updated_at` 分开比较 |
| `source_message_id/persisted_at` | 去重、排查和数据新鲜度依据 |

持久化和读取边界建议如下：

1. 只有通过现有新旧判定的边缘本体状态才能更新 `runtime_updated_at`；媒体心跳、GIS 补全和离线扫描不得推进该时间。
2. 状态和位置独立幂等更新：只有更新的 `runtimeUpdatedAt/location.updatedAt` 才覆盖各自字段，乱序位置不得回退快照。
3. 不保存位置轨迹，只保存每台设备最新一行；设备存续期间不设 TTL，因为容量只随设备数增长。设备硬删除时同步清理该快照，停用只禁止展示，不删数据。
4. 快照写入不得阻断 MQTT 消费、当前注册表更新或 WebSocket 推送。Control 使用按 `robotId` 合并最新值的有界单写队列、失败重试/告警和周期检查点收敛；这是可丢弃中间版本的最新快照，不需要 Control outbox。
5. 新增独立内部读接口 `POST /internal/control/robots/last-known-queries`，仅接受 BFF 已经 Management 授权并启用筛选后的 `robotIds`；不将位置加入状态历史统计接口。
6. BFF 优先使用 Control 当前内存快照；只在当前快照缺失时使用持久快照，并返回 `snapshotSource=PERSISTED/stale=true`。复用现有状态/时间位置表达陈旧性，不得用该快照判定当前在线、允许控制或计算运行时长。若原展示无法区分最后已知与当前值，只阻塞 F2 的该展示接入，新增文案/标识单独确认，不突破第 4 节冻结边界。
7. 这项 P2 可复用第 8 章的本地 MySQL、幂等、监控和备份机制，但它不是设备运行时长的数据源，也不阻塞 P0/P1 统计查询迁移。

按上表确认后，`task/lastHeartbeatAt` 死映射可先清理；待统计页已通过本项目 Control `runtime-queries` 使用窗口历史，
且 Management `ACTIVE_MAX_SEVERITY_BY_DEVICE` 与旧 `alarmLevel` 完成双读对账后，BFF 才不再需要
EIOP 实时状态明细，并可删除：

- `PanoramaService.statusBySerial()` 和 `deviceTasks()` 等死映射；
- `PanoramaCenterClient.realtimeStatuses()`；
- BFF 专用 EIOP Control `RestClient`、并发门闩、熔断状态、`CENTER_EIOP_CONTROL_BASE_URL` 及对应超时配置；
- 只验证该旧链路的测试与过时文档描述。

这些删除只发生在 BFF，**不删除、不修改 EIOP 现有实时状态 HTTP/WebSocket、Redis TTL 和 Admin UI 消费链路**。

#### 7.5.3 不新增 EIOP 实时状态批查

按已确认的字段归属，本次没有必须由 EIOP 实时状态明细继续供给的页面字段，
因此删除早期备选的接口设计，不新增第二套状态批查。若实施时发现遗漏的真实消费者，
先给出字段和调用证据，再单独确认，不以备选方案为默认开发授权。
EIOP 现有 GET、内部 `/summary`、Redis 过期语义、MQTT 处理及其他消费者均保持不变。

#### 7.5.4 旧公开查询入口与代理别名的授权收口

本次源码核验发现：Control `ControlRobotController.registry()` 直接 `robotRegistryService.list()`，
BFF `BigscreenProxyController` 仍匹配 `/api/control/**` 和 `/api/bigscreen/**`；
`CenterProxyClient.targetPath()` 会把部分大屏路径重写到 Control。JWT/客户端校验不等于设备数据授权。
这是源代码层面的旁路风险，部署侧是否另有拦截必须在切换环境验证，不能把未验证的网关规则当作已有保护。

| 原目标及外部路径 | 本次处理 |
| --- | --- |
| `/api/control/robots/registry`，以及 `/api/bigscreen/control/robots/registry`、`/api/bigscreen/robots/registry` | BFF 禁止直接透传全局注册表；默认外部返回 404。确有当前消费者时，只能在该路径增加按 Management 权限过滤的适配并保持必要响应字段，不能继续返回全量 |
| `/api/control/statistics/mileage` 及同样重写到它的两类大屏别名 | 先核验消费者；无消费者的外部路径禁用。有消费者时由 BFF 解析权限、校验显式 ID 属于允许集合后调用内部批查；省略 ID 仅表示当前用户允许集合，空集合不查全局 |
| `/internal/control/**` 及任何可重写到内部查询的公开别名 | Nginx 和 BFF 均不得暴露；不能只靠 URL 以 internal 开头认定安全 |

1. 门禁针对实际转发目标统一执行，覆盖直接路径、别名及框架支持的路径规范化形式，不能只拦一个字面 URL。
   不改变无关命令、媒体、文件或 Management 代理规则，不以本次迁移重写整个网关。
2. 原公开读接口若保留适配，仍执行 `resource.device.view` 和当前数据范围；客户端显式提交无权 ID 返回 403，
   根授权查询失败返回 503，不回退全局。统计调用另满足已确认的启用/类型过滤；注册表展示不能借机改变原页面设备集合。
3. Control 原内部接口可继续服务核验过的内部消费者；内部地址不得直接暴露到不可信网络。
   BFF 新旧源对账只在受控服务内进行，返回前执行授权关联，日志不记录全量注册表。
4. 切换前形成「路径/重写目标/消费者/权限适配或禁用/验证结果」清单，包含实际 Nginx 和 BFF 配置。
   两组织交叉 ID、缺省 ID、空集、无权限及别名均回归；灰度和回滚开关不得重新打开全局旁路。

### 7.6 全景任务卡片

```http
POST /api/v1/management/task-workflow-plans/panorama-queries
```

请求支持 `mapId`、`enabled`、`includeActiveExecution`、`cursor/limit/expectedRevision` 及默认 false 的 `verifyOnly`；
`limit` 默认 200、最大 500，首轮 `cursor/expectedRevision=null`。响应 `data` 为
`records/total/nextCursor/queryRevision/snapshotAt/complete/reasonCodes`，不使用 `PageResult`，不改原 `PageQuery`。
供 Overview 使用时 BFF 固定传 `enabled=true/includeActiveExecution=true`，按 `nextCursor` 完整翻页并核对 `total`，
不把首页或固定 100/500 条当作全量。每项包含：

- 计划摘要与冻结版本标识；
- 当前唯一活动工作流实例摘要，无则为 `null`；
- 现有卡片依赖的 `executionMode/expectedDurationSeconds/enabled`、`activeWorkflowInstanceId/activeWorkflowInstanceStatus`、
  `lastWorkflowInstanceId`、开始/完成时间及 `availableLifecycleActions`；操作可用性复用 Management 现有领域计算；
- 角色绑定的设备 ID/序列号/快照名称与类型；
- 冻结引用完整性标识。

不包含回放文件、轨迹字节、地图点位、路线点和摄像头凭据。BFF 继续按用户打开动作读取详情、回放和摄像头。

任务卡片集合和状态口径已于 2026-09-27 确认如下：

1. 正常集合为当前用户有权且 `enabled=true` 的非临时计划，包括没有活动实例的待执行计划；
   不能为了「活动任务」优化而把大屏现有可启动的 `WAITING` 计划丢掉。
2. Management 普通计划分页不返回 `TEMPORARY` 计划；新读模型必须将当前用户可见的活动临时计划合并进同一分页集合，并标记
   `planType=TEMPORARY/runtimeOnly=true`。临时实例进入终态后自然移出，不变成常驻待执行卡片。
3. 活动实例状态严格沿用 Management `TaskWorkflowInstanceStatus.active()`：
   `PREPARING/RUNNING/PAUSING/PAUSED/RESUMING/TERMINATING/CONTROL_FAILED`；
   `COMPLETED/FAILED/TERMINATED` 为终态，不得被附加为当前活动实例。
4. 继续分开两个状态字段：`activeWorkflowInstanceStatus` 保留上述精细状态；
   面向现有列表的 `executionStatus` 仍只返回 `WAITING/RUNNING/PAUSED`，其中只有精细状态 `PAUSED` 映射为 `PAUSED`，
   其他活动状态映射为 `RUNNING`，无活动实例映射为 `WAITING`。不借迁移扩展现有前端状态集。
5. Management 现有启动逻辑通过计划行锁保证同一计划最多一个活动实例。新读接口不得用「最新一条」掩盖异常重复数据；
   若同一计划查到多个活动实例，该页返回 `complete=false/reasonCode=ACTIVE_INSTANCE_CONFLICT`，BFF 不随机关联设备或开放控制操作。
6. 合并后集合按计划 ID 升序游标分页，普通/临时计划共用一套排序和正确 `total`；BFF 完整读取后再按现有展示顺序写入 store。
   `queryRevision` 复用 7.1.3 的只读指纹协议，但**只覆盖权限、集合和关键关联**：当前身份、各自有效权限/数据范围、
   查询条件，以及按计划 ID 排序的全部命中成员的计划类型/启用及地图归属、冻结引用标识、活动实例 ID、角色—设备 ID/序列号绑定。
   不把计划名称、显示时长、观测时间、同一实例的活动状态及由其派生的 `availableLifecycleActions` 纳入集合指纹。
   每页在同一只读数据库边界读取最小集合投影并校验 `expectedRevision`，仅为当前页加载卡片字段和计算可操作项；
   `verifyOnly` 不加载全体卡片详情或逐项计算按钮，不以单独 `snapshotAt/MAX(updated_at)` 代替集合校验。
   游标绑定身份、条件、指纹和末项 ID；停用、撤权、冻结引用/设备绑定变化、活动实例更换或结束，以及活动临时计划移出均使上下文失效。
   非法游标返回 400；查询上下文失效返回 409 / `409000`。后续页必须携带首轮指纹，末页后再做仅摘要的最终校验
   （相同筛选条件和 `verifyOnly=true/expectedRevision`，不带 cursor、不返回 records；缺指纹返回 400）。BFF 仅允许整轮重试一次，持续变化则该域不可用。
   这保证完整集合及关键关联一致，不承诺全部卡片的动态状态属于同一全局时刻；不新增跨请求快照会话或页面分页交互。
7. 单张卡片的实例身份、精细状态、粗粒度映射和 `availableLifecycleActions` 必须在当前页同一读取边界内生成，不能拼接不同状态缓存。
   同一实例在活动状态之间暂停/恢复等变化不单独触发分页 409；各页 `snapshotAt` 如实表示读取时点，不能将首/末页时间冒充整集合事务快照。
   BFF 与页面复用既有任务事件、刷新合并及 `taskVersions/taskSnapshotVersion` 的迟到响应保护，动态字段按卡片一起更新；
   旧 HTTP 结果不能覆盖已应用的新事件或恢复已删除实例，不新增每卡片轮询、持久版本表或另一套 WS 协议。
   按钮继续消费 Management 原领域计算，实际操作经原写接口重新校验权限和状态；不改启动互斥、状态机或操作权限逻辑。

### 7.8 WebSocket 授权最小投影

```http
POST /api/v1/management/authorized-resource-queries
```

```json
{"resourceTypes": ["DEVICE", "FIXED_CAMERA"], "cursor": null, "limit": 500, "expectedRevision": null}
```

响应包含 `records[].resourceType/resourceId/externalId`、`total/nextCursor/authorizationRevision/generatedAt`。

- `DEVICE.externalId = serialNumber`，`FIXED_CAMERA.externalId = cameraId`。
- 每类资源独立执行已有查看权限和数据范围；缺少某类权限时该类为空，不影响另一类。
- 按 `resourceType + resourceId` 稳定游标分页，默认 200、最大 500；每页响应不得混入未请求资源类型。
  `authorizationRevision` 在同一只读快照中按当前身份、各类有效权限/数据范围及完整最小资源投影计算内容指纹，
  不依赖原业务写钩子，也不代替实际资源集合或操作时再授权。后续页必须携带 `expectedRevision`，游标同时绑定条件和指纹。
- `verifyOnly` 默认 false；非法游标 400、上下文变化 409 / `409000`；末页后用相同 resourceTypes 和 `verifyOnly=true/expectedRevision` 复核，不带 cursor、不返回 records，缺指纹返回 400。
  BFF 仅整轮重试一次，不发布半份授权集合，持续变化按现有 fail-closed 处理。复用 7.1.3 的协议机制，不共享不同领域权限结果。
- BFF 保持现有按 `issuer + subject + orgId` 隔离、错峰刷新和 fail-closed，只把载荷从全档案降为最小投影。

### 7.9 里程多窗口批查

现有 `GET /api/control/statistics/mileage` 会把 `robotIds` 展开到 URL，且统计页为了同期比重复传递同一批机器人。
新增无副作用读接口，一次最多查询当前与上一两个窗口：

```http
POST /internal/control/statistics/mileage/queries
```

```json
{
  "robotIds": ["robot-001", "robot-002"],
  "windows": [
    {
      "key": "CURRENT",
      "from": "2026-09-01T00:00:00+08:00",
      "to": "2026-09-26T10:30:00+08:00"
    },
    {
      "key": "PREVIOUS",
      "from": "2026-08-01T00:00:00+08:00",
      "to": "2026-08-26T10:30:00+08:00"
    }
  ]
}
```

```json
{
  "snapshotAt": "2026-09-26T10:30:00+08:00",
  "windows": [
    {
      "key": "CURRENT",
      "totalMeters": 12345.6,
      "hasData": true,
      "selectedRobotCount": 2,
      "robotsWithData": 2,
      "coverageFrom": "2026-09-01T00:00:00+08:00",
      "coverageTo": "2026-09-26T10:30:00+08:00",
      "qualityCoverageFrom": "2026-09-01T00:00:00+08:00",
      "qualityCounts": {"NORMAL": 120, "BASELINE": 0, "RESET": 0, "ESTIMATED": 0, "SUSPECT": 0},
      "valueComplete": true,
      "complete": true,
      "reasonCodes": []
    }
  ]
}
```

- `robotIds` 由 BFF 按本次 `FilterContext` 的当前授权、`enabled=true` 和机器人类型筛出，Control 不接受类型名称，也不扩大设备集合；去重后单批最多 500 个。
- 新端点只允许受控内网调用，Nginx 不暴露 `/internal/**`，BFF 通用代理不得提供到该端点的公开别名。
  登录身份不能替代设备授权；测试必须证明外部调用者不能自行提交其他组织的 robotIds 获取结果。
  原公开 GET、注册表及代理别名统一按 7.5.4 审计；旧入口存在绕过时需封闭或补齐鉴权后才允许正式切换，不能因新端点安全而忽略旧入口。
- `robotIds` 必填且非空；空选中集合由 BFF 返回明确空态，不调用 Control。超过 500 台时分批有界并发，
  窗口统一；任一批失败使里程域不可用，不将成功批之和冒充完整结果。质量计数求和、覆盖取保守边界，
  `complete` 必须所有批成立；不得把分批上限误作整页最大设备数。
- `windows` 的 `key` 在同一请求内唯一，最多 2 个，均使用 `[from,to)`；`ALL` 只传 `CURRENT`，不构造不存在的上一窗口。
- `from` 省略表示无下界，用于 ALL；`to` 必填且由 BFF 固定。边界必须对齐完整分钟，非分钟边界返回 400，不在 Control 内静默舍入；规则见 8.4.1。新端点实际读取时间使用自身 `snapshotAt`，不伪装成 BFF 查询截止时刻。
- `totalMeters` 是既有增量算法已接受并持久化的里程之和，含原算法已接受的估算值，不是对真实运动的重新推算。`hasData=true,totalMeters=0` 表示有记录证据且按该口径为 0；`hasData=false,totalMeters=null` 表示无可核算记录，两者不能互换。是否足够完整供页面展示另按 8.3.1 判断。
- BFF 用 `CURRENT/PREVIOUS.totalMeters` 计算 `kpis.patrolMileage.compareRate`，并把覆盖不足写入 `dataQuality.patrolMileage`；同期比较必须复用完全相同的 `robotIds`。
- `qualityCoverageFrom/qualityCounts` 来自 8.4.1 的持久质量记录；旧区间无法判定的计数返回 null，不能以全 0 表示历史无异常。`hasData/valueComplete/complete` 分别表示有已记录值、所需数值事实完整、数值与质量均完整，具体判定见 8.3.1；任一窗口 `complete=false` 时 `compareRate=null`。
- 该响应只返回页面所需的窗口汇总和质量信息，不返回每分钟桶；指挥中心今日里程必须复用同一内部接口并只传一个窗口。
  首屏及 WS 的 `todayMileageSummary()` 均按 7.10 传入授权启用机器人集合，不能保留空 ID 表示全局的旧调用。
- 新接口验收后再删除统计页对旧 GET 的使用；查询包不改变里程增量算法或 MQTT 协议。C1 仅在本项目 Control 增补必要质量持久化和日台账；旧 GET 内部语义保留，对外访问按 7.5.4 授权收口。

### 7.10 今日巡逻时长与里程的统一编排（2026-09-29 已确认）

两个指标继续使用现有 `patrolOverview` 和页面展示，不为它们新增浏览器接口或页面组件。
Management 计算任务时长，本项目 `control-service` 计算里程；这里的 Control 不是 EIOP Control。
BFF 负责统一权限范围、时间窗口、结果组装和失效刷新，不将两种原始事实搬到同一个服务。

#### 7.10.1 公共条件与计算归属

1. BFF 一次解析当前用户有权且启用的机器人集合，并固定上海时区今日 `[00:00,to)`。
   复用 7.1.3 的资源与权限校验；任务还必须满足自身及关联子任务的数据权限，不能仅有设备权限就读取任务事实。
   这份机器人集合只用于两项统计，不因此删除地图中原有的固定摄像头展示。
2. Management 以该集合关联任务并按工作流实例去重；Control 只接受明确的授权 `robotIds`。
   有权限但选中集合为空时，由 BFF 返回合法空态；权限失败不得转为空集或请求全局汇总。
3. 两项使用同一查询截止边界 `floorToMinute(requestNow)`，即本次请求前最近一个完整分钟边界，详见 8.4.1。
   Management 也用该边界求任务窗口交集，不一项到当前秒、另一项到上个分钟；实际读取时间分别留在质量元数据中，不声称跨服务事务快照。
4. BFF 仅将 Management 的秒数换算为小时、Control 的米数换算为公里，沿用现有精度与字段。
   不让 Management 调 Control，不向 Management 复制里程，不把任务明细拉入 Control 或 BFF 重新聚合。

当前里程事实没有任务标识，可能包含非任务期间移动；任务时长包含暂停和等待。
因此统一的是授权与窗口，不宣称两项是一一对应的同一批巡逻任务耗时和路程。
本次不新增任务里程绑定、轨迹推算、设备实际运动计时或任务分类规则。

#### 7.10.2 今日巡逻时长算法

以现有工作流实例的 `started_at/completed_at/status` 为事实；符合授权、启用设备关联和时间条件的实例计一次。
不按当前计划绑定代替历史设备子任务关联，也不凭任务名称猜测新的“巡逻任务”类别。

```text
windowStart = 今日 00:00（Asia/Shanghai）
windowEnd   = 本次统一查询截止时间
instanceEnd = 终态实例的 completed_at；合法非终态实例使用 windowEnd
seconds     = max(0, min(instanceEnd, windowEnd) - max(started_at, windowStart))
duration    = 所有命中工作流实例的 seconds 之和
```

- 候选任务必须与今日有交集，不能仅筛选 `started_at` 在今日，或仅查今天开始/结束的任务。
- 非终态仅接受现有正式枚举；终态 `COMPLETED/FAILED/TERMINATED` 均累计结束前的经过时间。
  准备、暂停、等待属于生命周期的一部分，不扣除，也不改变 EIOP 现有 `durationSeconds` 定义。
- 尚未启动的计划不计时。同一实例关联三台机器人仍只计一次；不同实例时间重叠仍分别累计，总和可以超过 24 小时。
- 昨日 23:00 到今日 02:00 计 2 小时；今日 09:00 到 10:30 仍活动计 1.5 小时；昨天开始且明天结束的任务不能漏掉。
- 终态缺结束时间、结束早于开始、非法状态等属于数据异常，不延长到当前时间、不补写原事实。
  查询披露异常数量和完整性；BFF 不把不完整总和或失败伪装为完整零值。合法空集为 0。

#### 7.10.3 加法式任务查询契约

复用 7.2 的 `POST /api/v1/management/task-workflow-instances/statistics-queries`，
在 P1 新增 `timeRange.basis=LIFECYCLE_OVERLAP` 与 `includes=[DURATION_SUMMARY]` 的白名单组合。
`from/to/zoneId` 必填；沿用 `executorResourceTypes=[DEVICE]`、`deviceEnabled=true`、
当前类型筛选和 `options.deviceScopeRevision`，BFF 今日查询不附加任务状态或触发方式筛选。

响应沿用 `snapshotAt/deviceScopeRevision`；`summary.instanceCount` 在此 basis 下表示与窗口相交的去重实例数，
不是“今日启动任务数”。`durationSummary` 返回 `durationSeconds/complete/invalidInstanceCount/reasonCodes`；
存在无法计算的候选实例时总时长不声明完整，前端不新增展示项。异常检测同样受权限约束，不泄露全局异常计数。
缺失时间导致是否相交也不可证明的实例须按未知质量处理，不能仅在时间 WHERE 后检查而将其静默排除。

此组合不接受 `STATUS_DISTRIBUTION` 或 `comparisonTimeRange`，不复用到统计页任务数/完成率；
P0 的 `STARTED_AT` 请求、响应含义和原列表 `durationSeconds` 保持不变。
同一只读数据库快照中完成权限、去重、相交时长与质量计算，不新增业务表或任务写入钩子。

#### 7.10.4 首屏、事件刷新与拆分边界

- 首屏和 WS 初始统计共用上述查询编排，替换 `taskSummaries()` 仅为时长读取 `scope=ALL` 的依赖；
  活动任务卡片继续按 7.6 获取，不为巡逻时长再次翻历史实例。
- 在现有 BFF 刷新组件内分离任务卡片、巡逻时长与里程的脏标记，合并同身份重复刷新；不重写 WS 框架。
  里程事件不再触发任务卡片/全历史任务查询，任务事件也不无条件使里程源缓存失效。
- 一次发布完整 `patrolOverview` 时，两项必须匹配同一授权集合与窗口；条件不匹配的缓存不直接拼接。
  为统一截止需要重读时，只调用两个有界摘要查询，不能回退全量事实；任一项失败单独保留不可用语义。
- `durationToday/durationUnit/mileageToday/mileageUnit/mileageHasData` 字段保持；HTTP 与 WS 使用同一组装器。
  两项的成功/失败不能继续一起受任务卡片 `dataQuality.tasks` 门禁控制，必要时在现有事件中加法式携带独立质量字段。
- 资源、权限变化及跨日使对应查询上下文失效；重连重新校验，旧授权或旧窗口结果不得覆盖新结果。
  当前值是查询截止时刻的快照，按 7.10.5 补齐有界时钟刷新，不新增浏览器秒级累计或高频全量轮询。
- 页面仍称「今日巡逻时长」「今日巡逻里程」，不改名称、布局、指标构成或新增口径解释文案；
  只作数据绑定、零值/不可用判定和已有事件处理的必要适配。

#### 7.10.5 实时摘要补刷与统计页快照

现有 `MileageService.publishIfNeeded()` 默认累计到 10 米才发事件，未达到阈值的有效增量也会入库。
因此“先有事件再补刷”不能覆盖无任务时少量移动后停止；同时，当前分钟事件后的立即查询会被完整分钟截止排除。
统一使用下面的最小刷新规则，不维护按机器人/事件的待补刷分钟队列，也不新增消息、订阅协议或定时调度平台。

1. **今日两项统一兜底**：现有大屏 WS 有效订阅期间，在每个完整分钟边界后，对今日时长和里程作一次摘要补刷，
   不以存在活动任务或收到事件为前置。无事件的 5 米增量、活动任务自然计时及终态最后一分钟均由同一路径覆盖。
   同一 BFF 实例内按授权身份/逻辑筛选合并，只管理一份刷新状态；不为同身份多会话或每台设备单独排任务。
2. **复用现有刷新编排**：事件仍走已有合并、脏标记和请求代次；与分钟触发重合的同上下文在途查询合并。
   每次执行重新取得授权设备集合和统一截止时间，只查询两个有界摘要，不拉任务卡片、设备详情或历史列表。
   调度延迟或恢复后只查最新窗口一次，不追放错过的每一分钟；不在浏览器累计时长，也不改变 Control 的里程算法/事件阈值。
3. **跨日及恢复**：分钟驱动到达上海日界时作废旧今日上下文，同时失效既有告警快照的今日块，保留跨日活动告警。
   重连、重新进入或恢复可见时校验并重查当前窗口；昨日/旧授权的在途响应不能回写。报告已冻结窗口及已归档内容不随刷新改变。
4. **统计页保持查询快照**：整页以最近一次成功响应的 `serverTime/range` 为准；进入、筛选变化、恢复可见及可见时跨日重查整份 Overview。
   已结束的自定义历史窗口不因日界自动重查。移除 v2.47 的每分钟整页刷新要求，ALL/本月等也不周期轮询；
   不增加新的 WS 订阅或页面组件。重查仍统一所有卡片/图表条件，不能只推进时间字段或一张图表。
5. **失败与释放**：每轮遵守第 10 节的一次重试/总预算；失败按分项不可用处理，下一分钟正常轮次可恢复，不立即无限补排。
   401/403 清除旧结果并取消对应身份刷新，最后一个有效订阅断开后释放刷新状态；页面退出清理自身监听/日界任务。
   不建设跨实例调度锁，各实例只服务本机有效订阅；授权、限流和容量预算不能因兜底刷新被跳过。

第 10 节只计入实际的摘要分钟开销和统计页上述触发查询；不得以刷新正确性为由恢复全量事实轮询。

## 8. 设备运行时长正式长稳模型

### 8.1 不采用按天计数采样

`online_count/offline_count/fault_count × 首末跨度` 不能作为长期契约：调度延迟、重启和缺样会放大为整段时长；无法表达跨天区间与数据缺口；多副本会重复计数，单副本文件无法容灾。

### 8.2 状态区间读模型

已确认的当前状态权威是本项目 Control，因此历史链路不应再以 EIOP Control 作为第二个转移生产者。
经确认，历史也由本项目 Control 直接持久和查询，不新增 Control outbox、不向 EIOP Management 投递状态转移。
职责固定为：

| 职责 | 归属 | 边界 |
| --- | --- | --- |
| 判定 `ONLINE/OFFLINE/FAULT` 真实转移 | 本项目 `control-service` | 复用 `RobotRegistryService` 的边缘状态、超时离线和故障口径；不让 Management 重新推断 |
| 幂等记录、区间切割和日汇总 | 本项目 `control-service` MySQL | 复用现有数据源，按机器人实际转移持久化；不在 BFF 或 EIOP 中生成第二份历史 |
| 当前启用授权设备与类型筛选 | EIOP Management + BFF | BFF 先取当前用户有权且 `enabled=true` 的设备，按 Management 当前设备类型过滤，只将这些 `robotIds` 传给 Control；停用设备历史仍保留但不参与页面统计 |
| 对外 DTO 和数据质量 | BFF | 将 Control 逐设备秒数汇总为现有 `equipmentRuntime` DTO，披露覆盖和 `UNKNOWN`；不持久历史 |

这不再是可选运维能力，而是统计页「装备运行时长」图表的正式数据源。
实施仍与 P0 任务/告警查询迁移分开，但优先级提升为 P1 独立闭环；旧采样路径只是过渡兼容，不是最终方案。

```text
control_device_status_interval
  id
  transition_id         -- Control 内部幂等键
  source_instance_id    -- Control 运行世代
  source_sequence       -- 世代内单调序号
  robot_id
  status                -- ONLINE/OFFLINE/FAULT/UNKNOWN
  started_at
  ended_at              -- 当前区间可为 null
  last_observed_at      -- 最后可靠检查点
  created_at/updated_at
```

规则：

- 用服务端观测时间建区间，不信任设备时钟改写在线时长。
- 在同一 MySQL 事务中锁定该 `robot_id` 的未闭合区间，闭合旧区间并插入新区间；重放同一 `transition_id` 不重复切割。
- 断线只由 `RobotRegistryService` 的心跳超时扫描产生，历史服务不另行猜测。
- 实时状态不因历史库写入失败而停止更新；失败必须记录指标/告警和内存中的降级起点。定时对账恢复时只从重新可信的时刻开始建段，无法证明的缺口记为 `UNKNOWN`。
- Control 定期持久服务检查点。新 `sourceInstanceId` 不盲目延续上一实例的未闭合区间；上一检查点到新实例首次可靠观测之间计入 `UNKNOWN`。
- 单实例部署必须明确为单写者；如需多副本，先增加数据库租约/主实例机制，不让多个内存注册表同时切割区间。
- 统计时对区间与查询 `[from,to)` 求交集后汇总；`UNKNOWN` 单独返回，不当作离线。
- 查询权限、启用状态和设备类型按 Management 当前档案计算：设备转移后，历史随设备归当前有权组织查看，原组织不再可见；设备停用后不参与任何统计块但历史不删除，重新启用后其保留历史重新可查；设备类型变更后，状态/里程历史按当前类型归类。这是不引入跨服务生命周期投影的明确取舍。
- 不导入旧 `DeviceStatusSampler` 计数作为精确历史；新模型从上线时开始累积，通过 `coverageFrom/coverageTo/unknownSeconds` 披露覆盖。

记录与查询必须共同遵守以下状态规则，不能只验正常上报路径：

| 场景 | 区间与持久化处理 | 查询处理 |
| --- | --- | --- |
| 正常上报/真实转移 | 从注册表接受后的状态生成世代内递增序号；单设备串行入账，事务闭合旧段并打开新段 | 已封闭区间与窗口求交；健康当前世代的开口尾段由同一权威注册表校验后补到查询截止时刻 |
| 写入失败或队列溢出 | 记录该设备不可信起点；状态转移队列不按“只保留最新值”吞掉中间状态。检查点只推进到已连续确认入账的序号 | 不将数据库旧 ONLINE/FAULT 开口段无限延长；可靠水位后的未证明区间返回 UNKNOWN，不能仅等恢复后再修正质量 |
| Control 重启 | 以最后持久检查点封闭旧世代可证明部分，新世代首次可靠观测前为 UNKNOWN；旧世代迟到消息不重开区间 | 不使用旧进程内存降级标记作为唯一证据；数据库检查点足以识别缺口 |
| 设备持续离线且被注册表清除 | 已确认 OFFLINE 区间及历史游标独立保留；写者健康且可靠监测未中断时继续确认离线，重新上报才转移 | 内存清理不是历史删除或停止计时；若写者/接收链路失去可靠性则后续为 UNKNOWN。从未有可信观测的设备不能凭缺记录补离线 |
| 跨日没有状态变化 | 日结按区间与上海自然日求交，不要求当天发生转移；迟到修正重算受影响日期 | 完整日用已验证日汇总，边界/未封账日期读原始区间，两个来源覆盖互斥，不能重复累加 |

每机器人需有唯一持久游标或等价约束，保存当前世代、最后已应用序号、开口区间和可靠水位；
首次建段也要受唯一性保护，不能只对“尚不存在的开口行”加锁。重复 transition_id 无副作用；
较旧序号拒绝回退；有序性无法证明时记录缺口而不是猜测。实例检查点不能越过尚未持久的设备转移。
日汇总必须可按设备/日期幂等重建，验证 `knownSeconds + unknownSeconds` 与实际覆盖相符、区间不重叠。
这些是 C1 包必要的数据规则，不需要 Control outbox、跨服务投递或新建全平台事件系统。

### 8.3 页面筛选与查询契约

查询必须正式支持现行页面的「时间范围 × 机器人类型」组合条件，不增加页面尚不存在的区域筛选。
BFF 每次概览请求只归一化一份 `FilterContext`，下游所有分块、前端渲染和 PDF 共用：

```json
{
  "timeRange": {
    "preset": "MONTH",
    "from": "2026-09-01T00:00:00+08:00",
    "to": "2026-09-26T10:30:00+08:00",
    "zoneId": "Asia/Shanghai"
  },
  "robotScope": {
    "mode": "ALL_ENABLED_ROBOTS",
    "deviceTypeCodes": [],
    "enabledOnly": true
  },
  "snapshotAt": "2026-09-26T10:30:00+08:00"
}
```

`robotScope` 规则：

1. BFF 使用 7.1.3 的 `scope-queries`、显式 `enabled=true` 取得当前用户可见设备最小投影及完整类型选项；不得依赖设备列表默认参数或固定单页字典。
2. Management `device_type` 字典是类型编码、正式名称和排序的唯一权威；BFF 以启用设备中的实际类型编码裁剪该字典，只返回「全部」和有启用设备引用的正式字典项。不得由 BFF 翻译、猜测或生成类型名称。
3. `ALL_ENABLED_ROBOTS` 是全部当前启用授权机器人的并集，不包含停用机器人、固定摄像头告警、里程或状态；固定摄像头只作为任务的辅助资源时，不会导致含启用机器人执行者的任务被排除。
4. 指定类型时，BFF 只将该类型、当前授权且 `enabled=true` 的 `robotIds` 传给 Control，并将同一类型编码与 `deviceEnabled=true` 传给 Management 统计接口。传入不在当前选项中的类型返回 400，不静默当作空数据。
5. 这是查询时当前状态口径，不新增启停历史区间：停用后立即从所有统计块排除，重新启用后保留的历史事实重新参与相应时间窗口。停用不会删除任务、告警、状态区间或里程台账。
6. Management 任务/告警统计必须在数据范围约束内关联当前 `device.enabled=true`，不能只信任 BFF 传入的类型；按 7.1.3 校验设备集合指纹并最终复核。事件代次用于提前取消旧请求，不能替代服务端校验。
7. 任一当前启用授权设备引用的类型编码在字典中不存在、重复或名称为空时，视为 Management 主数据不一致：统计页返回 503 / `503003`，并在 `reasonCodes` 中包含 `DEVICE_TYPE_DICTIONARY_INCONSISTENT`；不显示“未知类型”、不回退为编码文本，也不静默排除该设备。已有历史快照的 `UNKNOWN` 不参与本页类型筛选或选项生成，不影响当前类型合法设备的统计。
8. 类型编码必须稳定且按加法式扩展；允许修改展示名称和排序。仍被当前设备或永久历史快照引用的编码不得直接删除或复用为另一语义，需先完成引用审计与数据迁移。

约束如下：

1. `serverTime` 是 BFF 本次固定的逻辑截止时刻；`range.startTime/endTime` 是归一化边界，ALL 的 startTime 为 null。三个既有字段保持上海时区 `yyyy-MM-dd HH:mm:ss`，不能直接透传下游带偏移字符串，见 4.1。各域实际读取时点单独记录，不能为保持字段相同而伪造。

5. BFF 内部向 Management 传稳定类型编码、`deviceEnabled=true` 和时间窗口，向 Control 传经过当前授权、启用状态和类型筛选后的显式 `robotIds`；两个下游不能各自扩大机器人集合。

前端渲染规则：

- 任一顶部筛选变化都重新请求整份 Overview；不得只在前端重算某些图表，也不得保留上一次筛选下的局部块。
- 仅渲染与当前选择匹配的最新响应。快速连续切换时使用请求序号或取消旧请求，旧响应不得覆盖新条件结果；并以响应 `range/filters` 做最终一致性校验。
- `0` 是有效统计值，应显示 `0`；`available=false` 使用现有 `--`/不可用态，`available=true` 的完整空集合使用现有空态。覆盖与质量按 8.3.1 分级判断，不把全部 `complete=false` 统一隐藏，也不把部分事实冒充整窗；具体原因保留在质量字段和报告原说明区，不能用 `value || 0` 把未知或故障伪装成 0。
- `compareRate=null` 时隐藏升降箭头并使用现有 `--`，不新增「暂无可比区间」文案，不显示「较同期 0%」。今日、本周、本月和自定义使用 8.4 定义的上一窗口，全部不做同期比。
- `equipmentRuntime.onlineRate`、运行/故障/离线时长与 `taskCompletionRate` 都读取本次 Overview 响应；切换今日、本周、本月后必须显示对应窗口结果，不保留请求时刻快照或上次筛选值。
- 所选类型失效时 BFF 返回 400，并以本项目错误响应扩展字段给出 `reasonCode=DEVICE_TYPE_SELECTION_INVALID`。
  前端据此立即清除旧数据、切回“全部”重查一次；只有此可识别错误执行恢复，其他 400 不自动重试。
  401/403 清除旧数据并按现有登录/无权限流程处理；根依赖 503 显示暂不可用。成功响应发现选项/回显不匹配也不得渲染旧结果。
- 经 2026-09-26 确认，报告生成沿用当前页面 `range/filters`；历史报告列表属于不可变档案管理，不随当前筛选重新计算或过滤，但每条记录必须展示其生成时保存的时间范围和机器人类型，避免误认成当前条件结果。
- 统计页按 7.10.5 在进入、筛选变化、恢复可见及适用日界重查，不作分钟级整页轮询；每次重查整份使用同一 FilterContext，不能只更新顶层时间却保留旧窗口图表。

经 2026-09-26 确认，「本周=自然周」和「全部=全历史覆盖」作为对现有实现的口径修正；
「本月」保持自然月口径，但结束时间收敛为同一请求的 `snapshotAt`。
「今日/本周/本月/自定义」下，任务、里程、告警、设备运行时长、任务完成率和导出报告必须共用完全相同的 `[from,to)`。
「全部」不伪造一个所有数据域都具有的起点：请求下界为无界，各数据块到同一
`snapshotAt` 为止返回自身全部可信历史，并分别披露 `coverageFrom/complete/reasonCodes`。
不允许任一数据块或导出报告暗中截取 6 个月；报告必须打印各块覆盖起点，避免把不同上线时间误解为同期可比。
自定义日期的结束日通过「下一日 `00:00`」转为右开边界，不再使用 `23:59:59` 遗漏最后一秒内的毫秒/微秒数据。

`equipmentRuntime.items[].runningHours/faultHours/offlineHours`，并从同一批秒数计算筛选窗口 `onlineRate`。
经 2026-09-27 修订确认，`runningSeconds` 对应正常在线状态，`faultSeconds` 对应仍连接但处于故障的状态；
两者互斥且均计入在线时间，断线后转入 `OFFLINE`，不能继续累计故障在线时间。
在线率先汇总所有选中机器人的秒数再计算，不能平均各设备百分比；对外百分数乘以 100 后保留一位小数。
例如正常在线 6 小时、在线故障 2 小时、离线 2 小时，返回在线率 80.0%，三类时长仍分别为 6/2/2 小时。
全窗口仅有在线故障时，在线率为 100%；全部离线时为 0%；无已知时长时为 `null`。
`unknownSeconds` 不进入百分比分母，但必须写入 `dataQuality.equipmentRuntime`；任一选中机器人覆盖不完整时，
页面按第 4 节使用原不可用占位，PDF 在原说明区记录覆盖，不把部分窗口百分比冒充完整结果。同一请求所有统计使用 BFF 固定的窗口边界，
各批实际读取时间独立披露，不因按类型或设备分批查询而重新计算查询截止时间。
接口单批最多 500 个 `robotIds`，BFF 可分批有界并发；生产 Nginx 不对外暴露 `/internal/**`。
`robotIds` 必填且非空；ALL 可省略 from，to 必填。空选中集合不调用下游；任一批失败令该域不可用，
不能按成功批返回完整总数。UNKNOWN 始终纳入质量字段，`includeUnknown=false` 也不能隐去覆盖问题。

#### 8.3.1 里程记录值与采集质量的统一判断

累计里程继续使用既有算法已接受、已入账的数值，不新增推算或改写算法。v2.48 取消“仅旧质量未知可展示”的例外名单：
**能否展示取决于该口径的数值事实是否完整取得；采集质量是否完整另行判断。** 这不是对未上报路程的补算或物理精度承诺。

- `available`：数据块源查询是否成功；失败不返回成功批的部分和冒充总量。
- `hasData`：是否存在可核算记录；不能代替覆盖判断。`valueComplete`：选中设备、全部批次及窗口所需记录/日台账/边界桶均可用且对账成立，
  没有影响累计计算的已知漏记、丢失或未知数值覆盖。固定窗口覆盖整个 `[from,to)`；ALL 从每设备实际数值起点取全部保留记录，
  不截短、不宣称包含上线前未记录路程。某设备无历史且不能证明记录零值时，不用其他设备的累计数掩盖；合法空选中集合仍走既定空态。
- `complete`：除数值完整外，采集质量也满足 8.4.1。已按既有算法处理并记录的 `RESET/SUSPECT` 不计其被拒增量，
  但不抹除之前/之后已入账的数值；`ESTIMATED` 仅保留原算法已接受的数值，必须标记估算；旧质量未知保留 null 计数。
  这些分类可使 `complete=false`，却不单独证明 `valueComplete=false`。确有漏采/写入丢失或处理结果无法证明时，后者仍为 false。
- 分批时两个完整性标志分别取逻辑与；缺少 `valueComplete` 不默认 true，无桶/无质量行也不自动证明零。
  当前值 `reasonCodes` 完整保留，比较原因独立放在 `dataQuality.<domain>.comparisonReasonCodes`；
  不能通过删原因、缩窗口、排除异常设备或额外重算历史来提高完整性。

`hasData/valueComplete` 由 8.4.1 的底层证据推导；可信零也属于有可核算记录，不能仅凭 SQL 的 `SUM/COALESCE` 或测试预置完整性标志判定。

| 情形 | 页面已有位置的呈现 | 比较值与 PDF |
| --- | --- | --- |
| 源查询成功，数值及质量完整 | 正常数值；真实零显示 0，完整空集合用原空态 | 比较另检查上一窗口和分母；报告正常生成 |
| 里程 `available=true/hasData=true/valueComplete=true`，但 `complete=false` | 显示按既有算法累计的已入账值，包括 ALL；保留全部质量标记，不按异常码一票否决，也不标成质量完整 | compareRate=null；PDF 可保留同一值，原说明区必须记录累计口径、覆盖及重置/排除/估算/未知等实际原因 |
| 所需数值记录缺失、边界不可算、设备覆盖未知，或任一批查询失败 | `--`/原不可用态；可保留部分数值供内部对账，不能作为窗口总量显示 | 比较为 null；报告必要源不满足门禁时拒绝生成 |
| 状态 UNKNOWN、无法计算的任务时间、无法分类的告警维度 | 受影响指标仍用原不可用态；完整的其他指标/总数继续展示，不将里程规则推广为所有指标可展示部分事实 | 不把部分分母当完整在线率/占比；报告沿用第 11 节来源门禁与既有维度说明规则 |

两窗口任一 `complete=false` 时仍不输出有效同期比；无可信数值保留 null，不因有异常分类而构造数值 0。
指挥中心、全景地图、统计页与 PDF 共用这一判定，不新增质量规则引擎、页面说明组件或历史修复能力。

### 8.4 按统计页所需设定的永久保留与汇总粒度

此处「永久」指页面所需的可信统计事实不设自动 TTL，不等于所有高频中间数据都在热库永久保存。
已核对的统计页只需要：时间和设备类型筛选下的累计任务数、里程、告警数，按设备类型汇总的运行/故障/离线时长，
告警范围分布/区域排行/小时-日-月趋势，以及任务状态占比；页面和 PDF 均不展示每分钟里程或每次状态跳变明细。

| 数据域 | 永久事实 | 近期/边界计算 | 长窗口查询 | 页面边界 |
| --- | --- | --- | --- | --- |
| 任务 | EIOP `task_workflow_instance` 及设备子任务关联 | 原始任务事实 | 先验证索引聚合；不足时按 C2 建保留实例、权限维度及实例—设备关系的可重建读模型 | 按当前选中机器人匹配后对工作流实例去重，不直接累加各设备/类型任务数；不在本页计算跨窗口执行时长 |
| 告警 | EIOP `alarm_record`、设备关联；区域快照按 F1 独立建设 | 当日小时趋势查询原始记录 | 先验证索引聚合；不足时按 C2 建保留设备标识、原事实权限维度、日期、范围/区域/终态的可重建日汇总 | 查询时关联当前类型与启用状态；持久告警总数不追加 suppressed_count；汇总不能丢失 SELF 权限维度 |
| 设备状态 | Control `control_device_status_interval` | 当日未封账区间与边界求交 | `control_device_status_daily` | 只返回各设备类型累计小时；原始区间长期保留是为审计、补算和 `UNKNOWN` 对账 |
| 里程 | 新增 `control_device_mileage_daily` 每设备每日里程台账 | 当日从分钟桶汇总 | 永久日台账 | 只需窗口总里程和同期比；不要求分钟桶在热库永久保留 |

具体规则：

- 任务、告警原始记录本来就是 Management 业务事实；大屏不复制第二份永久明细，需要加速时才增加可重建投影。现状未发现自动清理逻辑，但正式迁移仍必须把「不设自动 TTL」写入数据保留契约，不以「当前没有删除代码」代替承诺。
- `control_device_status_interval` 首版使用现有 MySQL、必要索引与日汇总；设备停用、转移或软删除不级联删除。`control_device_status_daily` 按上海日界、设备和状态保存精确秒数，可从原区间按天重建。月度分区/冷热分层不作默认前置；仅在索引和查询优化后仍无法满足第 10 节预算，或容量评估证明现有存储/备份无法支撑约定规模时，再对该域单独选择和验证，不改变永久保留承诺。
- 当前里程分钟桶没有清理代码，但这不是永久契约；一台活跃设备最多可持续产生每年约 52.6 万个分钟桶，不应为了本页累计卡片无界增长热表。分钟桶作为校正明细保留 90 天；需要更长审计时可转冷归档，但不得影响永久日台账。
- `control_device_mileage_daily` 是里程的永久统计事实，不是 90 天后仍声称可从已删除分钟桶重建的普通缓存。日结后修正必须保留 `revision/correctedAt/correctionReason`和变更审计；备份和恢复验证以日台账为准。
- 里程查询统一使用分钟对齐的 `[from,to)`，修正当前 `bucket_time <= endTime` 会重复计入下一窗口边界分钟的问题；单改比较符不能恢复分钟内明细。质量持久化、历史未知及共同截止时间按 8.4.1 实施，不从已丢失信息生成质量计数。
- 历史任务、告警状态变化后，读模型须修正事实所属日期的状态分组；例如今天处置上月告警，应修正上月发生日的终态计数。派生更新应可幂等重放和对账，不改变现有业务写入语义。
- Control 完整历史日查已验证日汇总/台账，边界按实际保留数据查询；超过 90 天且分钟桶已清理的里程非整日窗口，不能按全天比例估算，须披露边界覆盖不足，相应同期比返回 null。自定义完整历史日仍支持永久台账。Management 长窗口按 C2 选择达标的数据库聚合或读模型，不向 BFF 传全量明细；告警趋势今日按小时、62 天内按日、更长窗口按月。
- 「全部」没有合理的等长上一周期，KPI `compareRate=null`并在对应 `comparisonReasonCodes` 给出 `NO_PREVIOUS_PERIOD`；前端使用现有 `--`，PDF 在既有说明区记录原因，不显示伪造的 `0%`。其他预设按相邻上一自然周期的同等已过时长比较，自定义按紧邻的等长前置窗口比较；短月不足等长时按 8.4.2 返回不可比，不能跨入本周期。
- 报告原数据与已生成 PDF 均不设时间 TTL，但两者必须分开治理；PDF 按 8.5 转入 Management 文件资源和 MinIO，不得因「无期限」继续无界扩大 BFF 本地目录。
- 正式表结构通过版本化 SQL 迁移交付，不依赖服务启动时 `CREATE TABLE IF NOT EXISTS`。备份、恢复演练、日结重跑和原始/汇总对账属于必要验收；实际启用分区/分层时才追加对应巡检和恢复验证，不先建设未采用的运维能力。

#### 8.4.1 里程分钟精度与持久质量闭环

当前 `MileageService` 的分钟桶只有 `mileage_m/sample_count` 等字段，`RESET/ESTIMATED/SUSPECT`
主要在计算结果/日志中出现；被排除的读数不写分钟桶，已纳入的估算值也未单独标记。因此历史桶可以迁移数值，
但不能凭 `sample_count>0` 证明质量完整，更不能把日志当作永久统计事实源。

**窗口精度采用最小必要方案，不新增秒级里程明细：**

1. 含当前时刻的统计页和今日巡逻查询统一取 `snapshotAt=floorToMinute(requestNow)`；例如 10:30:20 的请求，
   所有域查询到 10:30:00，不含 10:30 分钟桶。已结束的自定义完整日期保留次日 00:00 右开边界；
   超过本次截止的结束时间裁剪到该截止。当前/比较窗口均对齐分钟，对外回显实际边界，不暗中改成秒级精度。
2. 本次 UI 自定义按日期选择，天然对齐分钟；若已有外部消费者提交秒级边界，迁移前列出兼容处理，
   不能默默舍入后声称精确。新的内部里程接口对非分钟边界直接 400；秒级能力不进入本次范围。
3. 日/周/月起点与截止恰好相等时是合法的「本周期尚无完整分钟」，BFF 返回计数/时长/里程 0、
   比率 null，不发送空窗口到下游，也不据此声称已有历史覆盖。权限和资源校验仍须先执行。
4. 里程仍按现有规则把有效增量归入读数事件所属分钟，不按任务或轨迹重新分摊，分钟精度也不等于物理运动区间可精确还原。
   截止边界分钟以后收到的迟到/乱序读数按既有采集规则处理；各域 `sourceReadAt` 如实记录，不承诺读后数据永不变化。

**质量持久化只扩展本项目 Control 的既有采集事务：**

1. 建立每设备/分钟质量记录（可与新分钟表合并，但不得遗漏零增量及被排除读数），保存
   `NORMAL/BASELINE/RESET/ESTIMATED/SUSPECT` 分类计数及质量覆盖起点；与原 checkpoint、被接受的里程增量同事务提交。
   首条读数只建基线；`RESET/SUSPECT` 仍不计里程；既有 `ESTIMATED` 数值可保留但必须标记不完整，不改原增量算法。
2. 复用原 checkpoint 的重复/乱序拒绝，不为重复投递多记质量；质量写失败不能独立提交 checkpoint 后再丢失该质量记录。
   此调整仅限自己的 Control，测试事务回滚、失败恢复及重放；不修改 EIOP、不增加客户端字段或 MQTT 消息。
3. 日台账同步保存质量计数、数值覆盖、`qualityCoverageFrom`、完整性、持久水位及修正审计；
   分钟质量记录与分钟桶一同经过日结对账和备份后才可清理。无桶不等于可信零值，无质量行不等于没有异常。
4. 旧桶只迁移已有累计值，质量无法重建的区间标记 `LEGACY_QUALITY_UNKNOWN`，未知计数为 null；
   不用新质量上线日期覆盖旧数值起点，也不把新旧混合窗口的 `qualityCounts` 伪装成全量已知计数。
   全历史包含未知旧区间时 `complete=false`；按 8.3.1 与新数据统一校验 `valueComplete`，数值可完整核算才展示，
   PDF 保留同一质量与覆盖说明。不能把所有旧记录标成质量完整，也不能为了让页面有数而改为全 0。
5. 窗口 `complete=true` 必须同时满足数值与质量覆盖、所需日台账/边界桶可用及所有批次成功；
   命中基线前缺口、重置/异常/估算、旧质量未知或缺失边界明细均按原因返回不完整，比较值为 null。
   `valueComplete` 独立判断：缺数或边界不可算为 false；分类已明确处理、数值记录完整则可为 true，
   不因历史上一次 RESET 就永久否定全部已入账值。分钟桶已按规则转成完整日台账不算丢数。
   `complete` 只承诺按既定采集口径处理的持久事实完整，不宣称可证明设备从未漏报或重建真实行驶轨迹。

**零值使用上述记录与日结机制判定，不另建覆盖采集系统：**

| 底层证据 | 零值与完整性判定 |
| --- | --- |
| 近期窗口：已有窗口前基线，窗口内零增量读数已在原事务中更新 checkpoint 并保存质量；本次读取的数值覆盖和连续入账水位覆盖所查窗口，所需记录对账一致，无已知未决写入缺口 | 即使无正增量桶，也可返回 `hasData=true/totalMeters=0/valueComplete=true`；`complete` 再按质量判断。单独一个 checkpoint 或一条零读数不能证明整窗 |
| 历史完整日：日结在一致读取边界核对源桶、质量记录及连续入账水位，确认数值覆盖后生成显式零日账，并完成对账/封账；明细按既定规则清理 | 由永久零日账返回 0；保存原覆盖与质量，不能在查询时把缺失日账补成零。无增量日也要经过相同日结判定；无法确认覆盖则保留不完整，不生成“可信零” |
| 已明确处理的 RESET/SUSPECT 等被排除读数，数值覆盖与全部处理记录完整，最终无被接受增量 | 记录累计可为 0 且 `valueComplete=true`，但 `complete=false`、比较 null；不能把被拒增量加入总量或宣称实测零路程 |
| 只有基线/无可信窗口记录，或应有的日账缺失、边界不可算、入账水位未确认、已知写入缺口未解决 | 无记录时 `hasData=false/totalMeters=null`；有部分记录也不能声明 `valueComplete=true`，页面不可用。不能靠其他设备有数、SQL 空和或当前在线状态补足 |

证据来自本包已规划的质量记录、日台账覆盖及持久水位；checkpoint 的最后时间不能独自充当连续覆盖证明。
不要求每分钟必有上报，不补造空分钟；日结零行只表达已核验口径下的记录累计，不证明机器人未移动。
零日账和正值日账共用已有日键、对账与修正流程；原始质量不足保留不足，不新增表、定时任务种类或物理里程推算。

A2 可先迁移批查和分钟边界，并如实返回现有质量能力；C1 独立补齐质量与永久日台账。
二者完成之前不得声明里程长期可信能力已验收，也不得清理旧分钟桶。

#### 8.4.2 上一窗口与短月边界

BFF 只构造一次比较窗口，供任务、告警、里程 KPI 共同使用；上海时区、分钟精度与 `[from,to)` 保持不变。
设当前规范化窗口为 `[currentStart,currentEnd)`，`elapsed=currentEnd-currentStart`：

1. 今日/本周/本月取相邻上一自然日/周/月的起点 `previousStart`，自然结束边界为 `currentStart`。
   候选比较终点 `candidateEnd=previousStart+elapsed`。仅当 `elapsed>0` 且 `candidateEnd<=currentStart` 时有效，
   比较窗口为 `[previousStart,candidateEnd)`；恰好相等表示完整上一周期，仍合法。
2. 本月已过时长超过上一月长度时，不缩短比较窗口、不跨入当前月，也不改成「当前起点之前紧邻的等长天数」。
   BFF 不下发 PREVIOUS/comparisonTimeRange 查询，相关 KPI `compareRate=null`，
   在对应 `dataQuality.<domain>.comparisonReasonCodes` 写入 `PREVIOUS_PERIOD_TOO_SHORT`；当前累计值和页面名称不受影响。
3. 自定义按**裁剪和分钟归一化后的**窗口长度取紧邻前置窗口 `[from-elapsed,from)`，不受自然月长度约束。
   ALL 不构造比较窗口；本周期首分钟 `elapsed=0` 也不向下游发送空比较窗口，比较值为 null。
4. 窗口合法不等于有可比较事实：当前或上一窗口不完整、无可信数值、上一值为 0 时均返回 null，
   不产生 Infinity/NaN，不伪造 0%。上一值大于 0 且当前值为 0 是合法 -100%。
   比率不可用使用原 `--` 并隐藏箭头，PDF 原说明区记录原因，不新增页面提示。

例：2026-03-31 12:00 的本月已过 30.5 天，而 2026 年 2 月仅 28 天，不可比；
2026-03-29 00:00 已过 28 天，上一窗口恰为完整 2 月，可比；
2024-03-30 00:00 已过 29 天，上一闰年 2 月可比，再推进一分钟则不可比。
以上只明确既有「本月」比较算法，不新增滚动月、日均折算或新的筛选预设。

### 8.5 PDF 报告无期限归档

「不设期限」定义为：不按生成日期自动删除，不按每用户数量自动淘汰；
只有用户显式删除、管理员受审计删除或法规流程可以删除报告。
当前 BFF `LocalStatisticsReportStore` 使用单实例本地目录、`index.json`、
硬编码 30 天和每用户 100 份上限，不能作为无期限正式方案。

目标边界：

1. **BFF 只负责生成和适配**：沿用现有 PDF 排版与对外
   `/api/bigscreen/statistics/reports/**` 契约，不在 BFF 新增永久数据库或对象存储客户端。
2. **Management 作为报告档案权威**：增加独立 `statistics_report` 元数据表和加法式读写接口，
   内部复用已有 `FileApplicationService.storeGenerated()`和 `file_resource`将 PDF 存入 MinIO。
   不改现有文件上传、地图导入导出或其他 EIOP 消费者逻辑。
3. **元数据可复核**：至少保存 `reportId/fileId/reportName/format/modules/timeRange/filters/snapshotAt`（报告查询截止时刻）、
   各数据块 `sourceReadAt/coverageFrom/complete/reasonCodes`、适用的 `valueComplete/comparisonReasonCodes`、设备集合指纹、统计口径版本、生成时类型编码/名称及选中设备数量、`checksum/size/ownerOrgId/createdBy/createdAt`，
   以及 8.5.1 的 `idempotencyKey/requestFingerprint`，以便历史 PDF 能说明「当时用什么口径和覆盖生成」，并可恢复同一次导出结果。
4. **文件不可变**：已生成 PDF 不就地覆盖；重新生成建立新报告和新 `fileId`。
   MinIO 对应前缀不配置自动过期生命周期规则。
5. **权限不依赖对象 URL**：列表、下载和删除都经 Management 校验当前用户和组织数据范围，
   MinIO bucket 保持私有；BFF 不持久预签名 URL。
6. **不用偷删解决容量**：监控对象数、总字节、增长率、失败数和 MinIO 剩余容量；
   达到安全阈值时告警并拒绝新建报告，不自动删除旧报告。
7. **备份与恢复成套验证**：`statistics_report`、`file_resource`和 MinIO 对象必须使用同一备份批次或可对账的检查点，
   定期校验孤儿元数据、孤儿对象和 checksum。

Management 新增接口仅服务报告档案，不替代 BFF 现有对外契约：

| 接口 | 用途 | 关键约束 |
| --- | --- | --- |
| `POST /api/v1/management/statistics-reports` | BFF 上传已生成 PDF 和元数据 | `multipart/form-data`；限制 PDF 类型/大小；`Idempotency-Key` 在当前用户范围唯一，重试不生成重复报告 |
| `GET /api/v1/management/statistics-reports` | 分页列出当前用户报告；或通过 `idempotencyKey` 精确查本次导出 | 沿用「用户私有+组织隔离」；普通列表按 `created_at,id` 倒序有界分页。按键查询不与列表分页组合，语义见 8.5.1，不开放跨用户检索 |
| `GET /api/v1/management/statistics-reports/{id}/content` | 读取 PDF 内容 | 校验报告归属后从 MinIO 读取；不返回永久公开 URL |
| `DELETE /api/v1/management/statistics-reports/{id}` | 用户显式删除 | 幂等；删除报告元数据与对应文件，失败可对账重试，记录审计日志 |

`POST` 必须先完成归档再向浏览器返回导出成功；归档失败时 BFF 返回明确 503，
不出现「用户下载成功但历史列表永久丢失」。若文件已写 MinIO 而元数据事务失败，
Management 必须尽力删除新对象并由孤儿对账任务最终收口；不改动现有 `FileApplicationService` 的其他调用语义。

迁移按以下顺序完成，不能把旧数据保护留到最后清理阶段：

1. 先备份各实际 BFF 存储目录与索引，冻结每小时过期清理和保存时每用户数量淘汰两条删除路径。
   迁移批次开始后暂停旧报告生成及删除，页面统计查询照常；完成后恢复新档案操作。不能边复制边让旧目录继续删改。
2. 使用受控、一次性导入工具读取原 `createdBy/orgId/createdAt`，保留原归属；不能用执行导入的管理员身份
   重建所有报告。原归属与 Management 本地组织无法映射的记录先隔离待核对，不对普通用户开放。
3. 旧索引没有保存完整筛选和覆盖信息，导入记录标记 `origin=LEGACY_IMPORT/metadataComplete=false`，
   未知字段为 null，在历史列表既有字段位置使用 `--`；保留原 PDF，不从文件名或当前设备类型猜测，不新增历史报告说明组件。
4. 以源存储实例、旧报告 ID 和 checksum 生成导入幂等键，保存旧 ID→新 ID 映射；校验数量、字节、checksum
   和用户隔离后，再切换列表、内容、删除及新报告写入。多实例旧 ID 相同也不能覆盖彼此。
5. 观察期旧目录仅作恢复副本，**不在新档案查无记录或失败时自动回退展示**。删除以新档案为权威并保留
   可恢复的删除标记/审计，使旧副本不能令已删除报告重新出现；文件删除失败留待幂等重试，不恢复可见性。
6. 回滚前冻结新档案写操作并按导入映射、新增记录和删除标记对账；不能只切配置回旧 index.json，
   否则会丢失切换后的新报告或复活删除项。优先回滚 BFF 版本但继续使用新档案存储契约。

新档案四个端点必须精确登记功能权限、许可和审计规则，列表/内容限定本人及组织边界；普通用户不能指定
ownerOrgId/createdBy 绕过当前身份。一次性导入的保留原归属能力不开放为普通创建接口参数。
上传幂等键相同而内容/元数据不同返回冲突；MinIO、file_resource、报告行的失败补偿及重试须在 D 包验证。

#### 8.5.1 报告生成、归档与重试的端到端幂等

当前 `StatisticsService.createReport()` 每次重新查询、生成 PDF 并保存；只在 Management 上传端接受
`Idempotency-Key` 不足以处理「归档成功但浏览器超时」。采用同一次请求标识和已有档案结果复用，
不新增异步导出平台、BFF 永久数据库或跨服务事务。

1. **浏览器固定一次导出意图**：生成随机 `Idempotency-Key`，随现有导出请求传入 BFF；
   冻结当前页面已应用的 `range/filters/serverTime` 和模块选择，时间边界已经按 8.4.1 对齐。
   重复点击/网络超时重试沿用相同键及原参数，不能重算 to 或生成新键；明确发起另一份报告或更改条件才使用新键。
   待确认请求可保存在当前身份隔离的 sessionStorage，成功、显式取消或退出身份后清理；不保存 PDF、凭据或完整设备集合。
2. **BFF 规范化请求而非信任客户端授权**：校验时间、预设、类型编码、模块白名单和格式，
   对稳定的请求参数及口径版本计算 `requestFingerprint`；不包含生成时钟、PDF checksum 或查询后得到的设备计数。
   已有键按档案保存的规范化参数/口径版本比对，不能因 BFF 升级或重启更换版本就误判同一次重试为新请求。
   首次生成仍重新执行当前权限与资源校验，不能把页面旧回显当作授权凭证。新建报告固定使用传入且校验过的实际窗口，
   不在重试时把「今日/本月」重新展开到新的截止时间。缺少键的新导出请求返回 400，前后端作为同一包切换。
3. **先查已归档结果再决定生成**：BFF 通过 Management 的按键查询恢复本用户/组织内的报告。
   已存在且请求指纹相同则返回原 `reportId` 和 PDF，不重新查询统计；不同指纹返回 409。
   只有明确未找到才允许生成；查询超时/5xx/权限失败不能当作不存在。被显式删除的键返回 410，不重新生成。
4. **同条件不等于数据库历史快照**：报告窗口与页面一致，但任务/告警状态可能在两次读取间变化，
   报告以本次成功生成时各域实际 `sourceReadAt` 为准，不承诺逐像素复刻页面或跨服务事务快照。
   保存实际筛选集合指纹、质量与读取时点；完成归档后内容不可变，重试永远读取该档案。
5. **Management 负责最终唯一性**：按服务端当前身份归属与 `Idempotency-Key` 建立唯一约束，
   验证 `requestFingerprint` 与随文件提交的规范化元数据一致；记录与 `file_resource` 引用提交完成后才返回成功。
   BFF 可做按身份/键的进程内 single-flight，但不能用它代替跨实例唯一约束。
   并发生成不同 PDF 时最多归档一份；后提交者遇到同键内容冲突，应按键读取并核对请求指纹，
   指纹相同则返回先完成的原报告，指纹不同则维持 409，不覆盖文件。未被采纳的对象由 Management 补偿删除/对账。
6. **结果未知时不盲目重传**：上传超时后先按键查询。查到已完成结果则复用；确认未找到可用原键、
   原参数重试，仍受唯一约束保护；服务不可用时保留待确认键并返回失败，不自动换键。
   若进程重启丢失尚未归档的 PDF，可按相同窗口重新生成，最终只采用第一次成功归档的结果。
7. **生命周期和权限一致**：按键查询精确复用档案查看权限，归档记录及最小幂等/删除标记不因短 TTL 自动遗忘；
   已删除键不复活报告。读取旧档案按已有本人/组织边界授权，不能因为请求键可猜测就返回他人报告。
   普通报告列表不显示删除标记，也不把内部幂等键新增成页面展示字段。

按键查询沿用 Management 通用响应包裹：命中时 `data.records=[报告元数据]/total=1`，明确未找到时
`data.records=[]/total=0`，已删除返回 410；该模式不接受 page/cursor，最多返回一条，元数据包含请求指纹。
任何单次返回成功都须能从正式报告列表和下载接口找到同一报告；删除后按删除契约处理。
以上覆盖正常新建、双击、响应丢失、BFF 重启、双实例并发、同键改参数和删除后重试，不改变既有 PDF 排版与入口路径。

### 8.6 实施前置门

当前状态和状态历史权威已确认为本项目 Control。该能力作为 P1 独立项目评审，
不与 P0 任务/告警查询迁移捆绑开发，但它是统计页「时间 × 机器人类型」整页正式验收、窗口在线率生效以及删除 BFF 旧采样的共同必要条件。
进入编码前必须验证以下已确认要求：

1. 运行时长是「查询时选中、启用且授权的机器人时长求和」，不是机器人类型的自然时钟时长；「全部」不包含停用机器人或固定摄像头。启用设备的 `OFFLINE` 是正式状态，仍进入离线时长和在线率分母，不能把 `enabled=false` 与 `OFFLINE` 混同。
2. `FAULT` 是 Control 当前状态机中的状态，不由历史告警数量推导。
3. `onlineRate=(running+fault)/(running+fault+offline)`，在线故障时间计入分子且故障时长仍单列；`UNKNOWN` 不进入分子或分母，覆盖不完整时质量与数值一起返回，页面按第 4 节使用原不可用占位，不单独显示该部分百分比。
4. 历史写入失败告警、服务检查点、`UNKNOWN` 缺口、永久保留、单写者、备份和恢复必须纳入同一验收闭环。
5. 先运行新旧双读对账，但不要求与旧采样估算数值完全相等；应核对转移、覆盖和差异原因。

在 P1 正式模型验收前不删除 BFF 采样兼容路径；旧路径在质量字段和运维说明中标记为「近似、默认仅保留 7 天、单实例本地」。
请求窗口超出实际采样覆盖时，BFF 在 `dataQuality.equipmentRuntime` 返回
`complete=false/coverageFrom/coverageTo/reasonCodes=[HISTORY_COVERAGE_INCOMPLETE]`；接口可保留已覆盖部分的近似值用于对账，
页面不得作为完整统计值渲染，也不得把无采样映射为真实 0 小时；勾选运行时长的 PDF 按第 11 节门禁拒绝生成，不能仅写近似说明后作为正式报告通过。

## 9. 权限、数据范围与缓存

### 9.1 权限复用

不新建粗粒度 `statistics/view` 来跨过原领域权限：

| 查询 | 应使用的权限 |
| --- | --- |
| 任务统计 | 建议沿用当前 `scope=ALL` 实际要求的 `task.execution.view`，不因响应只有计数而降为 `task.record.view`；2026-09-27 源码校正，纳入第 18 节首批清单确认 |
| 今日巡逻时长 | `task.execution.view` 与 `resource.device.view` 同时满足，各自数据范围分别用于任务、子任务及设备关联；只返回权限内实例聚合 |
| 任务卡片 | `task.plan.view`；活动实例部分要求 `task.execution.view` |
| 告警统计/快照 | `monitor.alarm.view` |
| 设备状态 | `resource.device.view`；BFF 仅将 Management 当前授权且 `enabled=true` 的 `robotIds` 传入 Control 内部查询 |
| 今日巡逻里程及统计页里程 | `resource.device.view`；首屏、WS、统计和报告均使用显式授权机器人集合，不能使用空 ID 表示全局 |
| 授权资源投影 | 按类型分别使用 `resource.device.view` / `resource.fixed-camera.view` |

`bigscreen.patrol.stats.view` 等大屏页面权限只控制菜单，不自动授予数据权限。

### 9.2 数据范围

- **所有统计只计算当前用户权限内的数据（2026-09-29 已确认）**：包括指挥中心、全景地图、统计页、HTTP/WS 摘要、比较窗口和报告；不能先返回全局统计再在前端隐藏明细。菜单可见、已登录或处于内网都不能替代领域数据授权。
- 聚合 SQL 必须经过与列表/详情相同的 `owner_org_id` 限制。
- 不假设 MyBatis-Plus 会对所有手写子查询/联表自动正确注入；每个新 Mapper 必须有 ENFORCE 模式跨组织集成测试。
- 联表两端都有归属时，必须验证两端一致，不能只过滤主表。
- 这里的一致指各自满足对应领域的数据权限，不要求历史任务归属与设备当前归属机械相等。任务/告警事实按其功能权限范围过滤，设备按 `resource.device.view` 的范围过滤；不能把一个请求上下文中的组织范围直接套到所有表，具体实施门禁见 18.3。
- Control 状态历史不储存组织快照，不直接面向用户；BFF 必须先用 Management 当前数据范围得到允许的 `robotIds`，不得把前端传入 ID 原样透传到 Control。

### 9.3 缓存

第一阶段优先做有界 SQL 和索引，压测后再决定是否缓存。如启用，缓存键至少包含：

```text
queryVersion
+ authorizationScopeFingerprint
+ from/to
+ deviceType/regionId/severity/status/granularity
+ dataRevision
```

- `authorizationScopeFingerprint` 必须由有效权限和组织范围生成，不能只用角色名或 `orgId`。
- 无法可靠生成指纹时，Management 缓存按 `issuer + subject` 隔离，不跨用户共享。
- 缓存仅在确有对应失效来源、版本校验和容量收益时启用；不能假定现有 `overview.changed.v1` 已覆盖所有字典和权限变更，更不能为读迁移修改所有业务写入口以推进全局版本。
- 首批设备/字典投影不做跨请求成功缓存，7.1.3 每轮直接读取并计算内容指纹；新增类型、改名和排序在下一次查询生效。实时摘要和统计页各按 7.10.5 的触发边界重查，不新增统计页分钟轮询或高频全量事实读取。后续缓存必须保留这一可见性和撤权边界。
- BFF 不缓存 `401/403/5xx`、部分结果或 `degraded=true`。

## 10. SQL、索引和容量边界

- 任务统计候选索引覆盖 `owner_org_id + started_at + status`；告警覆盖 `owner_org_id + occurred_at + status/severity`。最终顺序必须以真实选择性和 `EXPLAIN ANALYZE` 决定。
- 不对索引时间列包裹 `DATE()` 后再筛选；先范围过滤，再对已筛选集分桶。
- 统计概览返回的分组数量有界，不设置 366 天全局截断；ALL 和自定义长窗口必须经过 C2 容量验证，按执行计划与真实成本决定是否增加汇总层，不以全量历史传输到 BFF 代替数据库聚合。
- 排名上限建议 100，批量设备/事件上限建议 500；超限显式返回 400，不静默截断。
- 长期查询按 8.4 保留 Control 状态历史/日汇总和里程永久日台账；Management 只有 C2 容量验证不达标才建设派生模型。建设时告警保留设备、日期及领域/权限维度，任务保留实例—设备关联以精确去重，不能只存历史类型总数。里程分钟桶清理仍须满足 90 天保留及日台账对账/修正审计条件。
- 上线前使用生产等价数据量验证 P50/P95/P99、扫描行数、临时表/文件排序、慢 SQL 和连接池。

查询预算和资源指纹成本按以下门禁执行，不把「需要压测」当作无验收阈值：

| 项目 | 本方案初始工程预算（设计目标，非已测结果） |
| --- | --- |
| 今日/本周/本月及常用自定义窗口的 BFF Overview | P95 ≤ 2 秒、P99 ≤ 5 秒；含筛选根、分页、各域读取与最终复核，不只测单条 SQL |
| ALL/最长自定义窗口的 BFF Overview | P95 ≤ 5 秒、P99 ≤ 10 秒；任务/告警不达标时只为对应查询启用 C2，不截断历史 |
| 一轮 Overview 总预算 | 12 秒，包含排队、分页、并发批查和允许的重试；下游超时按剩余时间收缩，耗尽后按第 11 节返回，不无限等待 |
| Control 同域分批并发 | 单请求最多 4 批同时执行；进程级并发、等待队列上限须结合实际 HTTP/数据库池冻结配置，不能按每用户无限新建执行器 |
| 重试/事件刷新 | 每轮仅一次重试预算；上下文 409 整轮重试与瞬时读失败重试共享预算，不层层叠加。按身份/查询上下文 single-flight，事件合并脏标记，不能为每条消息排一份完整查询 |
| 时钟刷新 | 7.10.5 的今日两项摘要每个 BFF 实例、同身份/逻辑筛选每分钟最多一轮时钟查询；与同上下文在途事件查询合并。统计页无分钟轮询，仅计入进入/筛选/恢复/日界触发。授权、队列和实际聚合开销仍计入总预算 |

以上阈值须在对应包编码前用目标设备数、历史记录量、并发用户/会话数和部署资源组成的容量基线确认；
如需调整，记录原因和新阈值，不能上线后再把不达标解释为通过。PDF 生成/归档属于 D 包独立资源预算，不套用 Overview 时延目标。

资源/任务/授权内容指纹必须单独计入成本：任务只扫描 7.6 的最小集合/关联投影，卡片动态字段和按钮仅计算当前页，最终复核不重建全体卡片。
若有 N 条最小投影、每页 L 条，逐页重算全集合仍可能产生
约 `N × ceil(N/L)` 次投影处理，另有统计校验和最终复核，不能以「每页最多 500」称总成本有界。
测试至少覆盖目标峰值设备量、跨多页冷缓存、普通活动状态变化及资源/关联变更，记录每轮 SQL 次数、扫描行数、哈希行数、卡片/按钮计算数量、响应字节与内存峰值。
普通暂停/恢复不因集合指纹反复重启分页；安全与成员变化仍严格失效，不能以减负为由省略授权复核。
首批优先复用同请求只读快照、必要索引和精简投影，不在 EIOP 原业务写入口增加全局版本钩子。
一致性合同和权限核验保持，计算只覆盖契约所需字段；同一只读事务内已有投影/摘要可复用，不能借此跨 HTTP 请求复用旧授权。
实现优化限定在对应查询及索引内，不建设全局版本服务、跨请求快照会话、跨服务锁或通用查询平台。
若当前指纹方式无法在预算内完成，则对应包先停止切换并收敛该查询实现；不能跳过权限复核、返回前几页或恢复全历史拉取。

## 11. 错误、超时与一致性

| 场景 | 要求 |
| --- | --- |
| 参数错误/超限 | 400 + `400001`，指出字段和上限 |
| 已选类型失效 | BFF 400 + `DEVICE_TYPE_SELECTION_INVALID` 原因；前端清屏并回到全部重查一次，不重试其他参数错误 |
| 资源集合在查询中变化 | Management 新只读查询 409 / `409000`；BFF 最多整轮重试一次，仍变化则 503 + `RESOURCE_SCOPE_CHANGED` |
| 身份失效 | 401 + `401002`，BFF 不降级 |
| 功能/数据范围不足 | 403 + `403002`，BFF 不转空集合；只有授权投影明确约定的某资源类可按空处理 |
| 筛选根依赖不可用 | 当前启用授权设备集合或 Management 类型字典无法取得、二者不一致时返回 503 + `503003`，不得使用旧集合、旧字典或自造名称降级 |
| 独立统计域失败 | Overview 返回 200，只有对应依赖块 `available=false`，值为 `null`/空集合并写入明确 `reasonCode`；其他成功块继续展示 |
| 全部统计域失败 | 当前启用授权设备集合虽成功，但任务、告警、里程、运行时长全部失败时返回 503，不返回只有筛选头的无效 200 |
| 重试 | BFF 幂等读查询共用第 10 节的一次重试/总时限预算；报告写入只按 8.5.1 的同键恢复流程，不自动换键或盲目重发 |
| 事件与在途请求竞态 | 沿用事件代次/single-flight，旧代响应不回写新代缓存 |

分块失败边界固定如下：

| 失败依赖域 | 标记不可用的页面数据 | 仍可展示的数据 |
| --- | --- | --- |
| 当前启用授权设备集合/类型字典 | 整份 Overview | 无；二者共同构成所有组合筛选的根，必须 fail-closed |
| Management 任务统计 | `kpis.taskTotal`、`equipmentRuntime.taskCompletionRate`、`taskCompletion` | 里程、运行时长/在线率及告警相关块 |
| Management 告警统计 | `kpis.aiAlarmTotal`、`aiAlarmAnalysis`、`alarmAreaRanking`、`alarmTrend` | 任务、里程和运行时长相关块 |
| Control 里程统计 | `kpis.patrolMileage` | 任务、告警和运行时长相关块 |
| Control 运行时长统计 | `equipmentRuntime.onlineRate/items` | `equipmentRuntime.taskCompletionRate` 仍可由任务统计供给，其他域不受影响 |

响应和渲染规则：

1. `dataQuality` 按 `taskStatistics/alarmStatistics/patrolMileage/equipmentRuntime` 分域返回 `available/complete/reasonCodes/coverageFrom/coverageTo`；对应 DTO 可加法式增加 `available`，不得删除既有字段。
2. 失败域使用 `TASK_STATISTICS_UNAVAILABLE`、`ALARM_STATISTICS_UNAVAILABLE`、`MILEAGE_STATISTICS_UNAVAILABLE`、`EQUIPMENT_RUNTIME_UNAVAILABLE`；类型主数据不一致使用 `DEVICE_TYPE_DICTIONARY_INCONSISTENT`。这些原因不复用「真实空集」语义；故障日志保留下游、耗时和 `traceId`，不返回敏感异常正文。
3. 前端对失败域显示「暂不可用/--」，对 `available=true` 的合法零值显示 `0`，对完整空集合显示「暂无数据」；一个图表失败不得清空其他成功图表。
4. 部分降级响应不进入正常成功缓存，只允许请求内 single-flight，防止故障恢复后继续命中旧降级结果；幂等读按第 10 节共享一次重试预算。
5. `401/403`、筛选根依赖失败和响应筛选回显不一致均为整页失败，不得按分块降级。
6. `complete=false` 不等于请求失败；里程按 8.3.1 的统一数值判定可展示时，仍保留质量标记，
   不进入正常完整成功缓存、不生成有效同期比。`valueComplete=false`、源失败或缺少必要标志时不得输出部分总量冒充完整记录。

PDF 是不可变档案，采用比页面更严格的完整性门禁：

- KPI 摘要属于每份报告的必选基础模块，因此任务、告警或里程统计任一意外失败都拒绝生成。
- 用户勾选「装备运行时长」时，Control 运行时长失败也拒绝生成；其他可选模块按其依赖域检查。
- 已确认长期无事实来源的 `autoHandleSuccessRate.available=false/AUTO_HANDLE_FACT_NOT_AVAILABLE` 属于已知产品状态，打印「暂无数据」但不阻断报告；它与运行时故障降级不同。
- 里程按 8.3.1 的同一数值门禁生成报告，不维护异常码放行名单。已入账数值完整但采集质量不足时，
  PDF 必须在既有说明区写明累计口径、数值覆盖、实际的重置/排除/估算/未知原因及不可比原因，元数据保存同样的质量。
  不把估算标成实测完整，不补算被排除或丢失路程；源失败、实际缺数、无法计算边界仍拒绝，不能因只保留了部分和就生成成功报告。
- 其他必选/勾选统计源的必要事实不完整时仍拒绝生成；已有告警维度覆盖说明与自动处置无事实规则保持，
  不将里程记录累计口径推广到运行时长、任务时长、比率或告警分布。
- 门禁失败返回 503 / `503003`，并在 `reasonCodes` 中包含 `REPORT_SOURCE_INCOMPLETE`及不完整模块代码；不生成 PDF、不写报告元数据、不占用 MinIO 对象。

## 14. 验收标准

### 14.1 契约与正确性

- BFF 既有核心 DTO 结构兼容；新增质量字段、空值/错误处理和已确认的口径修正有前后端成对契约测试，不要求复制旧错误值。
- 时间窗口左闭右开，覆盖 Asia/Shanghai 日/月边界。
- 构造 10:30:20 发起且 10:30:40 才执行到里程查询的请求，验证各域均截止 10:30:00，不纳入 10:30 桶；覆盖零点首分钟、上一窗口及自定义完整历史日。内部里程非分钟边界返回 400。
- 建立「全部/今日/本周/本月/自定义 × 全部机器人/每一种实际机器人类型」组合验收矩阵；每个组合逐项核对 KPI、窗口在线率、三类运行时长、任务完成率、全部告警图表、全部任务图表和 PDF，不能只抽测一个卡片。
- 同一次 Overview 的任务、告警、里程和状态均使用响应 `filters.selectedRobotCount` 对应的同一当前启用授权、类型匹配机器人集合；各领域内部的卡片和图表须能回算到同一事实集。
- 将一台启用机器人从 A 类型改为 B 类型，验证其历史任务、告警、里程及状态统一纳入 B 类型，A 类型不再因该机器人命中；任务有其他 A 类型参与设备时仍按实例去重计入 A。旧 PDF 及其筛选名称不变，新 PDF 使用变更后的集合。
- 准备正常在线 6 小时、在线故障 2 小时、离线 2 小时，验证在线率为 80.0%，时长柱图仍为 6/2/2；覆盖纯故障在线 100%、纯离线 0%、纯未知 `null`，以及多设备先合计秒数再计算、故障后断线不继续累加故障时长。
- 响应 `serverTime/range/filters` 与页面当前条件一致；构造先发慢回、后发快回场景，验证旧请求响应不会覆盖新筛选结果。
- 统计页类型选项及 `all` 结果中均无固定摄像头；有机器人查看权限但范围内无启用机器人的账号返回「全部」和合法空态；缺少机器人查看功能权限返回 403，不与空集合混同。
- 为 Management 字典新增类型并绑定启用设备，验证大屏无需改代码即可按字典名称和顺序出现新选项；构造设备类型编码缺失、字典重复编码和空名称，均应整页 503 且不得出现“未知类型”或编码兜底。
- 准备关联同一台启用授权机器人的 `TASK/DEVICE/COMPONENT` 告警，验证告警范围分布分别显示「任务告警/设备告警/组件告警」，计数之和等于告警总数；修改 `alarm_type` 不得改变该分布，不得仅因 `source_type!=DEVICE` 排除任务或组件告警。
- 注入一条三值以外的存量 `source_type` 异常数据，验证页面不出现「未知类型」或第四类图例，范围分布标记不完整，告警总数仍保持持久记录数口径。

### 14.2 权限与安全

- 使用至少两个组织、自定义范围、无权限、撤权中和 Token 刷新账号验证。
- 统计、列表、详情、导出和 WS 快照数据范围一致。
- 缓存不得命中其他用户结果；撤权后在契约最大陈旧时间内 fail-closed。
- 新里程 POST 与状态/历史查询只走内部路径；外部不能通过 BFF 通用代理传任意机器人集合。按 7.5.4 清单逐一验证注册表、旧里程 GET、路径别名、实际网关和回滚配置，不能遗留公开旁路。

### 14.3 性能与稳定性

- 统计窗口不再向 BFF 传输全量任务/告警记录。
- 单次全景告警快照对 Management 只有 1 个业务请求。
- 不存在随设备数线性增长的详情 HTTP N+1。
- 当前运行态及里程内部批查以 500 台单批上限验证，超批有界并发且不漏项；不以“总设备最多 500”替代分页。移除 EIOP 实时状态明细前证明无字段丢失。
- 峰值压测下 Management/Control/BFF 线程池、连接池、CPU、堆和慢 SQL 无持续增长。
- 下游延迟、部分 5xx、权限服务失败和缓存冷启不引发重试风暴或无界队列。
- 按第 10 节记录容量基线及阈值，覆盖多页资源指纹的重复扫描、整轮超时、每域最多 4 批并发、进程级队列限制和共享一次重试预算；不以单 SQL 低延迟代替端到端验收。
- 在未建立 Management 派生表、状态表分区/冷热分层的基线下先验证查询与长期保留；达标即允许对应包通过。
  若不达标，记录目标规模、瓶颈及 SQL/索引优化结果，只为必要领域选择进一步手段；不把后置能力或通用基础设施作为默认门槛。

通用字段约束建议：

1. `timeRange` 必填，`to/zoneId/basis` 必填；时间按瞬时转换后比较，`from < to`。
   为表达通用的“无历史下界”，允许省略 `from`，表示该权限和设备集合下可查询的全部保留历史；
   BFF 仅对 `range=all` 使用，不以某个域较晚的采集起点截断另一域已有事实。
   `coverageFrom` 描述实际覆盖而非凭空补出的统一起点；比较窗口必须有明确 `from/to`。
2. BFF 固定采用 `Asia/Shanghai`；新接口校验合法 IANA 时区，按 EIOP 配置时区转换数据库
   `LocalDateTime` 后查询，再按请求分桶时区返回带偏移桶起点；不更改全局时区或既有列表日期语义。
3. `filters` 缺省/空数组语义沿用 7.1.1；BFF 必须显式传 `deviceEnabled=true`。
   类型代码不硬编码枚举，按 Management 当前字典校验；未知代码/空白元素返回 400，重复值去重。
   多值输入最多 500 项；缺省不限制不代表允许前端传入任意组织或设备授权上下文。
4. `includes` 省略或空数组仅返回 summary；未请求块省略，已请求且无数据的块返回空数组/零计数。
   `comparisonSummary` 仅在请求比较窗口时存在。非支持的枚举、字段和组合拒绝，不返回假占位实现。
   严格反序列化仅作用于新 DTO/端点，不能修改全局 ObjectMapper 而破坏旧接口兼容性。
5. `rankingLimit` 默认 10、范围 1–100；只在请求排名块时接受。计数倒序，平局按稳定领域代码/
   locationKey 排序，保证重复查询顺序确定。范围分布和终态处理方式是完整有限分类，不受 Top-N 截断。
6. `TIME_TREND` 必须显式传 `trendGranularity=HOUR|DAY|MONTH`；BFF 按 8.4 选择。
   非趋势请求不接受该参数；建议最多 1200 个桶，超限明确 400，BFF 改用合适粒度，不静默丢桶。
   真实空窗口返回空数组，BFF 按已知完整窗口补零桶；覆盖未知或请求失败不能补成零。
7. 同一端点内 summary、分布和比较结果使用同一次只读数据库一致性快照，避免状态更新导致
   分类之和与总数不同。`snapshotAt` 是该查询快照的观测时点，**不是跨接口/跨页一致性凭证**。
   任务和告警独立响应，不声称仅凭相同时间戳就有跨服务事务。

关联规则必须在 SQL 层表达，并建立同一批数据的参考查询对账：

- 任务：`task_workflow_instance -> device_task_instance.workflow_instance_id -> device.id`，
  使用 `EXISTS`/半连接，类型、启用和设备权限作用于同一台设备。任务及子任务按原事实授权边界过滤；
  不从计划当前绑定推导历史执行者，不对分设备/分类型计数直接求和。
- 告警：优先使用 `alarm_record.device_id`；仅在 ID 缺失时按 `serial_number` 精确关联。
  ID 存在但与序列号冲突时不得以 OR 条件同时命中另一台设备；不能确认的异常关联需质量披露，
  不计入任意机器人。实现前用真实字段投影确认旧数据情况，不补写原告警。
- 数据权限：分别解析事实域和设备域上下文，保留 `ORG_ONLY/ORG_AND_DESCENDANTS/CUSTOM_ORGS/SELF/ALL`
  的现有语义，尤其 SELF 使用各自 `created_by`。`DataAuthorizationService.resolve()` 只生成数据范围，
  不能代替功能权限拒绝检查。无功能权限返回 403，有权限但范围内确实无数据才返回零。
- 不修改全局 `OrganizationDataPermissionHandler`。优先通过新查询专用 Port/Adapter 显式传递
  可信权限谓词，在受控 Mapper 中证明各表应用的是正确范围；若现有单上下文插件无法兼容，
  先提交局部适配方案评审，不能简单关闭拦截器或让 BFF 提交可信组织 ID。
- 地址排行按现有 `StatisticsService.alarmAreaName()` 的真实投影优先级建立 fixture，包含顶层、
  `location` 以及 `rawPayload.location` 中的字段；缺失/损坏 JSON 不应使整个查询失败。
  不将无位置记录计入虚构区域，质量字段和百分比分母按 7.3.1 与页面映射验收。

### 18.4 B1 筛选根与正式切换前置门

1. B1 使用 M0 的 `POST /devices/scope-queries`（完整路径见 7.1.3），显式查询启用设备，

2. 类型选项由 M0 对实际引用的 Management 字典编码完整解析，返回 `value/label/sortOrder`，
   不要求使用者取得字典管理权限，不更改旧选择器返回形状或全局分页上限。
   引用缺失、重复或空名称按既定 503 处理；超过 200 条字典及多页设备是正式切换必测项。
3. 一个请求只生成一份时间、当前/上一窗口、类型和启用设备集合；ID 为 Management 主键，
   `robotId` 为传给本项目 Control 的正式序列号，二者不可混用。空授权设备集合必须保留“明确空集”
   语义，不能将空 ID 数组发送给默认表示“不限制”的接口后误查全局。
4. B1 不增加跨请求成功缓存；按 7.1.3 校验每页、领域响应及最终复核的 `deviceScopeRevision`。
   发生启停、改类型、撤权或字典改名时丢弃整轮聚合，最多完整重试一次；持续变化返回 503，
   401/403 直接失败，不参与此重试。UI 请求代次只负责丢弃旧筛选结果，不能替代服务端指纹校验。

   不要求与旧错误算法数值相等；其余等价数据集才做逐字段新旧一致性对账。
6. 筛选上下文按 8.4.2 统一比较窗口：短月不可比时不下发比较查询，但当前窗口照常。
